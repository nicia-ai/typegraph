# Operational Identity benchmark report

Date: 2026-07-15, identity-enabled lanes re-measured 2026-07-30

## Environment

- macOS 26.5.2 (25F84)
- Apple M4 Pro, 48 GiB RAM
- Git baseline for the 2026-07-15 lanes: `e4ed8e53dc78f97c68438ac060a11c217feb724f`
- Git baseline for the 2026-07-30 identity-enabled lanes: `a2b2eb722493`, with
  the current-class-read query-shape fix re-measured at `c3aeef32db06`
- SQLite: in-memory `better-sqlite3`
- PostgreSQL: local Docker backend (2026-07-15 at `127.0.0.1:5432`, 2026-07-30 at
  `127.0.0.1:4130` on a dedicated `identity_bench_worktree` database)
- Identity lane: two warmups, seven recorded samples, medians and p95s in
  milliseconds per operation
- Seed: 100 `Person` and 100 `Author` rows before enabled-path measurements

Raw samples and per-sample operation counts are retained in `history.jsonl`.
The canonical identity runs are `2026-07-30T17:44:52.142Z` (SQLite) and
`2026-07-30T17:45:16.033Z` (PostgreSQL), except for the current-class-read row,
which comes from the post-fix reruns `2026-07-30T18:47:40.672Z` (SQLite) and
`2026-07-30T18:49:07.408Z` (PostgreSQL). The superseded first pass is
`2026-07-15T17:00:06.177Z` and `2026-07-15T17:00:41.899Z`. Every row in the
identity-enabled table carries its `history.jsonl` metric label so the report
and the raw history line up mechanically.

The 2026-07-30 PostgreSQL lane shared its server with concurrent test lanes, so
its absolute numbers carry more ambient noise than the SQLite lane; the shapes,
not the last digits, are the result.

Identity-disabled graphs take no identity lock, folding probe, closure write, or
query expansion. The implementation also avoids async identity-hook yields,
tombstone probes, and write-session lookup when the corresponding capabilities
are disabled. Store construction remains about two microseconds; its median
shift is 0.169 microseconds. No disabled write, import,
or ordinary-query lane shows a practically meaningful regression.

The identity lane carries its own disabled controls,
`identity:disabled-store-create` and `identity:disabled-property-update`. In the

Import is normalized per imported item. Assert/retract is normalized per
individual assertion action. Bulk chain assert is normalized per asserted pair
in one 500-pair `bulkAssertSame` call over a single growing class.

Current class reads use the materialized closure. The `current-class-read` row
reflects a query-shape fix in `loadCurrentVisibleMembers`: the previous
row-value `(class_kind, class_id) IN (subquery)` defeated the closure's class
index, and SQLite's planner drove the visibility join from the nodes table via
the `(graph_id, deleted_at)` index — a scan of every live node per read, so
the metric grew with total graph size (0.11 ms at the original 2026-07-15
state, 0.56 ms at this run's larger accumulated state). The rewritten
statement joins the anchor row and pins the join order with `CROSS JOIN`,
making the read O(class size): 0.013 ms on SQLite regardless of graph size,
and 0.28 ms on PostgreSQL where the remainder is round-trip overhead.

The two historical class reads
are different reconstructions, and the 2026-07-15 report conflated them:

- The valid-time read (`store.asOf(...)`) runs against a store with no recorded
  history, so it rebuilds the fixed point from the live rows — their validity
  windows plus the `created_at`/`deleted_at` lifecycle that same-id folds
  conduct on. No recorded relation is involved.
- The recorded-time read (`store.asOfRecorded(...)`) runs against a
  history-enabled store and rebuilds the fixed point over the recorded node and
  assertion relations. This is the read the earlier report described but did not
  measure.

The valid-time metric is the one the 2026-07-15 table called "Historical class
read"; it was recorded as `identity:historical-class-read` before this run and
is `identity:valid-time-class-read` from 2026-07-30 onward.

Both reconstructions cost six to twelve times a current class read and remain
the optimization target for class reads.

`identity:expanded-traversal-asof` is the same single-source-row traversal as
`identity:expanded-traversal`, pinned to a valid-time coordinate so it takes the
compiler's historical identity branch instead of the materialized closure. The
two `-n125` / `-n250` metrics are the growth pair for that branch: a narrow-edge
fixture where every `Person` row is a source row, so the reconstruction runs
over (source rows x graph size). Doubling the row count costs 4.0x on SQLite
(1.89 ms to 7.48 ms) and 2.2x on PostgreSQL (2.15 ms to 4.79 ms) — SQLite
reproduces the quadratic growth the compiler's cost note describes, while
PostgreSQL's planner keeps it closer to linear at these sizes. The absolute
values are well below the figures quoted in that note, which came from a fixture
that is not in the repository; this pair is the committed, re-runnable stand-in
for it. Identity-expanded traversal has separate current and historical planner
work tracked in
[typegraph#270](https://github.com/nicia-ai/typegraph/issues/270) and
[typegraph#310](https://github.com/nicia-ai/typegraph/issues/310).

## Folding probe and index decision

> *Superseded in the final PR implementation.* It does keep the global
> `typegraph_nodes_id_idx (graph_id, id)` index and uses one bare-id probe for
> caller-supplied ids (plus one batched probe for bulk creates). The
> measurements below describe an earlier per-kind-probe implementation and are
> retained only as benchmark history.

| Shape | SQLite median / p95 | PostgreSQL median / p95 |
| --- | ---: | ---: |
| Existing per-kind primary-key probes | 0.006308 / 0.006620 | 0.584718 / 0.658721 |
| Global probe with temporary `(graph_id, id)` index | 0.003067 / 0.004077 | 0.185438 / 0.209788 |
| Disabled create before temporary index | 0.028842 / 0.031525 | 0.913971 / 0.963023 |
| Disabled create after temporary index | 0.031554 / 0.041529 | 0.924685 / 1.027248 |

The earlier benchmark decision was not to add a permanent global nodes
`(graph_id, id)` index: it saved about 0.0032 ms per SQLite fold probe and 0.40
ms per PostgreSQL probe, while the temporary-index comparison increased
disabled-create median and p95 on both backends. That decision is retained here
only as benchmark history; the superseding implementation described above does
keep the global index and uses the batched kind-free probe.
