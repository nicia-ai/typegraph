Vector capabilities gain a `repeatableApproximateSearch` declaration: `{ repeatable: true }` when an approximate search returns the same rows on every execution over an unchanged database, or `{ repeatable: false, reason }`. pgvector and sqlite-vec declare it repeatable. libSQL declares it not repeatable, because DiskANN's `vector_top_k` starts each search from a randomly chosen node, and paging an approximate search there is refused. A custom vector strategy that does not state it resolves to not repeatable (`resolveRepeatableApproximateSearch`, exported from `./backend`), so paging an approximate search on it is refused until it declares `{ repeatable: true }`. A strategy whose engine form is exact (`searchIsExact: true`) never retrieves approximately, so paging its exact or approximate search is not refused.

Every vector search form, in the query builder and in `store.search.vector` and `store.search.hybrid`, now breaks distance ties by node id, in byte order, inside the engine's own top-`k` where the engine takes an order: pgvector reads an HNSW or IVFFlat index's candidates by distance alone, keeping every row tied with the last one it needs (`FETCH FIRST … WITH TIES`), and breaks the tie by node id in a sort over them, in a materialized wrapper PostgreSQL 17 and later cannot plan away (which also re-sorts the relaxed order of an IVFFlat iterative scan), so a filtered search keeps the index scan whatever the planner would cost a second ORDER BY key at; the wrapper also applies the cosine defined-distance condition, which inside the index read skewed the planner off probing the candidate filter per row; libSQL and sqlite-vec scans add the same order. sqlite-vec's KNN cut takes no tiebreak and keeps its deterministic storage order. Which tied neighbors make the top `k` therefore no longer varies with the plan.

A zero-norm embedding no longer matches a cosine search. Its cosine distance is undefined: SQLite ranked it as the nearest neighbor, PostgreSQL as the furthest, and sqlite-vec's KNN let it displace a real neighbor from the top `k`. It is now excluded from every cosine search form on every backend, and a zero query embedding under cosine matches nothing. Writing a zero embedding is still accepted, since l2 and inner-product distances to it are defined.

A cursor whose value for an ordered field is not a value of that field (a string for a numeric field, an object for a string field), or that the field's predicate operand contract refuses (a `meta.version` that is not a 32-bit integer, a timestamp key such as `meta.createdAt` or a date property that is not a canonical UTC instant), is now refused with a `ValidationError` on every query, instead of reaching the database as a type error or comparing across types. Every form a terminal has issued is accepted, including the `0`/`1` that SQLite's and libSQL's `store.batchOnce()` carry a Boolean as and the offset text (`2024-01-01T19:04:05.678-08:00`, or `+00:09:21` with seconds, which a zone's local mean time gives an early date, and a local year outside 0001 to 9999 for an instant inside them: `10000-01-01T10:00:00+14:00` east of UTC, a `BC` year west of it) that PostgreSQL's `store.batchOnce()` carries a timestamp as and the rendering a PostgreSQL driver returns one in, which is compared as the instant it names on every dialect. On PostgreSQL, whose text cannot hold a NUL character, a cursor whose text holds one is refused the same way instead of failing in the database, and a cursor whose text holds a lone UTF-16 surrogate, which no database stores or returns, is refused on every dialect.

For backend authors: `compileRelevanceCandidateOrder(value, direction, { nodeKind, nodeId }, dialect)` (exported from `./backend`, with `RelevanceSortSource`) is the candidate order every top-`k` cut uses, comparing the identity through `dialect.binaryText`; a strategy's scan of one kind's table passes `nodeKind: undefined`. A custom `DialectAdapter` must declare `capabilities.textAdmitsNul`, `batchExactNumber` (the value a `store.batchOnce()` envelope carries a search page's numeric `orderBy()` key as, so its cursor reads back the exact double: a number, or its exact binary text `[-]<significand>p<exponent>`, the significand an integer in [2^52, 2^53)) and a `relevanceCursorKey` whose `value`, `select` and `bind` take the key's source and whose `operand` writes a bound numeric key into the cursor comparison (the hybrid node-id key never reaches it: it is always bound as text).
