A read-only transaction now stays read-only when its native handle is adopted again. A write through any context over a transaction `store.transaction(fn, { accessMode: "read_only" })` opened is refused like a write on its own `tx`. Before this, the read-only fact lived on that `tx` object, so handing `tx.sql` back to the store built a context that knew nothing of it: `store.withTransaction(tx.sql)` and `withRecordedTransaction(tx.sql, fn)` committed writes inside the "read-only" transaction on SQLite, and on PostgreSQL the engine rejected the statement and aborted the transaction. The fact now belongs to the native transaction itself, from the moment the callback starts until the transaction's `COMMIT`, `ROLLBACK` or savepoint `RELEASE`, so a write left floating after the callback settled is refused too, and every context over that transaction asks it at each write. `withTransaction(tx.sql)` and `withRecordedTransaction(tx.sql, fn)` refuse every collection and identity write, `writeNodeUpsertBatch()` and `applyMergePlanInTransaction()` with the same `UnsupportedBackendCapabilityError` (capability `"write transaction access"`) and `operation` names as `tx`. A history store's `withRecordedTransaction(tx.sql, fn)` and `withEvolvedTransaction(tx.sql, plan, fn)` are refused before their callback, whatever the plan.

The refusal covers two routes: the transaction's own backend and every backend derived from it, and every adoption of its native handle. Each backend object on those routes refuses each of its members that can write or run DDL, before any statement and whatever reached it, with the same `UnsupportedBackendCapabilityError`, whose `operation` names the backend member (`backend.upsertFulltextBatch()`). That covers a backend built over `tx.sql` (`createPostgresTransactionBackend(tx.sql)`, `createSqliteBackend(tx.sql)`), a backend from `backend.adoptTransaction(tx.sql)` and root `adoptSchemaWriteTransaction(tx.sql)`, and the transaction backend of a read-only unit, its own included. Entry points that take such a backend and know nothing of the read-only transaction are refused with it: `createAdapterStoreWithSchema()`, `migrateSchema()` and `rollbackSchema()` over it no longer initialize, migrate or roll back a graph inside the transaction, and `store.search.rebuildFulltext()` on a Store over it no longer writes fulltext rows. Which backend members write is one table typed over every backend member name, so a new member does not compile until it is classified; a transaction opener is a write unless it opens a read-only transaction. Atomic mutation programs are refused at dispatch, and every write library code runs through a raw-SQL member (identity relations, recorded history, retention pruning, removal cleanup, `repairInvertedValidityWindows({ mode: "apply" })`) is marked as a write and refused the same way. SQL you run yourself through `tx.sql` or a backend's `executeStatement` is left to the engine, as before. A hand-written backend gets the Store's refusals below but no backend-level refusal, since nothing ties its objects to a native transaction.

The root backend is not covered, and is not changed. A call another flow makes on the root backend, or on a Store over it, while a read-only transaction is open runs exactly as before, as does a root call awaited inside the callback. On a SQLite driver that runs every transaction on one connection (better-sqlite3, `@libsql/client` before 0.18, sql.js, Durable Object storage), a root write that goes through the root's serialized queue waits for the read-only transaction to end, and a root member that runs its statements on the connection at once (`refreshStatistics()`, `executeDdl()`, the `ensure*` provisioning members, the materialization records, a bulk write's statistics refresh) runs them inside the read-only transaction's span, as it did before this change. On those drivers a backend built over `tx.sql` when `tx.sql` is the database handle is a root backend unless the driver proves the transaction: on better-sqlite3 one built inside the callback is bound to the transaction until it ends; on `@libsql/client` before 0.18, sql.js and Durable Object storage it is a root backend.

A Store over a backend built over `tx.sql` refuses its own members that write first, named by the Store member and before it reads its arguments: its collection and identity writes (`store.nodes.Person.create()`), `clear()`, `evolve()`, `deprecateKinds()`, `undeprecateKinds()`, `removeKinds()`, `materializeRemovals()`, `materializeIndexes()`, `materializeSystemIndexes()`, `refreshStatistics()`, `reembedVectorField()`, `repairContributions()`, `rebuildContribution()`, `pruneRecordedInstants()`, `rotateAllocationOwner()`, `rebuildIdentityClosure(store)`, `importGraph()`, `importGraphStream()` and `trustedImportGraphStream()`. A read-write `store.transaction()` or `transactionWithReceipt()` on such a Store is refused as it opens, before its fences or a history store's isolation check, so `merge()`, `applyMergePlan()` and the other graph-merge writes are refused at the unit they open; a read-only one runs. Reads run, `branch()` from such a Store included: reading the allocation owner no longer runs the revision-origin DDL there, which PostgreSQL refused in a read-only transaction and aborted it, and a graph that has no revision origin yet is refused rather than minted.

A read-only `store.transaction()` on a Store over a caller's read-write transaction runs as a savepoint and issues the same statements as before: TypeGraph leaves the caller's access mode alone, so the read-only scope alone refuses TypeGraph's writes there, through every context and backend over the caller's transaction, until that savepoint ends. A write another call on the same transaction reaches while it is open is refused too, before any statement. That includes a read-write `store.transaction()` already open on the same caller's transaction when the read-only one opens beside it: its later writes are refused, so it rejects, and what it wrote before the refusal follows the caller's transaction rather than the unit (on node-postgres and PGlite it commits with your transaction; postgres-js rolls it back with the unit). Do not overlap a read-write and a read-only unit on one caller's transaction. SQL you run through `tx.sql` inside it is the engine's, and commits with your transaction. Only a `store.transaction()` you open read-only opens that scope: TypeGraph's own read-only units on such a Store (an export's snapshot, the confirm read of `getOrCreateByEndpoints()`, the iterative algorithms) open none and issue exactly the statements they did before, so calls that overlap them under `Promise.all` behave as before, and the algorithms run inside a read-only `store.transaction()` there as before. A native read-only transaction the Store did not open carries no such fact, and the engine decides as before. For an adoption TypeGraph cannot tie to the transaction, the driver connection the transaction runs on holds the read-only scope too: an adoption of `tx.sql` on a driver that cannot report whether a transaction is open (`@libsql/client` before 0.18, sql.js, Durable Object storage), a context bound in an earlier transaction on the same better-sqlite3 connection, and a savepoint the caller opens with `tx.sql.transaction(...)` on node-postgres, which keeps the pooled client. Such a savepoint is refused on better-sqlite3, libSQL and PGlite as well, whose drivers show which transaction it is in. On postgres-js it gets a client of its own: PostgreSQL rejects its write with SQLSTATE `25006` in a read-only transaction TypeGraph opened, and accepts it in a read-only `store.transaction()` that runs as a savepoint of your read-write transaction.

The connection a handle runs on is the one `resolveConnectionIdentity` names for the serialized-resource audit, so on a driver TypeGraph cannot detect (`sqlite-proxy`) two backends declaring the same `serializedResource: { mode: "shared", resource }` are one connection here too. A declaration proves no transaction: an adoption of the second backend's own handle is never joined to a read-only transaction opened through the first, and while that transaction is open its writes are refused before any statement. The second backend's root runs as before, and without a declaration the adoption writes as before.
