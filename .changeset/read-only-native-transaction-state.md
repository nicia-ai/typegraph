A write through any context over a transaction `store.transaction(fn, { accessMode: "read_only" })` opened is now refused like a write on its own `tx`. Before this, the read-only fact lived on that `tx` object, so handing `tx.sql` back to the store built a context that knew nothing of it: `store.withTransaction(tx.sql)` and `withRecordedTransaction(tx.sql, fn)` committed writes inside the "read-only" transaction on SQLite, and on PostgreSQL the engine rejected the statement and aborted the transaction. The fact now belongs to the native transaction itself, for as long as the read-only callback runs, and every context over that transaction asks it at each write. `withTransaction(tx.sql)` and `withRecordedTransaction(tx.sql, fn)` refuse every collection and identity write, `writeNodeUpsertBatch()` and `applyMergePlanInTransaction()` with the same `UnsupportedBackendCapabilityError` (capability `"write transaction access"`) and `operation` names as `tx`. A history store's `withRecordedTransaction(tx.sql, fn)` and `withEvolvedTransaction(tx.sql, plan, fn)` are refused before their callback, whatever the plan. A Store over `createPostgresTransactionBackend(tx.sql)`, or over `createSqliteBackend(tx.sql)` on a libSQL transaction, refuses its own collection and identity writes (named `store.nodes.Person.create()`), `store.clear()`, `importGraph()`, `importGraphStream()` and `trustedImportGraphStream()`, and the writes and provenance verbs in its own `store.transaction()`. Every refusal comes before any statement on SQLite and PostgreSQL alike, so the transaction stays usable. A read-only `store.transaction()` on a Store over a caller's read-write transaction runs as a savepoint, and the caller's transaction refuses writes only while that callback runs. A native read-only transaction the Store did not open carries no such fact, and the engine decides as before. A savepoint the caller opens with `tx.sql.transaction(...)` and adopts directly is refused the same way on better-sqlite3, libSQL and PGlite, whose drivers show which transaction it is in. On node-postgres and postgres-js nothing links it to the enclosing transaction, so TypeGraph does not refuse it and the read-only engine transaction rejects the write. On a driver that cannot report whether a transaction is open (`@libsql/client` before 0.18, sql.js, Durable Object storage), an adoption of `tx.sql` cannot be shown to run in the read-only transaction. It is still refused while that transaction's callback runs, because a statement on that one connection runs inside it.
