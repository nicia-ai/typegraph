A write through any context over a transaction `store.transaction(fn, { accessMode: "read_only" })` opened is now refused like a write on its own `tx`. Before this, the read-only fact lived on that `tx` object, so handing `tx.sql` back to the store built a context that knew nothing of it: `store.withTransaction(tx.sql)` and `withRecordedTransaction(tx.sql, fn)` committed writes inside the "read-only" transaction on SQLite, and on PostgreSQL the engine rejected the statement and aborted the transaction. The fact now belongs to the native transaction itself, for as long as the read-only callback runs, and every context over that transaction asks it at each write. `withTransaction(tx.sql)` and `withRecordedTransaction(tx.sql, fn)` refuse every collection and identity write, `writeNodeUpsertBatch()` and `applyMergePlanInTransaction()` with the same `UnsupportedBackendCapabilityError` (capability `"write transaction access"`) and `operation` names as `tx`. A history store's `withRecordedTransaction(tx.sql, fn)` and `withEvolvedTransaction(tx.sql, plan, fn)` are refused before their callback, whatever the plan. A Store over `createPostgresTransactionBackend(tx.sql)`, or over `createSqliteBackend(tx.sql)` on a libSQL transaction, refuses its own collection and identity writes (named `store.nodes.Person.create()`), `store.clear()`, `evolve()`, `deprecateKinds()`, `undeprecateKinds()`, `removeKinds()`, `materializeRemovals()`, `materializeIndexes()`, `repairContributions()`, `rebuildIdentityClosure(store)`, `importGraph()`, `importGraphStream()` and `trustedImportGraphStream()`, and the writes and provenance verbs in its own `store.transaction()`; a history Store there refuses them before its PostgreSQL isolation check. Every refusal comes before any statement on SQLite and PostgreSQL alike, so the transaction stays usable. A read-only `store.transaction()` on a Store over a caller's read-write transaction runs as a savepoint, and the caller's transaction refuses writes only while that callback runs. A native read-only transaction the Store did not open carries no such fact, and the engine decides as before. The read-only scope is also held by the driver connection its transaction runs on, while the callback runs, so a context TypeGraph cannot tie to the transaction is still refused when its statements would run on that connection: an adoption of `tx.sql` on a driver that cannot report whether a transaction is open (`@libsql/client` before 0.18, sql.js, Durable Object storage), a context bound in an earlier transaction on the same better-sqlite3 connection, and a savepoint the caller opens with `tx.sql.transaction(...)` on node-postgres, which keeps the pooled client. Such a savepoint is refused on better-sqlite3, libSQL and PGlite as well, whose drivers show which transaction it is in. On postgres-js it gets a client of its own: in a read-only engine transaction the engine rejects its write, but inside a read-only `store.transaction()` that runs as a savepoint of a caller's read-write transaction the write is not refused.
