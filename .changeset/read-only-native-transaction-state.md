A write through any context over a transaction `store.transaction(fn, { accessMode: "read_only" })` opened is now refused like a write on its own `tx`. Before this, the read-only fact lived on that `tx` object, so handing `tx.sql` back to the store built a context that knew nothing of it: `store.withTransaction(tx.sql)` and `withRecordedTransaction(tx.sql, fn)` committed writes inside the "read-only" transaction on SQLite, and on PostgreSQL the engine rejected the statement and aborted the transaction. The fact now belongs to the native transaction itself, from the moment the callback starts until the transaction's `COMMIT`, `ROLLBACK` or savepoint `RELEASE`, so a write left floating after the callback settled is refused too, and every context over that transaction asks it at each write. `withTransaction(tx.sql)` and `withRecordedTransaction(tx.sql, fn)` refuse every collection and identity write, `writeNodeUpsertBatch()` and `applyMergePlanInTransaction()` with the same `UnsupportedBackendCapabilityError` (capability `"write transaction access"`) and `operation` names as `tx`. A history store's `withRecordedTransaction(tx.sql, fn)` and `withEvolvedTransaction(tx.sql, plan, fn)` are refused before their callback, whatever the plan.

A Store over `createPostgresTransactionBackend(tx.sql)`, or over `createSqliteBackend(tx.sql)` on a libSQL transaction, refuses every member that can write before anything else, whatever its arguments: its collection and identity writes (named `store.nodes.Person.create()`), `clear()`, `evolve()`, `deprecateKinds()`, `undeprecateKinds()`, `removeKinds()`, `materializeRemovals()`, `materializeIndexes()`, `materializeSystemIndexes()`, `refreshStatistics()`, `reembedVectorField()`, `repairContributions()`, `rebuildContribution()`, `pruneRecordedInstants()`, `rotateAllocationOwner()`, `rebuildIdentityClosure(store)`, `importGraph()`, `importGraphStream()` and `trustedImportGraphStream()`. Before this, `pruneRecordedInstants()`, `rotateAllocationOwner()`, `refreshStatistics()` and `materializeSystemIndexes()` ran and committed inside the read-only transaction on SQLite, and aborted it on PostgreSQL. A read-write `store.transaction()` or `transactionWithReceipt()` on such a Store is refused as it opens, before its fences or a history store's isolation check, so `merge()`, `applyMergePlan()` and the other graph-merge writes are refused at the unit they open; a read-only one runs. Every Store member is declared as a write, a surface whose writes are refused this way, or a read, and a new member does not compile until it is declared. Reads run, `branch()` from such a Store included: reading the allocation owner no longer runs the revision-origin DDL there, which PostgreSQL refused in a read-only transaction and aborted it, and a graph that has no revision origin yet is refused rather than minted.

A read-only `store.transaction()` on a Store over a caller's read-write transaction runs as a savepoint, and on PostgreSQL that savepoint is now read-only at the engine (`SET TRANSACTION READ ONLY` as its first statement; PostgreSQL restores the caller's access mode when the savepoint ends), so a raw write through its `tx.sql`, and a savepoint the caller opens inside it on any driver, is rejected by the engine instead of committing with the caller's transaction. The caller's transaction refuses TypeGraph writes until that savepoint ends. A native read-only transaction the Store did not open carries no such fact, and the engine decides as before. The read-only scope is also held by the driver connection its transaction runs on, so a context TypeGraph cannot tie to the transaction is still refused when its statements would run on that connection: an adoption of `tx.sql` on a driver that cannot report whether a transaction is open (`@libsql/client` before 0.18, sql.js, Durable Object storage), a context bound in an earlier transaction on the same better-sqlite3 connection, and a savepoint the caller opens with `tx.sql.transaction(...)` on node-postgres, which keeps the pooled client. Such a savepoint is refused on better-sqlite3, libSQL and PGlite as well, whose drivers show which transaction it is in. On postgres-js it gets a client of its own, and PostgreSQL rejects its write with SQLSTATE `25006`.
