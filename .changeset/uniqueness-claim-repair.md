`store.verifyConstraintFences()` now finds uniqueness claims that no longer fence the value their holder stores, and the new `store.repairUniquenessClaims()` re-keys them in place. A claim fences a value only while its key bytes are the ones a create of that value derives. A claim an earlier release keyed in another form (a fixed-literal `.default()` object in its literal's key order, a date under its unquoted ISO text from an earlier import) holds the same value under bytes no create derives, so a create of the value was admitted beside it, and no update of a fixed-literal holder could move it. Reading the claim relation alone cannot see this, because the stale claim and the duplicate's claim sit on different rows, so the audit derives each holder's key again from the row it stores, through the same key owner every write uses, and compares it with the claims the holder holds.

The audit reports two new families. `nodeUniquenessClaimStale` names a live claim whose key is not the one its owner derives today (`target` is the stored row, `expectedKey` the derived key or `undefined` when the owner is soft-deleted, gone, or its `where` no longer holds). `nodeUniquenessClaimMissing` names a live holder with no live claim of its derived key, or, with `released: true`, a soft-deleted holder whose released claim has another form, so `getOrCreateByConstraint()` cannot find it to resurrect it. `nodeUniqueness` now also reports two or more live nodes that store the same value under one constraint whatever claims they hold, merged with the row the claim relation already shows contended.

`store.repairUniquenessClaims(options?)` is a dry run by default and returns `{ dryRun, repaired, duplicates, blocked }`; `{ dryRun: false }` applies the plan. It writes only claim rows, through `releaseUniquesByOwner`, `insertUnique` and `deleteUnique`: a live holder's stale claims are released and its derived key is claimed, and a soft-deleted holder gets a released claim of its derived key. No node row, edge, history row, revision or validity window changes, so a holder with live edges keeps them. A constraint that carries a duplicate changes nothing (`blocked`) until the duplicate is resolved. An applying run is one write transaction that takes the graph's write fence, row-locks every holder it re-keys and audits again before writing; a holder a concurrent write changed refuses it with `ConfigurationError` (`UNIQUENESS_CLAIM_REPAIR_CONCURRENT_WRITE`), and a concurrent create that claimed a repaired key first refuses it with `UniquenessError`, either with nothing written.

### Upgrade notes

- **`ConstraintFenceViolation` has two new members**, `nodeUniquenessClaimStale` and `nodeUniquenessClaimMissing`, both carrying `target` and `owner`. A `switch` over `violation.family` that must be exhaustive needs a case for each, and a graph holding claims keyed in another form now reports them where the audit was clean before.
- **`store.verifyConstraintFences()` reads every node row of each kind that declares a unique constraint**, live and soft-deleted, in pages, and holds every claim key and derived key in memory. A graph that declares no unique constraint issues no new statement. The audit and the repair read the claim relation through `execute` against the backend's `tableNames`, so a custom backend whose claims are not stored in the bundled `uniques` layout cannot run them.
- **To establish uniqueness after upgrading**, stop the graph's writers, run `store.repairUniquenessClaims({ dryRun: false })` until it reports no `duplicates` and nothing left in `repaired`, resolving each duplicate it reports (for example by hard-deleting one holder), and then start the writers.
- **An applying run needs a backend with transactions.** On one without, `store.repairUniquenessClaims({ dryRun: false })` is refused with `ConfigurationError` (`CONSTRAINT_WRITE_FENCE_UNSUPPORTED`) before it writes; the dry run and the audit still work.
