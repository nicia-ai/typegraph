---
"@nicia-ai/typegraph": minor
---

**`partOf` and `hasPart` are now a real [composition](https://typegraph.dev/ontology#composition) relation**, realized by an edge kind that stores the containment. `partOf(part, whole, { via, partSide? })` and its mirror `hasPart(whole, part, { via, partSide? })` name that edge with `via`; orientation is inferred from the declared pair against the edge's endpoints, and when both orientations are admissible (a same-kind containment edge) the declaration names `partSide: "from" | "to"`. The realizing edge must declare its whole-side cardinality as `"one"` or `"oneActive"` (`cardinality` when the part is the edge's `from`, `targetCardinality` when the part is its `to`), must be composition-exact (every endpoint pair it admits is a declared composition pair), and every composition edge that can accept a given part kind must declare the same temporal population. `KindRegistry.compositionRelation()` returns the derived `CompositionRelation` — pairs, realizing edge kinds, and part side per pair — and `via` and `partSide` travel through every representation of an ontology relation (compile-time, named, serialized, extension document, introspection).

**`partOf` / `hasPart` gain `existence?: "optional" | "required"`** (default `"optional"`, so existing declarations keep their semantics): `"required"` says a part of that kind can never exist without a live whole, and `KindRegistry.compositionExistence(kind)` reports it. Two declarations disagreeing on `existence` for one part kind refuse at registry build with `ONTOLOGY_COMPOSITION_EXISTENCE_MIXED`. `existence` is emitted only when `"required"`, so an explicit `"optional"` serializes byte-identically to omitting it and an untouched graph's schema hash is unchanged.

**A part names the edge that realizes its attachment.** `NodeCollection.create`'s options are extracted into `NodeCreateOptions`, and `partOf` — on `create`, `bulkCreate`'s per-item options and both get-or-create entries — is a `CompositionAttachment`, `{ kind, id, via?, props? }`, written in the same write as the node: a dead or missing whole, an undeclared pair, or a lost composition claim aborts the node create too, leaving no orphan row. An undeclared pair refuses with `ConfigurationError` (`COMPOSITION_WHOLE_NOT_DECLARED`). `via` names the realizing edge kind and is required only when the part kind declares more than one composition pair toward that whole kind: omitting it there refuses with `COMPOSITION_VIA_AMBIGUOUS`, and naming an edge kind that realizes no declared pair between the two refuses with `COMPOSITION_VIA_NOT_DECLARED`. `props` are the realizing edge's own properties, validated against that edge kind's schema exactly as `store.edges.<via>.create(...)` would, so a realizing edge with required schema fields is now attachable from a node create at all. A required-existence kind created with no `partOf` refuses with `CompositionExistenceError` (`COMPOSITION_WHOLE_REQUIRED`, `situation: "create"`) before any row is written; `partOf` is honored on an optional-existence pair too. A required-existence kind, or any input carrying `partOf`, always takes the portable, fully-validated write path.

**`partOf` on `getOrCreateByConstraint` is a POSTCONDITION, not a create-only option**: when the call returns, the resolved node holds exactly the stated attachment. The attachment is resolved before the match is read, so an undeclared whole kind, an unknown `via` and an ambiguous omitted `via` refuse with the same `ConfigurationError` whether the call created the node or found it. A node that already holds this whole through the resolved pair's realizing edge satisfies the call — idempotently when stated `props` are omitted, or valid and value-identical to the edge's live stored props; a valid but DIFFERENT `props` is refused (`CompositionExistenceError`, `situation: "props"`). A node with no live whole has the attachment written now, whatever its pair's declared `existence`, and a resurrection restores the whole alone. A node with a DIFFERENT live whole, or the same whole through another realizing edge, is refused (`situation: "existing"`) naming both sides. `bulkGetOrCreateByConstraint` behaves identically per item. Two concurrent get-or-create calls naming DIFFERENT wholes for one part end with exactly one attachment and one `CompositionExistenceError`, never a silent move. When `ifExists: "update"` applies, the attachment and the property update commit together, so any refusal — including a unique or validation error from the update itself — leaves properties, ownership and history untouched, including inside an enclosing `store.transaction(...)`. An already-satisfied call with no update to make stays read-only and takes no write fence.

**`nodes.<Kind>.reparent(id, attachment)` moves a part to a new whole**, which no sequence of detach and attach could express. It performs both halves in one transaction and validates the final state: one whole, acyclicity over the oriented composition union, and a required part never left detached. The part keeps its id, its properties and every descendant beneath it, and a refused move leaves it attached where it was, including inside an enclosing `store.transaction(...)`. How the old attachment retires follows the population declared by the incumbent row's own pair: a `population: "one"` edge is deleted, so the attachment disappears from every `store.asOf(t)` coordinate before the move, while a `population: "oneActive"` edge has its window ended at the move instant, leaving the previous membership readable as valid-time history. That instant is both the old window's `validTo` and the new edge's `validFrom`, so for a `oneActive` pair the two halves abut: no `store.asOf(t)` coordinate shows the part with zero wholes, and none with two. Reparenting to the whole the part already holds is a no-op, no write and no history, though a stated `props` is still checked: value-identical to the live stored props the no-op stands, valid but different refuses (`situation: "props"`).

**Detaching a live required part is refused.** Ending, soft-deleting or hard-deleting a required-existence part's composition edge while the part is LIVE refuses with `CompositionExistenceError` (`COMPOSITION_DETACH_REFUSED`, `situation: "detach"`); detaching from a soft- or hard-deleted part is allowed. Deleting the *whole* still cascades to its required parts — `existence: "required"` governs bare creation and detachment, not whole deletion. `CompositionExistenceError.code` names the situation: `COMPOSITION_WHOLE_REQUIRED` (a bare create), `COMPOSITION_DETACH_REFUSED` (a refused detach), `COMPOSITION_WHOLE_CONFLICT` (a stated `partOf` contradicting the whole an existing node holds) and `COMPOSITION_PROPS_CONFLICT` (a stated `partOf.props` differing from the already-satisfied attachment's stored props). `details.situation` carries the same distinction and remains the discriminant for which optional detail fields are populated, so a handler may branch on either.

**Deleting a composition whole cascades leaf-first through its live parts closure**, each part running through its own node-delete pipeline inside the whole's transaction, with restrict and cascade `onDelete` behaviors on non-composition edges honored per part. Composition edges never count as a `restrict` obstacle on either end. An instance-level cycle among reflexive composition edges is refused with `CompositionCycleError` (`COMPOSITION_CYCLE_DETECTED`) rather than looping or truncating. Resurrecting a soft-deleted whole restores the whole alone, ending a whole's validity window is not a cascade, and the cascade emits one operation-hook event, for the whole. See [Composition Cascade](https://typegraph.dev/limitations#composition-cascade). `NodeDeletePolicy` gains `consumedEdgeIds` (connected edges the cascade has already consumed, filtered out before the kind's `onDelete` behavior applies) and `cascadeComposition`.

**A whole's delete says which parts it took.** The delete's `onOperationEnd` hook context and `store.transactionWithReceipt`'s receipt both carry `cascadedParts`, `{ kind, id }` refs that never name a part the cascade did not delete, in the cascade's own delete order: leaf-first, then by kind, then id, within one level of the closure. That order is fully deterministic, so the same closure reports the same list on every run and every backend and a consumer may compare `cascadedParts` for equality. The receipt covers `bulkDelete` too, accumulating every item's cascade in batch order, and the batch path still emits no per-item operation hooks. A `tx.measure(...)` scope's sub-receipt carries the refs for the deletes issued THROUGH that scope, so a delete issued through the outer transaction during an open scope stays out of it. `onOperationStart` never carries them, and the refs are not folded into the receipt's write counters: one caller-issued delete stays one write intent. There is no cascade preview API in this release; read the closure ahead of time with `store.subgraph(id, { edges: [], composition: true })`.

**`QueryBuilder` gains `parts()` and `wholes()`**, declared-structure sugar over the recursive `Traversal` AST for a declared composition relation. `parts("alias", { from?, maxHops?, depth?, path? })` derives the edge kind(s) and direction(s) from the registry's composition relation and recurses to the full transitive closure by default; pass `maxHops: 1` for the direct level only. `wholes()` is the mirror, returning the ancestor chain. Direction is derived per realizing edge kind: a `part -> whole` edge is followed reversed, a `whole -> part` (`has_*`) edge in its own direction, and a relation realized by both orientations across levels compiles to one traversal step. The result alias is untyped (`DynamicNodeType`/`DynamicEdgeType`, reached via `.field(name)`), since the closure under a kind may span several node kinds with different schemas. `parts()`/`wholes()` on a kind declaring no composition parts/wholes refuses with `ConfigurationError` (`COMPOSITION_NO_PARTS_DECLARED` / `COMPOSITION_NO_WHOLES_DECLARED`) rather than returning zero rows, and `expand` is not accepted on either step. `TraversalBuilder` gains `toKindSet(kinds, alias)`, a finalizer parallel to `to()`/`toDynamic()` for an explicit, already-resolved set of target node kinds.

A related defect is fixed: a recursive traversal combining `.recursive()` with a non-empty inverse edge-kind set (`{ expand: "inverse" }`, or the mixed-orientation case `parts()`/`wholes()` now exercise) emitted SQL that PostgreSQL rejected and SQLite accepted. Such traversals now compile and run on both dialects.

**`subgraph({ composition: true })` returns the complete owned unit.** `SubgraphOptions` gains `composition?: boolean`, which closes the selected root over the composition edge kinds under its actual kind, in addition to whatever `edges` already lists. A root kind declaring no composition parts contributes nothing and the read still runs; a graph declaring no composition relation at all refuses with `ConfigurationError` (`COMPOSITION_NO_PARTS_DECLARED`). Because which composition edge kinds join depends on the root's runtime kind, `composition: true` widens the result's edge-key type to the graph's whole edge-kind union (the new `SubgraphResultEdgeKinds`), so every key the traversal can put in `adjacency` / `reverseAdjacency` is reachable through the result type; `composition` absent or `false` keeps the existing `edges`-list typing unchanged. The `project.edges` keys a call may name widen with the result (`SubgraphProjectFor`), so a `composition: true` read can project the composition edges it receives; an edge kind outside `edges` is still refused without it. The closure is exhaustive, bounded neither by `maxDepth` nor by the engine's 1000-hop cap on explicit traversals, so a part chain of any depth comes back whole rather than truncated, and `maxDepth` / `cyclePolicy` bound only the `edges` traversal listed alongside it. It is delivered or refused, never partial: a closure statement the database cut short (a `statement_timeout`, a cancelled query) refuses with `ConfigurationError` (`COMPOSITION_UNIT_INDETERMINATE`) naming the root.

**A batch create whose items carry `partOf` does per-batch rather than per-item work**, with the same refusals: whole rows are read once per kind, a part row is never re-read after the insert that wrote it, and acyclicity is walked once over every composition edge the batch inserted — which is what makes a cycle running through two of the batch's own items visible at all. A cycle refusal names a concrete offending edge: the self-attaching item's own edge for a self-loop, otherwise the first of the batch's edges lying on the cycle.

**Import, the audit and graph merge all see composition.** Validating import tracks every required-existence part it creates and, once the payload's node and edge sets are both known, accepts one already attached in the same batch or already live on the target and reports a per-row error — removing the orphaned node row in the same transaction — for anything still unattached; the rest of the import commits. Trusted import refuses every declared composition pair regardless of `existence` (`composition_unsupported`). `store.verifyConstraintFences()` gains a `compositionExistence` family reporting any live required-existence part with no live whole, and a `composition` family reporting two or more live edges holding one part's reserved composition axis; a schema commit newly declaring `existence: "required"` on an already-populated pair runs a tightening preflight and refuses a dirty graph rather than silently admitting orphans. `planMerge` and `planMergeIncremental` report composition orphans in `MergePlanReview.compositionOrphans` under two causes: a part attached on the target to a whole the branch deletes (`cause: "deleted"`), and a required part this merge writes — or whose composition edge this merge explicitly deletes or ends — that resolves to no live whole at all (`cause: "unattached"`). `applyMergePlan` re-verifies both inside the apply transaction and refuses with `MergeCompositionOrphanError` (`MERGE_COMPOSITION_ORPHAN`), and merge apply deletes nodes with `cascadeComposition: false` so the plan stays the authority over what apply deletes. One residual gap remains: a composition edge dropped by canonicalization's own endpoint-deleted repointing issues no write for any per-write guard to see, so run `store.verifyConstraintFences()` against a merged store to catch that case; see [Limitations](https://typegraph.dev/limitations#composition-existence-existence-required).

### Breaking

- `partOf` / `hasPart` require `via`, in a third options argument. A missing realizing edge, or a `via` or `partSide` on any other meta-edge, is refused at registry build and at schema load with `ConfigurationError` (`ONTOLOGY_COMPOSITION_VIA_REQUIRED`, `ONTOLOGY_COMPOSITION_VIA_FORBIDDEN`, `ONTOLOGY_COMPOSITION_PART_SIDE_FORBIDDEN`). A persisted schema carrying the old three-part relation fails on load; `getSchemaChanges` reports it before upgrade.
- Refused declarations: `"many"` or `"unique"` on the whole side (`ONTOLOGY_COMPOSITION_CARDINALITY`), an edge admitting an endpoint pair that is not a declared composition pair (`ONTOLOGY_COMPOSITION_VIA_ENDPOINTS`), one edge kind declared in two orientations (`ONTOLOGY_COMPOSITION_VIA_MIXED`), mixed `one` / `oneActive` populations for one part kind (`ONTOLOGY_COMPOSITION_POPULATION_MIXED`).
- Deleting a node that is a composition whole now deletes its parts. Move any relation that re-homes or retains parts on delete off composition; the [containment tiers](https://typegraph.dev/ontology#choosing-a-containment-tier) section says where each case belongs.
- `KindRegistry.getCompositionEdge(partKind, wholeKind)` is removed. Use `compositionPairsBetween(partKind, wholeKind)` (every declared pair, code-point ordered by realizing edge kind) or `compositionPairVia(partKind, wholeKind, viaEdgeKind)`.
- `partOf` on `create` / `bulkCreate` / `getOrCreateByConstraint` / `bulkGetOrCreateByConstraint` is typed `CompositionAttachment` rather than `CompositionWholeRef`. Existing `{ kind, id }` call sites are unchanged, but a part kind with more than one declared pair toward the named whole kind refuses until the call states `via`.
- `getOrCreateByConstraint` / `bulkGetOrCreateByConstraint` no longer refuse every `partOf` stated against a `"found"` / `"updated"` result. Code that relied on the refusal as a "this node already existed" signal must check the returned `action` instead.
- `CompositionExistenceError.code` is per situation rather than `COMPOSITION_WHOLE_REQUIRED` for every shape. Code matching on `code === "COMPOSITION_WHOLE_REQUIRED"` to catch any composition-existence refusal must match the class, or all four codes.
- `CompositionExistenceErrorDetails` gains `currentVia`, `requestedWhole` and `requestedVia` (optional, `situation: "existing"` only; `requestedVia` carries the resolved realizing edge, so it is present even when the call omitted one), and `situation` gains `"props"` with `currentProps`/`requestedProps` (optional, that situation only). The `"existing"` message names both the held and the requested attachment.
- `NodeCollection` gains `reparent`; a hand-written implementation of that interface must add it.
- `TransactionReceipt` gains a required `cascadedParts` field, always present and empty when the transaction deleted no composition whole; anything constructing a receipt literal must add it.
- `OperationHookContext` gains an optional `cascadedParts`, and `StoreHooks`' runner signature gains a fourth, optional operation-facts argument; a hand-written hook runner needs the extra parameter.
- `CompositionPair` (internal to the registry, not part of the public entrypoint) gains a required `existence` field — anything constructing one directly, such as a test fixture, must add it.
- `ConstraintFenceViolation` gains `composition` and `compositionExistence` members; an exhaustive `switch (violation.family)` outside the library needs an arm for each.
- `MergePlanCompositionOrphan` gains a required `cause: "deleted" | "unattached"` field and its `whole` becomes optional, absent for `cause: "unattached"`; a consumer constructing or exhaustively matching this shape needs updating.
- `MERGE_PLAN_FORMAT_VERSION` is now `2`: `parseMergePlanArtifact` reports a stored version-1 artifact as `unsupported-version`, so re-plan any artifact captured before the upgrade. The artifact type and schema family are renamed (`MergePlanArtifactV2`, `MergePlanArtifactV2Input`, `mergePlanArtifactV2Schema`); the version-agnostic `MergePlanArtifact` alias is unchanged. `MergeCompositionOrphanErrorDetails` is removed in favor of `MergePlanCompositionOrphan`, which the error's `details` carries directly.
