"@nicia-ai/typegraph": minor

**`partOf` and `hasPart` are now a real [composition](https://typegraph.dev/ontology#composition) relation**, realized by an edge kind that stores the containment. `partOf(part, whole, { via, partSide? })` and its mirror `hasPart(whole, part, { via, partSide? })` name that edge with `via`; orientation is inferred from the declared pair against the edge's endpoints, and when both orientations are admissible (a same-kind containment edge) the declaration names `partSide: "from" | "to"`. The realizing edge must declare its whole-side cardinality as `"one"` or `"oneActive"` (`cardinality` when the part is the edge's `from`, `targetCardinality` when the part is its `to`), must be composition-exact (every endpoint pair it admits is a declared composition pair), and every composition edge that can accept a given part kind must declare the same temporal population. `KindRegistry.compositionRelation()` returns the derived `CompositionRelation` — pairs, realizing edge kinds, and part side per pair — and `via` and `partSide` travel through every representation of an ontology relation (compile-time, named, serialized, extension document, introspection).

**`partOf` / `hasPart` gain `existence?: "optional" | "required"`** (default `"optional"`, so existing declarations keep their semantics): `"required"` says a part of that kind can never exist without a live whole, and `KindRegistry.compositionExistence(kind)` reports it. Two declarations disagreeing on `existence` for one part kind refuse at registry build with `ONTOLOGY_COMPOSITION_EXISTENCE_MIXED`. `existence` is emitted only when `"required"`, so an explicit `"optional"` serializes byte-identically to omitting it and an untouched graph's schema hash is unchanged.

**A part names the edge that realizes its attachment.** `NodeCollection.create`'s options are extracted into `NodeCreateOptions`, and `partOf` — on `create`, `bulkCreate`'s per-item options and both get-or-create entries — is a `CompositionAttachment`, `{ whole, via?, props?, validFrom?, validTo? }`, written in the same write as the node. `whole` is a node you already hold or a `{ kind, id }` reference, and only its `kind` and `id` are read, so a whole node's own properties never bleed into the attachment. On `store.nodes.<Kind>` its `kind` is limited at compile time to the whole kinds the ontology declares for that part kind through `partOf` / `hasPart` (the new `CompositionWholeKinds<G, K>`); when the ontology also declares a subclass or equivalence relation, or has lost its tuple type, any node kind of the graph is accepted and the runtime check decides. Any other top-level key on the attachment refuses with `ValidationError` (issue path `partOf.<key>`) rather than being dropped. The window is validated once for every surface (canonical bounds, ordered pair), and on a `population: "oneActive"` pair, where only an open-ended edge is a membership, a stated `validTo` refuses with `ValidationError` (code `COMPOSITION_ATTACHMENT_WINDOW_BOUNDED`) instead of writing an edge that attaches nothing. The write is atomic: a dead or missing whole, an undeclared pair, a cardinality or acyclicity refusal, or a lost composition claim aborts the node create too, leaving no orphan row. Every one of those refusals is reached before the node row is written — for `bulkCreate` before any row of the batch, including a cycle or a whole-side cardinality the batch's own items would close together — so a caller that catches one inside an enclosing `store.transaction(...)` keeps nothing of the refused create. An undeclared pair refuses with `ConfigurationError` (`COMPOSITION_WHOLE_NOT_DECLARED`). `via` names the realizing edge kind and is required only when the part kind declares more than one composition pair toward that whole kind: omitting it there refuses with `COMPOSITION_VIA_AMBIGUOUS`, and naming an edge kind that realizes no declared pair between the two refuses with `COMPOSITION_VIA_NOT_DECLARED`. `props` are the realizing edge's own properties, validated against that edge kind's schema exactly as `store.edges.<via>.create(...)` would, so a realizing edge with required schema fields is now attachable from a node create at all. A required-existence kind created with no `partOf` refuses with `CompositionExistenceError` (`COMPOSITION_WHOLE_REQUIRED`, `situation: "create"`) before any row is written, and so does restoring a soft-deleted one through an entry that takes no `partOf` (`upsertById`, `bulkUpsertById`, `bulkReplaceById`) unless it still holds a live whole; `partOf` is honored on an optional-existence pair too. A required-existence kind, or any input carrying `partOf`, always takes the portable, fully-validated write path.

**`partOf` on `getOrCreateByConstraint` is a POSTCONDITION, not a create-only option**: when the call returns, the resolved node holds exactly the stated attachment. The attachment is resolved before the match is read, so an undeclared whole kind, an unknown `via` and an ambiguous omitted `via` refuse with the same `ConfigurationError` whether the call created the node or found it. A node that already holds this whole through the resolved pair's realizing edge satisfies the call — idempotently when stated `props` are omitted, or valid and value-identical to the edge's live stored props; a valid but DIFFERENT `props` is refused (`CompositionExistenceError`, `situation: "props"`). A stated `validFrom` / `validTo` is held to the same rule: a bound equal to the edge's stored one is satisfied, a different one refuses with `ValidationError` (issue path `partOf.validFrom` / `partOf.validTo`, code `COMPOSITION_ATTACHMENT_WINDOW_CONFLICT`). A node with no live whole has the attachment written now, whatever its pair's declared `existence`, and a resurrection restores the whole alone. A node with a DIFFERENT live whole, or the same whole through another realizing edge, is refused (`situation: "existing"`) naming both sides. `bulkGetOrCreateByConstraint` behaves identically per item and decides its matched items as a set: every verdict a read can reach for an item that matched an existing node — the attachment's (a different whole or realizing edge, differing `props` or window, a dead whole, cardinality, and acyclicity over all of the batch's attachments, counting the attachments of the rows the batch is about to create), on the `ifExists: "update"` and resurrection legs the property update's validation and unique-key probes, and on a resurrection its disjointness and identity-fold checks — precedes the batch's first write, and so does every unique key of the rows the batch creates, probed after the matched items' in the order the batch writes them so a matched update that gives up a key lets a new row take it. A refused batch therefore attaches, updates, resurrects and creates nothing, including when the caller catches the refusal inside an enclosing `store.transaction(...)`. Two refusals stay with the write: an identity fold that depends on another row the same batch restores, and a concurrent writer the fence does not exclude; the batch's convergence retry re-runs it only where the refusal left nothing of it written (the call opened its own transaction, or no leg had written), so a race inside a caller's transaction surfaces instead of applying a matched update twice. A batch with more than one item that owes a write, or one such item next to a new row, pays one extra fenced read pass for this. Writing a realizing edge directly is held to the same rule: `edges.<via>.bulkCreate` and `bulkInsert` decide every item before writing, and `bulkUpsertById` and `bulkGetOrCreateByEndpoints` decide every update, resurrection and reopen (its composition claim and existence, counting the edges the batch creates) before their first write. Two concurrent get-or-create calls naming DIFFERENT wholes for one part end with exactly one attachment and one `CompositionExistenceError`, never a silent move. When `ifExists: "update"` applies, the attachment and the property update commit together, so any refusal — including a unique or validation error from the update itself — leaves properties, ownership and history untouched, including inside an enclosing `store.transaction(...)`. An already-satisfied call with no update to make stays read-only and takes no write fence.

**A second whole is refused identically on every write path.** `CompositionError` (`COMPOSITION_WHOLE_OCCUPIED`, `details.situation: "occupied"`) with `details.incumbentEdgeId` is raised whether the claim row or the pre-write probe decides it: a batch, a custom command port that answers `unsupported`, an edge kind declaring both cardinality axes, and a backend that carries no claim relations all count the part's attachments across every realizing edge kind before writing, and report composition ahead of the edge kind's own `CardinalityError`. A backend without claim relations therefore still holds "one whole per part" across two different realizing edge kinds, under the per-graph lock.

**A composition window never starts or ends later than its write.** Every write of a realizing edge — `partOf` on every create and get-or-create entry, `store.edges.<via>` `create`, `bulkCreate`, `bulkInsert`, `update`, `bulkUpsertById`, `getOrCreateByEndpoints` and `bulkGetOrCreateByEndpoints`, validating import (as a per-row error carrying the code) and a graph merge's apply — refuses a `validFrom` later than the operation clock with `CompositionError` (`COMPOSITION_VALIDITY_FUTURE_START`, `situation: "futureStart"`) and a later `validTo` with `COMPOSITION_VALIDITY_FUTURE_END` (`situation: "futureEnd"`), both carrying the stated `bound` and the `operationInstant` it was judged against; `reparent` and `bulkReparent` refuse a later `at` with `COMPOSITION_MOVE_FUTURE` (`situation: "futureMove"`), and judge a move's two edge writes (the incumbent's window end and the new edge) at the move instant rather than a second clock read. Each refusal is reached before the write's first statement. This is what makes membership a fact of the row: a composition row with no `validTo` is the part's attachment now and at every later instant, and an ended row is history for good, so the claim, the audit, the delete cascade, the acyclicity check and every current-time read decide which whole a part holds by one rule instead of each choosing an instant — a scheduled end could otherwise leave a part with two current wholes behind a released claim, and a scheduled start a required part with none. `CompositionError.details` is a union discriminated by `situation`. A schema commit that declares a `partOf`/`hasPart` pair over an edge kind whose non-deleted rows already start or end later than the commit is refused with `MigrationError` (`reason: "ontology-tightening-violated"`) carrying `family: "compositionFutureWindow"` violations, and `store.verifyConstraintFences()` reports the same rows wherever they came from.

**`nodes.<Kind>.reparent(id, options)` moves a part to a new whole**, which no sequence of detach and attach could express. `options` is `{ whole, via?, props?, at? }`: the destination attachment and the one instant the move happens at. It performs both halves in one transaction and validates the final state: one whole, acyclicity over the oriented composition union, and a required part never left detached. That union holds the rows composition counts as memberships, so the ended row a `oneActive` move leaves behind does not constrain later moves, and resurrecting such an ended history row attaches nothing and is not refused because the part now holds another whole. Every write is judged on the row it leaves, by the same rule: a history row created, imported, cloned, merged or restored still ended is outside the union and closes no cycle, while reopening an ended row with `clearValidTo` (`update`, `bulkUpsertById`, `getOrCreateByEndpoints`) puts it back and is probed and fenced like a create — a batch probing its re-admitted rows together before its first write. A realizing edge kind that is also declared `acyclic: true` keeps that declaration's rule: every non-deleted row of the kind counts, ended or not, and a `bulkReparent` that only ends such an incumbent's window still walks it. The part keeps its id, its properties and every descendant beneath it, and a refused move leaves it attached where it was, including inside an enclosing `store.transaction(...)`. How the old attachment retires follows the population declared by the incumbent row's own pair: a `population: "one"` edge is deleted, so the attachment disappears from every `store.asOf(t)` coordinate before the move, while a `population: "oneActive"` edge has its window ended at the move instant, leaving the previous membership readable as valid-time history. That instant — `options.at`, or one clock read when it is omitted — is both the old window's `validTo` and the new edge's `validFrom`, so for a `oneActive` pair the two halves abut: no `store.asOf(t)` coordinate shows the part with zero wholes, and none with two. A `oneActive` window cannot end before it starts: an `at` earlier than the incumbent's `validFrom` refuses before any write with `CompositionError` (`COMPOSITION_MOVE_BEFORE_INCUMBENT`, `situation: "moveBeforeIncumbent"`, naming the incumbent edge and its `validFrom`), and an omitted `at` whose clock read has fallen behind that `validFrom` — the clock stepped backward — moves the part at the incumbent's `validFrom` instead, retiring a zero-width window. `at` is the only temporal option a move takes: a stated `validFrom` or `validTo` refuses with `ValidationError` (issue path `options.<key>`) rather than being dropped, since the move opens the new attachment and bounding a membership is a window edit on the realizing edge. The call returns `{ edge, moved }`: `edge` is the holding realizing edge (the new one, or the incumbent on a no-op) and `moved` is false when the part already held that whole through the same realizing edge. A stated `props` is still checked on that no-op: value-identical to the live stored props the no-op stands, valid but different refuses (`situation: "props"`). `bulkReparent` runs the same operation for many parts in one transaction and reaches every item's verdict before its first write, so a refused batch moves nothing, including when the caller catches the refusal inside an enclosing `store.transaction(...)`. The batch is judged on the state it produces as a whole: two moves that close a cycle between them are refused, a part may move under one the same batch moves out from under it in either item order, and a part listed twice is refused with a `ValidationError`. An incumbent a `oneActive` move ends still occupies every bound that counts its whole life (a whole-side `targetCardinality: "one"`, say), so a swap under such a bound is refused at preparation rather than after the windows end. Like every other batch method, `bulkReparent` fires no operation hooks; `reparent` fires one `update` operation naming the part.

**Detaching a live required part is refused.** Ending, soft-deleting or hard-deleting a required-existence part's composition edge while the part is LIVE refuses with `CompositionExistenceError` (`COMPOSITION_DETACH_REFUSED`, `situation: "detach"`); detaching from a soft- or hard-deleted part is allowed. Deleting the *whole* still cascades to its required parts — `existence: "required"` governs bare creation and detachment, not whole deletion. `CompositionExistenceError.code` names the situation: `COMPOSITION_WHOLE_REQUIRED` (a bare create), `COMPOSITION_DETACH_REFUSED` (a refused detach), `COMPOSITION_WHOLE_CONFLICT` (a stated `partOf` contradicting the whole an existing node holds) and `COMPOSITION_PROPS_CONFLICT` (a stated `partOf.props` differing from the already-satisfied attachment's stored props). `details.situation` carries the same distinction and remains the discriminant for which optional detail fields are populated, so a handler may branch on either.

**Deleting a composition whole cascades leaf-first through its live parts closure**, each part running through its own node-delete pipeline inside the whole's transaction, with restrict and cascade `onDelete` behaviors on non-composition edges honored per part. Every part's verdict, and the whole's, is reached before the first row is deleted, so a `RestrictedDeleteError` from a part deep in the closure leaves the whole closure intact, including when the caller catches it inside an enclosing `store.transaction(...)`; `bulkDelete` reaches every item's verdict before deleting any of them. Composition edges never count as a `restrict` obstacle on either end. An instance-level cycle among reflexive composition edges is refused with `CompositionCycleError` (`COMPOSITION_CYCLE_DETECTED`) rather than looping or truncating. The closure is read under the per-graph write fence, and the delete and every attach advance the graph's fence row behind it, so on PostgreSQL a `REPEATABLE READ` or `SERIALIZABLE` transaction that cannot see a part attached after its snapshot fails at the fence with a serialization failure instead of deleting from a stale view; a custom backend whose fence advances no fence row refuses the delete at those levels with `ConfigurationError` (`COMPOSITION_CASCADE_REQUIRES_FRESH_SNAPSHOT`). Each part the cascade deletes takes the same delete row lock a direct delete of that part takes, before any part's connected edges are read, so an edge written concurrently onto a part either commits first and is removed or refused with the part, or waits and is refused with `EndpointNotFoundError`; it never stays live on a deleted part. A whole's delete also removes the composition edge of a part that is already tombstoned, and each part's delete releases the unique keys the part holds at that moment. Resurrecting a soft-deleted whole restores the whole alone, ending a whole's validity window is not a cascade, and the cascade emits one operation-hook event, for the whole. See [Composition Cascade](https://typegraph.dev/limitations#composition-cascade). `NodeDeletePolicy` gains `consumedEdgeIds` (connected edges the cascade has already consumed, filtered out before the kind's `onDelete` behavior applies) and `cascadeComposition`.

**A whole's delete says which parts it took.** The delete's `onOperationEnd` hook context and `store.transactionWithReceipt`'s receipt both carry `cascadedParts`, one `CompositionCascadedPart` per part (`{ kind, id, whole, viaEdgeKind }`: the part, the whole it was directly a part of, and the composition edge kind that bound them, enough to re-attach the tree once the deleted whole itself is restored) that never names a part the cascade did not delete, in the cascade's own delete order: leaf-first, then by kind, then id, within one level of the closure. That order is fully deterministic, so the same closure reports the same list on every run and every backend and a consumer may compare `cascadedParts` for equality. The receipt covers `bulkDelete` too, accumulating every item's cascade in batch order (a node an earlier item's cascade deleted is reported once, whichever order the batch names a part and its whole in), and the batch path still emits no per-item operation hooks. A `tx.measure(...)` scope's sub-receipt carries the refs for the deletes issued THROUGH that scope, so a delete issued through the outer transaction during an open scope stays out of it. `onOperationStart` never carries them, and the refs are not folded into the receipt's write counters: one caller-issued delete stays one write intent. Resurrecting a deleted whole restores the whole alone; its parts stay deleted.

**`nodes.<Kind>.planDelete(id)` previews a delete.** It runs the delete's own planner with every write skipped and returns a `NodeDeletePlan`: `cascadedParts`, in the shape and order the delete reports them, and `removedEdgeIds`, every edge the delete would remove. It returns `undefined` for an absent or already-deleted node, and a delete the planner refuses is refused with the same error (`RestrictedDeleteError`, `CompositionCycleError`). On a transaction's collections, for a composition whole, it takes the per-graph write lock the delete takes and holds it to the end of the transaction, so no concurrent attach or reparent can add a part before a `delete(id)` later in that transaction; writes that take no per-graph lock (a detach, a part's own delete, an ordinary edge) can still change the outcome, and any other kind's delete takes no per-graph lock at all. On the store's collections it is an unlocked, best-effort read. Neither form writes a graph, sidecar, history or revision row; the transactional form takes the delete's lock, which for a composition whole on PostgreSQL advances the graph's fence row as the delete does, so it can fail the way the delete's fence fails (see the `REPEATABLE READ` / `SERIALIZABLE` note on the cascade above). Inside `store.transaction(fn, { accessMode: "read_only" })` the transactional form refuses before any statement, on every backend and for every kind, with `UnsupportedBackendCapabilityError` naming the store's `planDelete` as the unlocked alternative.

**`nodes.<Kind>.delete(id, { expect: plan })` deletes only if a confirmed preview still holds.** A preview the user confirms in a later request cannot hold a lock, so `delete` takes `NodeDeleteOptions`, `{ expect: NodeDeletePlan }`, on the store's and a transaction's collections. The delete computes its own plan with the same planner inside its transaction (for a composition whole, under the per-graph write lock its delete takes) and compares it with `expect` in any order: the same parts by `(kind, id, whole, viaEdgeKind)`, so a reparented part counts as changed, and the same `removedEdgeIds`. A difference refuses with the new `NodeDeletePlanMismatchError` (`NODE_DELETE_PLAN_MISMATCH`, category `"constraint"`, like `RestrictedDeleteError`, `details.situation: "changed"` with `addedParts`, `droppedParts`, `addedEdgeIds` and `droppedEdgeIds`) before any node, edge, sidecar, history or revision write and before `onOperationEnd`; a node absent or already deleted refuses with `situation: "notLive"` instead of the usual no-op. A guarded delete always takes the portable delete path, never the fused single-statement delete. `expect` is required once options are passed, so `planDelete`'s `undefined` cannot be passed as an expectation, and options of the wrong shape, `{ expect: undefined }` or a plan naming a part or edge id twice are refused with `ValidationError`. `hardDelete` and `bulkDelete` take no options and refuse any with `ValidationError`: a hard delete also purges a tombstoned node and the soft-deleted edge rows at each deleted node, which the plan does not name. The comparison covers the parts and edges the delete planned; for any kind other than a composition whole there is no per-graph lock, so every concurrent write can change the answer up to the comparison. A write that takes no per-graph lock and commits after the comparison, before the delete's statements, is treated exactly as an unguarded delete treats it: at `READ COMMITTED` an edge created on a node the delete removes is removed with it (`cascade` / `disconnect`) or refuses the delete (`restrict`), and at PostgreSQL `REPEATABLE READ` / `SERIALIZABLE` the delete's snapshot does not see it and it stays live on the deleted node, as for every delete. SQLite admits no concurrent writer.

**Undoing a cascading delete is a documented recipe, not a feature.** Restoring a soft-deleted whole still restores the whole alone. The [composition docs](https://typegraph.dev/ontology#undoing-a-cascading-delete) show how to capture the whole, the parts `planDelete` names and their props before a guarded delete, and how to recreate them whole-first (`cascadedParts` reversed) with their ids and `partOf: { whole, via: viaEdgeKind }`, and say what that does not bring back: the ordinary edges the delete removed, and the composition edges' ids, props and windows unless captured.

**`QueryBuilder` gains `parts()` and `wholes()`**, declared-structure sugar over the recursive `Traversal` AST for a declared composition relation. `parts("alias", { from?, maxHops?, depth?, path?, via? })` derives the edge kind(s) and direction(s) from the registry's composition relation and recurses to the full transitive closure by default, with no hop ceiling, so a chain of any depth returns whole rather than a bare `.recursive()`'s implicit 10; a `maxHops` you state bounds the walk exactly as given (up to 1000), and `maxHops: 1` reaches the direct level only. With `maxHops: 1` and neither `depth` nor `path`, the step compiles to a fixed one-hop traversal rather than a recursive one, so `paginate()`, `page()` and `stream()` accept it: that is how to page one level of a part tree. `via` narrows the walk to one realizing edge and to the kinds that edge alone reaches, so it works on a multi-level composition and on a whole with several realizing edges; a `via` that realizes no pair at the source alias itself refuses with `ConfigurationError` (`COMPOSITION_VIA_NOT_DECLARED`). `wholes()` is the mirror, returning the ancestor chain. Direction is derived per realizing edge kind: a `part -> whole` edge is followed reversed, a `whole -> part` (`has_*`) edge in its own direction, and a relation realized by both orientations across levels compiles to one traversal step. The result alias is untyped (`DynamicNodeType`/`DynamicEdgeType`, reached via `.field(name)`), since the closure under a kind may span several node kinds with different schemas. `parts()`/`wholes()` on a kind declaring no composition parts/wholes refuses with `ConfigurationError` (`COMPOSITION_NO_PARTS_DECLARED` / `COMPOSITION_NO_WHOLES_DECLARED`) rather than returning zero rows, and `expand` is not accepted on either step. `TraversalBuilder` gains `toKindSet(kinds, alias)`, a finalizer parallel to `to()`/`toDynamic()` for an explicit, already-resolved set of target node kinds. `VariableLengthSpec` gains `exhaustive?: boolean`, which walks every path to its end with no hop ceiling and is what `parts()`/`wholes()` set when no `maxHops` is stated. It requires `cyclePolicy: "prevent"` and cannot also state a `maxDepth`; the compiler refuses either contradiction with `UnsupportedPredicateError` rather than ignoring the bound. The walk carries one path per row to prevent cycles, so on a chain deeper than a few thousand levels its cost grows faster than `subgraph({ composition: true })`'s set-semantics closure; the result is complete either way.

A related defect is fixed: a recursive traversal combining `.recursive()` with a non-empty inverse edge-kind set (`{ expand: "inverse" }`, or the mixed-orientation case `parts()`/`wholes()` now exercise) emitted SQL that PostgreSQL rejected and SQLite accepted. Such traversals now compile and run on both dialects.

**`subgraph({ composition: true })` returns the complete owned unit at the read's temporal coordinate.** `SubgraphOptions` gains `composition?: boolean | { via? }`, which closes the `{ kind, id }` root over the composition edge kinds under its kind, in addition to whatever `edges` already lists; `{ via }` restricts the closure to one realizing edge kind (an edge type or its kind string) and refuses with `ConfigurationError` (`COMPOSITION_VIA_NOT_DECLARED`) when that edge realizes no composition pair under the root. A root kind declaring no composition parts contributes nothing and the read still runs; a graph declaring no composition relation at all refuses with `ConfigurationError` (`COMPOSITION_NO_PARTS_DECLARED`). Because the composition edge kinds a read adds are not in the `edges` list the call names, `composition: true` widens the result's edge-kind type to the graph's whole edge-kind union (the new `SubgraphResultEdgeKinds`), so every edge kind the read can return in `edges` is reachable through the result type and the `indexSubgraph()` lookups; a `{ via }` selection adds exactly its one realizing edge kind, and `composition` absent or `false` keeps the existing `edges`-list typing unchanged. The `project.edges` keys a call may name widen with the result (`SubgraphProjectFor`), so a `composition: true` read can project the composition edges it receives; an edge kind outside `edges` is still refused without it. The closure walks each edge from the `(kind, id)` it reached, like `parts()` and the cascade, so another kind's node sharing a part's id never pulls its own parts in. The closure is exhaustive, bounded neither by `maxDepth` nor by the engine's 1000-hop cap on explicit traversals, so a part chain of any depth comes back whole rather than truncated, and `maxDepth` / `cyclePolicy` bound only the `edges` traversal listed alongside it. It is delivered or refused, never partial within that coordinate: a part attached through a `population: "one"` edge whose validity window has ended is outside a current read although the delete cascade still takes it, so pass `temporalMode: "includeEnded"` to include it. It is an export, not a delete preview: under any one temporal mode it can name fewer or more parts than a delete removes, so preview a delete with `planDelete`. A closure statement the database cut short (a `statement_timeout`, a cancelled query) refuses with `ConfigurationError` (`COMPOSITION_UNIT_INDETERMINATE`) naming the root. `tx.subgraph()` accepts and honors `composition` the same way, reading through the transaction's session, so the transaction context's `subgraph` signature gains the same `C` type parameter as `store.subgraph()`. The batch-scoped `read.subgraph()` inside `batchOnce()` compiles to one statement and the composition closure is a second walk read in its own statement, so it refuses any requested `composition` with `ConfigurationError` (`SUBGRAPH_COMPOSITION_ONE_STATEMENT_UNSUPPORTED`) before the batch runs a statement. A `composition` value that is neither a boolean nor `{ via?: edge type or kind string }` is refused on every subgraph surface with `ValidationError` (issue path `composition`) instead of being treated as absent.

**A batch create whose items carry `partOf` does per-batch rather than per-item work**, with the same refusals: whole rows are read once per kind, a part row is never re-read after the insert that wrote it, and acyclicity is walked once over every composition edge the batch will insert, before the first of them is written — which is what makes a cycle running through two of the batch's own items visible at all. A cycle refusal names a concrete offending edge: the self-attaching item's own edge for a self-loop, otherwise the first of the batch's edges lying on the cycle.

**Import, the audit and graph merge all see composition.** Validating import tracks every required-existence part it creates and, once the payload's node and edge sets are both known, judges each of them through the same reader the `compositionExistence` audit uses: one attached in the same batch or already attached on the target is accepted, and anything left without a live whole is reported as a per-row error and its node row removed in the same transaction; the rest of the import commits. A created composition edge is not evidence on its own — an ended `oneActive` window, or a whole that does not exist (reachable with `validateReferences: false`), leaves the part refused. The check runs to a fixed point, so a required part attached only to a part this import refuses is refused with it, and the result counts track what was committed: a refused part and each edge removed with it come off every `created` and `updated` count this import had added them to, and every removed edge is reported as its own per-row error, including one that was already on the target (written ahead of the part under `validateReferences: false`). A part nothing can attach — no composition edge in the payload names it and the target holds no attachment for it — is refused before its row is written, so no other row is judged against it and the outcome does not depend on row order. A part a payload edge does name is written and judged afterwards: while its row exists a later row that collides with it is refused against it and is not judged again once the part is removed; re-run the import without the refused part to accept it. An `onConflict: "update"` whose `validTo` would end a live required part's open attachment is refused per row (`COMPOSITION_DETACH_REFUSED`), as the same edge update is through the store. Trusted import refuses every declared composition pair regardless of `existence` (`composition_unsupported`). Streamed import commits each chunk on its own, so a part and the edge attaching it arrive in separate transactions: `importGraphStream` refuses a graph declaring any required-existence part kind before reading a chunk, and `branch()`, `branchForEvolution()` and candidate staging clone such a graph through a single-transaction `importGraph` instead. The heterogeneous recorded upsert `tx.writeNodeUpsertBatch()` writes node rows only, so it refuses a required-existence part kind with `ConfigurationError` `HETEROGENEOUS_NODE_BATCH_UNSUPPORTED_KIND` before writing, rather than inserting a part with no whole or resurrecting one the composition cascade deleted. `store.verifyConstraintFences()` gains a `compositionExistence` family reporting any live required-existence part with no live whole, and a `composition` family reporting two or more live edges holding one part's reserved composition axis; a schema commit newly declaring `existence: "required"` on an already-populated pair runs a tightening preflight and refuses a dirty graph rather than silently admitting orphans. A commit that widens the composition relation's population — adding a pair, redeclaring a `oneActive` realizing edge `one`, or declaring `acyclic: true` on one, so its ended rows start to count — probes the whole proposed composition relation for a cycle, built by the same owner the write path uses; redeclaring a realizing edge so its ended rows count also audits every part those rows attach for a second whole, so a part with an ended row under one realizing edge and an open row under another refuses the commit instead of landing with two wholes. `planMerge` and `planMergeIncremental` report composition orphans in `MergePlanReview.compositionOrphans` under three causes: a part attached on the target to a whole the branch deletes, which the plan neither deletes nor moves to another whole (`cause: "deleted"`); the mirror, a part the plan deletes — directly, or through the branch's cascade from its old whole — that the target has meanwhile moved under another live whole the plan neither deletes nor detaches it from (`cause: "moved"`); and a required part this merge writes — or whose composition edge this merge explicitly deletes or ends — that resolves to no live whole at all (`cause: "unattached"`). All three are judged against the state the plan would leave: a part the plan deletes or moves to another whole is not a `deleted` orphan, and a required part the plan creates together with its composition edge is not an `unattached` one. A part the plan deletes is still reported as `moved` when the target holds it under a live whole the plan keeps. Two branches that conflict over one attachment — one moves or attaches a part, or re-attaches it by reopening an ended `oneActive` row, while another deletes the part or its whole — are refused at plan time by every planning entry point with `MergeCompositionOrphanError` (`cause: "moved"` or `"deleted"`), whose new optional `details.branchId` names the attaching branch; before, the attaching branch's composition edge was silently dropped as `edge:endpoint-deleted`, and a reopened row was absorbed by its deletion without a trace. `planMergeForEvolution()` judges them against the registry the evolution will commit. `applyMergePlan` re-checks `deleted` and `moved` inside the apply transaction under the per-graph write lock, asserts `unattached` for the plan's parts after its last edge in the same transaction, and refuses with `MergeCompositionOrphanError` (`GRAPH_MERGE_COMPOSITION_ORPHAN`), and merge apply deletes nodes with `cascadeComposition: false` so the plan stays the authority over what apply deletes. A branch's composition writes merge as a unit: apply postpones the per-write required-existence rule for the parts the plan touches and asserts it for those same parts after the plan's last edge, in the same transaction, so a required part created with `partOf` and a `reparent` under either cardinality merge like any other edit. A composition edge that already attached its part at the branch point and is dropped by canonicalization's endpoint-deleted repointing needs no write to be caught: the plan deletes one of its endpoints, and a deleted part leaves nothing to orphan while for a deleted whole the `deleted` check reports the surviving part at plan time and apply refuses it.

### Breaking

- `partOf` / `hasPart` require `via`, in a third options argument naming the realizing edge kind. A missing realizing edge, or a `via` or `partSide` on any other meta-edge, is refused at registry build and at schema load with `ConfigurationError` (`ONTOLOGY_COMPOSITION_VIA_REQUIRED`, `ONTOLOGY_COMPOSITION_VIA_FORBIDDEN`, `ONTOLOGY_COMPOSITION_PART_SIDE_FORBIDDEN`). A persisted schema carrying a `partOf` / `hasPart` relation with no `via` is refused wherever it would be loaded as a registry, and upgrades forward through the ordinary schema paths: after upgrading the library, give the graph's `partOf`/`hasPart` a `via` (or delete the relation) and open it with `createStoreWithSchema()` or commit it with `migrateSchema()`. `getSchemaChanges()` reports the change beforehand as the old relation removed (`safe`, since it realized nothing) plus, when a `via` is declared, the new pair added (`warning`, probed against live data like any new composition pair). A graph that still declares the relation without `via` is refused at registry build.
- Declarations the composition relation now refuses, which were previously accepted as an unconstrained part-whole closure: `"many"` or `"unique"` on the whole side (`ONTOLOGY_COMPOSITION_CARDINALITY`), an edge admitting an endpoint pair that is not a declared composition pair (`ONTOLOGY_COMPOSITION_VIA_ENDPOINTS`), one edge kind declared in two orientations (`ONTOLOGY_COMPOSITION_VIA_MIXED`), and mixed `one` / `oneActive` populations for one part kind (`ONTOLOGY_COMPOSITION_POPULATION_MIXED`).
- Deleting a node that is a composition whole now deletes its parts. Move any relation that re-homes or retains parts on delete off composition; the [containment tiers](https://typegraph.dev/ontology#choosing-a-containment-tier) section says where each case belongs.
- `NodeCollection` gains a third type parameter, the whole kinds its attachments accept (default `string`). Code that names `NodeCollection<N, CN>` for a graph's own collection (rather than reading it off `Store<G>`) no longer accepts `store.nodes.<Kind>` as that type: the whole kinds sit in contravariant option positions, so a collection that accepts any whole kind string is not assignable from one limited to the kinds the ontology declares. Pass `CompositionWholeKinds<G, K>` as the third argument. `StoreProjection` takes the same `CompositionWholeKinds<G, K>` per projected kind, so `partOf` and `reparent` stay callable on a projection; a store of another graph is assignable to it only when that graph's collection accepts at least those whole kinds.
- `NodeCollection` gains `reparent(id, options)`, `bulkReparent` and `planDelete(id)`, and its `delete` takes an optional second `NodeDeleteOptions` argument. A hand-written implementation of that interface must add all three methods and honor or refuse `delete`'s options.
- `exportGraph` / `exportGraphStream` now include `validFrom` / `validTo` by default for a graph with any edge kind whose `cardinality` or `targetCardinality` is `"oneActive"` (every `oneActive` composition pair included), as they already did for identity-enabled graphs, and refuse an explicit `includeTemporal: false` there with `ConfigurationError` (`ACTIVE_CARDINALITY_EXPORT_REQUIRES_TEMPORAL_FIELDS`, `details.edgeKinds`). Without its `validTo` an ended row re-imported as current — a reparented part attached to its former whole again. Drop `includeTemporal: false` from such exports; a consumer of the document sees the two extra fields on every row.
- `TransactionReceipt` gains a required `cascadedParts` field, always present and empty when the transaction deleted no composition whole; anything constructing a receipt literal must add it. `OperationHookContext` gains an optional `cascadedParts`. Both are typed `readonly CompositionCascadedPart[]`.
- `ConstraintFenceViolation` gains `composition` and `compositionExistence` members; an exhaustive `switch (violation.family)` outside the library needs an arm for each.
- `MERGE_PLAN_FORMAT_VERSION` is now `2`: `applyMergePlan` refuses a stored version-1 artifact with `UnsupportedMergePlanVersionError` (`GRAPH_MERGE_PLAN_VERSION_UNSUPPORTED`), so re-plan any artifact captured before the upgrade. The exported artifact types are renamed (`MergePlanArtifactV1` and `MergePlanArtifactV1Input` become `MergePlanArtifactV2` and `MergePlanArtifactV2Input`); the version-agnostic `MergePlanArtifact` alias is unchanged.
- `MERGE_REVIEW_FORMAT_VERSION` is now `3` and the candidate-scoped review format is `4` (`MERGE_REVIEW_FORMAT_VERSION_CANDIDATE_SCOPED`, for `reviewScope: "candidate"`), because a candidate-write-set review embeds a version-2 merge plan. `MERGE_REVIEW_FORMAT_VERSION_V1` and `MERGE_REVIEW_FORMAT_VERSION_V2`, exported by the latest released tag, are REMOVED; the supported formats are exactly `3` and `4`. A stored version-1 or version-2 review is refused: revalidating it refuses with `MergeReviewError` `details.reason: "unsupported-version"` (`details.supported` lists `[3, 4]`); plan and review the candidate write set again.
- An explicitly requested candidate review scope is refused on a graph that declares a target-side cardinality, an `acyclic` edge or a composition pair: `planCandidateWriteSetReview` with `reviewScope: "candidate"` refuses with `MergeReviewError` `details.reason: "candidate-scope-ineligible"` (as does revalidating a stored candidate-scoped review against a target that can no longer be read sparsely), because the sparse base such a review reads never sees the rows those constraints depend on. Planning itself is not refused unless it is called with `planningScope: "candidate"`: `planCandidateWriteSet`, and a review planned without `reviewScope`, fall back to whole-target planning on such a graph, produce the plan and conflicts a whole-target plan would, and report the reason in `planningScope`. The default whole-target review is unaffected.
