"@nicia-ai/typegraph": minor
---

**`partOf` and `hasPart` are now a real [composition](https://typegraph.dev/ontology#composition) relation**, realized by an edge kind that stores the containment. `partOf(part, whole, { via, partSide? })` and its mirror `hasPart(whole, part, { via, partSide? })` name that edge with `via`; orientation is inferred from the declared pair against the edge's endpoints, and when both orientations are admissible (a same-kind containment edge) the declaration names `partSide: "from" | "to"`. The realizing edge must declare its whole-side cardinality as `"one"` or `"oneActive"` (`cardinality` when the part is the edge's `from`, `targetCardinality` when the part is its `to`), must be composition-exact (every endpoint pair it admits is a declared composition pair), and every composition edge that can accept a given part kind must declare the same temporal population. `KindRegistry.compositionRelation()` returns the derived `CompositionRelation` — pairs, realizing edge kinds, and part side per pair — and `via` and `partSide` travel through every representation of an ontology relation (compile-time, named, serialized, extension document, introspection).

**`partOf` / `hasPart` gain `existence?: "optional" | "required"`** (default `"optional"`, so existing declarations keep their semantics): `"required"` says a part of that kind can never exist without a live whole, and `KindRegistry.compositionExistence(kind)` reports it. Two declarations disagreeing on `existence` for one part kind refuse at registry build with `ONTOLOGY_COMPOSITION_EXISTENCE_MIXED`. `existence` is emitted only when `"required"`, so an explicit `"optional"` serializes byte-identically to omitting it and an untouched graph's schema hash is unchanged.

**A part names the edge that realizes its attachment.** `NodeCollection.create`'s options are extracted into `NodeCreateOptions`, and `partOf` — on `create`, `bulkCreate`'s per-item options and both get-or-create entries — is a `CompositionAttachment`, `{ whole, via?, props?, validFrom?, validTo? }`, written in the same write as the node. `whole` is a node you already hold or a `{ kind, id }` reference, and only its `kind` and `id` are read, so a whole node's own properties never bleed into the attachment. On `store.nodes.<Kind>` its `kind` is limited at compile time to the whole kinds the ontology declares for that part kind through `partOf` / `hasPart` (the new `CompositionWholeKinds<G, K>`); when the ontology also declares a subclass or equivalence relation, or has lost its tuple type, any node kind of the graph is accepted and the runtime check decides. Any other top-level key on the attachment refuses with `ValidationError` (issue path `partOf.<key>`) rather than being dropped. The window is validated once for every surface (canonical bounds, ordered pair), and on a `population: "oneActive"` pair, where only an open-ended edge is a membership, a stated `validTo` refuses with `ValidationError` (code `COMPOSITION_ATTACHMENT_WINDOW_BOUNDED`) instead of writing an edge that attaches nothing. The write is atomic: a dead or missing whole, an undeclared pair, a cardinality or acyclicity refusal, or a lost composition claim aborts the node create too, leaving no orphan row. Every one of those refusals is reached before the node row is written — for `bulkCreate` before any row of the batch, including a cycle or a whole-side cardinality the batch's own items would close together — so a caller that catches one inside an enclosing `store.transaction(...)` keeps nothing of the refused create. An undeclared pair refuses with `ConfigurationError` (`COMPOSITION_WHOLE_NOT_DECLARED`). `via` names the realizing edge kind and is required only when the part kind declares more than one composition pair toward that whole kind: omitting it there refuses with `COMPOSITION_VIA_AMBIGUOUS`, and naming an edge kind that realizes no declared pair between the two refuses with `COMPOSITION_VIA_NOT_DECLARED`. `props` are the realizing edge's own properties, validated against that edge kind's schema exactly as `store.edges.<via>.create(...)` would, so a realizing edge with required schema fields is now attachable from a node create at all. A required-existence kind created with no `partOf` refuses with `CompositionExistenceError` (`COMPOSITION_WHOLE_REQUIRED`, `situation: "create"`) before any row is written, and so does restoring a soft-deleted one through an entry that takes no `partOf` (`upsertById`, `bulkUpsertById`, `bulkReplaceById`) unless it still holds a live whole; `partOf` is honored on an optional-existence pair too. A required-existence kind, or any input carrying `partOf`, always takes the portable, fully-validated write path.

**`partOf` on `getOrCreateByConstraint` is a POSTCONDITION, not a create-only option**: when the call returns, the resolved node holds exactly the stated attachment. The attachment is resolved before the match is read, so an undeclared whole kind, an unknown `via` and an ambiguous omitted `via` refuse with the same `ConfigurationError` whether the call created the node or found it. A node that already holds this whole through the resolved pair's realizing edge satisfies the call — idempotently when stated `props` are omitted, or valid and value-identical to the edge's live stored props; a valid but DIFFERENT `props` is refused (`CompositionExistenceError`, `situation: "props"`). A stated `validFrom` / `validTo` is held to the same rule: a bound equal to the edge's stored one is satisfied, a different one refuses with `ValidationError` (issue path `partOf.validFrom` / `partOf.validTo`, code `COMPOSITION_ATTACHMENT_WINDOW_CONFLICT`). A node with no live whole has the attachment written now, whatever its pair's declared `existence`, and a resurrection restores the whole alone. A node with a DIFFERENT live whole, or the same whole through another realizing edge, is refused (`situation: "existing"`) naming both sides. `bulkGetOrCreateByConstraint` behaves identically per item, and a matched item's refusal is reached before the batch creates any of its unmatched items. Two concurrent get-or-create calls naming DIFFERENT wholes for one part end with exactly one attachment and one `CompositionExistenceError`, never a silent move. When `ifExists: "update"` applies, the attachment and the property update commit together, so any refusal — including a unique or validation error from the update itself — leaves properties, ownership and history untouched, including inside an enclosing `store.transaction(...)`. An already-satisfied call with no update to make stays read-only and takes no write fence.

**A second whole is refused identically on every write path.** `CompositionError` with `details.incumbentEdgeId` is raised whether the claim row or the pre-write probe decides it: a batch, a custom command port that answers `unsupported`, an edge kind declaring both cardinality axes, and a backend that carries no claim relations all count the part's attachments across every realizing edge kind before writing, and report composition ahead of the edge kind's own `CardinalityError`. A backend without claim relations therefore still holds "one whole per part" across two different realizing edge kinds, under the per-graph lock.

**`nodes.<Kind>.reparent(id, options)` moves a part to a new whole**, which no sequence of detach and attach could express. `options` is `{ whole, via?, props?, at? }`: the destination attachment and the one instant the move happens at. It performs both halves in one transaction and validates the final state: one whole, acyclicity over the oriented composition union, and a required part never left detached. The part keeps its id, its properties and every descendant beneath it, and a refused move leaves it attached where it was, including inside an enclosing `store.transaction(...)`. How the old attachment retires follows the population declared by the incumbent row's own pair: a `population: "one"` edge is deleted, so the attachment disappears from every `store.asOf(t)` coordinate before the move, while a `population: "oneActive"` edge has its window ended at the move instant, leaving the previous membership readable as valid-time history. That instant — `options.at`, or one clock read when it is omitted — is both the old window's `validTo` and the new edge's `validFrom`, so for a `oneActive` pair the two halves abut: no `store.asOf(t)` coordinate shows the part with zero wholes, and none with two. `at` is the instant's only spelling: `reparent` takes no `validFrom`, and stating one is a compile error and a `ValidationError` at runtime. `validTo` is refused the same way: a move opens the new attachment, and bounding a membership is a window edit on the realizing edge. The call returns `{ edge, moved }`: `edge` is the holding realizing edge (the new one, or the incumbent on a no-op) and `moved` is false when the part already held that whole through the same realizing edge. A stated `props` is still checked on that no-op: value-identical to the live stored props the no-op stands, valid but different refuses (`situation: "props"`). `bulkReparent` runs the same operation for many parts in one transaction.

**Detaching a live required part is refused.** Ending, soft-deleting or hard-deleting a required-existence part's composition edge while the part is LIVE refuses with `CompositionExistenceError` (`COMPOSITION_DETACH_REFUSED`, `situation: "detach"`); detaching from a soft- or hard-deleted part is allowed. Deleting the *whole* still cascades to its required parts — `existence: "required"` governs bare creation and detachment, not whole deletion. `CompositionExistenceError.code` names the situation: `COMPOSITION_WHOLE_REQUIRED` (a bare create), `COMPOSITION_DETACH_REFUSED` (a refused detach), `COMPOSITION_WHOLE_CONFLICT` (a stated `partOf` contradicting the whole an existing node holds) and `COMPOSITION_PROPS_CONFLICT` (a stated `partOf.props` differing from the already-satisfied attachment's stored props). `details.situation` carries the same distinction and remains the discriminant for which optional detail fields are populated, so a handler may branch on either.

**Deleting a composition whole cascades leaf-first through its live parts closure**, each part running through its own node-delete pipeline inside the whole's transaction, with restrict and cascade `onDelete` behaviors on non-composition edges honored per part. Every part's verdict, and the whole's, is reached before the first row is deleted, so a `RestrictedDeleteError` from a part deep in the closure leaves the whole closure intact, including when the caller catches it inside an enclosing `store.transaction(...)`; `bulkDelete` reaches every item's verdict before deleting any of them. Composition edges never count as a `restrict` obstacle on either end. An instance-level cycle among reflexive composition edges is refused with `CompositionCycleError` (`COMPOSITION_CYCLE_DETECTED`) rather than looping or truncating. Resurrecting a soft-deleted whole restores the whole alone, ending a whole's validity window is not a cascade, and the cascade emits one operation-hook event, for the whole. See [Composition Cascade](https://typegraph.dev/limitations#composition-cascade). `NodeDeletePolicy` gains `consumedEdgeIds` (connected edges the cascade has already consumed, filtered out before the kind's `onDelete` behavior applies) and `cascadeComposition`.

**A whole's delete says which parts it took.** The delete's `onOperationEnd` hook context and `store.transactionWithReceipt`'s receipt both carry `cascadedParts`, `{ kind, id }` refs that never name a part the cascade did not delete, in the cascade's own delete order: leaf-first, then by kind, then id, within one level of the closure. That order is fully deterministic, so the same closure reports the same list on every run and every backend and a consumer may compare `cascadedParts` for equality. The receipt covers `bulkDelete` too, accumulating every item's cascade in batch order (a node an earlier item's cascade deleted is reported once, whichever order the batch names a part and its whole in), and the batch path still emits no per-item operation hooks. A `tx.measure(...)` scope's sub-receipt carries the refs for the deletes issued THROUGH that scope, so a delete issued through the outer transaction during an open scope stays out of it. `onOperationStart` never carries them, and the refs are not folded into the receipt's write counters: one caller-issued delete stays one write intent. There is no cascade preview API in this release; read the closure ahead of time with `store.subgraph(id, { edges: [], composition: true })`.

**`QueryBuilder` gains `parts()` and `wholes()`**, declared-structure sugar over the recursive `Traversal` AST for a declared composition relation. `parts("alias", { from?, maxHops?, depth?, path?, via? })` derives the edge kind(s) and direction(s) from the registry's composition relation and recurses to the full transitive closure by default, up to the 1000 levels a recursive traversal accepts rather than a bare `.recursive()`'s implicit 10; pass `maxHops: 1` for the direct level only. `via` narrows the walk to one realizing edge and to the kinds that edge alone reaches, so it works on a multi-level composition and on a whole with several realizing edges; a `via` that realizes no pair at the source alias itself refuses with `ConfigurationError` (`COMPOSITION_VIA_NOT_DECLARED`). `wholes()` is the mirror, returning the ancestor chain. Direction is derived per realizing edge kind: a `part -> whole` edge is followed reversed, a `whole -> part` (`has_*`) edge in its own direction, and a relation realized by both orientations across levels compiles to one traversal step. The result alias is untyped (`DynamicNodeType`/`DynamicEdgeType`, reached via `.field(name)`), since the closure under a kind may span several node kinds with different schemas. `parts()`/`wholes()` on a kind declaring no composition parts/wholes refuses with `ConfigurationError` (`COMPOSITION_NO_PARTS_DECLARED` / `COMPOSITION_NO_WHOLES_DECLARED`) rather than returning zero rows, and `expand` is not accepted on either step. `TraversalBuilder` gains `toKindSet(kinds, alias)`, a finalizer parallel to `to()`/`toDynamic()` for an explicit, already-resolved set of target node kinds.

A related defect is fixed: a recursive traversal combining `.recursive()` with a non-empty inverse edge-kind set (`{ expand: "inverse" }`, or the mixed-orientation case `parts()`/`wholes()` now exercise) emitted SQL that PostgreSQL rejected and SQLite accepted. Such traversals now compile and run on both dialects.

**`subgraph({ composition: true })` returns the complete owned unit.** `SubgraphOptions` gains `composition?: boolean | { via? }`, which closes the selected root over the composition edge kinds under its actual kind, in addition to whatever `edges` already lists; `{ via }` restricts the closure to one realizing edge kind (an edge type or its kind string) and refuses with `ConfigurationError` (`COMPOSITION_VIA_NOT_DECLARED`) when that edge realizes no composition pair under the root. A root kind declaring no composition parts contributes nothing and the read still runs; a graph declaring no composition relation at all refuses with `ConfigurationError` (`COMPOSITION_NO_PARTS_DECLARED`). Because which composition edge kinds join depends on the root's runtime kind, `composition: true` widens the result's edge-key type to the graph's whole edge-kind union (the new `SubgraphResultEdgeKinds`), so every key the traversal can put in `adjacency` / `reverseAdjacency` is reachable through the result type; `composition` absent or `false` keeps the existing `edges`-list typing unchanged. The `project.edges` keys a call may name widen with the result (`SubgraphProjectFor`), so a `composition: true` read can project the composition edges it receives; an edge kind outside `edges` is still refused without it. The closure is exhaustive, bounded neither by `maxDepth` nor by the engine's 1000-hop cap on explicit traversals, so a part chain of any depth comes back whole rather than truncated, and `maxDepth` / `cyclePolicy` bound only the `edges` traversal listed alongside it. It is delivered or refused, never partial: a closure statement the database cut short (a `statement_timeout`, a cancelled query) refuses with `ConfigurationError` (`COMPOSITION_UNIT_INDETERMINATE`) naming the root. `tx.subgraph()` accepts and honors `composition` the same way, reading through the transaction's session, so the transaction context's `subgraph` signature gains the same `C` type parameter as `store.subgraph()`. The batch-scoped `read.subgraph()` inside `batchOnce()` compiles to one statement and cannot resolve the root's kind first, so it refuses any requested `composition` with `ConfigurationError` (`SUBGRAPH_COMPOSITION_ONE_STATEMENT_UNSUPPORTED`) before the batch runs a statement. A `composition` value that is neither a boolean nor `{ via?: edge type or kind string }` is refused on every subgraph surface with `ValidationError` (issue path `composition`) instead of being treated as absent.

**A batch create whose items carry `partOf` does per-batch rather than per-item work**, with the same refusals: whole rows are read once per kind, a part row is never re-read after the insert that wrote it, and acyclicity is walked once over every composition edge the batch will insert, before the first of them is written — which is what makes a cycle running through two of the batch's own items visible at all. A cycle refusal names a concrete offending edge: the self-attaching item's own edge for a self-loop, otherwise the first of the batch's edges lying on the cycle.

**Import, the audit and graph merge all see composition.** Validating import tracks every required-existence part it creates and, once the payload's node and edge sets are both known, judges each of them through the same reader the `compositionExistence` audit uses: one attached in the same batch or already attached on the target is accepted, and anything left without a live whole is reported as a per-row error and its node row removed in the same transaction; the rest of the import commits. A created composition edge is not evidence on its own — an ended `oneActive` window, or a whole that does not exist (reachable with `validateReferences: false`), leaves the part refused. The check runs to a fixed point, so a required part attached only to a part this import refuses is refused with it, and the result counts track what was committed: each edge removed with a refused part comes off `edges.created` and is reported as its own per-row error. An `onConflict: "update"` whose `validTo` would end a live required part's open attachment is refused per row (`COMPOSITION_DETACH_REFUSED`), as the same edge update is through the store. Trusted import refuses every declared composition pair regardless of `existence` (`composition_unsupported`). Streamed import commits each chunk on its own, so a part and the edge attaching it arrive in separate transactions: `importGraphStream` refuses a graph declaring any required-existence part kind before reading a chunk, and `branch()`, `branchForEvolution()` and candidate staging clone such a graph through a single-transaction `importGraph` instead. The heterogeneous recorded upsert `tx.writeNodeUpsertBatch()` writes node rows only, so it refuses a required-existence part kind with `ConfigurationError` `HETEROGENEOUS_NODE_BATCH_UNSUPPORTED_KIND` before writing, rather than inserting a part with no whole or resurrecting one the composition cascade deleted. `store.verifyConstraintFences()` gains a `compositionExistence` family reporting any live required-existence part with no live whole, and a `composition` family reporting two or more live edges holding one part's reserved composition axis; a schema commit newly declaring `existence: "required"` on an already-populated pair runs a tightening preflight and refuses a dirty graph rather than silently admitting orphans. `planMerge` and `planMergeIncremental` report composition orphans in `MergePlanReview.compositionOrphans` under two causes: a part attached on the target to a whole the branch deletes (`cause: "deleted"`), and a required part this merge writes — or whose composition edge this merge explicitly deletes or ends — that resolves to no live whole at all (`cause: "unattached"`). `planMergeForEvolution()` judges both against the registry the evolution will commit. `applyMergePlan` re-verifies both inside the apply transaction and refuses with `MergeCompositionOrphanError` (`MERGE_COMPOSITION_ORPHAN`), and merge apply deletes nodes with `cascadeComposition: false` so the plan stays the authority over what apply deletes. One residual gap remains: a composition edge dropped by canonicalization's own endpoint-deleted repointing issues no write for any per-write guard to see, so run `store.verifyConstraintFences()` against a merged store to catch that case; see [Limitations](https://typegraph.dev/limitations#composition-existence-existence-required).

### Breaking

- `subgraph()`, `tx.subgraph()` and `batchOnce`'s `read.subgraph()` validate the `composition` option: a value that is neither a boolean nor `{ via?: edge type or kind string }`, which a JavaScript caller could previously pass and have ignored, is now refused with `ValidationError`. `read.subgraph()` inside `batchOnce()` also refuses a well-formed `composition` (`SUBGRAPH_COMPOSITION_ONE_STATEMENT_UNSUPPORTED`); read the composition unit with `store.subgraph()` or `tx.subgraph()` instead.
- `partOf` / `hasPart` require `via`, in a third options argument. A missing realizing edge, or a `via` or `partSide` on any other meta-edge, is refused at registry build and at schema load with `ConfigurationError` (`ONTOLOGY_COMPOSITION_VIA_REQUIRED`, `ONTOLOGY_COMPOSITION_VIA_FORBIDDEN`, `ONTOLOGY_COMPOSITION_PART_SIDE_FORBIDDEN`). A persisted schema carrying the old three-part relation fails on load; `getSchemaChanges` reports it before upgrade.
- Refused declarations: `"many"` or `"unique"` on the whole side (`ONTOLOGY_COMPOSITION_CARDINALITY`), an edge admitting an endpoint pair that is not a declared composition pair (`ONTOLOGY_COMPOSITION_VIA_ENDPOINTS`), one edge kind declared in two orientations (`ONTOLOGY_COMPOSITION_VIA_MIXED`), mixed `one` / `oneActive` populations for one part kind (`ONTOLOGY_COMPOSITION_POPULATION_MIXED`), different `existence` across the pairs that can hold one part kind or across a mirrored `partOf` / `hasPart` declaration of one pair, in either declaration order (`ONTOLOGY_COMPOSITION_EXISTENCE_MIXED`), an `existence` outside `"optional" | "required"` (`ONTOLOGY_COMPOSITION_EXISTENCE_INVALID`), a `partSide` outside `"from" | "to"` (`ONTOLOGY_COMPOSITION_PART_SIDE_INVALID`, also where the edge admits both orientations), and an option key `partOf` / `hasPart` do not know (`ONTOLOGY_COMPOSITION_OPTION_UNKNOWN`).
- Deleting a node that is a composition whole now deletes its parts. Move any relation that re-homes or retains parts on delete off composition; the [containment tiers](https://typegraph.dev/ontology#choosing-a-containment-tier) section says where each case belongs.
- `KindRegistry.getCompositionEdge(partKind, wholeKind)` is removed. Use `compositionPairsBetween(partKind, wholeKind)` (every declared pair, code-point ordered by realizing edge kind) or `compositionPairVia(partKind, wholeKind, viaEdgeKind)`.
- `NodeCollection` gains a third type parameter, the whole kinds its attachments accept (default `string`); `NodeCreateOptions`, `NodeGetOrCreateByConstraintOptions`, `NodeReparentOptions` and `CompositionAttachment` carry it as their trailing parameter. Code that names `NodeCollection<N, CN>` for a graph's own collection (rather than reading it off `Store<G>`) no longer accepts `store.nodes.<Kind>` as that type: the whole kinds sit in contravariant option positions, so a collection that accepts any whole kind string is not assignable from one limited to the kinds the ontology declares. Pass `CompositionWholeKinds<G, K>` as the third argument. `StoreProjection` takes the same `CompositionWholeKinds<G, K>` per projected kind, so `partOf` and `reparent` stay callable on a projection; a store of another graph is assignable to it only when that graph's collection accepts at least those whole kinds.
- `NodeCollection` gains `reparent(id, options) => Promise<NodeReparentResult>` and `bulkReparent`. A hand-written implementation of that interface must add both. `options.at` is the single move instant; omitting it reads the clock once. `NodeReparentOptions` has no `validFrom`.
- `getOrCreateByConstraint` / `bulkGetOrCreateByConstraint` no longer refuse every `partOf` stated against a `"found"` / `"updated"` result. Code that relied on the refusal as a "this node already existed" signal must check the returned `action` instead.
- `CompositionExistenceError.code` is per situation rather than `COMPOSITION_WHOLE_REQUIRED` for every shape. Code matching on `code === "COMPOSITION_WHOLE_REQUIRED"` to catch any composition-existence refusal must match the class, or all four codes.
- `CompositionExistenceErrorDetails` gains `currentVia`, `requestedWhole` and `requestedVia` (optional, `situation: "existing"` only; `requestedVia` carries the resolved realizing edge, so it is present even when the call omitted one), and `situation` gains `"props"` with `currentProps`/`requestedProps` (optional, that situation only). The `"existing"` message names both the held and the requested attachment.
- `TransactionReceipt` gains a required `cascadedParts` field, always present and empty when the transaction deleted no composition whole; anything constructing a receipt literal must add it.
- `OperationHookContext` gains an optional `cascadedParts`, and `StoreHooks`' runner signature gains a fourth, optional operation-facts argument; a hand-written hook runner needs the extra parameter.
- `CompositionPair` (internal to the registry, not part of the public entrypoint) gains a required `existence` field — anything constructing one directly, such as a test fixture, must add it.
- `ConstraintFenceViolation` gains `composition` and `compositionExistence` members; an exhaustive `switch (violation.family)` outside the library needs an arm for each.
- `MergePlanCompositionOrphan` gains a required `cause: "deleted" | "unattached"` field and its `whole` becomes optional, absent for `cause: "unattached"`; a consumer constructing or exhaustively matching this shape needs updating.
- `MERGE_PLAN_FORMAT_VERSION` is now `2`: `parseMergePlanArtifact` reports a stored version-1 artifact as `unsupported-version`, so re-plan any artifact captured before the upgrade. The artifact type and schema family are renamed (`MergePlanArtifactV2`, `MergePlanArtifactV2Input`, `mergePlanArtifactV2Schema`); the version-agnostic `MergePlanArtifact` alias is unchanged. `MergeCompositionOrphanErrorDetails` is removed in favor of `MergePlanCompositionOrphan`, which the error's `details` carries directly.
- `importGraphStream()` refuses a target graph that declares any `existence: "required"` part kind with `ConfigurationError` `IMPORT_STREAM_REQUIRED_COMPOSITION_UNSUPPORTED`, before reading any chunk or writing any row. Import such a graph with `importGraph()`.
- `MERGE_REVIEW_FORMAT_VERSION` is now `3` and the candidate-scoped review format is `4`, because a candidate-write-set review embeds a version-2 merge plan. `MERGE_REVIEW_FORMAT_VERSION_V1` and `MERGE_REVIEW_FORMAT_VERSION_V2` are removed: use `MERGE_REVIEW_FORMAT_VERSION` for the default whole-target format and the new `MERGE_REVIEW_FORMAT_VERSION_CANDIDATE_SCOPED` for the `reviewScope: "candidate"` format. Revalidating a stored format-1 or format-2 review refuses with `MergeReviewError` `details.reason: "unsupported-version"` (`details.supported` lists `[3, 4]`); plan and review the candidate write set again. Candidate-scoped planning and review are not offered on a graph that declares a target-side cardinality, an `acyclic` edge or a composition pair; such a graph plans against the whole target.
