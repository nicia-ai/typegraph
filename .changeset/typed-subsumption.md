"@nicia-ai/typegraph": minor

**`subClassOf` and `equivalentTo` now carry a structural contract, checked at compile time and again at registry build.** `subClassOf(child, parent)` becomes generic and requires that the child's schema output structurally extend the parent's — every property the parent requires, the child has with a compatible type, with the child free to add properties or narrow an optional-in-parent property. `equivalentTo` between two registered kinds checks the same contract in both directions, because equivalence is mutual subsumption. A failing pair is refused at compile time with a named `StructuralSubtypeMismatch` object naming the offending fields, and at registry build — live graphs, `evolve()`-authored extensions and deserialized documents alike — with a `ConfigurationError` under one of four codes (`ONTOLOGY_SUBCLASS_NOT_STRUCTURAL_SUBTYPE`, `ONTOLOGY_SUBCLASS_SCHEMA_INCOMPARABLE`, `ONTOLOGY_EQUIVALENCE_NOT_STRUCTURAL_SUBTYPE`, `ONTOLOGY_EQUIVALENCE_SCHEMA_INCOMPARABLE`) naming the child, the parent, whether the pair was declared or reached transitively, and the full violation list. `getSchemaChanges` reports the same refusal before an upgrade, including when a migration only edits a property schema on a kind already party to an existing hierarchy; `requiresMigration` collapses it to `true` by design, so call `getSchemaChanges` directly for the detail. The new `isTypeLevelSubtype` (on the `/schema` entrypoint) is the runtime prediction of the compile-time check, for tooling that wants to know in advance whether a pair will compile. Known gap: the registry check compares projected JSON Schema, so a node kind containing a Zod construct `z.toJSONSchema` cannot convert (`z.set()`, `z.map()`, and others) is skipped rather than guaranteed — avoid those constructs on a kind participating in `subClassOf`/`equivalentTo` for now.

**`equivalentTo` between two registered kinds means mutual subsumption**, and every reading of "same class" now agrees with it: `isAssignableTo`, `isSubClassOf`, `expandSubClasses`, `getSubClassComponent`, disjointness propagation, edge-endpoint admission, query expansion and uniqueness fencing. With `equivalentTo(Company, Corporation)`, `isAssignableTo("Corporation", "Company")` is true, a `Company` alias (`expansion: "subclasses"`, the default) returns `Corporation` rows, an edge declared `to: [Company]` accepts a `Corporation` endpoint, `search(..., { expansion: "subclasses" })` covers both kinds, and a `kindWithSubClasses` uniqueness constraint fences across the pair. Subsumption stays strict — a kind is never its own subclass, and `expandSubClasses` still lists each kind once. External IRIs stay out of subsumption: they are inert references, so `Person ≡ schema:Person ≡ Individual` folds `Person` and `Individual` together without making the IRI a kind. `reconcileTypes` now reads the store's own validated `KindRegistry`, so a merge and a query can no longer disagree about which kinds are the same class, and every kind-name ordering in that path is code-point order. `equivalentTo`'s left parameter widens to `NodeType | AnyEdgeType` so an edge kind can be mapped to an external IRI; an equivalence class that mixes node and edge kinds, or that contains more than one registered edge kind (reachable transitively through a shared IRI), is refused at registry build and at schema load with `ConfigurationError` code `ONTOLOGY_EQUIVALENCE_INVALID_CLASS`.

**`from()`/`to()`/`fromDynamic()`/`toDynamic()` are polymorphic by default**: a query against a supertype returns its subtype rows, typed with the parent's properties, and the alias's `kind` discriminant and `NodeId` brand widen to `string` only for a kind the ontology can actually affect. `queryDefaults.expansion: "exact"` on `createStore(...)` restores the previous exact-kind behavior everywhere in one place; `search()` and the collection APIs (`find`, `count`, `updateWhere`, `compareAndSet`) are unaffected and stay exact-kind.

**An alias states its expansion as one option**, `expansion: "exact" | "subclasses" | "narrower"` (default `"subclasses"`), on `from()`/`to()`/`fromDynamic()`/`toDynamic()`. `"narrower"` expands a kind through its `broader`/`narrower` kind-taxonomy relations instead of `subClassOf`, and types the alias untyped since no schema relationship is claimed. An alias cannot state two axes at once; a value outside the three is refused (`QUERY_ALIAS_EXPANSION_INVALID`), as is a narrower expansion naming an unregistered kind or, on `to()`/`toDynamic()`, a kind the traversed edge does not admit as an endpoint (`ONTOLOGY_NARROWER_KIND_NOT_REGISTERED` / `ONTOLOGY_NARROWER_ENDPOINT_NOT_ADMITTED`). Omitting the options argument, passing `{}` and passing an explicit `undefined` all mean "take the store default", so an options bag forwards through a caller's own helper without special-casing the empty case; `queryDefaults.expansion` and `createQueryBuilder`'s `defaultExpansion` accept a stated `undefined` too. A bag that can carry an axis the call site does not pin, such as `{ expansion?: "exact" }`, forwards as well and types its alias untyped, as `"narrower"` does. `store.search()` spells the same axis under the same name (`expansion: "exact" | "subclasses"`, default `"exact"`; the search facade is not polymorphic by default).

**Every meta-edge factory now returns a relation typed with its meta-edge name literal and its endpoint kinds**, not only `subClassOf`/`equivalentTo`, the IRI overload (`equivalentTo(Kind, iri)`, typed `from: Kind, to: string`) included. A kind whose only equivalence is IRI-routed therefore widens its alias like any other equivalenced kind, and a graph mixing `subClassOf` with `broader` / `inverseOf` / `disjointWith` keeps exact alias types for the kinds no subsumption relation names. The flip side: a relation annotated as the bare `OntologyRelation` widens every alias in that graph conservatively. An endpoint declared as a union of node types keeps its literals and stays precise, widening exactly the kinds the union can hold and nothing else.

### Breaking

- **`subClassOf`/`equivalentTo` are now generic and carry a structural contract**, which a callers-bypassing path cannot skip: an extension's raw `{ metaEdge: "subClassOf", from, to }` relation and a persisted document are both refused at registry build. Run `getSchemaChanges(backend, graph)` before upgrading a populated deployment: an incompatible hierarchy surfaces there as a `ConfigurationError` naming the child, the parent and the offending property path. No data migration is required; every refusal is a schema-authoring fix.
- **Supertype queries now return subtype rows**, and rows of kinds declared `equivalentTo` the queried kind rather than only its `subClassOf` descendants. To keep the previous behavior everywhere, pass `createStore(graph, backend, { queryDefaults: { expansion: "exact" } })`; per call site, pass `{ expansion: "exact" }`. Omitting the option no longer stops expansion. If an `equivalentTo` pair was never meant to be substitutable, drop the declaration.
- **The `includeSubClasses` / `includeNarrower` booleans are replaced by one `expansion` option** on `from()`/`to()`/`fromDynamic()`/`toDynamic()`: `{ includeSubClasses: false }` becomes `{ expansion: "exact" }`, `{ includeSubClasses: true }` becomes `{ expansion: "subclasses" }`, `{ includeNarrower: true }` becomes `{ expansion: "narrower" }`. `createStore(..., { queryDefaults: { includeSubClasses } })` becomes `queryDefaults: { expansion }`, `createQueryBuilder`'s `defaultIncludeSubClasses` becomes `defaultExpansion`, and `store.search()`'s `includeSubClasses: true` becomes `expansion: "subclasses"`. `QUERY_ALIAS_EXPANSION_CONFLICT` is removed with the contradiction it described; `QUERY_ALIAS_EXPANSION_INVALID` replaces it for an out-of-domain value.
- **`QueryAst`'s `start.includeSubClasses: boolean` becomes `start.expansion: "exact" | "subclasses" | "narrower"`.** This affects only code inspecting a compiled AST directly.
- **Alias types widen under the polymorphic axis.** For a kind that some other kind declares itself a subclass of, or that participates in a registered-kind `equivalentTo`, the alias's `kind` is `string` and its `NodeId` brand widens. A relation endpoint declared as a UNION of kinds, spelled `typeof Audio | typeof Video` or `NodeType<"Audio" | "Video">`, widens every kind the union can hold. A graph declaring no subsumption relations is unaffected.
- **Annotating a relation as `OntologyRelation` widens every alias in that graph.** Such code still compiles, but its aliases' `kind` and `NodeId` types widen to the polymorphic form — let the factory's return type be inferred to keep the narrow types.
- **`equivalentTo(nodeKind, edgeKind)` no longer compiles**, and `equivalentTo`'s first parameter is now `NodeType | AnyEdgeType`. The overload set accepts `(NodeType, NodeType)`, `(NodeType | AnyEdgeType, string)` (the IRI form) and `(AnyEdgeType, NodeType)`. An equivalence class mixing node and edge kinds, or holding two registered edge kinds, is refused where it previously loaded inert; a persisted schema carrying one fails on load with `ONTOLOGY_EQUIVALENCE_INVALID_CLASS`, so correct the stored document before upgrading.
- **Edge endpoints, `implies` and `inverseOf` endpoint validation, and `importGraph`'s endpoint check all accept equivalent kinds.** Some declarations previously refused at registry build now construct.
- **A `kindWithSubClasses` uniqueness constraint spans the equivalence class**, so a value that was unique per kind before can now collide. The claim axis moves to the code-point minimum of the widened component, and **no data migration is required**: rows written under the previous axis are still found and still fence.
- **The serialized schema's precomputed `ontology.closures` change for any graph declaring `equivalentTo` between registered kinds**, and with them the schema hash. It resolves as a semantic no-op on both boot paths: the relations are unchanged, the schema diff reports no changes, and the store reports `status: "unchanged"`.
- If an existing `subClassOf` was modelling a taxonomy rather than a genuine subtype relationship, replace it with `broader(narrowerKind, broaderKind)` and query with `{ expansion: "narrower" }`; for a vocabulary that grows at runtime, prefer an instance-level concept kind with a `broader` edge traversed with `.recursive()`.
