`subClassOf` and `equivalentTo` (and the deprecated `sameAs` alias) now carry a structural contract, checked twice: at compile time, and at registry build for whatever the type checker cannot see. `subClassOf(child, parent)` becomes generic and requires that the child's schema output structurally extend the parent's — every property the parent requires, the child has with a compatible type, with the child free to add properties or narrow an optional-in-parent property. `equivalentTo`/`sameAs` between two registered kinds check the same contract in both directions (D1's mutual-subsumption reading). A pair that fails is refused at compile time with a named `StructuralSubtypeMismatch` object naming the offending fields, and at registry build (live graphs, `evolve()`-authored extensions, and deserialized documents alike) with a `ConfigurationError` under one of four codes (`ONTOLOGY_SUBCLASS_NOT_STRUCTURAL_SUBTYPE`, `ONTOLOGY_SUBCLASS_SCHEMA_INCOMPARABLE`, `ONTOLOGY_EQUIVALENCE_NOT_STRUCTURAL_SUBTYPE`, `ONTOLOGY_EQUIVALENCE_SCHEMA_INCOMPARABLE`) naming the child, the parent, whether the pair was declared or reached transitively, and the full violation list. `getSchemaChanges`/`requiresMigration` report the same refusal before an upgrade, including when a migration only edits a property schema on a kind already party to an existing hierarchy. The new `isTypeLevelSubtype` (on the `/schema` entrypoint) is the runtime prediction of the compile-time check, useful for tooling that wants to know in advance whether a pair will compile.

Now that the structural contract holds, `from()`/`to()`/`fromDynamic()`/`toDynamic()` default to `includeSubClasses: true`: a query against a supertype returns its subtype rows, typed with the parent's properties (the alias's `kind` discriminant and `NodeId` brand widen to `string` only for a kind the ontology can actually affect). `queryDefaults.includeSubClasses` on `createStore(...)` restores the previous exact-kind behavior everywhere in one place; `search()` and the collection APIs (`find`, `count`, `updateWhere`, `compareAndSet`) are unaffected and stay exact-kind.

`from()`/`to()`/`fromDynamic()`/`toDynamic()` also accept `includeNarrower: true`, expanding a kind through its `broader`/`narrower` kind-taxonomy relations instead of `subClassOf` — the alias type is untyped, since no schema relationship is claimed. `includeSubClasses` and `includeNarrower` are mutually exclusive on one alias, refused (`QUERY_ALIAS_EXPANSION_CONFLICT`) rather than silently unioned; an `includeNarrower` expansion naming an unregistered kind or, on `to()`/`toDynamic()`, a kind the traversed edge does not admit as an endpoint is refused too (`ONTOLOGY_NARROWER_KIND_NOT_REGISTERED` / `ONTOLOGY_NARROWER_ENDPOINT_NOT_ADMITTED`).

## Breaking changes

- **`subClassOf`/`equivalentTo`/`sameAs` are now generic and carry a structural contract.** Code that annotates a relation's result as `OntologyRelation` still compiles unchanged; code declaring a pair whose child does not structurally extend the parent no longer compiles, and the identical pair is refused at registry build even for callers that bypass the compile-time check (an extension's raw `{ metaEdge: "subClassOf", from, to }` relation, or a persisted document).
- **Supertype queries now return subtype rows.** `from()`/`to()`/`fromDynamic()`/`toDynamic()` default to `includeSubClasses: true`. `search()` and the collection APIs are unchanged and stay exact-kind.
- **Alias types widen under the polymorphic axis.** For a kind that some other kind declares itself a subclass of, or that participates in a registered-kind `equivalentTo`/`sameAs`, the alias's `kind` is `string` and its `NodeId` brand widens, because the row may be a subtype. A graph that declares no subsumption relations is unaffected.
- **`QueryAst`'s `start.includeSubClasses: boolean` becomes `start.expansion: "exact" | "subClasses" | "narrower"`**, so a `narrower`-expanded alias is describable. Only affects code inspecting a compiled AST directly.

## Upgrade notes

- To keep the previous query behavior everywhere, pass `createStore(graph, backend, { queryDefaults: { includeSubClasses: false } })`. Per call site, pass `{ includeSubClasses: false }` to narrow one alias instead.
- If an existing `subClassOf` was modelling a taxonomy rather than a genuine subtype relationship, replace it with `broader(narrowerKind, broaderKind)` and query with `{ includeNarrower: true }`; for a vocabulary that grows at runtime, prefer an instance-level concept kind with an `acyclic` `broader` edge traversed with `.recursive()`.
- Run `getSchemaChanges(backend, graph)` (or `requiresMigration`) before upgrading a populated deployment: an incompatible hierarchy surfaces there as a `ConfigurationError` naming the child, the parent, and the offending property path, before any commit reaches it. No data migration is required — every refusal is a schema-authoring fix.
