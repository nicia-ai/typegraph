`subClassOf` and `equivalentTo` now carry a structural contract, checked twice: at compile time, and at registry build for whatever the type checker cannot see. `subClassOf(child, parent)` becomes generic and requires that the child's schema output structurally extend the parent's — every property the parent requires, the child has with a compatible type, with the child free to add properties or narrow an optional-in-parent property. `equivalentTo` between two registered kinds checks the same contract in both directions (D1's mutual-subsumption reading). A pair that fails is refused at compile time with a named `StructuralSubtypeMismatch` object naming the offending fields, and at registry build (live graphs, `evolve()`-authored extensions, and deserialized documents alike) with a `ConfigurationError` under one of four codes (`ONTOLOGY_SUBCLASS_NOT_STRUCTURAL_SUBTYPE`, `ONTOLOGY_SUBCLASS_SCHEMA_INCOMPARABLE`, `ONTOLOGY_EQUIVALENCE_NOT_STRUCTURAL_SUBTYPE`, `ONTOLOGY_EQUIVALENCE_SCHEMA_INCOMPARABLE`) naming the child, the parent, whether the pair was declared or reached transitively, and the full violation list. `getSchemaChanges` reports the same refusal before an upgrade, including when a migration only edits a property schema on a kind already party to an existing hierarchy — `requiresMigration` collapses it to `true` by design (least-privilege routing) rather than surfacing it; call `getSchemaChanges` directly for the detail. The new `isTypeLevelSubtype` (on the `/schema` entrypoint) is the runtime prediction of the compile-time check, useful for tooling that wants to know in advance whether a pair will compile. Known gap: the registry check compares projected JSON Schema, so a node kind containing a Zod construct `z.toJSONSchema` cannot convert (`z.set()`, `z.map()`, and others) is skipped rather than guaranteed — avoid those constructs on a kind that participates in `subClassOf`/`equivalentTo` for now.

Now that the structural contract holds, `from()`/`to()`/`fromDynamic()`/`toDynamic()` default to `includeSubClasses: true`: a query against a supertype returns its subtype rows, typed with the parent's properties (the alias's `kind` discriminant and `NodeId` brand widen to `string` only for a kind the ontology can actually affect). `queryDefaults.includeSubClasses` on `createStore(...)` restores the previous exact-kind behavior everywhere in one place; `search()` and the collection APIs (`find`, `count`, `updateWhere`, `compareAndSet`) are unaffected and stay exact-kind.

`from()`/`to()`/`fromDynamic()`/`toDynamic()` also accept `includeNarrower: true`, expanding a kind through its `broader`/`narrower` kind-taxonomy relations instead of `subClassOf` — the alias type is untyped, since no schema relationship is claimed. `includeSubClasses` and `includeNarrower` are mutually exclusive on one alias, refused (`QUERY_ALIAS_EXPANSION_CONFLICT`) rather than silently unioned; an `includeNarrower` expansion naming an unregistered kind or, on `to()`/`toDynamic()`, a kind the traversed edge does not admit as an endpoint is refused too (`ONTOLOGY_NARROWER_KIND_NOT_REGISTERED` / `ONTOLOGY_NARROWER_ENDPOINT_NOT_ADMITTED`).

Every meta-edge factory — not only `subClassOf`/`equivalentTo` — now returns a relation typed with its meta-edge name literal and its endpoint kinds, the IRI overload (`equivalentTo(Kind, iri)`, typed `from: Kind, to: string`) included. A kind whose only equivalence is IRI-routed therefore widens its alias like any other equivalenced kind, and a graph whose ontology mixes `subClassOf` with `broader` / `inverseOf` / `disjointWith` keeps exact alias types for the kinds no subsumption relation names. The flip side: a relation a caller annotates as the bare `OntologyRelation` has lost the literals the alias computation reads, so it now widens EVERY alias in that graph conservatively rather than reporting an affected kind as unaffected.

## Breaking changes

- **Annotating a relation as `OntologyRelation` widens every alias in that graph.** Such code still compiles unchanged, but its aliases' `kind` and `NodeId` types widen to the polymorphic form — let the factory's return type be inferred to keep the narrow types.
- **`subClassOf`/`equivalentTo` are now generic and carry a structural contract.** Code that annotates a relation's result as `OntologyRelation` still compiles unchanged; code declaring a pair whose child does not structurally extend the parent no longer compiles, and the identical pair is refused at registry build even for callers that bypass the compile-time check (an extension's raw `{ metaEdge: "subClassOf", from, to }` relation, or a persisted document).
- **Supertype queries now return subtype rows.** `from()`/`to()`/`fromDynamic()`/`toDynamic()` default to `includeSubClasses: true`. `search()` and the collection APIs are unchanged and stay exact-kind.
- **Alias types widen under the polymorphic axis.** For a kind that some other kind declares itself a subclass of, or that participates in a registered-kind `equivalentTo`, the alias's `kind` is `string` and its `NodeId` brand widens, because the row may be a subtype. A graph that declares no subsumption relations is unaffected.
- **`QueryAst`'s `start.includeSubClasses: boolean` becomes `start.expansion: "exact" | "subClasses" | "narrower"`**, so a `narrower`-expanded alias is describable. Only affects code inspecting a compiled AST directly.
- **`equivalentTo(nodeKind, edgeKind)` no longer compiles.** The new overload set accepts `(NodeType, NodeType)`, `(NodeType | AnyEdgeType, string)` (the IRI form), and `(AnyEdgeType, NodeType)`, but not a node kind followed by an edge kind — this pairing has always been refused at registry build (`ONTOLOGY_EQUIVALENCE_INVALID_CLASS`) and is now also refused at compile time.

## Upgrade notes

- To keep the previous query behavior everywhere, pass `createStore(graph, backend, { queryDefaults: { includeSubClasses: false } })`. Per call site, pass `{ includeSubClasses: false }` to narrow one alias instead.
- If an existing `subClassOf` was modelling a taxonomy rather than a genuine subtype relationship, replace it with `broader(narrowerKind, broaderKind)` and query with `{ includeNarrower: true }`; for a vocabulary that grows at runtime, prefer an instance-level concept kind with a `broader` edge traversed with `.recursive()`.
- Run `getSchemaChanges(backend, graph)` before upgrading a populated deployment: an incompatible hierarchy surfaces there as a `ConfigurationError` naming the child, the parent, and the offending property path, before any commit reaches it. `requiresMigration` collapses this refusal to `true` by design and does not surface the detail — use `getSchemaChanges` directly. No data migration is required — every refusal is a schema-authoring fix.
