---
"@nicia-ai/typegraph": minor
---

**`subClassOf` and `equivalentTo` now carry a structural contract, checked at compile time and again at registry build.** `subClassOf(child, parent)` becomes generic and requires that the child's schema output structurally extend the parent's — every property the parent requires, the child has with a compatible type, with the child free to add properties or narrow an optional-in-parent property. `equivalentTo` between two registered kinds checks the same contract in both directions, because equivalence is mutual subsumption. A failing pair is refused at compile time with a named `StructuralSubtypeMismatch` object naming the offending fields, and at registry build — live graphs, `evolve()`-authored extensions and deserialized documents alike — with a `ConfigurationError` under one of four codes (`ONTOLOGY_SUBCLASS_NOT_STRUCTURAL_SUBTYPE`, `ONTOLOGY_SUBCLASS_SCHEMA_INCOMPARABLE`, `ONTOLOGY_EQUIVALENCE_NOT_STRUCTURAL_SUBTYPE`, `ONTOLOGY_EQUIVALENCE_SCHEMA_INCOMPARABLE`) naming the child, the parent, whether the pair was declared or reached transitively, and the full violation list. `getSchemaChanges` reports the same refusal before an upgrade whenever the graph declares such a relation — including when nothing changed at all, which is the case of a hierarchy an earlier release accepted, and when a migration only edits a property schema on a kind already party to an existing hierarchy; `requiresMigration` collapses it to `true` by design, so call `getSchemaChanges` directly for the detail. The new `isTypeLevelSubtype` (on the `/schema` entrypoint) is the runtime prediction of the compile-time check, for tooling that wants to know in advance whether a pair will compile. The registry check compares projected JSON Schema, so a field holding a Zod construct `z.toJSONSchema` cannot convert (`z.set()`, `z.map()`, `z.date()`, `z.bigint()`, a `.transform()`, or a `z.custom()` such as `embedding()`) is accepted without a value-level comparison, on either side, while every other field of the pair is still compared: a subclass that adds an `embedding()` opens, and one that also loosens a parent's `z.string().min(5)` is refused. This per-field comparison needs Zod 4.5 or later; with an older Zod, a pair with such a field on either side is skipped. A field Zod converts only in part, such as a `.catch()` with a dynamic fallback, keeps the type it states and is comparable only to the same schema. A deserialized document has no Zod schemas and stores such a kind without a property projection, so its own registry check skips a pair with that kind on either side; every commit, `createStore`, `getSchemaChanges` and `requiresMigration` also check the code graph.

**`equivalentTo` between two registered kinds means mutual subsumption**, and every reading of "same class" now agrees with it: `isAssignableTo`, `isSubClassOf`, `expandSubClasses`, `getSubClassComponent`, disjointness propagation, edge-endpoint admission, query expansion and uniqueness fencing. With `equivalentTo(Company, Corporation)`, `isAssignableTo("Corporation", "Company")` is true, a `Company` alias (`expansion: "subclasses"`, the default) returns `Corporation` rows, an edge declared `to: [Company]` accepts a `Corporation` endpoint, `search(..., { expansion: "subclasses" })` covers both kinds, and a `kindWithSubClasses` uniqueness constraint fences across the pair. Subsumption stays strict — a kind is never its own subclass, and `expandSubClasses` still lists each kind once. External IRIs stay out of subsumption: they are inert references, so `Person ≡ schema:Person ≡ Individual` folds `Person` and `Individual` together without making the IRI a kind. `reconcileTypes` now reads the store's own validated `KindRegistry`, so a merge and a query can no longer disagree about which kinds are the same class, and every kind-name ordering in that path is code-point order. `equivalentTo`'s left parameter widens to `NodeType | AnyEdgeType` so an edge kind can be mapped to an external IRI; an equivalence class that mixes node and edge kinds, or that contains more than one registered edge kind (reachable transitively through a shared IRI), is refused at registry build and at schema load with `ConfigurationError` code `ONTOLOGY_EQUIVALENCE_INVALID_CLASS`.

**`from()`/`to()`/`fromDynamic()`/`toDynamic()` are polymorphic by default**: a query against a supertype returns its subtype rows, typed with the parent's properties, and the alias's `kind` discriminant and `NodeId` brand widen to `string` only for a kind the ontology can actually affect. `queryDefaults.expansion: "exact"` on `createStore(...)` restores the previous exact-kind runtime behavior everywhere in one place (it does not restore the narrow alias types, see Breaking); `search()`, the collection APIs (`find`, `count`, `updateWhere`, `compareAndSet`) and `subgraph({ includeKinds })` are unaffected and stay exact-kind. A parent-kind alias reads each property as the parent declares it: a subclass that omits a parent-optional property, or narrows its type, leaves that property usable in `select()` (decoded as the parent's type on every backend), `whereNode()`, `orderBy()` and `groupBy()`, and `$fulltext.matches()` is available whenever the parent kind declares a `searchable()` field and every subclass either omits it or declares it `searchable()` too. A subclass that redeclares a parent's `searchable()` or `embedding()` field untagged (a legal subtype, since neither annotation is a structural constraint) would leave its rows out of the parent-typed accessor's index, so `$fulltext.matches()` refuses and names the kind, and the embedding accessor is refused as a field the kinds do not agree on. An explicit kind list, `from([...], alias, options?)`, takes the same `expansion` option and the same store default: each listed kind expands as `from(kind)` would, the union is deduplicated, and the alias types each listed kind as a single-kind alias over it would be. Because the alias type is computed from the compile-time graph, a subclass that only a persisted extension declares (added through `store.evolve()`, or folded back in by `createStoreWithSchema` on a later boot) cannot be typed: when an alias states no `expansion`, its kind is exact in the compile-time graph, and the live schema would expand it to further kinds, `from()`/`to()` refuse with `ConfigurationError` (`QUERY_ALIAS_EXPANSION_UNTYPED_SUBCLASSES`, naming the kind and the extra kinds) instead of returning rows whose `kind` and `NodeId` contradict their type. A list source is refused only for an extra kind no member of its type admits: a kind the list names is typed exactly by the list, as is a kind in the expansion of a listed kind the compile-time graph already types polymorphically. State `{ expansion: "subclasses" }` (typed polymorphically) or `{ expansion: "exact" }` on the query, or use `fromDynamic()`/`toDynamic()`. `store.search()` is not refused: its `expansion: "subclasses"` hit is typed polymorphically whatever the compile-time graph declares. The refusal is decided from the graph's ontology values at run time, which cannot show the type a store was declared with, so it also fires for a store typed over a widened graph type (`Store<GraphDef>`) or an ontology whose literals an `OntologyRelation` annotation erased, although such a store already types the alias polymorphically; such code states `expansion` or uses `fromDynamic()`. An `updateWhere({ candidates })` query is an ordinary query and follows the default, and a candidate query must resolve to exactly one kind: over a kind with subclasses or `equivalentTo` kinds it is refused with `ConfigurationError` (`SET_UPDATE_CANDIDATE_MULTIPLE_KINDS_UNSUPPORTED`) unless it passes `{ expansion: "exact" }`.

**An alias states its expansion as one option**, `expansion: "exact" | "subclasses" | "narrower"` (default `"subclasses"`), on `from()`/`to()`/`fromDynamic()`/`toDynamic()`. `"narrower"` expands a kind through its `broader`/`narrower` kind-taxonomy relations instead of `subClassOf`, and types the alias untyped since no schema relationship is claimed. An alias cannot state two axes at once; a value outside the three is refused (`QUERY_ALIAS_EXPANSION_INVALID`), as is a narrower expansion naming an unregistered kind or, on `to()`/`toDynamic()`, a kind the traversed edge does not admit as an endpoint (`ONTOLOGY_NARROWER_KIND_NOT_REGISTERED` / `ONTOLOGY_NARROWER_ENDPOINT_NOT_ADMITTED`). Endpoint admission is read from the edge's registration, so it holds whether the endpoints are declared on the edge type or on the graph's `{ type, from, to }` entry; `toDynamic()` refuses a target kind such a registration does not admit with `EndpointError` the same way. Omitting the options argument, passing `{}` and passing an explicit `undefined` all mean "take the store default", so an options bag forwards through a caller's own helper without special-casing the empty case; `queryDefaults.expansion` and `createQueryBuilder`'s `defaultExpansion` accept a stated `undefined` too. Any other default outside `"exact"` / `"subclasses"`, `"narrower"` included, is refused with `QUERY_ALIAS_EXPANSION_INVALID` when the store or builder is constructed rather than at the first alias that falls back to it. A bag that can carry an axis the call site does not pin, such as `{ expansion?: "exact" }`, forwards as well and types its alias untyped, as `"narrower"` does. `store.search()` spells the same axis under the same name (`expansion: "exact" | "subclasses"`, default `"exact"`; the search facade is not polymorphic by default). A search hit is typed by the axis it states, as the `from()` alias stating that axis is: `store.search.fulltext` / `vector` / `hybrid` with `expansion: "subclasses"` returns hits whose `node` keeps the searched kind's properties while its `kind` and `NodeId` brand widen, since the row may be a subclass or an equivalent kind, including one only a persisted extension declares; `"exact"` or an omitted option keeps the exact type, and an `expansion` value that is not a literal at the call site types the hit in the widened form. Spelling the kind generic by hand, `store.search.fulltext<"Doc">(...)`, takes the exact overload, or the widened one when the call states an `expansion`. An options value typed by the library's own `FulltextSearchOptions` / `VectorSearchOptions` / `HybridSearchOptions`, whose `expansion` is optional and either axis, forwards through a caller's wrapper unchanged and types the hit in the widened form. A search that would silently miss rows the index cannot reach is refused with `ConfigurationError` (`SEARCH_EXPANSION_KIND_UNINDEXED`, naming the kinds) instead of under-returning, exactly where `$fulltext.matches()` and the embedding accessor refuse the same alias: a fulltext search of any kind list, exact included, in which a kind has no `searchable()` field or redeclares it untagged, and a vector expansion in which a subclass declares the `embedding()` field with a tag that differs from the subsuming kind's declaration. An exact `store.search.fulltext()` (or hybrid fulltext leg) over a kind that declares no `searchable()` field therefore refuses where it returned `[]`. A subclass that merely omits the field holds no content there and is skipped.

**Every meta-edge factory now returns a relation typed with its meta-edge name literal and its endpoint kinds**, not only `subClassOf`/`equivalentTo`, the IRI overload (`equivalentTo(Kind, iri)`, typed `from: Kind, to: string`) included. A kind whose only equivalence is IRI-routed therefore widens its alias like any other equivalenced kind, and a graph mixing `subClassOf` with `broader` / `inverseOf` / `disjointWith` keeps exact alias types for the kinds no subsumption relation names. The flip side: a relation annotated as the bare `OntologyRelation` widens every alias in that graph conservatively. An endpoint declared as a union of node types keeps its literals and stays precise, widening exactly the kinds the union can hold and nothing else. Typed edge collections (`store.edges.<kind>`, the view and recorded-time collections, `bulkFindEdgesFrom`/`bulkFindEdgesTo` and the edges `neighbors()` returns) type each declared endpoint through the same alias typing (`SubsumedNodeType`): an endpoint kind the ontology can affect reads back with a `string` kind and a widened `NodeId` brand, and endpoint arguments accept a node or `{ kind, id }` of any kind assignable to the declared one (`AssignableNodeKinds`, transitive over `subClassOf` and `equivalentTo`) and a polymorphic query row or widened endpoint reference (`{ kind: edge.toKind, id: edge.toId }`), so a subclass row from a supertype query connects without a cast. `bulkFindEdgesFrom`/`bulkFindEdgesTo` sources and targets and the `neighbors()`/`countNeighbors()` source accept the same widened reference, so an endpoint read off one edge feeds the next hop as it is; each result bucket's `source` / `target` echoes that reference back and is typed as the same widened input (`GraphNodeReferenceInput`), so on an affected graph its `kind` reads as `string`. The widened arm is structural: a node or reference of an unrelated kind whose properties include the declared kind's also compiles, and the runtime refuses it (`EndpointError` on an edge write, `KindNotFoundError` for an unregistered kind). The new `store.getNodeByRef({ kind, id })` (also on transactions and views) reads the node a reference names through that kind's collection, typed as the kind's node for a literal kind and as the kind-discriminated union of the graph's node types plus the base `Node` for a `string` kind; it returns `undefined` for a missing node and rejects with `KindNotFoundError` for an unregistered kind.

### Breaking

- **`subClassOf`/`equivalentTo` are now generic and carry a structural contract**, which a callers-bypassing path cannot skip: an extension's raw `{ metaEdge: "subClassOf", from, to }` relation and a persisted document are both refused at registry build. Run `getSchemaChanges(backend, graph)` before upgrading a populated deployment: an incompatible hierarchy surfaces there as a `ConfigurationError` naming the child, the parent and the offending property path. No data migration is required; every refusal is a schema-authoring fix.
- **Supertype queries now return subtype rows**, and rows of kinds declared `equivalentTo` the queried kind rather than only its `subClassOf` descendants. To keep the previous row behavior everywhere, pass `createStore(graph, backend, { queryDefaults: { expansion: "exact" } })`; per call site, pass `{ expansion: "exact" }`. Omitting the option no longer stops expansion. The store default governs which rows come back, not how an alias is typed: see the alias-type bullet below. If an `equivalentTo` pair was never meant to be substitutable, drop the declaration.
- **An explicit kind list, `from([...])`, now expands each listed kind** through its subclasses and `equivalentTo` kinds under the store default, where it always scanned exactly the listed kinds and refused an options bag. To keep the previous rows, state `from([...], alias, { expansion: "exact" })`, or set `queryDefaults: { expansion: "exact" }` on the store. The alias type widens the same way a single-kind alias does: for a listed kind the ontology affects, `kind` is `string` and its `NodeId` brand widens; `{ expansion: "exact" }` keeps the exact union. A saved pagination cursor from a single-kind list whose kind has subclasses is refused for the same reason the cursor bullet below gives; restart pagination or state `{ expansion: "exact" }`.
- **A query over a kind whose subclasses exist only in a persisted extension is refused when it states no `expansion`**, with `ConfigurationError` `QUERY_ALIAS_EXPANSION_UNTYPED_SUBCLASSES`, where it returned the extension's subclass rows under an exact `kind` type. This covers `from()`, a list source (for an extra kind no listed kind's type admits) and `to()`. State `{ expansion: "subclasses" }` or `{ expansion: "exact" }` on the call, or use `fromDynamic()`/`toDynamic()`. The decision reads the graph's ontology values at run time, not the store's declared type, so it also fires for a store typed over a widened `GraphDef` or an erased ontology, whose aliases are already typed polymorphically; state `expansion` there too.
- **An `updateWhere({ candidates })` query over a kind with subclasses or `equivalentTo` kinds is refused** with `ConfigurationError` (`SET_UPDATE_CANDIDATE_MULTIPLE_KINDS_UNSUPPORTED`), because `from(kind)` now resolves such a kind to several kinds. Pass `{ expansion: "exact" }` to the candidate query's `from()`. A candidate kind with no subclasses or equivalents is unaffected.
- **A saved pagination cursor from a supertype query no longer matches that query.** A query whose source now resolves to several kinds orders by an added `kind` tiebreaker before `id`, so a cursor encoded before the upgrade is refused with `ValidationError` (cursor column mismatch). Restart pagination from the first page, or pass `{ expansion: "exact" }` to keep the single-kind order the cursor was encoded against.
- **The `includeSubClasses` boolean is replaced by one `expansion` option** on `from()`/`to()`/`fromDynamic()`/`toDynamic()`: `{ includeSubClasses: false }` becomes `{ expansion: "exact" }` and `{ includeSubClasses: true }` becomes `{ expansion: "subclasses" }`, which is now also what an omitted option means. `store.search()`'s `includeSubClasses: true` (the `includeSubClasses` member of `SearchScopeOptions`) becomes `expansion: "subclasses"`. `createStore(..., { queryDefaults: { expansion } })` and `createQueryBuilder`'s `defaultExpansion` set the default everywhere in one place. A value outside the accepted set is refused with `QUERY_ALIAS_EXPANSION_INVALID`, and so is a stated `includeSubClasses` from untyped code, on every one of those entry points and on `store.search()` (the message names `expansion`): the option is never read as "no option", so a JavaScript `{ includeSubClasses: false }` cannot silently become the polymorphic default.
- **The internal `SchemaIntrospector` replaces `hasSearchableField` with `kindsWithoutSearchableField`**, which answers the same question and names the kinds that leave an alias without searchable content, and gains `kindsRedeclaringEmbeddingUntagged`. The introspector is built by the library for the query builder and the search facade and is not exported from any entrypoint, so only code that reaches into a builder's internals is affected.
- **`QueryAst`'s `start.includeSubClasses: boolean` becomes `start.expansion: "exact" | "subclasses" | "narrower"`.** This affects only code inspecting a compiled AST directly.
- **Alias types widen under the polymorphic axis.** For a kind that some other kind declares itself a subclass of, or that participates in a registered-kind `equivalentTo`, the alias's `kind` is `string` and its `NodeId` brand widens. A relation endpoint declared as a UNION of kinds, spelled `typeof Audio | typeof Video` or `NodeType<"Audio" | "Video">`, widens every kind the union can hold. A graph declaring no subsumption relations is unaffected. Alias types widen whatever the store default: `queryDefaults: { expansion: "exact" }` changes the rows an alias returns, not its type, so an affected kind still types `kind` as `string` and its id is not accepted by the kind's own collection. State `{ expansion: "exact" }` on the call (`from("Person", "p", { expansion: "exact" })`) to keep the literal alias type.
- **Expanded search hits widen unconditionally.** `store.search.fulltext` / `vector` / `hybrid` called with `expansion: "subclasses"` no longer claims the exact searched kind, on any kind, as `from(kind, alias, { expansion: "subclasses" })` types its alias: `hit.node.kind` is `string` and `hit.node.id` is no longer accepted by the searched kind's own collection methods. This includes a kind no compile-time subsumption relation names, because a persisted extension can still subclass it. Narrow on `hit.node.kind` first, or search with the default `"exact"` axis. A search that states no `expansion` is unaffected.
- **`ReturnType<typeof store.search.fulltext<"K">>` (and `vector` / `hybrid`) now names the widened hit.** The facade's last overload is the one an options value of the library's own `FulltextSearchOptions` / `VectorSearchOptions` / `HybridSearchOptions` type takes, and `ReturnType` reads the last overload. Name the exact hit as `FulltextSearchHit<Node<typeof K>>`, or take the type of a call that omits `expansion`.
- **Typed edge reads widen an affected endpoint.** For an endpoint whose declared kind has `subClassOf` descendants or `equivalentTo` kinds, `edge.fromKind`/`edge.toKind` is `string` and `edge.fromId`/`edge.toId` is no longer accepted by the declared kind's own collection, so `store.nodes.Person.getById(edge.toId)` stops compiling where the edge may point at an `Employee`. Resolve the endpoint with `store.getNodeByRef({ kind: edge.toKind, id: edge.toId })`, narrowing `edge.toKind` first for a specific kind's typed node. An endpoint kind no subsumption relation names is unaffected, unless the ontology's literals are erased (see the `OntologyRelation` bullet).
- **`TypedEdgeCollection`, `TypedStoreViewEdgeCollection` and `TypedRecordedStoreViewEdgeCollection` take the graph as a second type argument**, and `EdgeCollection`, `StoreViewEdgeCollection` and `RecordedStoreViewEdgeCollection` take it as their last. Named without it, they keep the declared endpoint kinds exactly, so an annotation such as `TypedEdgeCollection<(typeof graph)["edges"]["worksAt"]>` no longer equals `store.edges.worksAt` for an affected endpoint; write `TypedEdgeCollection<(typeof graph)["edges"]["worksAt"], typeof graph>`.
- **Annotating a relation as `OntologyRelation` widens every alias in that graph**, and every typed edge endpoint read with it, including endpoints between kinds no relation names. Aliases still compile with their `kind` and `NodeId` types widened to the polymorphic form, but `store.nodes.X.getById(edge.toId)` stops compiling for every edge in the graph — let the factory's return type be inferred to keep the narrow types.
- **An equivalence class mixing node and edge kinds, or holding two registered edge kinds, is refused** with `ConfigurationError` `ONTOLOGY_EQUIVALENCE_INVALID_CLASS` where it previously loaded inert; a persisted schema carrying one fails on load, so correct the stored document before upgrading. `equivalentTo`'s first parameter widens to `NodeType | AnyEdgeType` so an edge kind can be mapped to an external IRI.
- **Edge endpoints, `implies` and `inverseOf` endpoint validation, and `importGraph`'s endpoint check all accept equivalent kinds.** Some declarations previously refused at registry build now construct.
- **A `kindWithSubClasses` uniqueness constraint spans the equivalence class**, so a value that was unique per kind before can now collide. The claim axis moves to the code-point minimum of the widened component, and **no data migration is required**: rows written under the previous axis are still found and still fence. The reverse is not covered: REMOVING a `subClassOf`/`equivalentTo` can move a kind's axis away from the kinds its existing claims sit under, and those claims then stop fencing new writes of that kind. `store.verifyConstraintFences()` reports any duplicate that results (claims are read by their owner's kind, not by where they were written); until claims are re-homed on removal, run it after dropping a relation from a populated hierarchy that declares a `kindWithSubClasses` constraint.
- **The serialized schema's precomputed `ontology.closures` change for any graph declaring `equivalentTo` between registered kinds**, and with them the schema hash. It resolves as a semantic no-op on both boot paths and needs no schema write: a stored version's hash is recomputed from its document with the closures re-derived from its own relations, so it equals the hash of the unchanged graph and the store reports `status: "unchanged"` (see the removed `metaEdge()` change for the full list of comparisons that read the recomputed hash).
- If an existing `subClassOf` was modelling a taxonomy rather than a genuine subtype relationship, replace it with `broader(narrowerKind, broaderKind)` and query with `{ expansion: "narrower" }`; for a vocabulary that grows at runtime, prefer an instance-level concept kind with a `broader` edge traversed with `.recursive()`.
