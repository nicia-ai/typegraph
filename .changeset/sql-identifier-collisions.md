A query whose generated SQL names cannot be told apart on every database engine is now refused before any SQL is sent, with the same `ValidationError` on every backend. Each alias becomes part of SQL names (`cte_<alias>`, `<alias>_<column>`, result columns such as `<alias>_<field>`); PostgreSQL clips every name to 63 bytes, and both engines compare names without regard to letter case wherever SQL refers to them. Until now such a query failed on PostgreSQL (`column reference is ambiguous`, `WITH query name specified more than once`) or silently returned another value's data, often on SQLite while PostgreSQL failed. The issue codes `SQL_IDENTIFIER_COLLISION` and `SQL_IDENTIFIER_TOO_LONG` are exported from `@nicia-ai/typegraph/errors` as `SQL_IDENTIFIER_COLLISION_CODE` and `SQL_IDENTIFIER_TOO_LONG_CODE`.

Every entry point checks the statement it actually sends or hands out. `execute()` checks the statement it sends: the one that reads only the selected fields when the selector reads plain fields, and the full statement if it falls back to it. `compile()` and `toSQL()` check the SQL they return, which always carries every column of every alias. `prepare()` checks every statement the prepared query can run, including the wrapped statement a checked read sends inside `withCheckedReads()`. So node `k` beside edge `K` selecting only ids still executes and returns the right rows, while its `compile()`, `toSQL()` and `prepare()` are refused, because the SQL they would hand out reads both `k_id` and `K_id`.

Which column names a statement reads is taken from the statement itself: the one function that writes a column reference into the SQL also records the read, so the check cannot miss a name the SQL reads (such as `e_from.id` on the right of a `having()` comparison) or count one it never reads (such as `e_from_id` for `max("e_from", "age")`). A name written without its relation, as `having()` writes it, is refused when more than one relation the statement reads from has a column by that name, which both engines reject as ambiguous.

Now refused:

- aliases that differ only by letter case, such as `item` and `Item`;
- long aliases whose generated names clip to the same 63 bytes, such as two 60-character aliases sharing their first 59 characters;
- an edge alias `e` beside a node alias `e_from` when the statement reads both the edge's `from_id` and the node's `id` (whole rows, any `compile()` of a `select()`, or a `having()` comparison that reads `e_from.id` on either side), and a property `edge_id` of alias `p` selected together with the id of alias `p_edge`;
- `aggregate()` or `project()` keys that are equal ignoring letter case, such as `total` and `Total`, refused when `aggregate()` or `project()` is called with `SQL_IDENTIFIER_COLLISION` naming both keys. SQLite compares result names without regard to case, so the same builder returned the wrong value through some terminals on SQLite (`orderBy("Total")`, `first()`, `store.batchOnce()`) and the right value through others; the builder is refused rather than some of its terminals. This is a deliberate restriction: it also refuses such keys where they happened to work, such as with `.orderBy("total")`, `count()` or `exists()`;
- a result column read back by name that is longer than 63 bytes, such as the id of a 61-character alias (#931);
- an `aggregate()` key longer than 63 bytes (counted in bytes, so 32 two-byte characters are too long), refused when `aggregate()` is called.

The check covers `execute()`, `first()`, `count()`, `exists()`, `executeOn()`, `executeChecked()`, `compile()`, `toSQL()`, `prepare()`, `paginate()`, `stream()` and `page()` of `select()` queries; the terminals of `project()` and `aggregate()` queries, including those that run through `asRelation()`; `count()` and `exists()` before `select()`; `store.batch()`, `store.batchOnce()` and `withCheckedReads()`; the operands of `union()`, `intersect()` and `except()`; and `updateWhere()` candidate queries. `store.batch()` checks the first statement of every item before it runs any of them, so a refused item leaves no statement sent. Where a statement is embedded in SQL that refers to its result columns by name (relations, checked reads, `batchOnce()`, the leftmost operand of a set operation), result names that differ only by letter case are refused too. A set operation takes its column names from its leftmost operand and matches every other operand's columns by position, so another operand's result names are not compared, except those a nested set operation's ordering refers to by name: a `union()` whose right operand returns both `K_id` and `k_id` runs.

Two names that meet are not refused when the statement never refers to that name in the relation that holds both, so the SQL text of every query that is not refused is unchanged, `.project((ctx) => ({ name: ctx.e_from.name }))` and `.aggregate({ age: max("e_from", "age") })` beside an edge `e` keep working, and a set-based update through a candidate query whose root alias is 61 characters long keeps working. To fix a refused query, rename: use aliases and keys that differ in more than letter case and early in the name, keep aliases short enough that `<alias>_<field>` fits in 63 bytes, or choose a shorter `aggregate()` key.

`aggregate()` keys and `project()` keys starting with the reserved `__tg_` prefix are now refused in any letter case with `ConfigurationError("Projection output name is reserved.")`; `project()` previously refused only the lowercase prefix and `aggregate()` refused none. Not checked yet: recursive traversals, subqueries, the names a relation or set operation adds around its operands, and the full statement a `select()` falls back to after its optimized statement has run (checked when it is sent, after that first statement).
