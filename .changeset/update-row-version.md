A node update's row write is now bound to the version of the row it was planned from. Every update reads the row, merges or replaces its props, plans its uniqueness claim transition from what it read, and then writes. Under PostgreSQL `READ COMMITTED` another session can commit a write to the same row in between, and the UPDATE, predicated on identity alone, wrote the props computed from the superseded row back over the newer one. Its claim decision had compared the superseded row with itself, so the row could store a unique value that no claim reserved: when another session moved a unique field from January 1 to January 2 while an update of an unrelated field was between its read and its write, the row went back to January 1 and its claim stayed January 2, and a second January 1 row was then admitted. The whole superseded row was also written over the other session's change, which was lost.

The node UPDATE now carries `version = <the version it read>` in its own `WHERE`, so a write that meets no concurrent writer issues exactly the statements it did before, and one that does matches no row. The claim transition then gives back what it claimed, and the entry point recovers according to what it promises:

- `update()`, `upsertById()`, `upsertByIdFromRecord()` and `bulkUpsertById()` name the fields they change, so they re-read the row and apply those fields to it again, with claims planned from the current row. Merge apply writes through `upsertByIdFromRecord()` and follows the same rule.
- `bulkReplaceById()` states the whole row, so it re-reads only to plan its claims from the row it replaces, and stores the row it was given (its version-gated batch statement already did this; its per-row path now does too).
- A provenance reopen, and a `create()` that lands on a tombstone, re-read the row: a row another session brought back is left as it is (for `create()`, the already-exists error), and a row still deleted is revived from what it holds now.
- `importGraph()` with `onConflict: "update"` reports the row with `INTERCHANGE_NODE_UPDATE_TARGET_CHANGED` and leaves the other session's write in place.

Each retrying call retries once. A row that moves again before the second write fails the call with a `DatabaseOperationError` whose message says the update could not be applied to a stable row.

### Upgrade notes

- **Concurrent updates of one node no longer overwrite each other on PostgreSQL.** Where two sessions update the same node at once, the later writer of `update()`, `upsertById()`, `upsertByIdFromRecord()`, `bulkUpsertById()` and `bulkReplaceById()` now re-reads the row and applies its call to it instead of writing back the row it read; fields the later call does not name keep the earlier writer's values. A call whose row is rewritten again during its retry now throws `DatabaseOperationError` (`details.operation: "update"`, `details.entity: "node"`) where it used to succeed; retry it, or serialize the writers. `importGraph()` with `onConflict: "update"` now reports a row another session wrote between the import's read and its write as a per-row `INTERCHANGE_NODE_UPDATE_TARGET_CHANGED` error, also for a document that states no validity window, where it used to overwrite it. SQLite admits one writer at a time, so none of these can occur there.
- **A custom backend's `updateNode` must apply `UpdateNodeParams.expectedVersion`.** The store now passes `expectedVersion` on every node update. Add `AND version = expectedVersion` to the UPDATE's `WHERE` when it is present, so that a mismatch matches no row and raises the existing `no_row_returned` `DatabaseOperationError`. A store write through a backend that ignores it is refused with a `ConfigurationError` (`details.operation: "updateNode"`) when the returned row's `version` is not exactly one past `expectedVersion` (so a backend that ignores `incrementVersion: true` is refused too), which aborts the write's transaction. Backends built by the bundled factories apply it.
