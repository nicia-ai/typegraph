A uniqueness claim over a date property is now released with the key it was taken with. With a unique constraint over a date property (`z.date()`, `z.coerce.date()`, a pipe ending in a date, optional or nullable), a write keyed its claim from the validated `Date` (its JSON-quoted ISO text), but a release keyed the row it read back, where the same value is unquoted ISO text, so the two keys differed. Every update that changed the date left the old value reserved, and a soft delete left the deleted row's value reserved wherever it released per key (a delete inside a transaction on every backend, every delete on better-sqlite3). A later create of that value was refused with a `UniquenessError` naming a node that no longer held it, and `findByConstraint()` / `getOrCreateByConstraint()` returned that node instead of reporting the value free. Keys are now derived through one owner that keys a date field as the JSON text of its timestamp whether it holds a `Date` or the stored text, so the write, the release, the update diff, the lookups, import, provenance revival and graph-merge blocking derive the same bytes. Every other value keys exactly as before.

### Upgrade notes

- No migration is needed for claims written by `create()`, the bulk and upsert writes, `updateWhere()` or import: their bytes are unchanged and keep matching their rows.
- Claims leaked before this release stay reserved until removed. A `UniquenessError` (or a `findByConstraint()` result) naming a holder whose current value differs, or a holder that is deleted, identifies one. To free it, update a live holder back onto the leaked value and then off it again, or `hardDelete()` a deleted holder (a hard delete removes every claim the node owns). `verifyConstraintFences()` and `validateStore()` do not report leaked claims.
- A row revived through provenance before this release holds its date claim under the unquoted text. That claim is no longer released by an update or delete of the row (hard delete still removes it), and, as before, it does not stop a create of the same date. Hard-delete such a row, or update it off the date and back, if it must keep its reservation.
- Still not covered, because the stored row cannot reproduce the original form: a `Date` held by a property whose schema output is not only a date (a union such as `z.union([z.date(), z.string()])`, `z.unknown()`, a `.transform()` returning a `Date`), and on PostgreSQL an object-valued unique property, whose keys `jsonb` reorders. Avoid unique constraints over such properties.
