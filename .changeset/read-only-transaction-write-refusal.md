A transaction opened with `store.transaction(fn, { accessMode: "read_only" })` now refuses every write its context offers before the write issues any statement, with the store's own `UnsupportedBackendCapabilityError` (capability `"write transaction access"`, `details.accessMode: "read_only"`, `details.operation` naming the call, such as `tx.nodes.Person.hardDelete()`). Previously only `planDelete`, `requestRecordedRevision`, `assertUnchangedSince` and `provenance.assertHolds(tx)` refused; every other write went through. On SQLite the write committed inside the "read-only" transaction; on PostgreSQL the engine rejected the first write statement and aborted the transaction, so later reads in the callback failed too. The refusal covers every node and edge collection write (`create`, `update`, `delete`, `hardDelete`, `bulkHardDelete`, the bulk and get-or-create writes, `reparent`, `compareAndSet`, `updateWhere`), every `tx.identity` write, `tx.writeNodeUpsertBatch` and `applyMergePlanInTransaction` (whose refusal arrives, like its other failures, as the `cause` of a `MergeError`). The transaction stays usable after a refusal. Code that wrote inside a read-only transaction on SQLite must drop `accessMode: "read_only"`. A statement issued through the native `tx.sql` handle is not checked by the store.
