"@nicia-ai/typegraph": minor
---

**Replayable identity history.** An identity-enabled graph with history capture now retains a replayable identity history: `store.identity.transitionsOf(ref)` returns every transition that changed a node's identity class — assertions, retractions, same-id folds, deletes and restores, validity-window ends, kind drops, schema transitions and the identity changes a graph merge applies — each carrying the ids of the `same` assertions that touched its own class (a bulk write names on each transition only the assertions with an endpoint in that class, never the whole batch), both temporal coordinates, and, for a change a merge applied, the branch, branch ancestry and plan and review digests that produced it. A transition an archival restore brought in carries `restored.at`, the destination's wall clock at restore time, so an audit view can tell an imported explanation from a locally replayable event. That marker is a wall clock rather than a `RecordedInstant` because a restore never advances the destination's recorded-revision counter; the retention watermark `truncatedBefore` remains the only revision-shaped signal a restore leaves behind. A restored transition's `recorded` is the source graph's instant, typed `RestoredRecordedInstant` (the `RestoredIdentityTransition` variant of `IdentityTransition`, beside `RecordedIdentityTransition`), which `store.asOfRecorded` does not accept.

`transitionsOf` and `replay` both page: `limit` caps the number of boundaries one page returns, and a capped page hands back a `nextCursor` to pass as the next call's `cursor`. The cursor is a position within the windowed lineage, so it composes with `fromRecorded`/`toRecorded` by intersection, and `fromRecorded`/`toRecorded` refuse a page cursor with a `ValidationError`. A cursor is bound to the reference whose lineage it pages; one passed to a read of another reference is refused with a `ValidationError`. Bounding the answer with `fromRecorded`/`toRecorded` never bounds the lineage search, so a window can never hide the note that names an earlier class canonical. `store.identity.replay(ref)` pairs each transition with the class membership before and after it, reconstructed through the same historical reader, at the same coordinate, as `store.asOfRecorded`: a step's `after` is what `store.asOfRecorded(step.transition.recorded).identity.membersOf(ref)` answers, and its `before` is the same read one revision earlier. Both are read under the graph's current schema, so a step recorded before a `sameIdAcrossKinds` flip or a kind removal shows that revision as the current schema reads it, and a validity window still open when a step was recorded stays open in that step however late the replay is asked for. Replay requires `history: true` and refuses with `IDENTITY_REPLAY_REQUIRES_HISTORY` otherwise, or with `IDENTITY_REPLAY_ENGINE_NATIVE_UNSUPPORTED` on a backend that owns recorded time itself, where TypeGraph captures no history to replay; Cloudflare D1 and neon-http continue to refuse identity-enabled graphs outright.

A lineage is discovered from the reference itself as well as from its current class, through the recorded `same` assertions and same-id nodes that ever tied it to one, so the history of a member that has since been deleted or split away is still returned from that member. Only the transitions recorded while the reference was a member of the class they name are returned: a class the reference has left keeps a history of its own, and its later merges and splits are not reported as the reference's. Membership is judged over the kinds the log names and, once a schema transition was recorded, under both same-id settings, so a later kind drop or `sameIdAcrossKinds` change does not remove the history that put the reference in the class. When a graph holds archivally restored transitions that discovery can neither tie to the reference nor rule out, `transitionsOf` and `replay` report the count as `incompleteDiscovery.unattributedRestoredTransitions` rather than returning a short page that looks complete.

`IdentityReplayError` (exported from the package root, `details.code` discriminates) is the typed refusal for a request the transition log cannot answer: history capture is off (`IDENTITY_REPLAY_REQUIRES_HISTORY`), the backend keeps engine-native recorded time (`IDENTITY_REPLAY_ENGINE_NATIVE_UNSUPPORTED`), a bounded range lies entirely below the retention watermark (`IDENTITY_REPLAY_HISTORY_TRUNCATED`), the lineage walk reached its read ceiling before converging (`IDENTITY_REPLAY_WALK_INCOMPLETE`), or a prune names a point beyond the recorded clock (`IDENTITY_PRUNE_BEYOND_RECORDED_CLOCK`). A range with more boundaries than `limit` pages and is not a refusal.

`pruneIdentityTransitions(store, { beforeRecorded })` trims retained explanations and records a watermark that replay reports rather than hiding. A `beforeRecorded` beyond every revision the graph holds (its next commit's revision, or one past the highest retained transition when an archival restore carried higher revisions in) is refused with `IDENTITY_PRUNE_BEYOND_RECORDED_CLOCK`, since it would claim history the graph has yet to record as already pruned; the retention watermark itself never rises above the next commit's revision, and restored rows are pruned by their raw revision number alongside native rows. Archival interchange carries a `transitions` section plus the retention watermark, bumping the interchange format to `3.0`; older documents still import and validate unchanged. Restoring an archive's transitions validates shape only and never re-derives membership, every restored row is marked as such so `replay` never pairs it with a fabricated before/after, and when the destination had no identity transitions of its own before the import began the restore also sets its own watermark, so `replay` reports the pre-restore range honestly instead of claiming a complete history it cannot reconstruct. That decision and the watermark's value are read once, ahead of the import's first write (for a stream, at its header, before the first chunk commits), so `importGraph` and `importGraphStream` restore one archive to the same watermark, and the transitions a streamed restore's own node and assertion chunks record never count as the destination's earlier history. A streamed document whose header does not announce identity transitions (`identity.hasTransitions`) but whose chunks carry them is refused, since an unannounced transition has no restore floor and would silently drop the watermark. A restored transition's `recordedRevision` must be one a recorded instant can carry (an integer from 1, below `Number.MAX_SAFE_INTEGER`), and the transitions must be in non-decreasing `recordedRevision` order. `importGraph` refuses a document breaking either rule with a `ValidationError` before anything is written; `importGraphStream` validates each `identity-transitions` chunk when it arrives, in order across chunks as well as within one, after the stream's node, edge and assertion chunks have committed. A stream whose header announces a restore (`hasTransitions`, or a non-zero `retention` watermark) but that ends without an `identity-transitions` chunk is refused at its end with `IDENTITY_IMPORT_STREAM_TRANSITIONS_MISSING`. A `state`-mode document carrying `transitions` or a `retention` watermark is refused before anything is written (`IDENTITY_STATE_IMPORT_TRANSITIONS`, `IDENTITY_STATE_IMPORT_RETENTION`), and a zero watermark restores nothing, so it is accepted by any target.

**Graph merge carries identity truth with fixed, reported rules.** There is no identity policy to configure. A merge three-way classifies every staged identity assertion and retraction against the target's current truth, and each one ends as a write, a `dropped` entry with a reason, or a refusal that names it: duplicate assertions of one pair reduce to one survivor (an id the target already holds, then the earliest `validFrom`, then the code-point-smallest id) with the rest reported as `identity:duplicate-assertion`; a retraction and a re-assertion of one pair land together only when every branch that retracts the pair also re-asserts it; branches asserting opposing relations for one pair, or branches disagreeing about whether a retracted pair is re-asserted, fail the merge with `GRAPH_MERGE_IDENTITY_CONFLICT`. A `same` assertion is ledger truth the merge carries across — it never fuses the rows it names.

A class-lifted `different` assertion now vetoes a candidate match at plan time on every identity-enabled merge, instead of aborting inside the commit on a database constraint. The veto reads the target's ledger and the assertions the merge itself stages: a staged `different` separates the entities it names before a scored match can fuse them, and lands with both rows, and a staged `same` joins its endpoints' classes, so a scored match into a class the ledger holds apart from the other side is vetoed too rather than failing the plan on the opposing relations it would create. A scored match between separated entities is dropped, the merge continues, and the pair is reported as an `IdentityUnresolvedConflict` (`kind: "separation"`, naming both entities, the separating assertion and the source that proposed the match) on the new `MergeReport.identityConflicts` and on a plan artifact's optional `review.identityConflicts`; candidate diagnostics report the pair as `excluded` with reason `"separation"`. A definitional match that survives the base and diameter guards, or a cluster that fuses a separated pair through a third node, fails the plan with the new code `GRAPH_MERGE_IDENTITY_SEPARATION_CONFLICT` on `IdentityMergeConflictError`. The veto adds no format number of its own: `review.identityConflicts` is omitted when empty, so a plan the veto never touched carries nothing for it.

Every transition a merge causes carries a `decision` naming the branch (when exactly one was merged), the root-first branch ancestry, the plan digest when a plan artifact was applied, the review digest of the compatible review revalidation the applier supplied (`MergePlanApplyOptions.review`, refused with `InvalidMergeOptionsError` unless its fresh plan is the plan being applied), and the source id the applier supplied. A transition caused by an identity assertion or retraction the merge applied is recorded with cause `reconcile`; one caused by a node row the merge wrote keeps the cause that names its mechanism — `detach` for a deleted class member, `fold` for a created same-ID peer — and carries the same `decision`. `merge()`, `mergeIncremental()`, `applyMergePlan()`, `applyMergePlanInTransaction()` and `applyDurableMergePlan()` order their node and identity writes the same way, so a plan that retracts an assertion and ends one endpoint's validity window lands through every one of them. A plan artifact also carries a branch's reopening of an ended node or edge window (`clearValidTo: true` on the upsert and on `review.validityEnds`), so a plan that reopens a window can be planned and applied through every one of them rather than being refused at planning.

One narrow, deliberate behavior change ships in how a merge ends an assertion: when two branches end the same base identity assertion at different valid-time instants, the merge commits the earliest staged `validTo` rather than whichever branch happened to be staged last. The rule is deterministic and branch-order-independent, but it is a real change to which instant a merge commits. The same rule holds when one branch's deletion cascades an ending onto an assertion and another branch retracts it explicitly: if the delete/modify resolution overrules the deletion, the surviving retraction commits at the instant and with the cause of the contributions that still stand, not those of the overruled cascade.

A durable merge plan built under `reconcileTypes: "ontology"` also no longer fails its own artifact validation ("A resolution must name its complete guarded cluster and carry exactly N-1 decisive edges") when a retype cluster spans several ids: the resolution now names the kind the canonical row is written under, the reconciled kind `TypeReconciliation.toType` records, rather than the staged survivor's pre-retype kind.

A transaction receipt's `writes.identity` gains `transitions`, counted beside and never inside `total`: the number of identity transition-log notes the transaction's flush wrote.

`applyMergePlanInTransaction()` records the same identity decision as `applyMergePlan()` for one plan, and accepts the same `review` and `sourceId` provenance as an optional fourth argument (`MergePlanDecisionOptions`). `applyDurableMergePlan()` always applies through the target Store transaction, so the plan's identity and composition work runs through TypeGraph's own write path; a strategy that still declares a native `merge()` is refused.

### Breaking

- A merge option `MergeOptions` does not declare is refused with `InvalidMergeOptionsError` (`details.option` names the key) by every merge and plan entry point (`merge()`, `mergeIncremental()`, `planMerge()`, `planMergeIncremental()`, …) and by candidate write-set review, where it was previously ignored. The refusal reaches inside `resolve`: an entry for a node kind the graph does not declare (`details.option` `"resolve.<kind>"`), an undeclared key in a kind's resolve config, its `keyless` bag, its similarity strategy or a hybrid strategy's `weights` (`"resolve.<kind>.similarity.<key>"`, …), and an unknown similarity `kind` are refused the same way. `applyMergePlan()` and `applyDurableMergePlan()` likewise refuse an apply option `MergePlanApplyOptions` does not declare. Remove the key, or correct its spelling.
- A merge where one branch retracts an inherited identity assertion while another branch retracts it and asserts the same pair again under a new id now fails with `IdentityMergeConflictError` ("retract/reassert race"), where it previously merged and silently kept the re-assertion. A retraction and a re-assertion of one pair merge only when every branch that retracts the pair also re-asserts it. Reconcile the branches — either every retracting branch re-asserts the pair or none does — then merge again.
- A candidate match between two entities whose identity classes a `different` assertion holds apart no longer reaches the commit. A scored match is dropped and reported on `MergeReport.identityConflicts`, and the merge succeeds where it previously failed in the commit; a definitional match or a transitive cluster fails at plan time with `GRAPH_MERGE_IDENTITY_SEPARATION_CONFLICT` rather than the commit's generic refusal. `IdentityMergeConflictError.code` is typed `IdentityMergeConflictCode`, the union of that code and `GRAPH_MERGE_IDENTITY_CONFLICT`.
- `MergeReport` gains the required member `identityConflicts`, and `CandidateDiagnostic`'s `clusterDisposition.reason` gains `"separation"`. Code that constructs a `MergeReport`, or switches exhaustively over the exclusion reason, must account for both.
- `EntityResolution.kind` (on `MergeReport.resolutions` and a plan artifact's `review.resolutions`) names the reconciled kind for a cluster the ontology cascade retypes. Code that joined a resolution to its staged members by the survivor's pre-retype kind should read `TypeReconciliation.fromTypes` for the staged kinds; clusters no retype touches are unchanged.
- The identity transition log adds two deployment-wide relations, `typegraph_identity_transitions` and `typegraph_identity_transition_retention`, created for every database whether or not any graph in it enables identity, with `createSqlSchema` accepting `identityTransitions` and `identityTransitionRetention` as optional name overrides and `ResolvedSqlTableNames` gaining both as required members. They ship as a new base-schema release: `CURRENT_BASE_SCHEMA_VERSION` advances from 5 to 6, id `"identity-transition-log"`, adopting both relations through `CREATE TABLE IF NOT EXISTS` and their indexes (idempotent, safe to run concurrently, and a no-op on a fresh install whose generated DDL already carries them). The bump is one-way and deployment-visible: a database stamped 5 or lower is caught up in place by the next privileged open (`createStoreWithSchema` / `createAdapterStoreWithSchema`) or an explicit `backend.adoptBaseSchema()`, and until one of those runs, a DML-only or zero-DDL runtime (`createVerifiedStore`, graph-template attach) refuses with `BaseSchemaMigrationError`, so privileged adoption must finish before those workers start. Once a database is stamped 6, a TypeGraph release that knows only version 5 or lower refuses it as newer; there is no downgrade path. A custom SQL engine profile's `BaseSchemaRuntime` gains two optional members, `identityTransitionsTableDdl` (the transition log's `CREATE TABLE` followed by its `CREATE INDEX` statements) and `identityTransitionRetentionTableDdl` (the retention watermark's `CREATE TABLE`), which back the version-6 adoption step; a profile that omits either still constructs, and version-6 adoption refuses with a `ConfigurationError` whose `details.missingDependencies` names what is missing. A profile whose adoption-step registry stops below 6 fails to construct (`CompilerInvariantError`, "adoption registry must end at the current version"). A deployment whose migration tooling enumerates TypeGraph's relations, or whose database role has restricted DDL, must account for both relations before upgrading; the statements are in the backend setup guide under "Base-schema version 6". On a database that has not adopted version 6, a plain `createStore` attach with `history: true` on an identity graph fails its first write that records an identity transition with a `ConfigurationError` whose `details.code` is `IDENTITY_TRANSITION_RELATIONS_MISSING`, naming both relations. A PostgreSQL durable working-copy allocation carries its own base-schema marker: reopening one provisioned under version 5 (`reopenDurableBranch`, and the durable operations that attach it) adopts version 6 into the allocation in place before its Store opens, through the `connect` session, which runs as the role that created the allocation; an allocation stamped by a newer release is refused with a `BaseSchemaMigrationError` as the cause. An unpublished namespace fork taken before the upgrade keeps its proof: a fork's content digest names a relation added after the first fork release only once that relation holds rows for the graph, so `forkGraphNamespace()` with the same operation key, and `abort()`, still verify a target the earlier release populated, including one whose database has not yet adopted the two relations.
- `exportGraph` and `exportGraphStream` emit interchange format `"3.0"` (`FORMAT_VERSION`), so a document it produces is refused by a TypeGraph release that knows only `"1.0"` and `"2.0"`. Documents in either earlier format still import and validate here unchanged.
