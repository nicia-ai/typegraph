"@nicia-ai/typegraph": minor
---

**Replayable identity history.** An identity-enabled graph with history capture now retains a replayable identity history: `store.identity.transitionsOf(ref)` returns every transition that changed a node's identity class — assertions, retractions, same-id folds, deletes and restores, validity-window ends, kind drops, schema transitions and the identity changes a graph merge applies — each carrying the assertion ids involved, both temporal coordinates, and, for a change a merge applied, the branch, branch ancestry and plan and review digests that produced it. A transition an archival restore brought in carries `restored.at`, the destination's wall clock at restore time, so an audit view can tell an imported explanation from a locally replayable event. That marker is a wall clock rather than a `RecordedInstant` because a restore never advances the destination's recorded-revision counter; the retention watermark `truncatedBefore` remains the only revision-shaped signal a restore leaves behind.

`transitionsOf` and `replay` both page: `limit` caps the number of boundaries one page returns, and a capped page hands back a `nextFrom` cursor to pass as the next call's `fromRecorded`. Bounding the answer with `fromRecorded`/`toRecorded` never bounds the lineage search, so a window can never hide the note that names an earlier class canonical. `store.identity.replay(ref)` pairs each transition with the class membership before and after it, reconstructed through the same historical reader `asOf` and `asOfRecorded` reads use, so replay can never disagree with a live read. Replay requires `history: true` and refuses with `IDENTITY_REPLAY_REQUIRES_HISTORY` otherwise, or with `IDENTITY_REPLAY_ENGINE_NATIVE_UNSUPPORTED` on a backend that owns recorded time itself, where TypeGraph captures no history to replay; Cloudflare D1 and neon-http continue to refuse identity-enabled graphs outright.

`pruneIdentityTransitions(store, { beforeRecorded })` trims retained explanations and records a watermark that replay reports rather than hiding. Archival interchange carries a `transitions` section plus the retention watermark, bumping the interchange format to `3.0`; older documents still import and validate unchanged. Restoring an archive's transitions validates shape only and never re-derives membership, every restored row is marked as such so `replay` never pairs it with a fabricated before/after, and when the destination has no identity transitions of its own yet the restore also sets its own watermark, so `replay` reports the pre-restore range honestly instead of claiming a complete history it cannot reconstruct.

**Graph merge carries identity truth with fixed, reported rules.** There is no identity policy to configure. A merge three-way classifies every staged identity assertion and retraction against the target's current truth, and each one ends as a write, a `dropped` entry with a reason, or a refusal that names it: duplicate assertions of one pair reduce to one survivor (an id the target already holds, then the earliest `validFrom`, then the code-point-smallest id) with the rest reported as `identity:duplicate-assertion`; a branch that retracts a pair and re-asserts it itself lands both; branches asserting opposing relations for one pair, or one branch retracting a pair another re-asserts, fail the merge with `GRAPH_MERGE_IDENTITY_CONFLICT`. A `same` assertion is ledger truth the merge carries across — it never fuses the rows it names.

A class-lifted `different` assertion now vetoes a candidate match at plan time on every identity-enabled merge, instead of aborting inside the commit on a database constraint. A scored match between separated entities is dropped, the merge continues, and the pair is reported as an `IdentityUnresolvedConflict` (`kind: "separation"`, naming both entities, the separating assertion and the source that proposed the match) on the new `MergeReport.identityConflicts` and on a plan artifact's optional `review.identityConflicts`; candidate diagnostics report the pair as `excluded` with reason `"separation"`. A definitional match that survives the base and diameter guards, or a cluster that fuses a separated pair through a third node, fails the plan with the new code `GRAPH_MERGE_IDENTITY_SEPARATION_CONFLICT` on `IdentityMergeConflictError`. `MERGE_PLAN_FORMAT_VERSION` and `MERGE_REVIEW_FORMAT_VERSION` stay at 2: `review.identityConflicts` is omitted when empty, so a plan the veto never touched is byte-identical to one written before it existed.

Every transition a merge causes is recorded with cause `reconcile` and a `decision` naming the branch (when exactly one was merged), the root-first branch ancestry, the plan digest when a plan artifact was applied, and the review digest and source id the applier supplied.

One narrow, deliberate behavior change ships in how a merge ends an assertion: when two branches end the same base identity assertion at different valid-time instants, the merge commits the earliest staged `validTo` rather than whichever branch happened to be staged last. The rule is deterministic and branch-order-independent, but it is a real change to which instant a merge commits.

A durable merge plan built under `reconcileTypes: "ontology"` also no longer fails its own artifact validation ("A resolution must name its complete guarded cluster and carry exactly N-1 decisive edges") when a retype cluster spans several ids: the resolution now names the kind the canonical row is written under, the reconciled kind `TypeReconciliation.toType` records, rather than the staged survivor's pre-retype kind.

A transaction receipt's `writes.identity` gains `transitions`, counted beside and never inside `total`: the number of identity transition-log notes the transaction's flush wrote.

`applyMergePlanInTransaction()` records the same identity decision as `applyMergePlan()` for one plan. `applyDurableMergePlan()` offers a plan to a strategy's native `merge()` only when the plan carries no identity or composition work — identity assertion or retraction writes, an identity separation conflict, a reported composition orphan, or a write to a composition whole, part or edge kind — and applies every other plan through the portable path, which owns the transition log, closure maintenance, and composition enforcement.

### Breaking

- A merge option `MergeOptions` does not declare is refused with `InvalidMergeOptionsError` (`details.option` names the key) by every merge and plan entry point (`merge()`, `mergeIncremental()`, `planMerge()`, `planMergeIncremental()`, …) and by candidate write-set review, where it was previously ignored. Remove the key, or correct its spelling.
- A candidate match between two entities whose identity classes a `different` assertion holds apart no longer reaches the commit. A scored match is dropped and reported on `MergeReport.identityConflicts`, and the merge succeeds where it previously failed in the commit; a definitional match or a transitive cluster fails at plan time with `GRAPH_MERGE_IDENTITY_SEPARATION_CONFLICT` rather than the commit's generic refusal. `IdentityMergeConflictError.code` is typed `IdentityMergeConflictCode`, the union of that code and `GRAPH_MERGE_IDENTITY_CONFLICT`.
- `MergeReport` gains the required member `identityConflicts`, and `CandidateDiagnostic`'s `clusterDisposition.reason` gains `"separation"`. Code that constructs a `MergeReport`, or switches exhaustively over the exclusion reason, must account for both.
- `EntityResolution.kind` (on `MergeReport.resolutions` and a plan artifact's `review.resolutions`) names the reconciled kind for a cluster the ontology cascade retypes. Code that joined a resolution to its staged members by the survivor's pre-retype kind should read `TypeReconciliation.fromTypes` for the staged kinds; clusters no retype touches are unchanged.
- `store.identity.transitionsOf` returns `{ transitions, nextFrom? }` rather than a bare array. Destructure the result (`const { transitions } = await store.identity.transitionsOf(ref)`). `nextFrom` is a `TransitionPageCursor`, not a `RecordedInstant`: pass it back as `fromRecorded`, never to `store.asOfRecorded`.
- `IDENTITY_REPLAY_LIMIT_EXCEEDED` is gone from `IdentityReplayErrorDetails` and the error catalog. A lineage with more boundaries than `limit` now pages: `replay` and `transitionsOf` return a `nextFrom` recorded instant naming the first boundary the page stopped short of. Code that caught the refusal and resumed from `details.resumeFromRecorded` reads `nextFrom` off the successful result instead.
- Lineage discovery no longer honors `fromRecorded`/`toRecorded`, so a narrow-window audit read now scans the full lineage on every call. Only a class lineage whose transition rows exceed an internal safety ceiling hits `IDENTITY_REPLAY_WALK_INCOMPLETE`, whose only remedy remains the destructive `pruneIdentityTransitions`.
- The identity transition log adds two deployment-wide relations, `typegraph_identity_transitions` and `typegraph_identity_transition_retention`, created for every database whether or not any graph in it enables identity, with `createSqlSchema` accepting `identityTransitions` and `identityTransitionRetention` as optional name overrides and `ResolvedSqlTableNames` gaining both as required members. They ship as a new base-schema release: `CURRENT_BASE_SCHEMA_VERSION` advances from 3 to 4, id `"identity-transition-log"`, adopting both relations through `CREATE TABLE IF NOT EXISTS` and their indexes (idempotent, safe to run concurrently, and a no-op on a fresh install whose generated DDL already carries them). The bump is one-way and deployment-visible: a database stamped 3 is caught up in place by the next privileged open (`createStoreWithSchema` / `createAdapterStoreWithSchema`) or an explicit `backend.adoptBaseSchema()`, and until one of those runs, a DML-only or zero-DDL runtime (`createVerifiedStore`, graph-template attach) refuses with `BaseSchemaMigrationError`, so privileged adoption must finish before those workers start. Once a database is stamped 4, a TypeGraph release that knows only version 3 (0.68 and earlier) refuses it as newer; there is no downgrade path. A custom SQL engine profile's `BaseSchemaRuntime` gains two required members, `identityTransitionsTableDdl` (the transition log's `CREATE TABLE` followed by its `CREATE INDEX` statements) and `identityTransitionRetentionTableDdl` (the retention watermark's `CREATE TABLE`), which back the version-4 adoption step; a profile whose adoption-step registry stops at 3 fails to construct (`CompilerInvariantError`, "adoption registry must end at the current version"). A deployment whose migration tooling enumerates TypeGraph's relations, or whose database role has restricted DDL, must account for both relations before upgrading.
- Restoring an archival export (`identityMode: "archival"`) whose source graph retains identity transitions or has ever pruned them now requires the restore target to be opened with `history: true`. `importGraph` and `importGraphStream` refuse such a document with `IDENTITY_REPLAY_REQUIRES_HISTORY` before writing anything, where they previously wrote the rest of it successfully.
- An archival interchange document's transition `decision` is validated strictly: `branchId`, `branchAncestry`, `mergePlanDigest`, `reviewDigest` and `sourceId` are the only members, and a document carrying any other is refused with a `ValidationError` before anything is written rather than restored with that member dropped.
