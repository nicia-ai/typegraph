"@nicia-ai/typegraph": minor

**Replayable identity history.** An identity-enabled graph with history capture now retains a replayable identity history: `store.identity.transitionsOf(ref)` returns every transition that changed a node's identity class — assertions, retractions, same-id folds, deletes and restores, validity-window ends, kind drops, schema transitions and the identity changes a graph merge applies — each carrying the assertion ids involved, both temporal coordinates, and, for a change a merge applied, the branch, branch ancestry and plan and review digests that produced it. A transition an archival restore brought in carries `restored.at`, the destination's wall clock at restore time, so an audit view can tell an imported explanation from a locally replayable event. That marker is a wall clock rather than a `RecordedInstant` because a restore never advances the destination's recorded-revision counter; the retention watermark `truncatedBefore` remains the only revision-shaped signal a restore leaves behind.

`transitionsOf` and `replay` both page: `limit` caps the number of boundaries one page returns, and a capped page hands back a `nextCursor` to pass as the next call's `cursor`. The cursor is a position within the windowed lineage, so it composes with `fromRecorded`/`toRecorded` by intersection, and `fromRecorded`/`toRecorded` refuse a page cursor with a `ValidationError`. Bounding the answer with `fromRecorded`/`toRecorded` never bounds the lineage search, so a window can never hide the note that names an earlier class canonical. `store.identity.replay(ref)` pairs each transition with the class membership before and after it, reconstructed through the same historical reader `asOf` and `asOfRecorded` reads use, so replay can never disagree with a live read. Replay requires `history: true` and refuses with `IDENTITY_REPLAY_REQUIRES_HISTORY` otherwise, or with `IDENTITY_REPLAY_ENGINE_NATIVE_UNSUPPORTED` on a backend that owns recorded time itself, where TypeGraph captures no history to replay; Cloudflare D1 and neon-http continue to refuse identity-enabled graphs outright.

A lineage is discovered from the reference itself as well as from its current class, through the recorded `same` assertions and same-id nodes that ever tied it to one, so the history of a member that has since been deleted or split away is still returned from that member. When a graph holds archivally restored transitions that discovery can neither tie to the reference nor rule out, `transitionsOf` and `replay` report the count as `incompleteDiscovery.unattributedRestoredTransitions` rather than returning a short page that looks complete.

`pruneIdentityTransitions(store, { beforeRecorded })` trims retained explanations and records a watermark that replay reports rather than hiding. A `beforeRecorded` beyond every revision the graph holds (its next commit's revision, or one past the highest retained transition when an archival restore carried higher revisions in) is refused with `IDENTITY_PRUNE_BEYOND_RECORDED_CLOCK`, since it would claim history the graph has yet to record as already pruned; the retention watermark itself never rises above the next commit's revision, and restored rows are pruned by their raw revision number alongside native rows. Archival interchange carries a `transitions` section plus the retention watermark, bumping the interchange format to `3.0`; older documents still import and validate unchanged. Restoring an archive's transitions validates shape only and never re-derives membership, every restored row is marked as such so `replay` never pairs it with a fabricated before/after, and when the destination had no identity transitions of its own before the import began the restore also sets its own watermark, so `replay` reports the pre-restore range honestly instead of claiming a complete history it cannot reconstruct. That decision and the watermark's value are read once, ahead of the import's first write, so `importGraph` and `importGraphStream` restore one archive to the same watermark. A restored transition's `recordedRevision` must be one a recorded instant can carry (an integer from 1, below `Number.MAX_SAFE_INTEGER`); a document carrying any other is refused with a `ValidationError` before anything is written.

**Graph merge carries identity truth with fixed, reported rules.** There is no identity policy to configure. A merge three-way classifies every staged identity assertion and retraction against the target's current truth, and each one ends as a write, a `dropped` entry with a reason, or a refusal that names it: duplicate assertions of one pair reduce to one survivor (an id the target already holds, then the earliest `validFrom`, then the code-point-smallest id) with the rest reported as `identity:duplicate-assertion`; a branch that retracts a pair and re-asserts it itself lands both; branches asserting opposing relations for one pair, or one branch retracting a pair another re-asserts, fail the merge with `GRAPH_MERGE_IDENTITY_CONFLICT`. A `same` assertion is ledger truth the merge carries across — it never fuses the rows it names.

A class-lifted `different` assertion now vetoes a candidate match at plan time on every identity-enabled merge, instead of aborting inside the commit on a database constraint. A scored match between separated entities is dropped, the merge continues, and the pair is reported as an `IdentityUnresolvedConflict` (`kind: "separation"`, naming both entities, the separating assertion and the source that proposed the match) on the new `MergeReport.identityConflicts` and on a plan artifact's optional `review.identityConflicts`; candidate diagnostics report the pair as `excluded` with reason `"separation"`. A definitional match that survives the base and diameter guards, or a cluster that fuses a separated pair through a third node, fails the plan with the new code `GRAPH_MERGE_IDENTITY_SEPARATION_CONFLICT` on `IdentityMergeConflictError`. `MERGE_PLAN_FORMAT_VERSION` and the review format versions are unchanged by this: `review.identityConflicts` is omitted when empty, so a plan the veto never touched is byte-identical to one written before it existed.

Every transition a merge causes carries a `decision` naming the branch (when exactly one was merged), the root-first branch ancestry, the plan digest when a plan artifact was applied, and the review digest and source id the applier supplied. A transition caused by an identity assertion or retraction the merge applied is recorded with cause `reconcile`; one caused by a node row the merge wrote keeps the cause that names its mechanism — `detach` for a deleted class member, `fold` for a created same-ID peer — and carries the same `decision`. `merge()`, `mergeIncremental()`, `applyMergePlan()`, `applyMergePlanInTransaction()` and `applyDurableMergePlan()` order their node and identity writes the same way, so a plan that retracts an assertion and ends one endpoint's validity window lands through every one of them. A plan artifact also carries a branch's reopening of an ended node or edge window (`clearValidTo: true` on the upsert and on `review.validityEnds`), so a plan that reopens a window can be planned and applied through every one of them rather than being refused at planning.

One narrow, deliberate behavior change ships in how a merge ends an assertion: when two branches end the same base identity assertion at different valid-time instants, the merge commits the earliest staged `validTo` rather than whichever branch happened to be staged last. The rule is deterministic and branch-order-independent, but it is a real change to which instant a merge commits.

A durable merge plan built under `reconcileTypes: "ontology"` also no longer fails its own artifact validation ("A resolution must name its complete guarded cluster and carry exactly N-1 decisive edges") when a retype cluster spans several ids: the resolution now names the kind the canonical row is written under, the reconciled kind `TypeReconciliation.toType` records, rather than the staged survivor's pre-retype kind.

A transaction receipt's `writes.identity` gains `transitions`, counted beside and never inside `total`: the number of identity transition-log notes the transaction's flush wrote.

`applyMergePlanInTransaction()` records the same identity decision as `applyMergePlan()` for one plan. `applyDurableMergePlan()` always applies through the target Store transaction, so the plan's identity and composition work runs through TypeGraph's own write path; a strategy that still declares a native `merge()` is refused.

### Breaking

- A merge option `MergeOptions` does not declare is refused with `InvalidMergeOptionsError` (`details.option` names the key) by every merge and plan entry point (`merge()`, `mergeIncremental()`, `planMerge()`, `planMergeIncremental()`, …) and by candidate write-set review, where it was previously ignored. Remove the key, or correct its spelling.
- A candidate match between two entities whose identity classes a `different` assertion holds apart no longer reaches the commit. A scored match is dropped and reported on `MergeReport.identityConflicts`, and the merge succeeds where it previously failed in the commit; a definitional match or a transitive cluster fails at plan time with `GRAPH_MERGE_IDENTITY_SEPARATION_CONFLICT` rather than the commit's generic refusal. `IdentityMergeConflictError.code` is typed `IdentityMergeConflictCode`, the union of that code and `GRAPH_MERGE_IDENTITY_CONFLICT`.
- `MergeReport` gains the required member `identityConflicts`, and `CandidateDiagnostic`'s `clusterDisposition.reason` gains `"separation"`. Code that constructs a `MergeReport`, or switches exhaustively over the exclusion reason, must account for both.
- `EntityResolution.kind` (on `MergeReport.resolutions` and a plan artifact's `review.resolutions`) names the reconciled kind for a cluster the ontology cascade retypes. Code that joined a resolution to its staged members by the survivor's pre-retype kind should read `TypeReconciliation.fromTypes` for the staged kinds; clusters no retype touches are unchanged.
- `store.identity.transitionsOf` returns `{ transitions, nextCursor? }` rather than a bare array. Destructure the result (`const { transitions } = await store.identity.transitionsOf(ref)`). `nextCursor` is a `TransitionPageCursor`, not a `RecordedInstant`: pass it back as `cursor`, never as `fromRecorded`/`toRecorded` and never to `store.asOfRecorded`.
- `IDENTITY_REPLAY_LIMIT_EXCEEDED` is gone from `IdentityReplayErrorDetails` and the error catalog. A lineage with more boundaries than `limit` now pages: `replay` and `transitionsOf` return a `nextCursor` naming the first boundary the page stopped short of. Code that caught the refusal and resumed from `details.resumeFromRecorded` reads `nextCursor` off the successful result and passes it as `cursor` instead.
- Lineage discovery no longer honors `fromRecorded`/`toRecorded`, so a narrow-window audit read now scans the full lineage on every call. Only a class lineage whose transition rows exceed an internal safety ceiling hits `IDENTITY_REPLAY_WALK_INCOMPLETE`, whose only remedy remains the destructive `pruneIdentityTransitions`.
- The identity transition log adds two deployment-wide relations, `typegraph_identity_transitions` and `typegraph_identity_transition_retention`, created for every database whether or not any graph in it enables identity, with `createSqlSchema` accepting `identityTransitions` and `identityTransitionRetention` as optional name overrides and `ResolvedSqlTableNames` gaining both as required members. They ship as a new base-schema release: `CURRENT_BASE_SCHEMA_VERSION` advances from 5 to 6, id `"identity-transition-log"`, adopting both relations through `CREATE TABLE IF NOT EXISTS` and their indexes (idempotent, safe to run concurrently, and a no-op on a fresh install whose generated DDL already carries them). The bump is one-way and deployment-visible: a database stamped 5 or lower is caught up in place by the next privileged open (`createStoreWithSchema` / `createAdapterStoreWithSchema`) or an explicit `backend.adoptBaseSchema()`, and until one of those runs, a DML-only or zero-DDL runtime (`createVerifiedStore`, graph-template attach) refuses with `BaseSchemaMigrationError`, so privileged adoption must finish before those workers start. Once a database is stamped 6, a TypeGraph release that knows only version 5 or lower refuses it as newer; there is no downgrade path. A custom SQL engine profile's `BaseSchemaRuntime` gains two optional members, `identityTransitionsTableDdl` (the transition log's `CREATE TABLE` followed by its `CREATE INDEX` statements) and `identityTransitionRetentionTableDdl` (the retention watermark's `CREATE TABLE`), which back the version-6 adoption step; a profile that omits either still constructs, and version-6 adoption refuses with a `ConfigurationError` whose `details.missingDependencies` names what is missing. A profile whose adoption-step registry stops below 6 fails to construct (`CompilerInvariantError`, "adoption registry must end at the current version"). A deployment whose migration tooling enumerates TypeGraph's relations, or whose database role has restricted DDL, must account for both relations before upgrading. An unpublished namespace fork taken before the upgrade keeps its proof: a fork's content digest names a relation added after the first fork release only once that relation holds rows for the graph, so `forkGraphNamespace()` with the same operation key, and `abort()`, still verify a target the earlier release populated, including one whose database has not yet adopted the two relations.
- Restoring an archival export (`identityMode: "archival"`) whose source graph retains identity transitions or has ever pruned them now requires the restore target to be opened with `history: true`. `importGraph` and `importGraphStream` refuse such a document with `IDENTITY_REPLAY_REQUIRES_HISTORY` before writing anything, where they previously wrote the rest of it successfully.
- An archival interchange document's transition `decision` is validated strictly: `branchId`, `branchAncestry`, `mergePlanDigest`, `reviewDigest` and `sourceId` are the only members, and a document carrying any other is refused with a `ValidationError` before anything is written rather than restored with that member dropped.
