Reads now return a `Date` for a property whose schema output is a `Date`. The store persists a `z.date()` property as its ISO text, and every read handed that text back even though the property is typed `Date`. A read now decodes it wherever the output can only be a `Date`: a `z.date()`, a `z.coerce.date()`, or a pipe that ends in one (`z.string().pipe(z.coerce.date())`), inside `.optional()`, `.nullable()`, `.default()` and similar wrappers, a nested `z.object()`, a `z.array()` or a `z.record()`. This covers collection reads and the nodes and edges every write returns, query rows and selected fields, `.project()` and `asRelation().project()`, aggregates, `first()`, `paginate()` and `stream()`, traversals, `subgraph()` (whole and projected), `neighbors()`, search hits, `asOf()` and `asOfRecorded()` views, reads inside a transaction, and the nodes a graph merge hands to a kind's `block()` and to a `custom` similarity `score()`.

Every read decodes through one owner. Only the canonical text the store writes (`YYYY-MM-DDTHH:mm:ss.sssZ`, years 0001 to 9999) becomes a `Date`; any other value is returned exactly as stored. `.project()` and aggregates already returned a `Date` for a scalar date, but they turned any string or number into one, so non-canonical text became an `Invalid Date`. They now return such text as stored on SQLite. PostgreSQL extracts a selected field, a `.project()` scalar, `$scalar()`, `min`/`max`, a `groupBy()` date key and `expr.collect()` elements with a `timestamptz` cast, so there such text comes back as the `Date` the cast reads; that existing backend parity gap is documented in the parity matrix. A column the compiler cast to `timestamptz` decodes as an engine timestamp, not as stored text: the `Date` a driver returns, or the offset-bearing text a driver that does not parse `timestamptz` returns (postgres-js, `2024-06-15 18:19:56.789+05:45`), becomes the `Date` of that instant under every session `TimeZone`, including an offset to the second, which PostgreSQL renders for an instant before a zone adopted standard time (`+00:09:21` in `Europe/Paris` before 1891); the one timestamp canonicalizer every driver-timestamp reader shares now reads such an offset. Text without an offset is returned as is. A date the query states rather than reads, an `expr.literal()` or `expr.param()` date (or a `coalesce()`/`when()` of only those), comes back as the `Date` stated, even outside the years 0001 to 9999. Collected into `expr.collect()`, such a date is the canonical text it is bound as and is never cast, so a date PostgreSQL cannot represent as a `timestamptz` (year 0000) collects on both dialects. A `coalesce()` or `when()` of structured properties, and a `union()`, `unionAll()`, `intersect()` or `except()` of two relations, decode only the date positions every branch or operand types as a date; any other position is returned as stored, whichever operand comes first. A set-operation column the left operand carries no date facts for returns exactly what that operand returns, as before (a legacy aggregate's numeric group key stays the driver's text on PostgreSQL). A union of structured branches likewise decodes a position only when every branch types it as a date. `$scalar()` of an array property decodes its date positions as the property read does. A read applies no parse, transform or refinement, so a union with a date member, a tuple, a `z.lazy()`, the values of an object's `.catchall()`, and a `.transform()` (even one returning a `Date`) still read as stored. A recursive schema (a getter-recursive `z.object()`) is supported: its root positions decode, and a position reached again through the cycle reads as stored. A kind with no date position pays nothing on a read.

PostgreSQL rendered a date inside `expr.collect()` elements and records, and the date columns of a `.project()`, `$scalar()`, aggregate or relation read embedded in `batchOnce()`, as `timestamptz` text in the session `TimeZone` (`2024-12-31T16:00:00-08:00`). The compiler now emits those dates as canonical UTC text through a new `DialectAdapter.jsonDateText` member, so SQLite and PostgreSQL return the same `Date` whatever the session zone. Legacy stored text PostgreSQL casts to a BC date has no canonical text; there it is emitted as its era-bearing UTC text (`0001-06-01T00:00:00.000Z BC`), which reads as text, rather than as a CE instant.

The stored form is unchanged. `JSON.stringify` of a read, `exportGraph()` documents, pagination cursors and graph-merge plan props hold the same bytes as before. Graph merge still compares, fingerprints and keys committed props in their stored form.

### Upgrade notes

- Code that treated a date property read as a string breaks: `.slice()`, `.localeCompare()`, `startsWith()` and regular-expression tests throw a `TypeError`, `a.at === b.at` compares identity and is always `false`, `String(value)` and template literals give local-time text rather than ISO, and `Date.parse(value)` drops the milliseconds. Use `Date` methods (`getTime()`, `toISOString()`). `new Date(value)` workarounds, `<` and `>` between two values, `JSON.stringify` and `structuredClone` keep working.
- A `z.union()` with a date member, a tuple of dates, a `z.lazy()`, `.catchall(z.date())` values and a `.transform()` that returns a `Date` still read as stored text, and so does every position under the recursive field of a recursive schema. Declare `z.string().pipe(z.coerce.date())` instead of `z.string().transform((text) => new Date(text))` to read a `Date`.
- Stored text that is not the canonical form is still returned as text, never an `Invalid Date`. Run `validateStore()` to find it.
- On PostgreSQL, `expr.collect()` over a date, and `batchOnce()` of a projection or aggregate holding a date, return a `Date` under every session `TimeZone`. Before, a non-UTC session produced offset text that did not equal the read run alone.
- A custom `DialectAdapter` must implement `jsonDateText(value)`: return SQL that renders the date `value` as `YYYY-MM-DDTHH:mm:ss.sssZ` UTC text (the identity where dates are already stored as that text).
- A custom `DialectAdapter` must declare `jsonExtractDateOrigin`: `"engine"` when its `jsonExtractDate` casts to the engine's timestamp type, `undefined` when it returns the stored text. A scalar date result column read through that extraction decodes as an engine timestamp (a `Date` or offset-bearing text) or as stored text accordingly.
- With postgres-js, a selected date field (`select()`, prepared or paginated) now returns a `Date`; it returned the driver's `timestamptz` text before.
- A `z.record()` of dates and a `.transform()` date read back decoded, but an `update()` of another property on such a kind, and a `branch()` of a store holding one, still refuse the stored row with a `ValidationError`. Keep such properties on a kind you do not update.
- These still read as stored text: a position one union branch types through a `z.object()` and another through a `z.record()`; a selected field of a multi-kind alias whose kinds disagree on whether it is a date (selecting the whole alias decodes each row for its kind); and, on PostgreSQL, a late instant rendered with a five-digit year in a session zone east of UTC in a scalar projection. A set operation of an `expr.literal()` date and a stored date property is still rejected by PostgreSQL (`text` against `timestamptz`).
- Node and edge `meta` timestamps (`createdAt`, `validFrom` and the rest) are unchanged: they are still ISO strings.
- `PreparedQueryConfig` has an optional `registry` member: the kinds whose stored props a prepared query's rows decode. A config built without one reads props exactly as stored, in whole rows and in selected fields alike.
