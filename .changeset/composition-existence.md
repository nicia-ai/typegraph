`partOf` / `hasPart` gain `existence?: "optional" | "required"` (default `"optional"`, so every declaration written before this option keeps its semantics): `"required"` says a part of that kind can never exist without a live whole. `KindRegistry.compositionExistence(kind)` is the one reader every write path consults; two declarations disagreeing on `existence` for the same part kind refuse at registry build with `ONTOLOGY_COMPOSITION_EXISTENCE_MIXED` (R4 gives a part one whole across every relation, so "must this part have one" is a property of the part kind, not of a pair). `existence` is emitted only when `"required"` — an explicit `"optional"` serializes byte-identically to omitting it, so an untouched graph's schema hash is unchanged.

`NodeCollection.create`'s options are extracted into `NodeCreateOptions`, `bulkCreate`'s per-item options and `NodeGetOrCreateByConstraintOptions` gain `partOf?: { kind: string; id: string }`: the whole a part is attached to, in the SAME write plan as the node — a lost composition claim, a dead or missing whole, or an undeclared pair aborts the node create too, so no orphan row survives a failed attach. `partOf` naming an undeclared pair refuses with `ConfigurationError` (`COMPOSITION_WHOLE_NOT_DECLARED`); a required-existence kind created with no `partOf` refuses with the new `CompositionExistenceError` (`COMPOSITION_WHOLE_REQUIRED`, `situation: "create"`) before any row is written. `partOf` is honored as a convenience on an optional-existence pair too, in the same one write. `getOrCreateByConstraint`/`bulkGetOrCreateByConstraint` apply `partOf` on the `"created"` and `"resurrected"` branches (resurrection restores the whole alone) and refuse it on `"found"`/`"updated"` with `CompositionExistenceError` (`COMPOSITION_WHOLE_CONFLICT`, `situation: "existing"`, naming the node's current whole when it has a live one) rather than silently dropping a stated whole. Every fused/read-free node-create and edge-delete program declines a required-existence kind (or any input carrying `partOf`), so a required-existence bulk create or delete always takes the portable, fully-validated path.

Ending, soft-deleting, or hard-deleting a required-existence part's composition edge while the part is LIVE is refused with `CompositionExistenceError` (`COMPOSITION_DETACH_REFUSED`, `situation: "detach"`); a part that is already retired is not orphaned by losing its edge, so detaching from a soft- or hard-deleted part is allowed. Deleting the *whole* still cascades to its required parts exactly as before — `existence: "required"` governs bare creation and detachment, not whole deletion.

Validating import tracks every required-existence part it creates and, once the whole payload's node and edge sets are both known, accepts one already attached in the same batch or already live on the target and reports a per-row error (removing the orphaned node row in the same transaction) for anything still unattached — the rest of the import commits. Trusted import already refuses every declared composition pair regardless of `existence` (`composition_unsupported`), so there is no separate reason code for the required case.

`CompositionExistenceError.code` names the situation the refusal came from: `COMPOSITION_WHOLE_REQUIRED` (a bare create), `COMPOSITION_DETACH_REFUSED` (a refused detach), `COMPOSITION_WHOLE_CONFLICT` (a stated `partOf` contradicting the whole an existing node holds) and `COMPOSITION_PROPS_CONFLICT` (a stated `partOf.props` differing from the already-satisfied attachment's stored props). `details.situation` carries the same distinction and remains the discriminant for which of the optional detail fields are populated, so a handler may branch on either.

A batch create whose items carry `partOf` now does per-batch work where it used to do per-item work, with the same refusals: the whole rows are read once per kind (one `getNodes` per distinct whole kind rather than a probe per item), a part row is never re-read after the insert that wrote it, and the acyclicity relation is walked ONCE over every composition edge the batch inserted instead of once per attaching item. The combined walk is what makes a cycle running through two of the batch's own items visible at all; a cycle refusal names a concrete offending edge — the self-attaching item's own edge for a self-loop, and otherwise the first of the batch's edges that lies on the cycle, which for a cycle spanning several items can be a different item than a per-item probe would have blamed.

`store.verifyConstraintFences()` gains a `compositionExistence` family, reporting any LIVE required-existence part with no live whole; a schema commit newly declaring `existence: "required"` on an already-populated pair runs the same check as a tightening preflight and refuses a dirty graph rather than silently admitting orphans.

Graph merge's composition-orphan check gains a second arm for `existence: "required"`: alongside the existing check (a live part left behind when the merge deletes its whole node), it now also catches a required part this merge writes — or whose composition edge this merge explicitly deletes or ends — that resolves to no live whole at all, reported at plan time (`MergePlanCompositionOrphan.cause: "unattached"`) and refused at apply with the same `MergeCompositionOrphanError`. One residual gap remains: a composition edge silently dropped by canonicalization's own endpoint-deleted repointing, which issues no write for this (or any) per-write guard to see — run `store.verifyConstraintFences()` against a merged store to catch that case; see [Limitations](/limitations#composition-existence-existence-required).

### Breaking

- `CompositionExistenceError.code` is per situation (`COMPOSITION_WHOLE_REQUIRED`, `COMPOSITION_DETACH_REFUSED`, `COMPOSITION_WHOLE_CONFLICT`, `COMPOSITION_PROPS_CONFLICT`) rather than `COMPOSITION_WHOLE_REQUIRED` for every shape. Code matching on `code === "COMPOSITION_WHOLE_REQUIRED"` to catch any composition-existence refusal must match the class (or the four codes) instead; `details.situation` is unchanged.
- `CompositionPair` (internal to the registry; not part of the public entrypoint) gains a required `existence` field — anything constructing one directly, such as a test fixture, must add it.
- `ConstraintFenceViolation`'s union gains the `compositionExistence` member; an exhaustive `switch (violation.family)` outside the library needs a new arm.
- `MergePlanCompositionOrphan` gains a required `cause: "deleted" | "unattached"` field and its `whole` becomes optional (absent for `cause: "unattached"`, which has no whole to name); a consumer constructing or exhaustively matching this shape needs updating.
