A TypeGraph savepoint no longer rolls back an overlapping call's completed writes. Inside one `store.transaction()` callback, two calls started without awaiting each other (for example under `Promise.all`) shared one rollback boundary: when a call that guards its writes with a savepoint, such as edge `bulkHardDelete`, failed after its first delete and the callback caught the error and committed, the savepoint's rollback also undid the writes of a call that had overlapped it and already reported success. Calls through one transaction now take turns: each collection call, `tx.writeNodeUpsertBatch`, `tx.assertUnchangedSince`, `applyMergePlanInTransaction` and the provenance reads and assertions on a caller's transaction has the transaction session to itself from its first read to its return, so an overlapping call can neither roll it back nor change what it decided from (an edge delete's lookup, a merge apply's pending-write check, a savepoint's capture checkpoint). A call nested inside another runs inside it; a callback scheduled inside a call that runs after the call returned takes its own turn. Every binding of one database transaction shares the turns, including `store.withTransaction(tx.sql)` inside `store.transaction()`, and `withRecordedTransaction` / `withEvolvedTransaction` each run as one turn. `tx.requestRecordedRevision()` throws a `ConfigurationError` (`RECORDED_REVISION_REQUEST_OVERLAPS_CALL`) while another call on the transaction is in progress. On a backend without transaction-scoped statement execution, and on a runtime without `AsyncLocalStorage`, overlapping calls run as before.
