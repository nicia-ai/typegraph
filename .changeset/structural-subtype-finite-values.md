**The structural `subClassOf` / `equivalentTo` check now accepts a finite value set under a bounded parent.** A child pinned with `z.literal` or `z.enum` is judged value by value against the parent's length bounds, `regex()` pattern (and the patterns behind `startsWith()`, `endsWith()`, `includes()`, `lowercase()` and `uppercase()`), numeric bounds, `multipleOf()` and type, so `z.literal("x")` under `z.string().min(1)`, `z.enum(["a", "b"])` under `z.string().max(10)` and `z.literal(5)` under `z.int().min(0)` no longer fail registry build with `ONTOLOGY_SUBCLASS_NOT_STRUCTURAL_SUBTYPE`. A value is accepted only when both Zod and JSON Schema accept it: lengths are counted in code points and in UTF-16 units, patterns are tested with and without the `u` flag, and `multipleOf` is decided on exact decimals. Standard formats such as `z.email()` are still not judged by value. A record's key set now compares as a subtype instead of requiring identical `propertyNames`, so `z.record(z.enum(["a", "b"]), V)` extends `z.record(z.string(), V)`. The check accepts strictly more valid hierarchies; nothing it accepted before is refused. A record whose key schemas are two different `$ref` definitions now reports `incomparable` (`schema-reference`) instead of `not-subtype` (`property-names-mismatch`), the same as every other unresolved reference pair.
