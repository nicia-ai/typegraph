`store.transaction()` no longer reports success on PostgreSQL when the database rolled the transaction back, whatever caused the rollback, and no longer retries a transaction whose callback was handed a raw-SQL port.

On PostgreSQL, a statement that fails inside a transaction aborts the whole transaction, even when the callback catches the error, and even when the client never sees the failure: with a node-postgres `query_timeout`, the driver gives up on a statement on the client while the server is still running it, and the statement can then fail on the server with nobody listening. The database answers the closing `COMMIT` of an aborted transaction with `ROLLBACK` instead of `COMMIT`, and node-postgres, neon-serverless and PGlite resolved that as a success: `store.transaction()` resolved although nothing the transaction wrote was saved. On postgres-js the transaction rejected, but with the raw driver error.

**What TypeGraph guarantees.** A transaction a bundled PostgreSQL backend opened never reports success after the database rolled it back. TypeGraph reads the database's reply to the `COMMIT` that ends the transaction: the command tag of Drizzle's `commit` on node-postgres and neon-serverless, the `COMMIT`'s `CommandComplete` message on PGlite. A `ROLLBACK` reply rejects with the new `TransactionRolledBackError` (code `TRANSACTION_ROLLED_BACK`). postgres-js does not expose that reply; it refuses to commit a transaction in which a statement failed and rolls back instead, which is reported as the same error. Work TypeGraph does after the callback returns, such as a history store's capture flush, can meet the aborted transaction first; the refusal (`25P02`) is reported as the same error and never escapes raw. `details.detectedBy` says which of the three it was (`"commit-reply"`, `"refused-statement"`, `"driver"`). `cause` is the first error the database reported in the transaction; when no database error reached the client, there is none and `details.causeObserved` is `false`. `details.conflict` is `true` when any of those errors was a serialization failure or deadlock, and `retry: { attempts }` then re-runs the callback. A deferred constraint that fails at `COMMIT` rejects with its own error, as before.

**What it costs.** Nothing on a clean transaction: it sends exactly `BEGIN`, its own statements and `COMMIT`, as before, and TypeGraph reads the reply the driver already received.

**What is unsupported.** Transaction control (`COMMIT`, `COMMIT AND CHAIN`, `ROLLBACK`, `BEGIN`) sent through any raw-SQL port inside a transaction TypeGraph opened: `tx.sql`, the native handle of a `transactionWithNative` callback, `executeRaw`, `execute` or `executeStatement` on a transaction backend, or `executeSchemaDdl` in a schema write. It can end or replace the transaction in ways that cannot be fully detected. As a defence for the known routes, when `tx.sql` is read, a `transactionWithNative` callback receives the native handle, or a schema preflight or `schemaWriteTransaction` callback is handed `executeSchemaDdl`, TypeGraph hands the driver a transaction-local marker (`SET LOCAL typegraph.transaction_marker`, which takes no snapshot) whose value it generates for the attempt, and reads it back before `COMMIT`. The transaction commits only when the marker is found and the `COMMIT` commits. Otherwise it rejects with the new `TransactionOutcomeUnknownError` (code `TRANSACTION_OUTCOME_UNKNOWN`): `details.reason` is `"transaction-ended"` when the marker was gone (TypeGraph then sends no `COMMIT`), and `"native-handle-released"` when the transaction was aborted or a serialization failure or deadlock rejected the callback or the `COMMIT`, with that failure as `cause`. Any other error the callback throws rejects unchanged. This costs one statement when the port is handed out and one before `COMMIT`. A callback that deliberately carries the marker into a transaction of its own defeats it; that is outside the supported contract.

**Retry change.** An attempt that was handed a raw-SQL port is never retried automatically, `retry: { attempts }` included, even when it hits a serialization failure or deadlock: re-running a callback that may have committed through the port could write twice. It rejects on the first attempt with `TransactionOutcomeUnknownError`, `details.reason` `"native-handle-released"`, and the conflict (SQLSTATE `40001` or `40P01`) as its `cause`. This now also applies to `schemaWriteTransaction` callbacks, whose `executeSchemaDdl` forwards any SQL text. A callback that never sends transaction control through the port can catch that error and re-run the transaction itself, as the transactions guide shows. Transactions that are never handed such a port are retried as before.

The evidence a backend uses is declared as `capabilities.execution.commitOutcome`: `"commit-reply"` on the bundled PostgreSQL backends, `"statement-scoped"` on SQLite, which keeps a transaction usable after a failed statement and commits as before. A backend built over a transaction handle opens savepoints, not transactions, and declares none. A custom backend that declares none behaves exactly as before. Transactions you open yourself and adopt with `store.withTransaction()` are committed by your code and are not checked.

A rejection does not always mean nothing was saved: `onOperationEnd` and `onBulkOperationEnd` run after the `COMMIT`, so an error one of them throws rejects a transaction whose writes are saved. That rejection is not a rollback.
