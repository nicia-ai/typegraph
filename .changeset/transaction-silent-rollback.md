`store.transaction()` no longer reports success on PostgreSQL when the database rolled the transaction back, no longer commits a transaction the callback ended itself, and no longer retries a transaction whose callback read `tx.sql`.

On PostgreSQL, a statement that fails inside a transaction aborts the whole transaction, even when the callback catches the error. A callback that, say, caught the duplicate-key error from creating an edge with an existing id and then returned normally used to see `store.transaction()` resolve on node-postgres and PGlite, although the database had answered the `COMMIT` with a rollback and nothing the transaction wrote, before or after the failure, was saved. On postgres-js the transaction rejected, but with the raw driver error.

Before it sends `COMMIT`, a bundled PostgreSQL backend now checks the transaction it opened, and the check costs nothing when nothing went wrong: a transaction in which no statement failed and whose native handle (`tx.sql`) was never read sends exactly the statements it sent before, `BEGIN`, the callback's statements and `COMMIT`. TypeGraph observes every statement the transaction sends.

- **The native handle was never read.** When a statement failed, TypeGraph probes the session once before `COMMIT`. Answered (a savepoint rolled back past the failure): the transaction commits. Refused because the transaction is aborted: it rejects with the new `TransactionRolledBackError` (code `TRANSACTION_ROLLED_BACK`). Its `cause` is the first error the database reported during the transaction; an error the driver raised without sending the statement is never the cause. `details.conflict` is `true` when any of those errors was a serialization failure or deadlock, and `retry: { attempts }` then re-runs the callback.
- **The native handle was read.** Through `tx.sql` the callback can end the transaction TypeGraph opened (`COMMIT`, `COMMIT AND CHAIN`, `ROLLBACK`) and begin another, which TypeGraph cannot tell apart once a transaction is aborted. Reading `tx.sql` first hands the driver a transaction-local marker (`SET LOCAL typegraph.transaction_marker`) whose value TypeGraph generates for the attempt, ahead of anything the callback sends through the handle, and TypeGraph reads it back before `COMMIT`. The transaction commits only when the marker is found and the `COMMIT` succeeds. Anything else rejects with the new `TransactionOutcomeUnknownError` (code `TRANSACTION_OUTCOME_UNKNOWN`): `details.reason` is `"transaction-ended"` when the marker was gone (TypeGraph then sends no `COMMIT`), and `"native-handle-released"` when the transaction was aborted or a serialization failure or deadlock rejected the callback or the `COMMIT`, with that failure as `cause`. Any other error the callback throws rejects unchanged, as before. This costs one statement when `tx.sql` is first read and one before `COMMIT`. `SET` takes no snapshot, so a `REPEATABLE READ` or `SERIALIZABLE` transaction still takes its snapshot at the callback's first statement. A `transactionWithNative` callback receives the native handle, and a schema preflight's `executeSchemaDdl` forwards any SQL text, so both count as reading it.

**Retry change.** A transaction whose callback reads `tx.sql` and then hits a serialization failure or deadlock is no longer retried by `retry: { attempts }`, whether the callback caught the conflict or let it propagate: re-running a callback that may have committed through the handle could write twice. It rejects on the first attempt with `TransactionOutcomeUnknownError`, `details.reason` `"native-handle-released"`, and the conflict (SQLSTATE `40001` or `40P01`) as its `cause`; the error is never classified as a conflict. A callback that never sends transaction control through `tx.sql` can catch that error and re-run the transaction itself, as the transactions guide shows. Transactions that never read `tx.sql` are retried as before.

This covers `store.transaction()`, `store.transactionWithReceipt()` and TypeGraph's own schema-write transactions, including a schema change whose data preflight caught a failed statement, whichever statement failed: a write, a read, or a statement on `tx.sql`. The check runs before a history store's capture flush, so no receipt is returned for a rejected transaction. When TypeGraph rolls back one of its own savepoints that the marker landed in, it sets the marker again, so a healthy transaction still commits. The marker is found when the Store and the adapter come from two copies of the package.

The evidence a backend uses is declared as `capabilities.execution.commitOutcome`: `"session-marker"` on the bundled PostgreSQL backends, `"statement-scoped"` on SQLite, which keeps a transaction usable after a failed statement and commits as before. A backend built over a transaction handle opens savepoints, not transactions, and declares none. A custom backend that declares none behaves exactly as before. Transactions you open yourself and adopt with `store.withTransaction()` are committed by your code and are not checked.

A rejection does not always mean nothing was saved: `onOperationEnd` and `onBulkOperationEnd` run after the `COMMIT`, so an error one of them throws rejects a transaction whose writes are saved. That rejection is not a rollback.
