A partial update no longer fails on a kind with a `z.date()` property it does not touch (#851). The store writes a `Date` as its ISO-8601 text, and every update parses the stored properties merged with its patch through the kind's schema, so `z.date()` was handed the stored text and refused it: `update()`, `upsertById()`, the `ifExists: "update"` forms of `getOrCreateByConstraint()` and `getOrCreateByEndpoints()`, their bulk forms, `updateWhere()`, `compareAndSet()` and an edge `update()` that only ends its window all threw `ValidationError` unless the date was restated. A `z.date().catch(fallback)` property did not throw: every update silently replaced its stored date with the fallback. `validateStore()` reported every stored date as a violation.

Stored props are now passed through one function before they are parsed again, which turns stored date text back into a `Date` where the schema accepts only a `Date`: a `z.date()` reached through `.optional()`, `.nullable()`, `.default()`, `.prefault()`, `.catch()`, `.readonly()` and `.nonoptional()`, a nested `z.object()` or a `z.array()`, and only when the text is the canonical form the store writes. Nothing else about validation changes: a value under a union, record, tuple, lazy schema or `.transform()` is parsed as stored, and a value a caller states is never converted, so a date stated as a string is still refused. Reads are unchanged and still return the stored ISO text. Importing an exported graph and merge plans still pass stored date text to the schema as input and still refuse it.
