Date operands in membership, JSON-path and subquery positions now pass the same canonical-date check as every other date predicate, before any SQL runs, so they compare the same way on every backend.

- `expr.arrayContains` on a date array checks its element, whether a literal, a `param()` binding, or one a `coalesce` or `when` forwards. A short form of a stored instant such as `"2024-01-01T00:00:00Z"` bound to `expr.param("at", "date")` previously matched on PostgreSQL, which re-renders the operand, and not on SQLite; a year-0000 operand failed PostgreSQL's cast. Both now throw `UnsupportedPredicateError`.
- The predicate builder's `contains`, `containsAll` and `containsAny` on a date array, `pathContains` on a date-array JSON path, and `pathEquals` on a date JSON path take a `Date` or a canonical string and refuse anything else with `UnsupportedPredicateError`. `pathEquals` compared a date path as a `timestamptz` on PostgreSQL and as text on SQLite, so a non-canonical string matched different rows; the array forms compared text on both and silently matched nothing. The `contains`, `containsAll` and `containsAny` signatures of a date array now accept a `string` element as well as a `Date`.
- A date a `$scalar()` subquery or an `inSubquery` / `notInSubquery` subquery projects, as a literal or a binding, is checked against the property it is compared with. When the `inSubquery` / `notInSubquery` field reference states no value type, the check uses the date type the subquery projects, the type the comparison compiles as. On PostgreSQL a projected literal or parameter compared with a date is now typed `timestamptz`: it was `text`, so comparing a date property with `$scalar(… project({ cutoff: expr.param("from", "date") }) …)`, or testing it `IN` such a subquery, failed with `operator does not exist: timestamp with time zone >= text` even for a canonical value, while SQLite returned rows. The comparison now runs and returns the same rows on every backend. A date a query only projects is not typed, so it projects as before.

`DialectAdapter` has a new required member, `dateValue`, which types a value compared with a date as the dialect's date type where the engine cannot infer it: identity on SQLite, `CAST(… AS timestamptz)` on PostgreSQL. A custom dialect adapter must implement it.
