"@nicia-ai/typegraph": minor

A write over an existing row no longer runs the schema's rewriting steps again on properties you did not state. This affects kinds whose schema has a non-idempotent `.transform()`, a rewriting `.overwrite()`, a `.catch()` fallback, or a transform that changes the type. Every such write still validates the whole row it leaves (the properties you state merged over the stored ones, parsed through the complete schema, so constraints, refinements and cross-field checks see every property and a newly added `.default()` is filled), but it now stores each property you did not state exactly as it was stored, and each property you did state as the schema makes it, exactly as a create stores it. Before, the parse's output was stored for every property: with `z.string().transform((v) => v + "!")` a create stored `"x!"` and an `update()` of another property stored `"x!!"`; an `.overwrite()` on a wrapper around a date shifted the stored date on every update; and a `.catch()` replaced a stored value it refused with its fallback. This applies to `update()`, `upsertById()`, `getOrCreateByConstraint()` and `getOrCreateByEndpoints()` with `ifExists: "update"`, the bulk forms of each, `updateWhere()`, `compareAndSet()`, an edge `update()` that only states `validTo`, and `reparent`. A property is stated when its top-level key is in what you pass, whatever its value (`undefined` removes an optional property or fills its default); a nested object or array is one property; a value an object-level `.overwrite()` derives from other properties is recomputed only when you state it.

A stored key the schema does not declare is now kept by an update rather than stripped. Under a `.strict()` schema the update is refused instead.

An update that does not state a property whose stored value is not valid input to its own schema (the number a `z.string().transform((v) => v.length)` produced, a value a tightened constraint refuses, an undeclared key under `.strict()`) is refused with a `ValidationError` whose issue carries the new code `STORED_PROPERTY_INVALID` (`STORED_PROPERTY_INVALID_CODE`, exported from `@nicia-ai/typegraph/errors`) and names the property, rather than with a generic Zod issue. Such updates were refused before as well. The same code refuses an update when the schema rewrites a property it does not state and the object has its own `.refine()` or `.superRefine()`, since the refinement would check the rewritten value while the row keeps the stored one; state the property to update the row. An `updateWhere()` or `compareAndSet()` over a row that lacks a property with a newly added `.default()` is still refused (the statement writes only the patch), while `update()` fills the default.

`getOrCreateByConstraint()` and `getOrCreateByEndpoints()` (and their bulk forms) no longer parse the properties you state twice. Their update leg ran the create parse's output through the schema again, so a non-idempotent transform was applied twice to a stated value, and `getOrCreateByEndpoints()` did the same when it created the edge. Their update leg now also keeps a property you did not state as stored, rather than resetting it to its `.default()` or `.catch()` value.

`importGraph()` stores each row's properties as the document carries them, after validating the whole row through the kind's schema, under every `onUnknownProperty` strategy and for both a new row and `onConflict: "update"`. A transform, `.overwrite()` or `.catch()` no longer rewrites an exported value on re-import, so an export/import round trip keeps every byte; a property the document lacks is filled as the schema makes it, and a value whose JSON type the schema changes (the text `"7"` for a `z.coerce.number()`) is stored as parsed, since no store wrote it. Under `onUnknownProperty: "allow"` a document carrying unknown properties used to be persisted verbatim, with no `.default()` filled, while one without them was normalized; both are now validated and stored by this rule, the unknown properties kept. A graph merge's apply (`applyMergePlan()`, `merge()`, `mergeIncremental()`) writes the branch's rows the same way. As a result, a mutation plan whose postimage has a non-idempotent transform now plans and applies instead of being refused with `stableMergePostimage` (a postimage the target's schema does not accept still is), and `mergeIncremental()` no longer refuses a base update over a committed row holding keys the active schema does not declare: it keeps them.

On PostgreSQL, an object-valued unique property imported under `onUnknownProperty: "allow"` now claims the same key a create of the same value claims, so the duplicate is refused. JSONB returns an object's keys in its own order, and the import stored that order verbatim, so the claim keys differed and two rows could hold one unique value. An unchanged value is now stored in the schema's key order on every re-validating write.
