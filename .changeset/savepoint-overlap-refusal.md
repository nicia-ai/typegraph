A call that overlaps another call's TypeGraph savepoint inside one `store.transaction()` is now refused instead of being silently rolled back with it. Node and edge `bulkHardDelete`, an interchange import into the transaction and `applyMergePlanInTransaction` run their writes behind a savepoint, and rolling back to a savepoint undoes every statement issued on the transaction since it was taken, whoever issued it. So when a sibling started without awaiting such a call (`Promise.all`) wrote while the savepoint was open, and the batch call's failure was caught and the transaction committed, the sibling's writes disappeared although the sibling had reported success. This happened on SQLite, libSQL, PGlite, node-postgres and postgres-js. While such a savepoint is open, every statement TypeGraph would issue on the same native transaction from outside the call that opened it, reads included, and also an attempt to open a second savepoint beside it, is now refused with the new `SavepointScopeConflictError` (code `SAVEPOINT_SCOPE_CONFLICT`, exported from `@nicia-ai/typegraph/errors`). The error is thrown before anything is sent to the driver, so the transaction stays usable. Its `details.holder` names the call holding the savepoint and `details.refused` names what was refused. This is an error callers can now see: code that overlapped a batch call with other work on the same transaction must await the batch call first. Work started from inside the call, including nested savepoints, is unaffected. A second binding of the same native transaction, through `store.withTransaction(tx.sql)`, is refused like the first. "Inside" is read from the async call graph through `AsyncLocalStorage`; a runtime without it, a custom backend, and a transaction without statement execution (which takes no savepoint) behave as before. Statements issued directly on `tx.sql` cannot be checked.
