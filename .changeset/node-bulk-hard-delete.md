Add `bulkHardDelete(ids)` to node collections: permanent removal of many nodes of one kind in one call. It leaves exactly the state that calling `hardDelete(id)` once per id, in first-occurrence order, inside one transaction leaves — each node goes with its uniqueness, fulltext and embedding rows and every connected edge (live or soft-deleted, any edge kind), its `onDelete` behavior applies against the graph the earlier ids' deletes leave, a composition whole's parts are deleted with it, its Operational Identity assertions are detached, absent ids, ids present only under another node kind and repeated ids are ignored, and a history store records no delete row — and it fails with the refusal that loop would reach first, with nothing deleted, because every node is judged before the first row is removed.

Plain nodes are removed set-wise: a node whose delete cascades to no composition parts, and that no identity assertion or identity class names, costs no statement of its own, so 10 and 1,000 of them issue the same statements apart from extra bind-budget chunks. A composition whole with parts and an identity participant take the same path as `hardDelete()`, inside the same transaction, and cost what it costs. The fast path uses two new optional backend ports, `hardDeleteNodesBatch` (removes one kind's rows with their uniqueness, fulltext and incident edge rows and reports exactly the node and edge ids it removed) and `findEdgesConnectedToNodes` (a kind-blind read of the live edges connected to a set of one kind's nodes); a backend without them falls back to one `hardDeleteNode` and one `findEdgesConnectedTo` per node, decided before any statement runs.

On its own the call is one write transaction; inside `store.transaction()` its writes run behind a savepoint, so a failure among them that the callback catches leaves none of them committed. On a raw store over a driver without interactive transactions (Cloudflare D1, `drizzle-orm/neon-http`) the statements are separate and a later statement's failure leaves the earlier ones applied, although every refusal still comes before the first delete; a schema-managed store on those drivers refuses the call before it writes. Like every batch method it fires no operation hooks, it counts one write intent per input id in transaction receipts, and it is refused on read-only views.
