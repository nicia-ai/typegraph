"@nicia-ai/typegraph": minor

The public custom `metaEdge()` factory, the public `InferenceType` union, and the deprecated `sameAs`/`differentFrom` type-level factories are removed. None of them ever drove runtime behavior beyond serialized introspection metadata: every closure and write-path decision for a meta-edge is made per literal name, never read off a `MetaEdge`'s properties. Free-form, type-level vocabulary the library has no built-in reasoning for now belongs in `defineGraph({ annotations })` — see [Type-Level Annotations](https://typegraph.dev/ontology#type-level-annotations) and `examples/08-custom-ontology.ts` for a complete example. Replace `sameAs(A, B)` with `equivalentTo(A, B)` (behaviorally identical in every release `sameAs` shipped in); delete `differentFrom(A, B)` calls (it was decorative and never enforced) or, for real cross-kind instance identity, use the TypeGraph Identity Profile (`identity: { sameIdAcrossKinds: "fold" }` and `store.identity`). The serialized schema document drops `metaEdges[*].transitive`/`symmetric`/`reflexive`/`inverse`/`inference` on the next write that a real ontology change triggers — `SerializedMetaEdge` now carries only `name`/`description` — and the deserializer's Zod validator no longer requires these fields, so a document written before this release keeps loading and its extra fields are ignored. Upgrading the library alone does not rewrite a stored document: `ensureSchema` only writes a new version when it detects a semantic change, so a graph whose ontology is otherwise untouched keeps its pre-removal document and its stored `schema_hash` until its next real schema change lands. That stored hash no longer matches the hash this release computes for the same graph, so every comparison of a stored schema version against a graph, or against another stored version, now hashes the stored document in this release's serialization instead of reading the `schema_hash` column: the dropped meta-edge fields are ignored and the precomputed closures are recomputed from the stored relations. Boot (`ensureSchema`, `createVerifiedStore`), `registerGraphTemplate`, `refreshSchema`, `planEvolution`, `branch()`, graph merge plans and candidate reviews, and the provenance sidecar ownership check therefore all treat such a document as current. The same holds for a graph template an earlier release registered and a target graph it instantiated: registering the template again and instantiating onto that target judge the stored document, so both succeed for an unchanged schema without rewriting either row, and a template registered with different content is still refused (`GRAPH_TEMPLATE_CONTENT_CONFLICT`). The handle `registerGraphTemplate` returns carries the new optional `registryHash`, the hash the registry stores the template under, which instantiation binds; it differs from `schemaHash` only for a template an earlier release registered, and a handle without it binds `schemaHash` as before. The document is parsed and hashed once per process; the `schema_hash` column stays the writing release's record and is never rewritten. A persisted `sameAs` relation keeps folding into the equivalence closure exactly like `equivalentTo`; a persisted `differentFrom` relation keeps being inert. A relation naming a custom `metaEdge()` you called before this release is different: since the factory that declared it is gone, your upgraded graph can no longer serialize that relation at all, so the first commit `ensureSchema` makes after upgrading auto-migrates it away — classified `safe` (a custom name reaches no closure or write-path decision) and dropped from the rewritten document with no opt-in. Copy anything you need from that relation into `annotations` **before** upgrading; see the migration guide linked below. The `OntologyChange` union's `entity` field narrows from `"metaEdge" | "relation"` to `"relation" | "edgeRegistration"`: a meta-edge name leaving the serialized `metaEdges` catalog is always a consequence of its last relation being removed or added, never an independent event, and `"edgeRegistration"` classifies an edge kind's own registration: its `acyclic` flag, or a narrowed `from`/`to` declaration. Graph extensions continue to refuse a `metaEdge` name outside the closed core set — nothing in this change reopens that.

**Rolling deploys and rollback.** The new serializer output is a one-way door: a document written by a `@nicia-ai/typegraph` release with this change (only after that document's next real schema commit — see above) cannot be parsed by an earlier release, because the pre-change `serializedSchemaZod` required `transitive`/`symmetric`/`reflexive`/`inference` on every `ontology.metaEdges` entry. Upgrade every reader of a shared database (every application instance, in a mixed-version fleet) to this release or later before any of them commits a schema change, and do not roll back to a pre-change release once one has — an older instance's `parseSerializedSchema` throws on the rewritten document instead of degrading.

See [Upgrading past the removed `sameAs`/`differentFrom`/`metaEdge()` APIs](https://typegraph.dev/schema-evolution#upgrading-past-the-removed-sameasdifferentfrommetaedge-apis) for the complete migration guide.

### Breaking

- Removed: `metaEdge()` and `MetaEdgeOptions` (`@nicia-ai/typegraph`, `@nicia-ai/typegraph/core`).
- Removed: the public `InferenceType` union (`@nicia-ai/typegraph`, `@nicia-ai/typegraph/backend`).
- Removed: `MetaEdgeProperties.transitive`, `.symmetric`, `.reflexive`, `.inverse`, and `.inference` — `MetaEdgeProperties` now carries only `description`.
- Removed: the deprecated `sameAs()` and `differentFrom()` relation factories (`@nicia-ai/typegraph`), and the matching `core.sameAs` / `core.differentFrom` members of the exported `core` object. The `sameAs`/`differentFrom` meta-edge NAMES are still recognized when they appear in a persisted document or a declarative graph extension — only the factory functions that construct them from code, and the `core.sameAsMetaEdge` / `core.differentFromMetaEdge` objects, are gone; `core` no longer carries any way to construct a relation naming either.
- Changed: `store.reconciledSchema.hash`, `store.introspect().schemaHash`, evolution-plan baselines, merge plan schema anchors, and transaction receipts report the hash of the stored schema document as this release serializes it, not the stored `schema_hash` column. For a version written by this release the two are equal; for a version an earlier release wrote for a graph declaring ontology relations they differ, so code that compares one of these values against `schema_hash` read from `typegraph_schema_versions` directly must compare against the recomputed value instead.
- Changed: `SerializedMetaEdge` narrows to `{ name, description }`, dropping `transitive`/`symmetric`/`reflexive`/`inverse`/`inference`. This document shape is a one-way door — see "Rolling deploys and rollback" above.
- Changed: `OntologyChange["entity"]` narrows from `"metaEdge" | "relation"` to `"relation" | "edgeRegistration"`. Code that matched on `entity === "metaEdge"` no longer has a case to match. `"relation"` is the relation-level severity table. `"edgeRegistration"` classifies an edge kind's `acyclic` flag turning on or off, and an edge kind's `from`/`to` declaration narrowing so it no longer admits endpoint pairs it did — those are edge-registration properties, not ontology relations, and a switch written from the old `"relation"`-only note does not compile.
- Changed (backend authors): `GraphBackend.registerGraphTemplate` returns the row stored under the template id and no longer refuses a row with a different hash itself; `registerGraphTemplate` judges the stored row and raises `GRAPH_TEMPLATE_CONTENT_CONFLICT`. A custom member that still refuses a differing hash keeps refusing a template an earlier release registered.
