`paginate()`, `page()` (alone and in `store.batchOnce()`) and `stream()` on a full-text, vector or hybrid query now read every row `execute()` returns exactly once, in `execute()`'s order, forward and backward. Before, the keyset cursor held only the `orderBy()` values and the row id and ignored the relevance keys that lead the query's ORDER BY. A page boundary then repeated rows and dropped others whenever relevance and `orderBy()` disagreed. The cursor was also applied to the candidates the search ranks, so every later page took a different top `k` and could return rows `execute()` never selects.

A search's cursor now carries the boundary row's relevance values as the database rendered them, so equal and nearly equal scores compare exactly. On PostgreSQL a rank or distance is carried, sorted and compared as `double precision`, and a fused hybrid score as the `numeric` it is computed in, which holds every score valid `fuseWith()` options produce (weights near `Number.MAX_VALUE` exceed a double). On SQLite every key is a REAL carried as its exact binary text (an integer significand and a power of two, computed with exact REAL arithmetic, since SQLite promises no decimal rendering that reads back as the same double), and an infinite L2 distance or fused score is carried as `Inf` / `-Inf` and compared as that infinity, so pagination reaches every row `execute()` returns. The hybrid node-id tiebreak is always compared as text, so an id such as `Inf` or `-Inf` is never read as an infinity. A NULL relevance value sorts after every value on every dialect and is carried as NULL. It is applied to the completed match rows after the search has taken its top `k`, so every page ranks the same candidates as `execute()`. An `orderBy()` is no longer required to page or stream a search, which is ordered by relevance. Rows tied on relevance and every `orderBy()` term now come in row-identity order (start node id, kind for a multi-kind alias, each traversal's edge id) in `execute()` and on every terminal, and every top-`k` cut breaks ties by node kind, then node id, both in byte order whatever the database's collation, as `store.search` does (an id is unique only within its kind, so a search whose alias spans several kinds can tie two nodes with one id), inside the engine's own search where the engine takes an order, so which tied match makes the top `k` is the same on every execution.

A page that does not advance past the cursor it was asked with is refused with a `CompilerInvariantError` instead of being returned, so following cursors never repeats a page forever and `stream()` always ends, on every query.

Each page runs the search again. Without writes between pages the walk is exact. Writes between pages give a weaker guarantee than keyset paging of a query without a search where a score depends on other rows (SQLite's BM25, a hybrid score): unchanged rows can then cross a page boundary.

A cursor that cannot position a search is refused with a `ValidationError` whose issue code is `SEARCH_CURSOR_MISMATCH`: one issued for another search (query text, embedding, `k`, minimum score, metric, approximate retrieval or fusion, recorded as a 128-bit digest), for a query without a search, or by another backend dialect, one whose relevance value the backend does not render or its key type cannot hold, and any search query's cursor issued before this release, since those were positioned wrongly. A query keeps the embedding passed to `similarTo()` and the options passed to `fuseWith()` as they were when it was built, so mutating the caller's array or object afterwards changes neither its rows nor its cursors. Restart such a walk without a cursor. Cursors of queries without a search are unchanged, byte for byte.

An approximate search on libSQL's DiskANN, whose `execute()` can return different neighbors on an unchanged database, cannot be paged: `paginate()`, `page()` and `stream()` refuse it with an `UnsupportedBackendCapabilityError` on `vector.repeatableApproximateSearch`. Two further refusals are typed `ConfigurationError`s. `GROUPED_SEARCH_PAGINATION_UNSUPPORTED` is raised when paging a search whose rows are groups (`groupByNode()`), which used to fail with an internal error. `SEARCH_CURSOR_KEY_UNAVAILABLE` is raised when PostgreSQL cannot render a relevance key exactly because the session's `extra_float_digits` is below 1. Cursor encoding also no longer throws on ids or sort values outside Latin-1: such characters are written as JSON escapes, and every cursor that encoded before keeps its bytes.
