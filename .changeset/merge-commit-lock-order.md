Fix a lock-order inversion in the graph-merge commit that could deadlock against a concurrent schema commit on PostgreSQL. A `merge()` into a target without `history` or `revisionTracking` took the per-graph write lock before the schema-version fence whenever the plan deleted a composition whole or part, or attached a composition part. A schema commit of an identity-enabled graph takes the same two locks in the opposite order: it locks the schema row, then the graph lock. When the two interleaved, PostgreSQL detected the deadlock after `deadlock_timeout` (1 s by default) and aborted one side. In the observed case the schema commit (`createStoreWithSchema` with an evolved graph) failed with `TransactionConflictError` caused by SQLSTATE `40P01`, and the merge committed. The `merge()` commit now takes the schema-version fence as the first statement of its transaction, through the store's shared write-fence prelude and the same call `mergeIncremental()` now makes. It also takes the graph lock there when the target's writers all take it or the base version is revision-anchored. Every later graph-lock acquisition in the apply happens after the schema fence. `mergeIncremental()`, `applyMergePlan()`, `applyMergePlanInTransaction()`, and merges into history or revision-tracked targets already took the fences in this order and are unchanged. Behavior change: because the fence now runs before the commit's first read, a `merge()` through a target handle whose schema another handle has since advanced is refused immediately as `BaseVersionMismatchError` (with the `StaleVersionError` as its `cause`) and writes nothing. Previously it failed later in the commit as a generic `MergeError` ("Merge failed while staging or committing"). Neither error is retried by the merge commit's retry loop, which retries only serialization failures and deadlocks. Re-open the store against the current schema, then branch and merge again.
