---
"@nicia-ai/typegraph": patch
---

A `Date` for a `z.date()` property is now accepted in an `updateWhere()` or `compareAndSet()` patch and stored as the same ISO text `create()` and `update()` store, at any depth of a nested object or array. Both refused it with `ConfigurationError` ("contains a non-JSON value (Date instance)"), and since a date property also refuses its ISO text, a set update could not write one at all. A set update refuses, with a `ValidationError`, a `Date` at a position whose schema would read its stored text back as something other than that `Date` (under a union, a record or `z.any()`): the row would hold a string, and under a unique constraint `z.union([z.date(), z.string()])` it let two rows hold the same instant. Text you state for a date property is still refused.

A `compareAndSet()` `expected` value may now be a `Date` (and `CompareAndSetExpected` admits one). It matches the stored text of the instant you state. An expectation is a comparison, not a write, so only its type is checked (a storable `Date` at a position the store reads back as a `Date`); it is not parsed through the property's schema, whose transforms or `.overwrite()` would otherwise compare a different instant than the one stated.

Every write now stores, and every comparison binds, the instant a `Date` holds, read from the `Date` itself rather than through a `toJSON()` or `toISOString()` the object carries (an own property or a subclass). Before, such a `Date` was stored as whatever its serializer returned on `create()`, `update()`, the upserts and bulk writes, edge writes, `importGraph()` and `trustedImportGraph()` of an in-memory document, and a set-update patch; a uniqueness constraint, an endpoint match (`getOrCreateByEndpoints()` with `matchOn`), a `bulkFindByIndex()` probe and a `compareAndSet()` expectation keyed or matched that other instant; and a date predicate compared it. The built-in backends encode a `Date` where it becomes stored text, so `validateProps()` returns the schema's own output unchanged.

`importGraph()` now accepts the stored date text `exportGraph()` writes. Import parsed each row as create input, where `z.date()` refuses a string, so every row of a kind with a date property was reported as an error and the round trip lost it. Import now turns that text back into a `Date` before parsing, by the same rule an update applies to a stored row: only canonical ISO text (`YYYY-MM-DDTHH:mm:ss.sssZ`, years 0001 to 9999), only where the schema accepts nothing but a `Date` (including inside `.optional()` and similar wrappers, a nested `z.object()` or a `z.array()`). Other text still refuses the row. Under `onUnknownProperty: "allow"` the stored bytes are unchanged and a uniqueness constraint over a date property claims the same key the store's own writes claim.

A graph merge now applies dated rows. Merge plans carry each row's properties in their stored form, so `applyMergePlan()` refused a plan `planMerge()` had just returned for a branch that added or edited a node or edge with a `z.date()` property, `merge()` failed while committing it, and candidate write sets and mutation plans planned what apply refused. Every merge apply path now turns stored date text back into a `Date` by the rule updates use before it validates and writes.

The `ConfigurationError` for a value that is not JSON, such as a `Map` in a set-update patch or in a durable operation document, no longer says "Annotations must be JSON-serializable" when no annotation is involved; it names the value and the JSON types allowed.
