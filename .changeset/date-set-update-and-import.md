---
"@nicia-ai/typegraph": patch
---

A `Date` for a `z.date()` property is now accepted in an `updateWhere()` or `compareAndSet()` patch and stored as the same ISO text `create()` and `update()` store, at any depth of a nested object or array. Both refused it with `ConfigurationError` ("contains a non-JSON value (Date instance)"), and since a date property also refuses its ISO text, a set update could not write one at all. A `compareAndSet()` `expected` value may now be a `Date` too (and `CompareAndSetExpected` admits one); it matches the stored text of that `Date`. Text you state for a date property is still refused.

`importGraph()` now accepts the stored date text `exportGraph()` writes. Import parsed each row as create input, where `z.date()` refuses a string, so every row of a kind with a date property was reported as an error and the round trip lost it. Import now turns that text back into a `Date` before parsing, by the same rule an update applies to a stored row: only canonical ISO text (`YYYY-MM-DDTHH:mm:ss.sssZ`, years 0001 to 9999), only where the schema accepts nothing but a `Date` (including inside `.optional()` and similar wrappers, a nested `z.object()` or a `z.array()`). Other text still refuses the row. Under `onUnknownProperty: "allow"` the stored bytes are unchanged and a uniqueness constraint over a date property claims the same key the store's own writes claim.

The `ConfigurationError` for a value that is not JSON, such as a `Map` in a set-update patch or in a durable operation document, no longer says "Annotations must be JSON-serializable" when no annotation is involved; it names the value and the JSON types allowed.

A set update refuses, with a `ValidationError`, a `Date` at a position whose schema would read its stored text back as something other than that `Date` (under a union, a record or `z.any()`): the row would hold a string, and under a unique constraint `z.union([z.date(), z.string()])` it let two rows hold the same instant. A stored date under an `.overwrite()` (on the date, on a wrapper such as `.optional()`, or on an object or array holding it) is turned back into a `Date` when a write parses the stored row again only if parsing that `Date` gives the same value back. An identity `.overwrite()` therefore no longer makes every update of an unrelated property fail, and `validateStore()` no longer reports such a row. One that would change the date makes `update()`, `updateWhere()`, `compareAndSet()` and `importGraph()` refuse with a `ValidationError` naming the property: before, an `.overwrite()` on a wrapper shifted the untouched date on every update, and under a `.catch()` the untouched date was replaced by the fallback. A write that states the property stores what its schema makes of the new value.

Every write now stores, and every comparison binds, the instant a `Date` holds, read from the `Date` itself rather than through a `toJSON()` or `toISOString()` the object carries (an own property or a subclass). Before, such a `Date` was stored as whatever its serializer returned on `create()`, `update()`, the upserts and bulk writes, edge writes, `importGraph()` and `trustedImportGraph()` of an in-memory document, and a set-update patch; a `compareAndSet()` expectation matched the row holding that other instant; and a date predicate compared it. `validateProps()` (from `@nicia-ai/typegraph/schema`) now returns each validated `Date` as a plain `Date` of the instant it holds.

A graph merge now applies dated rows. Merge plans carry each row's properties in their stored form, so `applyMergePlan()` refused a plan `planMerge()` had just returned for a branch that added or edited a node or edge with a `z.date()` property, `merge()` failed while committing it, and candidate write sets and mutation plans planned what apply refused. Every merge path now turns stored date text back into a `Date` by the rule updates use before it validates and writes, and a planned write whose schema would rewrite a stored date is refused when the plan is made, with the `InvalidMergePlanError` apply raises for it.
