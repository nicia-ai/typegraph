`importGraph` with `onConflict: "update"` now refuses a composition move of an `existence: "required"` part whose two rows do not abut (`importGraphStream` already refuses a graph declaring a required part before it reads any chunk). A document could end the part's attachment at one instant and attach it again from a later one, or attach it with no `validFrom` (so the new window opens when the import writes it), and the import committed both rows, leaving the part with no whole on valid-time reads in between, which `verifyConstraintFences()` does not report. `reparent` cannot produce this, since it gives both halves one instant, and an imported move is now held to the same rule. Such a move is refused both-or-neither before anything is written: both rows report the new `CompositionError` code `COMPOSITION_MOVE_GAP` (`situation: "moveGap"`), whose details and message name the part, the ended window, the new attachment's window and the gap, and the part keeps its current whole. A new attachment that states no `validFrom` is judged as opening at the instant the import judges the move, and when the move is accepted it is written with that instant rather than a later clock read, so an end at that instant abuts it in the committed rows too. A move whose new window overlaps the old one is still refused as `COMPOSITION_WINDOW_OVERLAP`, and a move that abuts is unchanged. An end at the old attachment's own `validFrom` leaves a zero-width window, which holds the part at no instant and overlaps nothing, so a new attachment opening before it leaves no gap and is judged only against the part's other rows. Optional parts may still move across a gap. `CompositionErrorDetails` gains the `"moveGap"` member, so an exhaustive `switch` over `situation` needs a case for it.
