**An edge registration can declare `targetCardinality: "many" | "one" | "oneActive"`**, bounding the edges that point AT one node independently of `cardinality`, which bounds the edges leaving one source. Target `"one"` with the default source `"many"` is many-to-one ownership: a source may point at many targets, each target may be pointed at once. The two axes compose freely — all twelve combinations with the existing `cardinality` values, `unique` included, are accepted and enforced together — and both are enforced atomically on every public write path: create, upsert, get-or-create, bulk writes, resurrection, validity-window reopening, validating import, and merge apply after endpoint canonicalization. Two concurrent writers cannot both take the same target, including on a default PostgreSQL store with history and revision tracking disabled.

The target allowance is scoped to the graph, the edge kind, the target kind and the target id, and deliberately not to the source: two permitted source kinds contend for one allowance, while equal ids under different target kinds, edge kinds or graphs never collide. `"one"` counts every non-deleted edge at the target, including edges with a validity end; `"oneActive"` counts only those whose `validTo` is unset. Soft-deleted edges occupy no slot, a resurrection or reopened window reacquires every applicable reservation, and ending an edge frees an active-only slot but never a `"one"` slot. These bound edge count rather than distinct neighbours, so a second distinct edge from the same source to a constrained target is refused too, while an idempotent operation returning the existing edge consumes nothing. `CardinalityError` stays the violation type, its details now naming the `direction` and both endpoints, and `verifyConstraintFences()` reports target-side violations in the existing `edgeCardinality` family.

**An edge registration also accepts `acyclic: true`**, declaring that the edge kind's live relation is a DAG. Every write path that can put an edge into that relation — `create`, `bulkCreate`, upsert and `getOrCreateByEndpoints`, resurrection into the live population, validating import, and merge apply — is refused with the new `EdgeAcyclicityError` when the new edge's `to` endpoint already reaches its `from` endpoint; a self-loop is a cycle of length one and is refused by the same rule. A batch (`bulkCreate`, `bulkInsert`, `bulkUpsertById`, `bulkGetOrCreateByEndpoints`) is checked as a whole before its first row is written, including a cycle two of its own rows close through each other, so a refusal caught inside an enclosing `store.transaction(...)` leaves none of the batch stored. A batch of any size is checked: the probe is sent in as many statements as the backend's `maxBindParameters` requires and still sees a cycle whose rows fall in different statements. The check is exhaustive, with no depth bound, so a cycle of any length is found. Non-deleted edges count regardless of their validity window, so ending an edge's window does not free the relation while soft-deleting it does. Two concurrent writers of `a → b` and `b → a` serialize and exactly one commits. On PostgreSQL that guarantee is between `READ COMMITTED` writers: a `SERIALIZABLE` transaction is accepted but is arbitrated only against other `SERIALIZABLE` transactions, so one acyclic relation should be written at one isolation level. A backend with no transactions cannot enforce the rule at all and refuses the write with `CONSTRAINT_WRITE_FENCE_UNSUPPORTED` and the new `details.constraint` value `edgeAcyclicity`, rather than enforcing it only when nothing races; a `REPEATABLE READ` session, which cannot observe a commit that landed while it waited, is refused with `EDGE_ACYCLICITY_REQUIRES_FRESH_SNAPSHOT` in every frame of its transaction; and a statement the engine cuts short raises the new `EdgeAcyclicityIndeterminateError`, so an incomplete search is never reported as "no cycle". `store.verifyConstraintFences()` gains an `edgeAcyclicity` family reporting edges already on a cycle. `trustedImportGraphStream` refuses a store declaring an acyclic edge kind (`reason: "acyclicity_unsupported"`); the portable validating import checks each row as it writes and rolls it back per-row on a cycle.

**Graph merge catches a would-be cycle at plan time.** `merge()`, `mergeAgainstBase()`, `planMerge()`, `planMergeIncremental()` and `mergeIncremental()` all check reachability over the resolved plan's projected edge writes, after canonicalization and repointing, layered onto the target's current live edges less the edges the same plan deletes — including a cycle formed entirely from rows the plan proposes, with nothing live yet, which was not previously detectable. A plan that reverses or re-roots edges of an acyclic relation is therefore judged by the DAG it produces and merges. A violation is the new typed `AcyclicityMergeConflictError` (code `GRAPH_MERGE_ACYCLICITY_CONFLICT`), carrying the offending relation name and every edge on the cycle (`edgeId`/`edgeKind`/`fromKind`/`fromId`/`toKind`/`toId`) in `details`, so a `planMerge()` review surfaces it before anything is written. A cycle that only appears from a write racing the plan is still caught at apply time as `MergeConstraintConflictError` wrapping `EdgeAcyclicityError`. On PostgreSQL the isolation caveat above applies to that apply-time check too: a merge into a store opened without `history: true` commits at `SERIALIZABLE`, so a `READ COMMITTED` writer that commits after the merge transaction's snapshot is not seen by it.

**`defineGraph` refuses an integrity option stated outside its domain.** An unknown `cardinality`, a `targetCardinality` other than `"many"`, `"one"` or `"oneActive"`, an `endpointExistence` other than `"notDeleted"`, `"currentlyValid"` or `"ever"`, and a non-boolean `acyclic` raise `ConfigurationError` `EDGE_INTEGRITY_OPTION_INVALID` (`details.option`, `details.value`) at declaration. TypeScript already rejects these; the check is for untyped callers, whose `acyclic: "yes"` would otherwise have been read as undeclared and whose `cardinality: "bogus"` would have been written into a stored schema the loader rejects.

Schema serialization, hashing, introspection, runtime graph extensions and schema diffing preserve both declarations; a schema stored before this release loads as `"many"` on both cardinality axes. Runtime graph-extension documents may now declare `cardinality`, `targetCardinality` and `acyclic` on an edge — previously the cardinality keys were rejected in strict mode and dropped otherwise, so an extension-authored edge kind was always unconstrained.

### Breaking

- `EdgeRegistration` gains `targetCardinality?`, `EdgeIntrospection` gains a required `targetCardinality` and a required `acyclic` boolean (`false` unless declared), and `SerializedEdgeDef` gains an optional `targetCardinality?`. Code that builds either object literal by hand adds the field; everything produced through `defineGraph`, the serializer or `introspectSchema` is unaffected. The serializer omits `targetCardinality` when it is undeclared or explicitly the default `"many"`, so a graph that never uses the option serializes and hashes byte-identically to a pre-release document and keeps `ensureSchema`'s schema-hash fast path. Declaring a non-default value picks up a new schema hash, like any other schema change.
- `GraphBackend.countEdgesFrom` is replaced by `countEdgesAtEndpoint`, whose params carry `endpoint: "from" | "to"` and the endpoint's identity as `endpointKind` / `endpointId`. A custom backend renames its implementation and reads the endpoint discriminant.
- `ClaimEdgeCardinalityParams` gains a required `direction: "source" | "target"` discriminant, and `EdgeCardinalityDeclaration` / `ContendedEdgeRow` gain the same. Source-side claim axis strings are byte-identical to before, so existing `typegraph_edge_claims` rows keep fencing what they fence today and no migration is required.
- `ManagedEdgeCreatePlan.cardinalityClaim` becomes `cardinalityClaims: readonly ClaimEdgeCardinalityParams[]`. A command port must apply every entry or return `unsupported` with the `"cardinalityClaim"` dimension before executing any SQL.
- `CardinalityErrorDetails` gains required `direction`, `toKind` and `toId`. Existing `edgeKind` / `fromKind` / `fromId` / `cardinality` / `existingCount` are unchanged.
- `ConstraintFenceViolation` gains an `edgeAcyclicity` member. Its `target` is present only on the claim-backed families, so narrow on `violation.family` before reading it.
- A trusted import now refuses a graph declaring any edge cardinality, in either direction, with `TrustedImportError` reason `"cardinality_unsupported"`, and a store declaring an acyclic edge kind with reason `"acyclicity_unsupported"`. Use `importGraph`, or declare the kind unconstrained and enforce the limit in application code.
- A schema commit that newly declares a constrained `cardinality` or `targetCardinality` — including on a brand-new kind, since a stored schema with no entry reads as unconstrained on both axes — runs an atomic data-check preflight and refuses with a `MigrationError` naming the violating endpoints. A backend that implements `commitSchemaVersion` but not `commitSchemaVersionWithPreflight` throws `ConfigurationError` code `EDGE_CARDINALITY_TIGHTENING_REQUIRES_ATOMIC_BACKEND` for such a commit, including one that only adds a new edge kind.
- Adding `acyclic: true` to a populated edge kind is classified as a tightening, probed against live rows inside the commit transaction, and refused with `MigrationError` `reason: "ontology-tightening-violated"` when a cycle already exists; inspect `details.violations` (same shape as `store.verifyConstraintFences()`) to find and resolve the offending rows before retrying. The classifier records that change as `OntologyChange` with `entity: "edgeRegistration"` (not `"relation"`) and a probe of kind `"edgeAcyclicity"`. `probeCoversViolationFamily` joins that probe to a violation of family `"edgeAcyclicity"`.
- A merge whose resolved plan would close a cycle now fails with `AcyclicityMergeConflictError` at plan time rather than `MergeConstraintConflictError` at apply time. Code that catches `MergeConstraintConflictError` (or matches `cause.name === "EdgeAcyclicityError"`) to detect this case must also handle the new error; the apply-time shape still occurs for a cycle that only appears from a write racing the plan.
- An edge kind name containing U+001E is refused at `defineGraph`, joining node kinds and unique constraint names. TypeGraph reserves that code point for claim axes.
