**An edge registration can declare `targetCardinality: "many" | "one" | "oneActive"`**, bounding the edges that point AT one node independently of `cardinality`, which bounds the edges leaving one source. Target `"one"` with the default source `"many"` is many-to-one ownership: a source may point at many targets, each target may be pointed at once. The two axes compose freely — all twelve combinations with the existing `cardinality` values, `unique` included, are accepted and enforced together — and both are enforced atomically on every public write path: create, upsert, get-or-create, bulk writes, resurrection, validity-window reopening, validating import, and merge apply after endpoint canonicalization. Two concurrent writers cannot both take the same target, including on a default PostgreSQL store with history and revision tracking disabled.

The target allowance is scoped to the graph, the edge kind, the target kind and the target id, and deliberately not to the source: two permitted source kinds contend for one allowance, while equal ids under different target kinds, edge kinds or graphs never collide. `"one"` counts every non-deleted edge at the target, including edges with a validity end; `"oneActive"` counts only those whose `validTo` is unset. Soft-deleted edges occupy no slot, a resurrection or reopened window reacquires every applicable reservation, and ending an edge frees an active-only slot but never a `"one"` slot. These bound edge count rather than distinct neighbours, so a second distinct edge from the same source to a constrained target is refused too, while an idempotent operation returning the existing edge consumes nothing. `CardinalityError` stays the violation type, its details now naming the `direction` and both endpoints, and `verifyConstraintFences()` reports target-side violations in the existing `edgeCardinality` family.

**An edge registration also accepts `acyclic: true`**, declaring that the edge kind's live relation is a DAG. Every write path that can put an edge into that relation — `create`, `bulkCreate`, upsert and `getOrCreateByEndpoints`, resurrection into the live population, validating import, and merge apply — is refused with the new `EdgeAcyclicityError` when the new edge's `to` endpoint already reaches its `from` endpoint; a self-loop is a cycle of length one and is refused by the same rule. A batch (`bulkCreate`, `bulkInsert`, `bulkUpsertById`, `bulkGetOrCreateByEndpoints`) is checked as a whole before its first row is written, including a cycle two of its own rows close through each other, so a refusal caught inside an enclosing `store.transaction(...)` leaves none of the batch stored. A batch of any size is checked: the probe is sent in as many statements as the backend's `maxBindParameters` requires and still sees a cycle whose rows fall in different statements. The check is exhaustive, with no depth bound, so a cycle of any length is found. Non-deleted edges count regardless of their validity window, so ending an edge's window does not free the relation while soft-deleting it does. Two concurrent writers of `a → b` and `b → a` serialize and exactly one commits, at every PostgreSQL isolation level and between writers at different levels: a write that checks an acyclic relation also advances the graph's row in `typegraph_fences` behind the per-graph write fence, so a `REPEATABLE READ` or `SERIALIZABLE` session whose snapshot predates another such writer's commit fails on that row with a serialization failure (SQLSTATE `40001`) instead of checking a relation it can no longer see. TypeGraph replays a collection write, an import or a merge commit it opened the transaction for; inside `store.transaction(...)` or an adopted transaction the failure surfaces as `TransactionConflictError` for the owner to re-run. (`applyMergePlanInTransaction` still requires a `READ COMMITTED` caller transaction.) A backend with no transactions cannot enforce the rule at all and refuses the write with `CONSTRAINT_WRITE_FENCE_UNSUPPORTED` and the new `details.constraint` value `edgeAcyclicity`, rather than enforcing it only when nothing races; a custom backend whose fence is an advisory lock with no fences relation cannot detect a stale snapshot, so a `REPEATABLE READ` or `SERIALIZABLE` write is refused there with `EDGE_ACYCLICITY_REQUIRES_FRESH_SNAPSHOT` in every frame of its transaction; and a statement the engine cuts short raises the new `EdgeAcyclicityIndeterminateError`, so an incomplete search is never reported as "no cycle". `store.verifyConstraintFences()` gains an `edgeAcyclicity` family reporting edges already on a cycle. Adding `acyclic: true` to a populated edge kind is a tightening: it is probed against live rows inside the schema-commit transaction and refused with `MigrationError` `reason: "ontology-tightening-violated"` when a cycle already exists, with `details.violations` in the shape `store.verifyConstraintFences()` returns. The classifier records that change as an `OntologyChange` with `entity: "edgeRegistration"`. `trustedImportGraphStream` refuses a store declaring an acyclic edge kind (`reason: "acyclicity_unsupported"`); the portable validating import checks each row as it writes and rolls it back per-row on a cycle.

**Graph merge catches a would-be cycle at plan time.** `merge()`, `mergeAgainstBase()`, `planMerge()`, `planMergeIncremental()` and `mergeIncremental()` all check reachability over the resolved plan's projected edge writes, after canonicalization and repointing, layered onto the target's current live edges less the edges the same plan deletes — including a cycle formed entirely from rows the plan proposes, with nothing live yet, which was not previously detectable. A plan that reverses or re-roots edges of an acyclic relation is therefore judged by the DAG it produces and merges. A violation is the new typed `AcyclicityMergeConflictError` (code `GRAPH_MERGE_ACYCLICITY_CONFLICT`), carrying the offending relation name and every edge on the cycle (`edgeId`/`edgeKind`/`fromKind`/`fromId`/`toKind`/`toId`) in `details`, so a `planMerge()` review surfaces it before anything is written. A cycle that only appears from a write racing the plan is still caught at apply time as `MergeConstraintConflictError` wrapping `EdgeAcyclicityError`. That holds for the `SERIALIZABLE` commit of a merge into a store opened without `history: true` as well: a writer into the same acyclic or composition relation, at any isolation level, that commits after the merge transaction's snapshot fails the merge on the graph's fence row, and the merge commit is replayed against the graph that writer left, where it is refused as stale (`BaseVersionMismatchError`) or for the constraint it would now violate.

**`defineGraph` refuses an integrity option stated outside its domain.** An unknown `cardinality`, a `targetCardinality` other than `"many"`, `"one"` or `"oneActive"`, an `endpointExistence` other than `"notDeleted"`, `"currentlyValid"` or `"ever"`, and a non-boolean `acyclic` raise `ConfigurationError` `EDGE_INTEGRITY_OPTION_INVALID` (`details.option`, `details.value`) at declaration. TypeScript already rejects these; the check is for untyped callers, whose `acyclic: "yes"` would otherwise have been read as undeclared and whose `cardinality: "bogus"` would have been written into a stored schema the loader rejects.

Schema serialization, hashing, introspection, runtime graph extensions and schema diffing preserve both declarations; a schema stored before this release loads as `"many"` on both cardinality axes. Runtime graph-extension documents may now declare `cardinality`, `targetCardinality` and `acyclic` on an edge — previously the cardinality keys were rejected in strict mode and dropped otherwise, so an extension-authored edge kind was always unconstrained.

### Breaking

- On PostgreSQL, a write that makes a decision only the per-graph write fence protects now advances one row per graph in `typegraph_fences` (part of the base schema since the fence-rows release), behind the advisory lock: a write into an `acyclic` or composition relation, a delete of a composition whole, and a match-key convergence (`getOrCreateByEndpoints`, `bulkGetOrCreateByEndpoints` or a coalescing upsert on a match key no database key backs). A role that performs those writes needs `INSERT` and `UPDATE` on that table. Every other holder of the fence — a history-capturing or revision-tracking write, a cardinality, uniqueness or disjointness write, a provenance `holding()` read — takes the lock alone, writes no row and issues the statements it issued before. The row is updated once per deciding transaction, so while a transaction holding an older snapshot stays open (`pg_dump`, a long report, an idle-in-transaction session) its dead versions accumulate and those deciding writes slow until the snapshot closes and the table is vacuumed; see "Write Fence Row" in the limitations guide.
- A `store.transaction` whose callback holds a raw SQL handle (`tx.sqlAvailability: "available"`) now takes the per-graph write fence at every constraint-fenced write instead of once per transaction. A `ROLLBACK TO SAVEPOINT` issued through `tx.sql` releases an advisory lock taken after that savepoint and undoes a fence-row advance made after it, so a later fenced write in the same transaction previously ran under a lock it no longer held. Transactions without the handle (history capture, revision tracking, or no native transaction) still take the fence once, and the schema-fence lease follows the same rule.
- `TransactionReadBackend`, the `tx.backend` of every transaction context, no longer has `execute`. Its compiled-query brand is a type only, so `tx.backend.execute` ran any SQL on the transaction's session — including a `ROLLBACK TO SAVEPOINT` that released the per-graph write fence and the schema fence while the transaction's later writes kept relying on them, which let two transactions commit a cycle into an `acyclic` relation, and on a history store writes that bypassed capture. `tx.sql` is now the one raw handle a transaction context carries. Run TypeGraph queries in a transaction with `tx.query()`, and raw SQL through an `AdapterStore` transaction's `tx.sql`, whose transactions take every fence again at each write.
- A PostgreSQL schema write now opens its transaction at `READ COMMITTED` whatever the server's `default_transaction_isolation` is, and the advisory schema fence refuses a session that reports any other isolation with `ConfigurationError` code `SCHEMA_WRITE_REQUIRES_READ_COMMITTED` (`details.isolation`). A schema write is every unit that runs under the schema fence: a schema commit or activation from `createStoreWithSchema`, `migrateSchema` or a schema evolution, with the tightening preflight or emptiness probe run before it; an identity schema transition; the graph-merge provenance sidecar claim; removal materialization; and a contribution rebuild. At a snapshot-isolation default the preflight previously read a snapshot taken before the commit waited for the writers holding the schema row, and could activate a tightening such as `acyclic: true` over rows written while it waited. Two caller-owned transactions cannot be moved to `READ COMMITTED` and are now refused when they run at `REPEATABLE READ` or `SERIALIZABLE`: one handed to `adoptSchemaWriteTransaction`, and one under a transaction-scoped backend (`createPostgresTransactionBackend(tx)`, or `createPostgresBackend(tx)` on a transaction), where the schema write runs in a savepoint of the caller's transaction. The second case previously committed and now refuses every schema write above, including the first commit of a brand-new graph, which has no data check: the rule is one per fence, not per write. Run such a schema write in a `READ COMMITTED` transaction. The refusal is raised before the adopted path acquires or changes anything, and the transaction-scoped path rolls its savepoint back, so a caller that catches it keeps its transaction as it was.
- At `REPEATABLE READ` or `SERIALIZABLE`, such a PostgreSQL write now fails with SQLSTATE `40001` on that row when another such writer committed past its snapshot, reported as `TransactionConflictError` with the driver error as `cause`. Retry the whole transaction, as for any serialization failure.
- A PostgreSQL collection write or import that names a constraint, in a transaction TypeGraph opened, and every `bulkUpsertById`, `bulkReplaceById` and `bulkGetOrCreateByConstraint`, is now replayed up to three times on a serialization failure or deadlock and raises `TransactionConflictError` once the attempts are spent, where the driver error previously propagated from the first failure. A write that names no constraint takes one attempt, as before. SQLite is unchanged.
- `getOrCreateByEndpoints` and `bulkGetOrCreateByEndpoints` now accept a `REPEATABLE READ` create leg on the bundled PostgreSQL backends, where it was refused with `MATCH_KEY_CONVERGENCE_REQUIRES_FRESH_SNAPSHOT`. A custom backend whose fence is an advisory lock with no fences relation (`tableNames.fences`) is now refused at `SERIALIZABLE` as well as `REPEATABLE READ`, with the same code, where `SERIALIZABLE` was previously accepted.
- `GraphBackend.lockSchemaVersionAndGraphWrite` resolves the new `GraphWriteFenceAcquisition` (`{ isolation, fenceRow: "advanced" | "none" }`) instead of a bare `GraphCommandIsolation`. Its params gain a required `fenceRow: "advance" | "leave"`: a custom backend implementing it advances the graph's fence row only for `"advance"`, and reports `fenceRow: "advanced"` only when its statement did. `FenceStatements` gains the optional `acquireKeyedSnapshotFence`, which is absent for an advisory fence that names no fences relation; a fence without it cannot advance a fence row, so the deciding writes above are refused on it at `REPEATABLE READ` and `SERIALIZABLE`.
- `EdgeRegistration` gains `targetCardinality?`, `EdgeIntrospection` gains a required `targetCardinality` and a required `acyclic` boolean (`false` unless declared), and `SerializedEdgeDef` gains an optional `targetCardinality?`. Code that builds either object literal by hand adds the field; everything produced through `defineGraph`, the serializer or `introspectSchema` is unaffected. The serializer omits `targetCardinality` when it is undeclared or explicitly the default `"many"`, so a graph that never uses the option serializes and hashes byte-identically to a pre-release document and keeps `ensureSchema`'s schema-hash fast path. Declaring a non-default value picks up a new schema hash, like any other schema change.
- `GraphBackend.countEdgesFrom` and its `CountEdgesFromParams` type are replaced by `countEdgesAtEndpoint` and `CountEdgesAtEndpointParams`, whose params carry `endpoint: "from" | "to"` and the endpoint's identity as `endpointKind` / `endpointId`. A custom backend renames its implementation and reads the endpoint discriminant.
- `ClaimEdgeCardinalityParams` gains a required `direction: "source" | "target"` discriminant, and `EdgeCardinalityDeclaration` / `ContendedEdgeRow` gain the same. Source-side claim axis strings are byte-identical to before, so existing `typegraph_edge_claims` rows keep fencing what they fence today and no migration is required.
- `ManagedEdgeCreatePlan.cardinalityClaim` becomes `cardinalityClaims: readonly ClaimEdgeCardinalityParams[]`. A command port must apply every entry or return `unsupported` with the `"cardinalityClaim"` dimension before executing any SQL.
- `CardinalityErrorDetails` gains required `direction`, `toKind` and `toId`. Existing `edgeKind` / `fromKind` / `fromId` / `cardinality` / `existingCount` are unchanged.
- `ConstraintFenceViolation` gains an `edgeAcyclicity` member. Its `target` is present only on the claim-backed families, so narrow on `violation.family` before reading it.
- A trusted import now refuses a graph declaring any edge cardinality, in either direction, with `TrustedImportError` reason `"cardinality_unsupported"`, where it previously wrote such a graph without maintaining the claims that fence it; `TrustedImportErrorReason` gains that member and `"acyclicity_unsupported"`. Use `importGraph`, or declare the kind unconstrained and enforce the limit in application code.
- A schema commit that newly declares a constrained `cardinality` or `targetCardinality` — including on a brand-new kind, since a stored schema with no entry reads as unconstrained on both axes — runs an atomic data-check preflight and refuses with a `MigrationError` naming the violating endpoints. A backend that implements `commitSchemaVersion` but not `commitSchemaVersionWithPreflight` throws `ConfigurationError` code `EDGE_CARDINALITY_TIGHTENING_REQUIRES_ATOMIC_BACKEND` for such a commit, including one that only adds a new edge kind.
- An edge kind name containing U+001E is refused at `defineGraph`, joining node kinds and unique constraint names. TypeGraph reserves that code point for claim axes.
