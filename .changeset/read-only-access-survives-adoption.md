A write through a context built over the native handle of a read-only transaction is now refused like a write on the transaction itself. Before this, `store.transaction(fn, { accessMode: "read_only" })` refused every write its own `tx` offered, but `store.withTransaction(tx.sql)` built a new context that knew nothing of the access mode: on SQLite its writes committed inside the "read-only" transaction, and on PostgreSQL the engine rejected the first statement and aborted the transaction. The read-only fact is now bound to the transaction's native database session for as long as the transaction runs, and every surface built over that session asks it at each write: `withTransaction(tx.sql)` and `withRecordedTransaction(tx.sql, fn)` refuse every collection and identity write and `applyMergePlanInTransaction` with the same `UnsupportedBackendCapabilityError` (capability `"write transaction access"`) and `operation` names as `tx`; a history store's `withRecordedTransaction(tx.sql, fn)` and `withEvolvedTransaction(tx.sql, plan, fn)` are refused before their callback; and a Store over `createPostgresTransactionBackend(tx.sql)` refuses its own collection and identity writes (`store.nodes.Person.create()`), writes in its own `store.transaction()`, and imports into it. Every refusal comes before any statement, on SQLite and PostgreSQL alike, so the transaction stays usable. A native read-only transaction TypeGraph did not open carries no such fact and behaves as before.
