`equivalentTo` between two registered kinds now means MUTUAL SUBSUMPTION, with one closure behind every reading of "same class". `KindRegistry` folds each equivalence class into `subClassAncestors` / `subClassDescendants` before the transitive closure, so `isAssignableTo`, `isSubClassOf`, `expandSubClasses`, `getSubClassComponent` and disjointness propagation now agree by construction instead of answering three different ways: with `equivalentTo(Company, Corporation)`, `isAssignableTo("Corporation", "Company")` is true, `includeSubClasses: true` on a `Company` alias returns `Corporation` rows, an edge declared `to: [Company]` accepts a `Corporation` endpoint, `search(..., { includeSubClasses: true })` covers both kinds, and a `kindWithSubClasses` uniqueness constraint fences across the pair. Subsumption stays strict — a kind is never its own subclass, and `expandSubClasses` still lists each kind once. External IRIs stay out of subsumption: they are inert references, so `Person ≡ schema:Person ≡ Individual` folds `Person` and `Individual` together without making the IRI a kind. `graph-merge`'s private subclass closure is gone; `reconcileTypes` now consumes the store's own validated `KindRegistry`, so a merge and a query can no longer disagree about which kinds are the same class, and every kind-name ordering in that path is code-point order. `equivalentTo`'s left parameter widens to `NodeType | AnyEdgeType` so an edge kind can be mapped to an external IRI; an equivalence class that mixes node and edge kinds, or that contains more than one registered edge kind (reachable transitively through a shared IRI), is refused at registry build and at schema load with a `ConfigurationError` whose details code is `ONTOLOGY_EQUIVALENCE_INVALID_CLASS`.

## Breaking changes

- `includeSubClasses: true` on `from()` / `to()` and on `search()` now returns rows of kinds declared `equivalentTo` the queried kind, not only its `subClassOf` descendants. A query that relied on equivalence being inert must drop `includeSubClasses`, or drop the `equivalentTo` declaration if the two kinds were never meant to be substitutable.
- Edge endpoints, `implies` and `inverseOf` endpoint validation, and `importGraph`'s endpoint check all accept equivalent kinds. Some declarations previously refused at registry build now construct.
- A `kindWithSubClasses` uniqueness constraint spans the equivalence class, so a value unique per kind before can now collide. The claim axis moves to the code-point minimum of the widened component; **no data migration is required** — the uniqueness probe reads the axis plus every covered kind, so rows written under the previous axis are still found and still fence.
- The serialized schema's precomputed `ontology.closures` change for any graph declaring `equivalentTo` between registered kinds, and with them the schema hash. This resolves as a semantic no-op on both boot paths (the relations are unchanged, so the schema diff reports no changes and the store reports `status: "unchanged"`); the stored document keeps its pre-fold closures until the next real schema change. Nothing reads them — the deserializer recomputes closures from the relations.
- An equivalence class that mixes node and edge kinds, or holds two registered edge kinds, is now refused where it previously loaded inert. A persisted schema carrying one fails on load with `ONTOLOGY_EQUIVALENCE_INVALID_CLASS`; correct the stored document before upgrading.
- `equivalentTo`'s first parameter is now `NodeType | AnyEdgeType`.
