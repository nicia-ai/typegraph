TypeGraph now leaves a caller's PostgreSQL transaction with the settings it had. Three units changed a transaction-local setting with `set_config(..., true)` and, on a backend built over a caller's transaction (`createPostgresBackend(tx)`), left it changed after returning: `RELEASE SAVEPOINT` keeps a setting changed under the savepoint, so the caller ran its later statements under TypeGraph's value. An iterative algorithm's `workingMemory` left `work_mem` at the requested value; a working-copy manager whose `control` is such a backend left `lock_timeout` at `cleanupLockTimeoutMs` after `listUnsealedAllocations`, `abortAllocation`, a destroy, or the removal behind closing a copy; and allocation provisioning (`makeBackend`, `ephemeral`, `durable`) left `search_path` led by the allocation schema, so a caller whose path named a schema it created later had its unqualified names resolve elsewhere. Each unit now reads the caller's value in the statement that sets it and restores it before returning. A unit that fails rolls back to its savepoint, which discards the setting. On a transaction TypeGraph opens itself nothing changes: the setting is applied with one statement and ends with the transaction. The vector-search index parameters and the adopted schema fence's `lock_timeout`, which already restored the caller's values, now go through the same owner.

Upgrade note: `DialectAdapter.setTransactionWorkingMemory(workingMemory)`, which returned the `set_config` statement, is replaced by `DialectAdapter.transactionWorkingMemory(workingMemory)`, which returns the setting (`{ name: "work_mem", value }` on PostgreSQL, `undefined` on SQLite) as the new `DialectTransactionSetting` type. A custom dialect adapter renames the member and returns the setting instead of a statement; TypeGraph builds the statements that apply and restore it.
