The provenance capability can refuse an unsupported derivation at commit time. `provenance.assertHolds(tx, facts)` runs inside your write transaction, after your writes, and throws `FactNotHoldingError` when a named fact is not believed, so a fact derived from an already-retracted source, or from a live fact that is unsupported, no longer commits. It returns one `{ fact, via }` entry per fact, where `via` is the justifications firing for it, so a caller can check its own justification is among them. The error lists every failing fact with a reason, and for a fact whose justifications do not fire, the premises that stop each one. A premise-less justification still fires, so a fact it derives holds. `assertHolds` needs a read-write transaction, refuses a read-only one with `UnsupportedBackendCapabilityError`, and takes the schema-version fence and then the graph write lock before it reads. An empty list is checked only for transaction ownership and returns `[]` without a lock. It reads only what is behind the named facts, not the whole provenance graph. `FactNotHoldingError` is exported from `@nicia-ai/typegraph/errors` and `@nicia-ai/typegraph/provenance`. Plain node and edge writes stay unchecked.

`provenance.holding(tx)` runs the believed-set computation on a transaction you supply, and sees the rows that transaction wrote. In a read-write transaction it takes the schema-version fence and then the graph write lock, like `assertHolds`, so the transaction's writes before or after it keep the canonical lock order; on a stale store handle it throws `StaleVersionError` there, and a `SELECT`-only role gets the database's permission error. In a transaction opened with `accessMode: "read_only"` it takes the graph write lock alone, so a `SELECT`-only role reads the believed set there or with `holding()`. `holding()` with no argument is unchanged: it takes the graph write lock alone and remains a point-in-time answer, not a write guard.

`retract`, `retractMany`, `unRetract` and `unRetractMany` now take the schema-version fence before the graph write lock, the store's canonical order. They took the graph lock first, so a retraction running at the same time as a schema commit could deadlock on PostgreSQL; the database aborted one side, so the effect was a stalled and retried transaction. Because the fence now comes before the verb's first read, a store handle whose schema version is stale throws `StaleVersionError` from these four verbs even when the call would have been a no-op or would have reported a missing source; they used to take the fence only at their first write. `holding()` is unchanged and still answers on a stale handle.
