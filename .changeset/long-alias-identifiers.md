Query aliases of up to 63 characters now work on PostgreSQL. The compiler derives SQL identifiers from an alias (`<alias>_id`, `<alias>_valid_from`, `cte_<alias>`, `<alias>_<field>` projections, recursive `<alias>_depth` / `<alias>_path` columns), and PostgreSQL clips identifiers to 63 bytes, so names that differed only past byte 63 became one identifier: a whole-node select failed from a 59- or 60-character alias, a root-id read from 61, and a field projected under a long alias, or under a multi-byte field name, could come back missing or wrong. SQLite ran the same queries correctly. Every derived name, including the `lm_<alias>` table aliases of late-materialized `orderBy().limit()` queries, now goes through one owner that leaves a name of at most 63 bytes untouched and allocates a longer one a shortened name (its leading bytes plus a 64-bit hash of the full name) per SQL statement, on every backend. The allocation checks every name the statement already uses, so a shortened name can never take the name of another column, CTE, or table alias in the same statement, even when a valid 63-byte name equals the shortened form of a longer one; the same query always compiles to the same SQL. Result decoding, `store.batchOnce()` (including recursive reads with default `<alias>_depth` / `<alias>_path` outputs on SQLite), checked reads, set operations, cursor pages, `updateWhere({ candidates })`, and search candidates read the allocated names. SQL for names that already fit is unchanged. The default `<alias>_depth` / `<alias>_path` outputs of `recursive({ depth: true, path: true })` and the `<alias>_edge` alias of `parts()` / `wholes()` are no longer refused when the derived name exceeds 63 characters.
