A `$fulltext.matches()` or `.similarTo()` predicate on an alias a recursive traversal walks from or to (its start, edge or target alias) is now refused with `UnsupportedPredicateError` (`details.reason` is `"recursive_traversal"`; `details.predicate` and `details.alias` name the predicate) when the query is compiled, on every terminal that compiles the query and before any statement runs (`executeChecked()` keeps refusing every recursive query with its own `ConfigurationError`). It used to compile to a constant-true term, so the filter was silently dropped and every reachable node came back. This covered `maxHops` above 1, `minHops` other than 1, `depth`, `path`, `stopExpansion()`, exhaustive `parts()` / `wholes()` walks, and the recursive stage of a chained query. These predicates select a ranked top-k match set and order rows by relevance, which only the standard statement's relevance joins apply; a recursive statement has neither, so the query is refused rather than answered without the predicate. Unchanged: a query whose only traversal is `recursive({ maxHops: 1 })` (with the default `minHops: 1`) without `depth`, `path` or `stopExpansion()` compiles to a fixed step and applies the predicate, a fixed traversal chained with a recursive one applies it on its own aliases, and so does the start alias of an optional first recursive traversal, which a fixed source step filters. The compiler now also treats a vector or fulltext predicate that reaches a WHERE clause of a statement that does not apply it as an internal invariant violation (`CompilerInvariantError`) instead of emitting a constant-true term for it.
