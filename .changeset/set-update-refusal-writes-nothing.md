A refused `updateWhere()` or `compareAndSet()` now writes nothing, including inside `store.transaction()` (#948). Both used to run their `UPDATE` first and validate the after-images it returned, so a `ValidationError` (a schema refinement or a row needing normalization) or a `UniquenessError` from the cross-row uniqueness check left the update applied in a caller's transaction: a callback that caught the refusal and returned normally committed the invalid row, every other row of a multi-row update, and a recorded history version, while the row's uniqueness claims, fulltext entry and embedding kept describing the old row. A call outside a transaction was unaffected, because its own transaction rolled back.

A set update now runs as a locked dry-run followed by a keyed write. The dry-run reads every selected row (PostgreSQL locks it `FOR NO KEY UPDATE`, the lock the `UPDATE` itself takes) and computes its after-image in SQL; the store validates every after-image, including uniqueness across the whole set, and then writes exactly those rows with the same SQL expression. The schema, normalization and uniqueness refusals are raised before the write, so no row, claim, sidecar, recorded capture, receipt entry or end hook survives them, on every path, a transaction the call opens itself included, without savepoints. A history store takes its graph write lock before the dry-run, so the dry-run's row locks keep the lock order of every other recorded write. The write is keyed to the exact stored rows the dry-run read (id, version, properties, validity window and creation time) and is all or nothing, also when `updateNodeSet` is called directly without the dry-run's locks: if a row changes between the two statements — possible only through the same transaction on an engine with row locks, for example an overlapping call that deletes and re-creates the row — it writes no row and the call throws `DatabaseOperationError` with `reason: "no_row_returned"`. The keyed write also compares each row's token in the `UPDATE`'s own predicate, on every write fence, so a row version PostgreSQL re-evaluates after a concurrent commit (possible under `writeFence.mechanism: "row"`, which takes no row lock) is not written with props the store never validated.

A uniqueness key the update moves a row onto is now reserved before the keyed write, and the claims the rows give up are released after it, in the order a single-row `update()` uses. Another writer that claims one of those keys after the uniqueness check makes the reservation raise `UniquenessError` before any row is written, where it used to raise after the rows were rewritten and their old claims dropped. Every batched claim member the update calls is bound off the transaction target before the dry-run, so a transaction handle without `hardDeleteUniquesByNodeIds` refuses with `SET_UPDATE_UNIQUENESS_UNSUPPORTED` and nothing written.

The keyed write binds its rows' keys, which carry each row's stored properties, as one value, and now splits them across statements to keep that value within the backend's new `maxBoundValueBytes` capability (64 MiB unless declared). A split write counts and locks every part before it writes the first, so it stays all or nothing inside a transaction; outside one, and for a single row whose key alone is larger than the budget, `updateNodeSet` refuses with `ConfigurationError` `SET_UPDATE_KEY_BUDGET_EXCEEDED` before running anything.

A set update costs one more statement than before (the dry-run), plus one reservation statement when it moves a uniqueness key; a refused or empty one runs only the dry-run. Both statements bind a constant number of parameters and reach rows only through keyed lookups, so the bounded plan under stale PostgreSQL statistics is unchanged.

### Upgrade notes

- **Custom backends: implement `previewNodeSetUpdate` and the keyed `updateNodeSet`.** `GraphBackend.compareAndSetNode` is removed. `previewNodeSetUpdate(params: PreviewNodeSetUpdateParams)` takes the former `updateNodeSet` / `compareAndSetNode` inputs (`UpdateWhereNodeSetParams`, `CompareAndSetNodeParams`), writes nothing, locks the rows it reads where the engine has row locks, and returns `{ rows: [{ id, version, props, rowToken }] }` with each after-image. `updateNodeSet(params: UpdateNodeSetParams)` now takes `{ graphId, kind, patch, unsetProperties?, rows: [{ id, rowToken }] }` and must write all of those rows or none. A backend that has only the old members refuses `updateWhere()` / `compareAndSet()` with `SET_UPDATE_UNSUPPORTED` / `COMPARE_AND_SET_UNSUPPORTED`.
- **Custom engine operation strategies (`CommonOperationStrategy`):** implement `buildPreviewNodeSetUpdate(params, rowLock)`, `buildCountNodeSetKeys(params, rowLock)` (the per-part count a split keyed write runs before writing) and `nodeSetUpdateRowLock` (the dialect's UPDATE-strength row lock, or an empty clause where writers serialize); `buildUpdateNodeSet` now takes `(params, timestamp, rowLock)` and the keyed `UpdateNodeSetParams`.
- **Callers of the backend port:** run `previewNodeSetUpdate`, then pass its rows' `id` and `rowToken` to `updateNodeSet`. The former `UpdateNodeSetParams` (with `operation: "updateWhere"` and a candidate query) is now `UpdateWhereNodeSetParams`.
- **Large set updates:** a direct `updateNodeSet` call outside a transaction whose row keys exceed `maxBoundValueBytes` now refuses with `SET_UPDATE_KEY_BUDGET_EXCEEDED`; run it inside a transaction, or raise the capability on the backend.
- **Error handling:** a set update whose validated rows change before its write, inside the same transaction, throws `DatabaseOperationError` (`details.reason: "no_row_returned"`) instead of writing them.
