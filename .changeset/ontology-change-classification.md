**`isStructuralSubtype(child, parent)`** joins the `@nicia-ai/typegraph/schema` entrypoint: a structural-subtyping check over TypeGraph's projected JSON Schema fragment that answers whether every value satisfying `child` is guaranteed to satisfy `parent`. The verdict is three-way — `subtype`, `not-subtype` with the deepest failing reason and path, or `incomparable` when either side carries a construct the projection cannot judge (`$ref`, `allOf`, `not`, unmodeled JSON Schema keywords, a parent `oneOf` whose members are not provably exclusive, or nesting past the depth guard) — so an unjudgeable pair is refused rather than accepted. A `$ref` is resolved against its own side's `$defs`: two properties that name the same reference are the same schema only when the definitions they reach are equal, since the projection numbers a recursive definition by encounter order and two unrelated recursive types share a name. A parent `oneOf` is read member-wise only when no value can match two members (different `type` tokens, or one required property pinned to disjoint `const`/`enum` sets): `z.discriminatedUnion` always qualifies, while a `z.xor` whose members overlap is `incomparable`. Width subtyping is allowed, required parent properties must stay required and narrower in the child, `integer` narrows `number`, unions match member-wise with sibling keywords ANDed, and `format` is compared as a constraint because the Zod projection emits it without a `pattern` for validators such as `z.url()`. It answers a different question from the migration classifier's `isBreakingPropertyChange`, which asks whether existing rows stay valid after a schema edit; the two disagree in both directions and the module documents why. It is the predicate this release's typed `subClassOf` / `equivalentTo` contract is built on.

**Ontology changes are now classified by what they do to existing data**, and a tightening the data violates is refused instead of auto-migrated. Adding `disjointWith`, `subClassOf` or `equivalentTo` is classified `warning` and probed inside the schema-commit transaction — before the Operational Identity closure rebuild — on every path that commits a version (`createStoreWithSchema` / `ensureSchema`, `Store.evolve()`, `migrateSchema()`, `Store.withEvolvedTransaction()`, and `rollbackSchema()`). An added `subClassOf`/`equivalentTo` is probed for the uniqueness components it merges — including a re-pairing where each kind swaps one neighbour for another, so no component grows — and for the kinds it makes required-existence composition parts: a live row of a kind that inherits `existence: "required"` with no live whole refuses the commit (`compositionExistence`). Removing `subClassOf`/`equivalentTo` is probed for live edges whose endpoints the remaining declarations no longer admit. Adding or removing `inverseOf` or `implies` is now `breaking`: both change what a default `expand` traversal returns, so they need an explicit `migrateSchema()`, exactly like the Operational Identity `sameIdAcrossKinds` flip. Adding `partOf`/`hasPart` is `warning`, probed for a part with more than one live whole and for a composition cycle (plus a part with no live whole when the pair is `existence: "required"`); removing one is `breaking`, like `inverseOf`/`implies` — except a stored relation with no `via`, which realizes no composition pair and is `safe` to remove. Removing `disjointWith` stays `safe`, and `broader`/`narrower`/`relatedTo`/`differentFrom` stay `safe` in both directions. A relation whose `from` or `to` names a kind the same commit removes is itself `safe`, and rows of the removed kind never block the commit. An edge kind that stops admitting an endpoint pair between surviving kinds is probed the same way whatever caused the loss — a removed `subClassOf`/`equivalentTo`, a narrowed `from`/`to` declaration (reported as an `entity: "edgeRegistration"` change), or a kind removed from the middle of a subclass chain — so `Store.removeKinds()` refuses when a surviving subclass's live edge was admitted only through the removed kind. `ChangeSeverity` itself is unchanged — `warning` now means "auto-migrates only if the data allows it".

**A refused tightening throws `MigrationError`** with `details.reason: "ontology-tightening-violated"` and `details.violations` in exactly the shape `store.verifyConstraintFences()` returns, so the same rows that block the migration can be listed, resolved, and the migration retried. The audit gains an `edgeEndpointAssignability` family reporting live edges sitting outside every declared endpoint pair. A backend implementing `readConstraintFenceViolations` may receive an `edgeEndpointAllowances` declaration and must answer with `misassignedEdgeEndpointRows`; omitting the key when the family was requested is refused with `CONSTRAINT_FENCE_AUDIT_FAMILY_UNSUPPORTED` rather than reported as a clean result. A backend that cannot commit a preflight atomically refuses a tightening with `ONTOLOGY_TIGHTENING_REQUIRES_ATOMIC_BACKEND`, and a preflight target that cannot run the audit refuses with the existing `CONSTRAINT_FENCE_AUDIT_UNSUPPORTED`. One residual window remains: a writer that commits under the previous schema version between the probe and the version compare-and-set is not seen, so `store.verifyConstraintFences()` remains the post-hoc detector.

**An ontology a diff cannot validate is now a refusal rather than a silent classification.** `classifyOntologyChanges` and `computeSchemaDiff` propagate `ConfigurationError` when a diff adds or removes an ontology relation and either side's stored or proposed ontology cannot be validated. The proposed side is held to every rule. The stored side is a delta input no store reads or writes through, so it is excused from the two contracts that postdate documents already stored — structural subsumption, and the `partOf`/`hasPart` declaration rules (a relation with no `via`, or a realizing edge those rules refuse) — which is what lets a fix-forward commit that corrects or removes the offending relation be classified at all. Any other stored-side incoherence (a subclass cycle, an invalid equivalence class) still refuses. Every read-only caller built on `computeSchemaDiff` inherits this: `loadAndVerifyGraph` (and so `createVerifiedStore` / `assertSchemaCurrent`) and `getSchemaChanges()` now also throw `ConfigurationError` for the same documents. `requiresMigration()` is the one exception: it treats "cannot classify" the same as "needs migration" and returns `true` instead of throwing, so a document only the privileged path can interpret still routes there.

**Adopted evolutions and rollbacks run the same tightening preflight.** `planEvolution()` derives the tightening check from the plan's own before/after documents and lists it as an `ontology-tightening` requirement, naming the probed ontology `changes` and the newly constrained `edgeCardinalityAxes`; `withEvolvedTransaction()` runs it on the fenced caller session before the schema compare-and-swap and refuses with the same `MigrationError` `Store.evolve()` raises, so a `disjointWith`, `acyclic: true` or tighter cardinality that existing rows violate can no longer be published through a plan. `rollbackSchema()` checks the version it reactivates against the active one the same way — a rollback to a stricter version whose declarations live rows violate is refused, while a rollback that tightens nothing still flips on any backend — and refuses to reactivate a version that re-keys a populated edge kind's match identity (`reason: "edge-match-identity-rekey"`). A rollback that would change an identity-enabled graph's identity profile, ontology or node kinds is refused with `ConfigurationError` `IDENTITY_ROLLBACK_REQUIRES_MIGRATION`: rebuilding the identity closure needs the graph definition, so commit that version's definition forward with `migrateSchema()` instead. Every commit path composes these checks in one fixed order: structural gates, edge match identity, ontology tightening, then the identity closure rebuild.

### Breaking

- `ConstraintFenceViolation` gains an `edgeEndpointAssignability` member, carrying `edgeKind`, `allowedPairs` and `edges` instead of a claim `target`. Narrow on `violation.family` before reading `violation.target`.
- A custom backend implementing `readConstraintFenceViolations` must answer `misassignedEdgeEndpointRows`, which the audit now requests for every registered edge kind. An un-updated custom backend finds the audit — and any ontology-tightening schema commit — refused with `ConfigurationError` `CONSTRAINT_FENCE_AUDIT_FAMILY_UNSUPPORTED` on any graph with at least one edge kind.
- `getSchemaChanges()`' `summary` counts `modified` ontology entries (`Ontology: 0 added, 0 removed, 1 modified`); a diff whose only change was one previously summarized as `No changes` beside `hasChanges: true`.
- Removing a `partOf`/`hasPart` pair, and adding or removing `inverseOf`/`implies`, now requires an explicit `migrateSchema()` even against clean data: `ensureSchema()`'s auto-migrate branch refuses these with `MigrationError` `reason: "breaking-change"`.
- A `subClassOf`/`equivalentTo`/`disjointWith`/`partOf`/`hasPart` addition the data already violates is refused with `MigrationError` `reason: "ontology-tightening-violated"`. Inspect `details.violations` to find and resolve the offending rows, then retry.
- Narrowing an edge kind's `from`/`to` out from under a live edge, and `Store.removeKinds()` of a mid-chain kind a surviving subclass's live edge relied on, are refused with `MigrationError` `reason: "ontology-tightening-violated"`. A narrowing no live edge sits outside still auto-migrates.
- `store.verifyConstraintFences()` now also reports the `edgeEndpointAssignability` family, so it may surface pre-existing violations on a database that has never run this check. Treat a non-empty result the way you treat the existing families: inspect, resolve, or track as known debt.
- `EvolutionRequirement` gains an `ontology-tightening` arm (`changes`, `edgeCardinalityAxes`), listed on a change plan whose delta tightens the ontology or an edge cardinality. An exhaustive `switch` over `requirement.kind` must handle it.
- `rollbackSchema()` may now refuse where it previously flipped the active version unconditionally: with `MigrationError` for a tightening live rows violate or a populated edge re-key, and with `ConfigurationError` `IDENTITY_ROLLBACK_REQUIRES_MIGRATION` for an identity-relevant change on an identity-enabled target.
- Backend authors: `GraphBackend` gains an optional `setActiveVersionWithPreflight(params, preflight)`, which runs `preflight` in the same schema-write transaction and under the same fence as the active-version flip. The bundled SQL backends implement it. A custom backend without it keeps working for rollbacks that owe no preflight; a rollback that owes one is refused with the same atomic-preflight capability error a forward commit raises (`ONTOLOGY_TIGHTENING_REQUIRES_ATOMIC_BACKEND`, `EDGE_CARDINALITY_TIGHTENING_REQUIRES_ATOMIC_BACKEND`, or `IDENTITY_REQUIRES_ATOMIC_BACKEND`).
