**`isStructuralSubtype(child, parent)`** joins the `@nicia-ai/typegraph/schema` entrypoint: a structural-subtyping check over TypeGraph's projected JSON Schema fragment that answers whether every value satisfying `child` is guaranteed to satisfy `parent`. The verdict is three-way — `subtype`, `not-subtype` with the deepest failing reason and path, or `incomparable` when either side carries a construct the projection cannot judge (`$ref`, `allOf`, `not`, unmodeled JSON Schema keywords, or nesting past the depth guard) — so an unjudgeable pair is refused rather than accepted. Width subtyping is allowed, required parent properties must stay required and narrower in the child, `integer` narrows `number`, unions match member-wise with sibling keywords ANDed, and `format` is compared as a constraint because the Zod projection emits it without a `pattern` for validators such as `z.url()`. It answers a different question from the migration classifier's `isBreakingPropertyChange`, which asks whether existing rows stay valid after a schema edit; the two disagree in both directions and the module documents why. It is the predicate this release's typed `subClassOf` / `equivalentTo` contract is built on.

**Ontology changes are now classified by what they do to existing data**, and a tightening the data violates is refused instead of auto-migrated. Adding `disjointWith`, `subClassOf` or `equivalentTo` is classified `warning` and probed inside the schema-commit transaction — before the Operational Identity closure rebuild — on every path that commits a version (`createStoreWithSchema` / `ensureSchema`, `Store.evolve()`, and `migrateSchema()`). Removing `subClassOf`/`equivalentTo` is probed for live edges whose endpoints the remaining declarations no longer admit. Adding or removing `inverseOf` or `implies` is now `breaking`: both change what a default `expand` traversal returns, so they need an explicit `migrateSchema()`, exactly like the Operational Identity `sameIdAcrossKinds` flip. Removing `disjointWith` stays `safe`, and `broader`/`narrower`/`partOf`/`hasPart`/`relatedTo`/`differentFrom` stay `safe` in both directions. A relation whose `from` or `to` names a kind the same commit removes is `safe`, so `Store.removeKinds()` is unaffected. `ChangeSeverity` itself is unchanged — `warning` now means "auto-migrates only if the data allows it".

**A refused tightening throws `MigrationError`** with `details.reason: "ontology-tightening-violated"` and `details.violations` in exactly the shape `store.verifyConstraintFences()` returns, so the same rows that block the migration can be listed, resolved, and the migration retried. The audit gains an `edgeEndpointAssignability` family reporting live edges sitting outside every declared endpoint pair. A backend implementing `readConstraintFenceViolations` may receive an `edgeEndpointAllowances` declaration and must answer with `misassignedEdgeEndpointRows`; omitting the key when the family was requested is refused with `CONSTRAINT_FENCE_AUDIT_FAMILY_UNSUPPORTED` rather than reported as a clean result. A backend that cannot commit a preflight atomically refuses a tightening with `ONTOLOGY_TIGHTENING_REQUIRES_ATOMIC_BACKEND`, and a preflight target that cannot run the audit refuses with the existing `CONSTRAINT_FENCE_AUDIT_UNSUPPORTED`. One residual window remains: a writer that commits under the previous schema version between the probe and the version compare-and-set is not seen, so `store.verifyConstraintFences()` remains the post-hoc detector.

**An ontology a diff cannot validate is now a refusal rather than a silent classification.** `classifyOntologyChanges` and `computeSchemaDiff` propagate `ConfigurationError` when a diff adds or removes an ontology relation and either side's stored or proposed ontology cannot be validated. This is new behavior for the stored side of the diff: nothing previously validated a persisted schema document's registry, so a document persisted under an older, laxer validator can surface this refusal the first time a relation-touching commit is attempted against it — including a fix-forward migration whose whole point is to remove the offending relation. There is no workaround for that case in this release; repair such a document through a path that does not diff ontology relations first. Every read-only caller built on `computeSchemaDiff` inherits this: `loadAndVerifyGraph` (and so `createVerifiedStore` / `assertSchemaCurrent`) and `getSchemaChanges()` now also throw `ConfigurationError` for the same documents. `requiresMigration()` is the one exception: it treats "cannot classify" the same as "needs migration" and returns `true` instead of throwing, so a document only the privileged path can interpret still routes there.

### Breaking

- `ConstraintFenceViolation` gains an `edgeEndpointAssignability` member, carrying `edgeKind`, `allowedPairs` and `edges` instead of a claim `target`. Narrow on `violation.family` before reading `violation.target`.
- A custom backend implementing `readConstraintFenceViolations` must answer `misassignedEdgeEndpointRows`, which the audit now requests for every registered edge kind. An un-updated custom backend finds the audit — and any ontology-tightening schema commit — refused with `ConfigurationError` `CONSTRAINT_FENCE_AUDIT_FAMILY_UNSUPPORTED` on any graph with at least one edge kind.
- Adding or removing `inverseOf`/`implies` now requires an explicit `migrateSchema()` even against clean data: `ensureSchema()`'s auto-migrate branch refuses these with `MigrationError` `reason: "breaking-change"`.
- A `subClassOf`/`equivalentTo`/`disjointWith` addition the data already violates is refused with `MigrationError` `reason: "ontology-tightening-violated"`. Inspect `details.violations` to find and resolve the offending rows, then retry.
- `store.verifyConstraintFences()` now also reports the `edgeEndpointAssignability` family, so it may surface pre-existing violations on a database that has never run this check. Treat a non-empty result the way you treat the existing families: inspect, resolve, or track as known debt.
