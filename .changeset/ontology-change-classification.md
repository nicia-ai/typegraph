Ontology changes are now classified by what they do to existing data, and a tightening the data violates is refused instead of auto-migrating. Adding `disjointWith`, `subClassOf`, or `equivalentTo` is classified `warning` and probed inside the schema-commit transaction — before the Operational Identity closure rebuild — on every path that commits a version (`createStoreWithSchema` / `ensureSchema`, `Store.evolve()`, and `migrateSchema()`). Removing `subClassOf`/`equivalentTo` is probed for live edges whose endpoints the remaining declarations no longer admit. Adding or removing `inverseOf` or `implies` is now `breaking`: both change what a default `expand` traversal returns, so they need an explicit `migrateSchema()`, exactly like the Operational Identity `sameIdAcrossKinds` flip. Removing `disjointWith` stays `safe`, and `broader`/`narrower`/`partOf`/`hasPart`/`relatedTo`/`differentFrom` stay `safe` in both directions. A relation whose `from` or `to` names a kind the same commit removes is `safe`, so `Store.removeKinds()` is unaffected. A refused tightening throws `MigrationError` with `details.reason: "ontology-tightening-violated"` and `details.violations` in exactly the shape `store.verifyConstraintFences()` returns, so the same rows that block the migration can be listed, resolved, and the migration retried. `ChangeSeverity` is unchanged — `warning` now means "auto-migrates only if the data allows it". `store.verifyConstraintFences()` gains a fourth `edgeEndpointAssignability` family reporting live edges sitting outside every declared endpoint pair. Backends implementing `readConstraintFenceViolations` may receive an `edgeEndpointAllowances` declaration and must answer with `misassignedEdgeEndpointRows`; a backend that omits the key when the family was requested is refused with `CONSTRAINT_FENCE_AUDIT_FAMILY_UNSUPPORTED` rather than reporting a clean result. A backend that cannot commit a preflight atomically refuses a tightening with `ONTOLOGY_TIGHTENING_REQUIRES_ATOMIC_BACKEND`, and a preflight target that cannot run the audit refuses with the existing `CONSTRAINT_FENCE_AUDIT_UNSUPPORTED`. The probe runs inside the commit transaction but takes no additional lock, so it carries the same residual window as the existing empty-kind fence: a writer that commits under the previous schema version between the probe and the version CAS is not seen, and `store.verifyConstraintFences()` remains the post-hoc detector. `classifyOntologyChanges` and `computeSchemaDiff` now propagate `ConfigurationError` when a diff adds or removes an ontology relation and either side's stored or proposed ontology cannot be validated. This is new behavior for the stored (before) side of the diff: nothing previously validated a persisted schema document's registry unless the code-level graph rebuilt one from it, so a document persisted under an older, laxer validator can surface this refusal the first time a relation-touching commit is attempted against it — including, in principle, a fix-forward migration whose whole point is to remove the offending relation. There is no workaround for that case in this release; repair such a document through a path that does not diff ontology relations first. Every read-only caller built on `computeSchemaDiff` inherits this: `loadAndVerifyGraph` (and so `createVerifiedStore` / `assertSchemaCurrent`) and `getSchemaChanges()` now also throw `ConfigurationError` for the same unclassifiable-ontology documents. `requiresMigration()` is the one exception — as the least-privilege routing predicate, it treats "cannot classify" the same as "needs migration" and returns `true` instead of throwing, so a document only the privileged path can interpret still routes there rather than crashing the check meant to route it.

### Breaking changes

- `ConstraintFenceViolation` (from `store.verifyConstraintFences()` and the new `MigrationError` `"ontology-tightening-violated"` detail) gains an `edgeEndpointAssignability` member that carries `edgeKind`, `allowedPairs`, and `edges` instead of a claim `target`. Code that reads `violation.target` unconditionally must narrow on `violation.family` first.
- A custom backend implementing `readConstraintFenceViolations` must now also answer `misassignedEdgeEndpointRows` whenever the request's `edgeEndpointAllowances` is non-empty. `store.verifyConstraintFences()` now always requests the family for every registered edge kind, so an existing custom backend that has not been updated will find `store.verifyConstraintFences()` — and any schema commit that tightens the ontology — refused with `ConfigurationError` `CONSTRAINT_FENCE_AUDIT_FAMILY_UNSUPPORTED` on any graph with at least one edge kind.

### Upgrade notes

- Adding or removing `inverseOf`/`implies` now requires an explicit `migrateSchema()` even against clean data — `ensureSchema()`'s auto-migrate branch refuses these with `MigrationError` `reason: "breaking-change"`.
- `subClassOf`/`equivalentTo`/`disjointWith` additions are probed against live rows inside the commit transaction and refused with `MigrationError` `reason: "ontology-tightening-violated"` when the data already violates the tightened ontology; inspect `details.violations` (same shape as `store.verifyConstraintFences()`) to find and resolve the offending rows before retrying.
- `store.verifyConstraintFences()` now also reports the `edgeEndpointAssignability` family, so it may surface pre-existing violations on a database that has never run this check before — treat a non-empty result the same way as the existing families (inspect, resolve, or track as known debt).
