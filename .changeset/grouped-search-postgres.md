A query that aggregates rows and carries a full-text, vector or hybrid predicate now runs on PostgreSQL and orders its groups by the same rule on every backend (#968). Every search statement appends a relevance ORDER BY (`rank DESC`, `distance ASC`, or the fused RRF score with a `node_id` tiebreak) that reads a per-match column. In a statement whose rows are groups (`groupBy()`, an ungrouped `aggregate()`, or a `project()` with an aggregate), PostgreSQL refused it (`column "cte_fulltext.rank" must appear in the GROUP BY clause`, likewise `cte_embeddings.distance` and `cte_embeddings.ord`), and SQLite ordered the groups by an arbitrary member's relevance. Such a statement now orders each group by its best member under the backend's native scoring: `MAX(rank)`, `MIN(distance)`, `MAX` of the fused score, with `MIN` of the `node_id` tiebreak. Native scores are engine-specific (SQLite's BM25 and PostgreSQL's `ts_rank_cd` can rank the same documents differently), so the rule is shared but the ranks it reads are not. The caller's `orderBy()` terms follow as tiebreakers, as in an ungrouped search.

The relevance ORDER BY also dropped `orderBy()` terms that name an `aggregate()` or `project()` output, so `.aggregate({ n: count("a") }).orderBy("n", "asc")` on a search query ignored the requested order on every backend. Those terms are now applied.

Every terminal of an aggregate query now selects the same rows in the same order. `first()`, `executeOn()`, `prepare()`, `count()`, `exists()` and `batchOnce()` run the statement through `asRelation()`, which moved the `aggregate()` output ordering to an outer query where it outranked relevance and dropped the relevance key altogether, so `.orderBy("n", "desc").first()` could return a different group from `.limit(1).execute()`. The relation now carries the statement's relevance keys and any `orderBy()` field terms as hidden columns and orders by them exactly as the statement does; `asRelation()` on a `project()` search query keeps its relevance order the same way. The public `QueryAst` type gains the optional `relevanceSortColumns` flag the adapters set to request those hidden columns; a statement without a search predicate ignores it, and a recursive statement refuses it.

The hybrid `node_id` tiebreak now compares in byte order on PostgreSQL (`COLLATE "C"`), as SQLite's BINARY collation and the store's own hybrid fusion already did, so tied hybrid matches and groups page in the same order on a database with a linguistic default collation.

A final `.limit()` no longer undercounts or drops the best match after a multi-hop traversal from an id-pinned start (#973). The compiler pushed the limit into the traversal CTEs whenever the statement had no `groupBy()`, `having()` or `orderBy()`, truncating the rows before an ungrouped `aggregate()` or aggregate `project()` folded them (a count of ten companies returned eight under `.limit(1)`) and before a full-text, vector or hybrid ORDER BY chose among them. The pushdown now applies only to statements that neither aggregate nor rank by relevance. Otherwise a search query that does not aggregate compiles to the same SQL as before, apart from the hybrid tiebreak's `COLLATE "C"` on PostgreSQL.
