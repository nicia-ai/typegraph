A SQLite transaction's backend now stops issuing statements when its transaction ends, as PostgreSQL's already did. On better-sqlite3 (and every other driver on the manual `BEGIN`/`COMMIT` path), a call or deferred read still running or kept when `store.transaction()` ended used to keep running on the connection: the rest of a write orphaned by a rejected `Promise.all` landed after `ROLLBACK` and reported success, a late write ran inside the next transaction and was rolled back with it, and a prepared query or `stream()` iterator kept past the callback read a later transaction's uncommitted rows. Every SQLite transaction TypeGraph opens (owned, manual, Durable Object storage, and schema-write transactions) now lets statements already running finish before `COMMIT`/`ROLLBACK` and refuses every later one with `TransactionClosedError`, the error PostgreSQL gives; libSQL's late statements now get that same typed error instead of the driver's own. This holds however the callback fails: one that throws synchronously, instead of returning a rejected promise, used to skip the drain, so a write through a backend it had kept reached the connection after `ROLLBACK`. Each transaction, and each retried attempt, gets a fresh view. Adopted transactions (`withTransaction`, `adoptTransaction`) are unchanged: the caller ends them.

The same now holds for the statements a transaction issues by other routes:

- **Trusted import, on both dialects.** A `TrustedImportSession` kept past `backend.trustedImport()` could still insert rows: on better-sqlite3 its batches ran on the root connection (autocommitting, or joining whatever transaction was open next), and on PostgreSQL they ran on the pinned client after the pool had taken it back. Both landed after the import's emptiness check and schema fence had expired, even when the import had rolled back. The session's `insertNodes()` / `insertEdges()` now run through the import transaction's view: a batch still in flight when the callback returns settles before `COMMIT` or `ROLLBACK`, and any later batch, an empty one included, is refused with `TransactionClosedError`. On PostgreSQL the batches also queue behind the transaction's other statements instead of bypassing its statement queue.
- **`createVectorIndex()` on a transaction backend** is refused, on both dialects, with a `ConfigurationError` whose `details.capability` is `"contributionAdministration"`, whether the transaction is open or has ended. Creating a vector index provisions storage (the per-field table, its durable marker, and the ANN index), which only the root backend does. Before, SQLite ran that DDL and marker write on the root connection, so an escaped transaction backend could create storage after its transaction ended; PostgreSQL already refused the storage half while the transaction was open. Call `createVectorIndex()` on the root backend (as `store.materializeIndexes()` does).
- **Contribution-marker reads on SQLite.** A transaction backend's vector writes and fulltext operations check the durable contribution marker on a cold cache. That read used to run on the root connection; it now goes through the transaction's view too, so after the transaction ends it is refused rather than reaching the connection. Where the transaction runs on the root's own connection (better-sqlite3, bun:sqlite, sql.js, Durable Object storage, the manual `BEGIN`/`COMMIT` frame) the marker cache is still shared with the root backend, so no transaction issues an extra statement. A libSQL transaction handle is a session of its own, and a caller's deferred libSQL transaction adopted with `adoptTransaction()` can hold a snapshot older than the root's reads: a marker another client recorded after that snapshot used to pass the check, and the write then failed with the driver's error on storage the transaction could not see. A libSQL transaction TypeGraph did not open holding the writer slot (an adopted transaction, or one opened deferred) now reads markers on its own session, with a cache of its own, as PostgreSQL transactions already did, and is refused with `StoreNotInitializedError`. A libSQL transaction keeps the shared cache only where it is proven to hold the writer slot: TypeGraph opened it `BEGIN IMMEDIATE` on a local client, which runs the `BEGIN` when the transaction opens and reports the engine's transaction state, so no other connection can commit while it is open. A remote client (`ws:`, `http:`) sends its `BEGIN` with the transaction's first statement, so a cold marker read through the shared cache ran on the root before that `BEGIN`; such a transaction now reads markers on its own stream.

A SQLite statement failure that ends its transaction no longer lets the callback carry on in autocommit. SQLite can end a transaction before the callback returns (a trigger's `RAISE(ROLLBACK)`, or an error SQLite answers by rolling back). A callback that caught that failure and kept going ran its next write outside any transaction on better-sqlite3 (and on a remote libSQL stream whose server runs a statement after its transaction ended), where it was saved, and the transaction then rejected with the driver's "cannot commit - no transaction is active"; local libSQL refused the next write with its own untyped error. Now, right after a statement fails and before any later statement of the transaction reaches the driver, the transaction's view asks whether the transaction is still open: the driver's own flag where it reports the engine's state (better-sqlite3's and bun:sqlite's `inTransaction`, a local libSQL transaction's `closed`), and otherwise SQLite itself, on the transaction's session (a `BEGIN` fails inside a transaction and opens one outside it, which is rolled back at once): a remote libSQL transaction, whose `closed` reports its stream rather than the server's transaction, libSQL before 0.18, sql.js and `sqlite-proxy`. Where neither can answer (Durable Object storage, which refuses raw transaction control) the view fails closed: the first statement failure ends the transaction. Once the transaction is not known to be open, every later statement of it is refused with `TransactionRolledBackError` (new `details.detectedBy: "statement-failure"`, `cause` the failed statement's error), which is distinct from the `TransactionClosedError` of a statement issued after the boundary, and the transaction rejects with that error without sending `COMMIT`. To make that hold for statements issued together (a `Promise.all`), a SQLite transaction's statements now reach the driver one at a time, in the order they were issued: a sibling submitted in the same turn as the failing statement waits for the answer instead of running in autocommit, as it did on an asynchronous execution profile over a synchronous driver.
