"@nicia-ai/typegraph": patch

A SQLite transaction's backend now stops issuing statements when TypeGraph ends its transaction, as PostgreSQL's already did. On better-sqlite3 (and every other driver on the manual `BEGIN`/`COMMIT` path), a call or deferred read still running or kept when `store.transaction()` ended used to keep running on the connection: the rest of a write orphaned by a rejected `Promise.all` landed after `ROLLBACK` and reported success, a late write ran inside the next transaction and was rolled back with it, and a prepared query or `stream()` iterator kept past the callback read a later transaction's uncommitted rows. Every SQLite transaction TypeGraph opens (Drizzle-run, manual frame, Durable Object storage, and schema-write transactions) now lets statements already admitted finish before `COMMIT`/`ROLLBACK` and refuses every later one with `TransactionClosedError`, the error PostgreSQL gives, before it reaches the connection; libSQL's late statements now get that same typed error instead of the driver's own. The callback runs inside the path that ends the view, so one that throws synchronously, instead of returning a rejected promise, closes it the same way. Each transaction, and each retried attempt, gets a fresh view. Statement ordering and queueing are unchanged: statements are admitted as they are issued, exactly as before.

The same now holds for the statements a transaction issues by other routes:

- **A backend adopted over the transaction's native handle, on both dialects.** `adoptTransaction(native)` inside `transactionWithNative()` used to get a view of its own that nothing closed, so a kept adoption's write after TypeGraph's `COMMIT` or `ROLLBACK` still reached the driver: on better-sqlite3 it ran in autocommit and was saved even though the transaction had rolled back. A transaction's view now belongs to the native transaction, as the engine identifies it (the identity the Store's per-native-transaction state uses): an adoption the engine can prove runs on a transaction TypeGraph opened shares that transaction's view, so its in-flight statements settle before the end and every later one is refused with `TransactionClosedError`. That proof exists on better-sqlite3, bun:sqlite, libSQL 0.18 and later, PGlite, node-postgres and postgres-js. On a driver that reports no transaction state (sql.js, libSQL before 0.18, Durable Object storage) the adoption cannot be proven to be the same transaction and keeps a view nothing closes, as before. A savepoint TypeGraph opens has a view of its own that closes with the savepoint.
- **A backend a public constructor builds over that native handle.** `createPostgresTransactionBackend(native)`, `createPostgresBackend(native)` given a transaction, and `createSqliteBackend(native)` given a transaction object (a libSQL transaction's native handle) used to build a fresh view nothing closed: on node-postgres a kept backend's write after TypeGraph's `ROLLBACK` ran on the released client in autocommit and was saved. They now adopt the native transaction exactly as `adoptTransaction(native)` does, sharing its view when the engine proves it is a transaction TypeGraph opened. That covers every member, not only the ones that go through the backend's execution adapter: the members that compose their statement on the Drizzle handle itself (contribution and reconciliation markers, index-materialization and kind-removal records, graph templates, lazy DDL, `refreshStatistics()`, index-build claims) used to write after the transaction ended, durably on PostgreSQL. They now go through the same view and, on PostgreSQL, the connection's statement queue. A backend built over a database handle is a root backend and is never refused; on better-sqlite3 the native handle a transaction callback receives is the connection itself, so a backend built over it is a root backend.
- **Trusted import, on both dialects.** A `TrustedImportSession` kept past `backend.trustedImport()` could still insert rows: on better-sqlite3 its batches ran on the root connection (autocommitting, or joining whatever transaction was open next), and on PostgreSQL they ran on the pinned client after the pool had taken it back. Both landed after the import's emptiness check and schema fence had expired, even when the import had rolled back. The session's `insertNodes()` / `insertEdges()` now run through the import transaction's view: a batch still in flight when the callback returns settles before `COMMIT` or `ROLLBACK`, and any later batch, an empty one included, is refused with `TransactionClosedError`. On PostgreSQL the batches also queue behind the transaction's other statements instead of bypassing its statement queue.
- **`createVectorIndex()` on a transaction's backend** (the one a transaction callback receives, or one `adoptTransaction()` returns) is refused, on both dialects, with a `ConfigurationError` whose `details.capability` is `"contributionAdministration"`, whether the transaction is open or has ended. Creating a vector index provisions storage (the per-field table, its durable marker, and the ANN index), which only a root backend does. Before, SQLite ran that DDL and marker write on the root connection, so an escaped transaction backend could create storage after its transaction ended; PostgreSQL already refused the storage half while the transaction was open. Call `createVectorIndex()` on the root backend (as `store.materializeIndexes()` does). A backend a caller builds over a transaction handle with `createPostgresTransactionBackend()` is not refused: it provisions in the caller's transaction as before, so `store.reembedVectorField()` and `store.materializeIndexes()` on a Store over it behave as they did.
- **Vector-slot marker eviction.** A transaction that deletes a vector slot's durable marker evicts the slot from the cache its marker checks read. A transaction that reads markers on its own session (every PostgreSQL transaction, and the SQLite transactions listed below) evicted only its own cache, so the root backend kept trusting the deleted marker after the delete committed and accepted a vector operation where it should refuse with `StoreNotInitializedError`. The eviction now reaches the root backend's cache too, and that key is re-read from the database from then on.
- **Contribution-marker reads on SQLite.** A transaction backend's vector writes and fulltext operations check the durable contribution marker on a cold cache. That read used to run on the root connection outside the transaction's view; it is now admitted through the view, so after the transaction ends it is refused rather than reaching the connection. A transaction whose handle resolves to the root backend's own connection (better-sqlite3, bun:sqlite, sql.js, Durable Object storage, the manual `BEGIN`/`COMMIT` frame) still shares the root's marker cache, so it issues no extra statement; so does a libSQL transaction TypeGraph opened `BEGIN IMMEDIATE` on a local client, which holds the writer slot from the moment it opens. Every other transaction reads markers on its own session with a cache of its own, as PostgreSQL transactions already did, and is refused with `StoreNotInitializedError` when its snapshot has no marker: a caller's deferred libSQL transaction or a caller's transaction on a second connection to the same WAL database (adopted with `adoptTransaction()`), which used to pass a marker committed after its snapshot and then fail with the driver's error, and a remote libSQL transaction, which sends its `BEGIN` with its first statement.

Known limits: the view closes when TypeGraph ends the transaction; an end SQLite makes on its own is not observed yet, and a later statement of the callback still reaches the driver exactly as before (on better-sqlite3 it runs in autocommit and is saved; libSQL refuses it with the driver's own error). The routes are a trigger's `RAISE(ROLLBACK)` fired by a native statement or by a TypeGraph statement, `COMMIT` or `ROLLBACK` sent through the native handle or through `executeStatement`, an `ON CONFLICT ROLLBACK` constraint, `SQLITE_FULL`, a backend adopted over the native handle writing after a trigger on the owner's write ended the transaction, a replacement transaction the native handle opened after a raw `ROLLBACK` (committed as the original), a lost `COMMIT` reply on `sqlite-proxy`, and a callback that fails with a retryable error after committing through the native handle (replayed under `retry`). A transaction the caller ends (`withTransaction`, `adoptTransaction`) is not closed by TypeGraph. On a single-connection libSQL client (`file::memory:`, an embedded replica), a transaction TypeGraph opens asking for the writer slot checks a cold contribution marker on the root client, whose one connection the transaction holds, and fails with the driver's `TRANSACTION_ACTIVE` error, as before; a check the root backend already confirmed issues no statement. On a client with a connection to spare, that same root-client check cannot see the transaction's own writes: after the transaction deletes a vector slot's marker, its next vector operation on that slot is still authorised by the committed marker, as before. A backend adopted over a savepoint's native handle shares the enclosing transaction's view, not the savepoint's, so after the savepoint rolls back its writes still run and commit with the enclosing transaction, as before. Conversely, a savepoint a constructor-built backend opens with `transaction()` has a view the enclosing transaction's end does not close: a savepoint callback still running when TypeGraph rolls the enclosing transaction back can write on the released connection (on node-postgres and postgres-js the write is saved in autocommit), as before. On PostgreSQL each binding of one transaction (its backend, each adoption) keeps its own marker cache: when an adoption deletes a slot's marker, a sibling binding that had already confirmed it keeps authorising vector operations on that slot until the transaction ends, as before.
