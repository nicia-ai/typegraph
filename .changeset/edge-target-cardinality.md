An edge registration can declare `targetCardinality: "many" | "one" | "oneActive"`, bounding the edges that point AT one node independently of `cardinality`, which bounds the edges leaving one source. Target `"one"` with the default source `"many"` is many-to-one ownership: a source may point at many targets, each target may be pointed at once. The two axes compose freely — all twelve combinations with the existing `cardinality` values, `unique` included, are accepted and enforced together — and both are enforced atomically on every public write path: create, upsert, get-or-create, bulk writes, resurrection, validity-window reopening, validating import, and merge apply after endpoint canonicalization. Two concurrent writers cannot both take the same target, including on a default PostgreSQL store with history and revision tracking disabled.

The target reservation is scoped to the graph, the edge kind, the target kind and the target id, and deliberately not to the source: two permitted source kinds contend for one target allowance. Equal ids under different target kinds, edge kinds or graphs never collide. The temporal populations are the existing ones read from the other end — `"one"` counts every non-deleted edge at the target, including edges with a validity end, while `"oneActive"` counts only those whose `validTo` is unset. Soft-deleted edges occupy no slot; a resurrection or a reopened window reacquires every applicable reservation; ending an edge frees an active-only slot and never frees a `"one"` slot. These are limits on edge count rather than on distinct neighbours, so a second distinct edge from the same source to a constrained target is refused too, while an idempotent operation returning the existing edge consumes nothing.

`CardinalityError` stays the violation type and its details now name the `direction` and both endpoints. `verifyConstraintFences()` reports target-side violations in the existing `edgeCardinality` family. Schema serialization, hashing, introspection, runtime graph extensions and schema diffing preserve the declaration; a schema stored before this release loads as `"many"`. Tightening either axis on a populated graph now validates the existing rows inside the schema-commit transaction and refuses with a `MigrationError` naming the violating endpoints rather than publishing a constraint the data already breaks.

Runtime graph-extension documents may now declare `cardinality` and `targetCardinality` on an edge. Previously both keys were rejected in strict mode and dropped otherwise, so an extension-authored edge kind was always unconstrained.

### Breaking changes

- `EdgeRegistration` gains `targetCardinality?`, and `SerializedEdgeDef` / `EdgeIntrospection` gain a required `targetCardinality`. Code that builds either object literal by hand must add it; everything produced through `defineGraph`, the serializer or `introspectSchema` is unaffected. The serializer now writes `targetCardinality` on every edge kind, defaulting to `"many"`, so the schema hash changes for any graph that declares at least one edge kind, whether or not it uses the new option. The change is semantically empty — a schema document stored before this release loads `targetCardinality` back as `"many"` via the same default the serializer applies, so `ensureSchema` computes an empty diff and returns `status: "unchanged"` — but every existing graph pays a one-time serialize-and-diff on its first boot after upgrading, because the stored hash no longer matches.
- `GraphBackend.countEdgesFrom` is replaced by `countEdgesAtEndpoint`, whose params carry `endpoint: "from" | "to"` and the endpoint's identity as `endpointKind` / `endpointId` (not `kind` / `id` — that narrower shape would structurally satisfy `DeleteEdgeParams` / `HardDeleteEdgeParams` and silently conscript the read into the library's derived graph-entity write surface). A custom backend renames its implementation and reads the endpoint discriminant.
- `ClaimEdgeCardinalityParams` gains a required `direction: "source" | "target"` discriminant, and `EdgeCardinalityDeclaration` / `ContendedEdgeRow` gain the same. Source-side claim axis strings are byte-identical to before, so existing `typegraph_edge_claims` rows keep fencing what they fence today and no migration is required.
- `ManagedEdgeCreatePlan.cardinalityClaim` becomes `cardinalityClaims: readonly ClaimEdgeCardinalityParams[]`. A command port that applies the claim must apply every entry or return `unsupported` with the `"cardinalityClaim"` dimension before executing any SQL; the bundled fused insert applies a single claim and refuses a two-axis plan to the portable path.
- `CardinalityErrorDetails` gains required `direction`, `toKind` and `toId`. Existing `edgeKind` / `fromKind` / `fromId` / `cardinality` / `existingCount` are unchanged.
- A trusted import now refuses a graph declaring any edge cardinality, in either direction, with `TrustedImportError` reason `"cardinality_unsupported"`. That path maintains no claims, so it previously wrote source-side-constrained graphs unfenced. Use `importGraph`, or declare the kind unconstrained on both axes and enforce the limit in application code.
- A schema commit that newly declares a constrained `cardinality` or `targetCardinality` on an edge kind — including declaring one on a brand-new kind, since a stored schema with no entry for that kind reads as unconstrained (`many`) on both axes — now runs the same atomic data-check preflight an ontology tightening does, inside the schema-commit transaction. A backend that implements `commitSchemaVersion` but not `commitSchemaVersionWithPreflight` throws `ConfigurationError` code `EDGE_CARDINALITY_TIGHTENING_REQUIRES_ATOMIC_BACKEND` for such a commit, including one that only adds a new edge kind and touches no existing ontology relation.
- An edge kind name containing U+001E is refused at `defineGraph`, joining node kinds and unique constraint names. TypeGraph reserves that code point for claim axes.
