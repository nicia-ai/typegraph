Add `store.pruneRecordedInstants(before, { limit })` for bounded recorded allocation-log retention. Each call deletes one limited revision range and returns the deleted count, retained boundary, and whether more physical cleanup remains. A durable coverage watermark distinguishes explicitly pruned lookup coverage from unlogged history and valid naturally gapped logs. Saved anchors, allocation ownership, and captured entity history remain intact.

Only pruning requires base-schema version 9, which adds nullable `anchor_retention` storage on the recorded clock. Existing `resolveRecordedInstant` calls continue to work on pre-v9 storage, including synchronous local SQLite upgrades and previously allocated PostgreSQL working copies. Lookup reads the optional watermark in the same statement as its candidate and adds no marker probe. Pruning calls the backend-owned `assertBaseSchemaCurrent` lifecycle assertion and reports the actual installed version in `BaseSchemaMigrationError`; custom backends must expose that member to support pruning. PostgreSQL skips installed columns and uses a bounded queued ALTER when adoption is needed, allowing progress through overlapping writers. It preserves stricter caller timeouts and restores caller sessions through savepoints. Persistent contention raises the table-specific `BaseSchemaAdoptionTimeoutError`. DML-only deployments must apply the published base-schema migration before pruning. Upgrade every reader before starting retention, and coordinate cleanup with checkpoint, replication, and entity-history retention. Both entrypoints retain capability-first validation; lookup retains its `resolve-recorded-anchor` missing-storage surface. The first batch retires lookup coverage immediately; resume while `hasMore` is true to finish physical cleanup.
