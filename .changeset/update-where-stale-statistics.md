The write phase of `updateWhere()` and `compareAndSet()` stays linear in its candidates when PostgreSQL's planner statistics predate the candidate rows, which is what a bulk load into a large shared table leaves behind because one import never reaches autovacuum's analyze threshold. The set update matched `(id, version) IN (SELECT … FROM (candidates) JOIN nodes …)` with `graph_id = ? AND kind = ?` as constant predicates on the nodes table; with statistics estimating the kind at one row, PostgreSQL drove a nested loop from that kind's range and rescanned the candidates, and the join behind them, once per row. The graph and kind now reach the nodes table only as columns of a `DISTINCT` key subquery, which the planner does not flatten, so it has no range to misestimate and the write phase never rescans: whatever the statistics, it costs at most one scan of the nodes table plus constant work per candidate, provided each candidate's id is unique within its graph across kinds, as generated ids are. Each keyed lookup reads the `(graph_id, id)` index and checks the kind afterwards, so an id that K other kinds of the same graph also hold can cost up to K more index entries per lookup: 1,000 candidates whose ids 100 other kinds held visited 202,000 index entries in the two lookups, still linear in the candidates for a given K. Whether PostgreSQL looks the keys up or scans the table follows its estimate of the candidate count, not the actual count. When the target graph is new to the statistics, each candidate is found by an index lookup on its id: three rows and about 29 buffers per candidate from 1,000 to 20,000 candidates, on a server and on PGlite, where the previous statement visited 167 million rows for 1,000 candidates; against 300,000 analyzed rows of other graphs, a whole `updateWhere()` call over 20,000 fresh ids takes 2.8 s, of which the `UPDATE` is 1.2 s. When the graph and the kind are each in the statistics but never together, PostgreSQL multiplies their frequencies, estimates thousands of candidates, and hashes them against one sequential scan of the table even for a single candidate. The previous statement read only the kind's index range there and was cheaper: one candidate against 1,000,000 analyzed rows now reads 1,000,003 rows and 13,905 buffers in 367 ms, where it read 3 rows and 14 buffers in 1 ms. A selection by id is estimated at one row in that state too, so `compareAndSet()` and an `updateWhere()` by id stay keyed. Above a few thousand candidates the row writes dominate both statements' cost.

The update is still one statement, so the selected rows are the rows written, and a direct `updateNodeSet` or `compareAndSetNode` call on an autocommit connection is atomic. For `updateWhere()`, a row changed after the statement's snapshot, or deleted and re-created under the same id, is skipped. `compareAndSet()` is unchanged in this respect: it writes a row a concurrent transaction changed as long as the expected properties still match.

The candidate query is evaluated once on every backend. SQLite codes the version-keyed row-value `IN` twice, once to walk the primary key and once to test the row, and ran the candidate query once per coding, so a direct `updateNodeSet` call whose candidate query returns different rows on each evaluation wrote only the rows both evaluations returned. The keys are now a CTE that SQLite materializes once (`MATERIALIZED`) and PostgreSQL inlines (`NOT MATERIALIZED`), which leaves PostgreSQL's plan unchanged.

The key subquery deduplicates and matches candidate ids with the primary key's own equality (`BINARY` on SQLite, the database's default collation on PostgreSQL, which is always deterministic), whatever collation the candidate query projects them under. A direct `updateNodeSet` or `compareAndSetNode` call whose candidates project ids case-insensitively therefore writes exactly the ids it names: two ids that differ only by case stay two rows, and on PostgreSQL a non-candidate id's case twin is no longer written too.

Candidate selection is unchanged and still depends on the statistics: the candidates are an ordinary query over the nodes table. Selecting a single id from a fresh kind can scan the kind's un-analyzed rows and filter the id (3,999 rows filtered to select one of 4,000), so a loop of single-row mutations over a fresh kind stays quadratic until the table is analyzed, as other per-row loops do. The PostgreSQL backend docs describe both states and how to refresh statistics after a large load.
