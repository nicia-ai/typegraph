The write phase of `updateWhere()` and `compareAndSet()` no longer depends on PostgreSQL's planner statistics, so a batch stays linear in its candidates when the nodes table's statistics predate the candidate rows, which is what a bulk load into a large shared table leaves behind because one import never reaches autovacuum's analyze threshold. The set update matched `(id, version) IN (SELECT … FROM (candidates) JOIN nodes …)` with `graph_id = ? AND kind = ?` as constant predicates on the nodes table; with statistics estimating the kind at one row, PostgreSQL drove a nested loop from that kind's range and rescanned the candidates, and the join behind them, once per row. The graph and kind now reach the nodes table only as columns of a `DISTINCT` key subquery, which the planner does not flatten, so it has no range to misestimate: the candidates are read once and each row is found by an index lookup on its id. Under the same stale statistics the plan visits three rows and about 29 buffers per candidate from 1,000 to 20,000 candidates, on a server and on PGlite, where the previous statement visited 167 million rows for 1,000 candidates; against 300,000 analyzed rows of other graphs, a whole `updateWhere()` call over 20,000 fresh ids takes 2.8 s, of which the `UPDATE` is 1.2 s. The update is still one statement, so the selected rows are the rows written: a row changed after the statement's snapshot, or deleted and re-created under the same id, is skipped, and a direct `updateNodeSet` call on an autocommit connection is atomic.

The key subquery deduplicates and matches candidate ids with the primary key's own equality (`BINARY` on SQLite, the database's default collation on PostgreSQL, which is always deterministic), whatever collation the candidate query projects them under. A direct `updateNodeSet` or `compareAndSetNode` call whose candidates project ids case-insensitively therefore writes exactly the ids it names: two ids that differ only by case stay two rows, and on PostgreSQL a non-candidate id's case twin is no longer written too.

Candidate selection is unchanged and still depends on the statistics: the candidates are an ordinary query over the nodes table. Selecting a single id from a fresh kind can scan the kind's un-analyzed rows and filter the id (3,999 rows filtered to select one of 4,000), so a loop of single-row mutations over a fresh kind stays quadratic until the table is analyzed, as other per-row loops do. The PostgreSQL backend docs describe the state and how to refresh statistics after a large load.
