`updateWhere()` and `compareAndSet()` stay linear on PostgreSQL when the nodes table's planner statistics predate the candidate rows, which is what a bulk load into a large shared table leaves behind because one import never reaches autovacuum's analyze threshold. The set update matched `(id, version) IN (SELECT … FROM (candidates) JOIN nodes …)` with `graph_id = ? AND kind = ?` as constant predicates on the nodes table; with statistics estimating the kind at one row, PostgreSQL drove a nested loop from that kind's range and rescanned the candidates, and the join behind them, once per row. The graph and kind now reach the nodes table only as columns of a `DISTINCT` key subquery, which the planner does not flatten, so it has no range to misestimate: the candidates are read once and each row is found by an index lookup on its id. Under the same stale statistics the plan visits three rows and about 29 buffers per candidate from 1,000 to 20,000 candidates, on a server and on PGlite, where the previous statement visited 167 million rows for 1,000 candidates; against 300,000 analyzed rows of other graphs, a whole `updateWhere()` call over 20,000 fresh ids takes 2.8 s, of which the `UPDATE` is 1.2 s. The update is still one statement, so the selected rows are the rows written: a row changed after the statement's snapshot, or deleted and re-created under the same id, is skipped, and a direct `updateNodeSet` call on an autocommit connection is atomic.
