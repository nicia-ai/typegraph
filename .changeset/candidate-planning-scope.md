**Candidate planning reports the scope it planned in, and says why bounded planning is refused.** `planCandidateWriteSet()` returns the scope beside the plan as `planningScope`: `{ scope: "candidate" }` when it staged the candidate from its own rows, or `{ scope: "full", reason }` when it copied the whole target. Bounded planning is also judged against the constraints the sparse base never reads: a graph declaring a composition pair, an `acyclic` edge or a target-side cardinality needs the whole target, as does a backend missing a keyed read. `reason` is one of `composition`, `acyclic-relation`, `target-side-cardinality`, `missing-active-source-read`, `missing-match-identity-read`, `missing-scoped-identity-reads`, `match-identity-owner-not-clone-visible`, `planned-evolution` or `full-requested`. Both scopes produce the same plan, so the scope is not part of the merge plan artifact or its digest. The new `CandidatePlanningScope`, `CandidatePlanningScopeReason`, `FullPlanningScope` and `CandidateWriteSetPlan` types are exported from `@nicia-ai/typegraph/graph-merge`.

**A refused bounded plan names its reason.** Under the default `planningScope: "candidate"`, a target or candidate that needs the whole target is refused with the new `CandidatePlanningScopeError` before any staging backend is created. It is a `MergePlanCapabilityError` with the same code (`GRAPH_MERGE_PLAN_CAPABILITY`), and its details are `{ capability: "boundedCandidatePlanning", requiredPlanningScope: "full", planningScope }`, where `planningScope.reason` names the cause. `planningScope: "full"` plans against the whole target and reports `full-requested`. The same rule now covers `planMutations()`, which previously checked only the backend's reads, and `planCandidateWriteSetForEvolution()`, which refuses with reason `planned-evolution` unless `"full"` is stated. A candidate the target's schema refuses still reports its own validation error (`CandidateWriteSetError`) under either scope, and a target that cannot carry a public merge plan at all (no revision tracking, or no interactive transactions) is refused with `MergePlanCapabilityError` before any staging backend is created. The review entry points forward the option to planning. A refused candidate-scoped review (`details.reason: "candidate-scope-ineligible"`) now also carries `details.planningScope` naming the cause.

### Breaking

- A graph that declared `partOf` or `hasPart` before this release now declares a composition relation (its declaration names the realizing edge with `via`), and candidate and mutation planning refuses on a composition graph by default: `planCandidateWriteSet()`, `planCandidateWriteSetReview()`, `revalidateCandidateWriteSetReview()` and `planMutations()` called without `planningScope` return `CandidatePlanningScopeError` (`details.planningScope.reason: "composition"`) where they used to plan. Pass `planningScope: "full"` on each such call, including every revalidation (the review does not record the planning scope), to plan against a complete copy of the target as before.
- `planCandidateWriteSet()` and `planCandidateWriteSetForEvolution()` now resolve to `Result<CandidateWriteSetPlan, MergeError>`, `{ plan, planningScope }`, instead of the bare `MergePlanArtifact`. Read the artifact from `result.data.plan`, for example `const { plan } = unwrap(await planCandidateWriteSet(args))`.
