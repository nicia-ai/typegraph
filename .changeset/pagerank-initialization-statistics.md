PageRank, personalized PageRank and label propagation on PostgreSQL refresh the working table's planner statistics after populating it and before the first initialization statement that joins against it: PageRank's out-weight accumulation and label propagation's neighbor materialization. The iterative runner used to refresh statistics only after an algorithm's whole initialization, so PostgreSQL planned those joins against its one-row estimate for an un-analyzed temporary table and chose nested loops that grow quadratically with the selected subgraph. Iterative plans can now declare a population phase, and the runner refreshes statistics between it and the rest of initialization through the same size-gated refresh it uses between rounds. The refresh is still skipped below 16 rows, and it replaces the post-initialization refresh, so each run issues the same number of `ANALYZE` statements as before. On a PostgreSQL 18 server, with a 1,000-node induced subgraph carrying 2 internal and 2 external outgoing edges per node, PageRank's out-weight statement dropped from about 401 ms to about 11 ms and its initialization from about 416 ms to about 24 ms. With 16 internal and 16 external edges per node at the same size, the old out-weight statement was still running after 21 minutes. On in-process PostgreSQL (PGlite), with 100 nodes and 2 + 2 edges per node, label propagation's neighbor materialization dropped from about 138 ms to about 6 ms. Results are unchanged. SQLite emits no temporary-table `ANALYZE` and is unaffected.
