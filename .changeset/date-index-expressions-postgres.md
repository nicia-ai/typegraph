A declared index that reads a `z.date()` property is now refused on PostgreSQL with a typed error before any DDL, instead of failing with the engine's `functions in index expression must be marked IMMUTABLE` (42P17) (part of #927). The index expression casts the stored ISO text to `timestamptz`, and PostgreSQL refuses that cast in an index because it depends on the session time zone, so such an index could never be built on any PostgreSQL driver. The gap is declared as a new backend capability, `capabilities.dateIndexExpressions`: `false` on the bundled PostgreSQL backends (node-postgres, postgres-js, Neon, PGlite), `true` on the bundled SQLite backends, and absent (supported) on a custom backend.

On a backend that declares `false`, `store.materializeIndexes()` (including the eager form of `store.evolve()`) throws `UnsupportedBackendCapabilityError` with `details.capability` `"dateIndexExpressions"` and the index's `entity`, `kind`, `indexName`, `field` and `position` (`"key"`, `"coveringField"` or `"where"`) when any selected node or edge index reads a date property in a lookup key, an ordered key, a covering column or a partial-index `where` clause, including nested date fields and a `where` null check. The refusal happens before the status table or any index is created, so no index of that call is built; pass `materializeIndexes({ kinds })` to build the other kinds' indexes. Previously the date index came back as a `failed` entry while its siblings were created. `store.evolve(extension, { eager })` runs the same checks against the evolved graph before its schema commit, so an eager evolution that would be refused writes no schema version; an unknown `eager.kinds` entry and a backend without the materialization primitives (`executeDdl`, `getIndexMaterialization`, `recordIndexMaterialization`, `catalog`) are now refused there too, before the commit rather than after it. `store.materializeIndexes()` itself now refuses a backend without `catalog` before it creates the status table, rather than after. Eager materialization then builds the indexes of the schema version that call committed rather than reloading the active schema, so a second writer that commits a date-typed index in between can no longer make an already-committed evolve throw the refusal. `prepareNamespaceForkTarget()` checks the indexes it replays from the source against the target backend's capability before any target DDL (the retry ledger included), so forking to a bundled PostgreSQL target from a source that could build a date-typed index is refused with the typed error instead of failing with 42P17 halfway through preparation. The PostgreSQL DDL entry points that take a dialect rather than a backend refuse the same declarations against the bundled PostgreSQL declaration: `createPostgresTables({ indexes })`, `generateIndexDDL` / `generateNodeIndexDDL` / `generateEdgeIndexDDL` with `"postgres"`, and `buildPostgresNodeIndexBuilders` / `buildPostgresEdgeIndexBuilders`, so neither drizzle-kit nor a hand-rolled migration can emit their DDL.

A relational index declaration whose `fields` and `fieldValueTypes` (or `coveringFields` and `coveringFieldValueTypes`) differ in length is now refused instead of pairing a field with a neighbour's value type: every path that compiles or classifies it throws `ConfigurationError` (code `INDEX_FIELD_VALUE_TYPES_MISMATCH`), and a stored schema document carrying one fails its parse. Previously it compiled silently. `defineNodeIndex` and `defineEdgeIndex` never produce one; a hand-built or edited declaration could, and the capability check and the DDL could then disagree on which field is date-typed.

`defineGraph` and store construction still accept the declaration: neither knows the engine (SQLite builds the same index), and a declaration that is never materialized still has non-DDL consumers. An array of dates indexed with `method: "gin"` is unaffected, as are number, coerced-number, boolean and string keys.
