A declared index that reads a `z.date()` property is now refused on PostgreSQL with a typed error before any DDL, instead of failing with the engine's `functions in index expression must be marked IMMUTABLE` (42P17) (part of #927). The index expression casts the stored ISO text to `timestamptz`, and PostgreSQL refuses that cast in an index because it depends on the session time zone, so such an index could never be built on any PostgreSQL driver. The gap is declared as a new backend capability, `capabilities.dateIndexExpressions`: `false` on the bundled PostgreSQL backends (node-postgres, postgres-js, Neon, PGlite), `true` on the bundled SQLite backends, and absent (supported) on a custom backend.

On a backend that declares `false`, `store.materializeIndexes()` (including the eager form of `store.evolve()`) throws `UnsupportedBackendCapabilityError` with `details.capability` `"dateIndexExpressions"` and the index's `entity`, `kind`, `indexName`, `field` and `position` (`"key"`, `"coveringField"` or `"where"`) when any selected node or edge index reads a date property in a lookup key, an ordered key, a covering column or a partial-index `where` clause, including nested date fields and a `where` null check. The refusal happens before the status table or any index is created, so no index of that call is built; pass `materializeIndexes({ kinds })` to build the other kinds' indexes. Previously the date index came back as a `failed` entry while its siblings were created. `createPostgresTables({ indexes })` refuses the same declarations, so drizzle-kit can no longer emit their DDL.

`defineGraph` and store construction still accept the declaration: neither knows the engine (SQLite builds the same index), and a declaration that is never materialized still has non-DDL consumers. An array of dates indexed with `method: "gin"` is unaffected, as are number, coerced-number, boolean and string keys.
