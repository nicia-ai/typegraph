"@nicia-ai/typegraph": minor
---

A date property can no longer be written with a `Date` that PostgreSQL cannot store as a date. `z.date()` accepts any valid `Date` and the store writes it as its `toISOString()` text, but PostgreSQL cannot cast the text of a `Date` in year 0000 (`date/time field value out of range`), before the common era (`-000001-…`) or after 9999 (`+010000-…`) to `timestamptz`. Once stored, such a value made every date predicate, `orderBy` and typed read of the property fail on PostgreSQL for the whole query, while SQLite answered and compared the latter two out of chronological order.

- Every store write that validates props — node and edge `create`, `update`, `upsertById`, the `*FromRecord` forms, `bulkCreate`, `bulkReplaceById`, `bulkUpsertById`, `bulkInsert` and the get-or-create methods — now refuses a `Date` outside the years 0001 to 9999 anywhere in the props, including array elements and nested object fields, with `ValidationError` naming its path. The decision is `canonicalDateOperandText`, the one every date predicate operand already passes.
- `trustedImportGraph` / `trustedImportGraphStream`, which store props verbatim, refuse a property the schema types as a date (including an array element or nested field) unless it is a canonical UTC instant in those years, with `TrustedImportError` (`details.reason === "invalid_stream"`) before the chunk is written. This also refuses a short or zoned form such as `"2024-01-01T00:00:00Z"`, which SQLite (comparing text) and PostgreSQL (comparing the instant) would have compared with a cutoff differently. A property value whose own string conversion throws, such as the JSON object `{"toString": 4, "valueOf": 5}`, is refused the same way instead of raising a raw `TypeError` while the refusal is built.
- `importGraph` / `importGraphStream` refuse a `Date` outside those years in the props each `onUnknownProperty` strategy stores: the parsed props, a `Date` a coercing schema such as `z.coerce.date()` produces from text, and under `"allow"` one at an unknown property, which that strategy stores verbatim. The row is reported in `errors` and not written. Previously an in-memory `Date` in year 0000 imported on every backend and then broke typed reads on PostgreSQL.
- Validity bounds (`validFrom`, `validTo`), `asOf` and recorded-time coordinates, and the timestamps of interchange documents, merge plans and candidate write sets now refuse year 0000 as well. An archival interchange document's transition `recordedAt` and retention `prunedBeforeRecordedAt` are now held to the same canonical form in the years 0001 to 9999: they accepted any `z.iso.datetime()` value, so a year-0000 `recordedAt` restored on SQLite and failed the transition insert on PostgreSQL, and a short form such as `"2024-01-01T00:00:00Z"`, which exports never write, is now refused too. A year-0000 `validFrom` previously stored on SQLite and failed the insert on PostgreSQL with a raw driver error; a year-0000 `asOf` ran on SQLite and failed on PostgreSQL.

The refusal does not repair rows written before it. `getById`, `find` and a whole-node select still return the stored text on every backend; on PostgreSQL a query that filters, orders by or selects the property still fails with the cast error. Repair such a row by writing a valid `Date` to the property, for example `update(id, { at: new Date(…) })`.
