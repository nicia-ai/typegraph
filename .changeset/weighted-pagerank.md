`store.algorithms.pageRank` and `personalizedPageRank` accept edge weights. `weightProperty` names a top-level numeric edge property and `defaultWeight` supplies the weight of an edge that lacks it, with the same meaning as on `weightedShortestPath`. A node's rank is then distributed over its out-edges in proportion to their weights instead of equally: parallel edges add their weights, a zero-weight edge carries nothing, and a node whose out-edge weights sum to zero is treated as a dangling node. With `direction: "both"` a weighted self-loop still counts once. Together with weighted seeds this lets a retrieval pipeline run search hits through personalized PageRank over weighted relationships. The weights go through the audit `weightedShortestPath` already runs, now owned by one module both algorithms call: before any round, a negative, non-numeric or out-of-range weight on any visible edge of the selected kinds, or a missing weight with no `defaultWeight`, throws `InvalidEdgeWeightError` naming the edge. `defaultWeight` without `weightProperty`, an empty `weightProperty`, and a negative, non-finite or out-of-range `defaultWeight` throw `ConfigurationError`. Weights are read at the call's temporal coordinate, including through `store.asOf(...)` and recorded-time views. Only the ratio between one node's out-edge weights matters, so their scale does not: integer-valued weights whose sum exceeds the 64-bit integer range are summed as doubles on SQLite, a node's lone out-edge carries its whole rank even at the smallest accepted weight, and an undirected self-loop is never rounded away. Calls without `weightProperty` issue the same statements and return the same scores as before. Scores agree between SQLite and PostgreSQL within the requested tolerance.
