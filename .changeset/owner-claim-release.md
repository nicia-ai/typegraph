A uniqueness claim is now released by the node that holds it, and a claim taken from a stored row is keyed from the value the row stores, with its date text read back as a `Date`. A write keyed its claim from the props it validated, where a date is a `Date` (keyed as its JSON-quoted ISO text), but an update, a soft delete and several batch and lookup paths keyed the row they read back, where the same date is unquoted ISO text and a PostgreSQL `jsonb` object has its keys reordered. The release then named a claim the write never took: the old value stayed reserved, a later create of it was refused with a `UniquenessError` naming a node that no longer held it, and `findByConstraint()` / `getOrCreateByConstraint()` could answer with that node. This held for every update that changed a unique date (`update()`, `upsertById()`, `bulkUpsertById()`, `bulkReplaceById()`, an import under `onConflict: "update"`), for a soft delete wherever it released per key, and for a date behind `z.lazy()` or inside a union with `null`.

Every update, soft delete, resurrection, upsert, set update, batch write, import update, merge apply and provenance close or reopen now gives back "the claims this node holds for this constraint" (for an update, those other than the key it now claims), selected by owner, never a key recomputed from the before-image. A claim keyed in any other form, such as a raw-text date or an object in another key order, is released by the same statement.

A claim is keyed by one owner, `uniqueConstraintKey`, which takes the kind's schema and puts each unique field's value in one canonical rendering before keying it, on every path: create, update, import in both `onUnknownProperty` modes, get-or-create and find lookups, resurrection, provenance retraction and reopen, batch writes and their cache priming, merge apply, its probes and its blocking signatures. No path chooses between a "validated" and a "stored" reading any more, so a write's parse output and the same value read back from storage key identically. At a date position (a `z.date()` reached through `.optional()`, `.nullable()`, `.default()` and the other transparent wrappers, through `z.lazy()`, through a pipe whose output is a date such as `z.string().pipe(z.coerce.date())`, through a union whose other branches are `null` or `undefined`, as a nested object property or as an array element), a `Date` and its stored ISO text key identically: at a top-level field as the JSON-quoted ISO text, the bytes `create()` has always claimed, and nested as the ISO text inside the enclosing value's JSON. At a `z.object()` position the value keys with its declared keys in the shape's order and its undeclared keys after them, whatever order the props carry (a `.default()` or `.catch()` literal, a PostgreSQL `jsonb` column, which returns an object's keys in its own order). Nothing is parsed through the schema again: a schema whose parse does not reproduce its own output (a transform that appends to its input) would key a value the row does not hold. At a union, a branch that structurally cannot hold the value has no say: a primitive of another type, a non-array for `z.array()`, a non-object for `z.object()`, or an object whose required `z.literal()` or `z.enum()` property (a discriminator) is missing or holds another value. A union whose remaining branches read a value differently (`z.union([z.date(), z.string()])`, or objects of different key orders that no discriminator tells apart) is keyed as given. The walk is linear in the value: one derivation walks a value at a schema once, and a discriminated recursive union walks only the branch its discriminator names, so keying a deeply recursive union costs one visit per level rather than one per branch per level.

An update compares, per constraint, the key the row holds as stored with the key of the props it is about to write, and touches only the constraints where the key or whether the constraint applies differs. An update that moves no key issues no claim statement, whichever fields it names, as before this change. Comparing keys rather than the fields a patch names matters because an update parses and rewrites the whole props object: under a transform, a field the patch does not name still changes value, and its claim moves with it.

`releaseUniquesByOwner` on the bundled backends splits a release into statements by constraint under the backend's declared bind budget, and lists the kept claims as one flat row-value list, so a write moving many constraints neither exceeds a 100-bind limit nor nests the predicate past SQLite's expression-depth limit. A constraint whose kept claims alone exceed the budget is not split, since the statement carrying one part of its kept list would release the keys another part keeps: the backend reads the owner's live keys under it and releases, by key, exactly those outside the complete kept list.

### Upgrade notes

- **A hand-written backend must implement `releaseUniquesByOwner`** (#1011). `GraphBackend.releaseUniquesByOwner(params: ReleaseUniquesByOwnerParams): Promise<void>` is a new required member of the custom-backend contract, on the root backend and on every `TransactionBackend` it hands out; a backend object without it no longer type-checks. Backends built by the bundled factories implement it, and no schema change is needed. A hand-assembled SQL operation strategy must likewise supply `CommonOperationStrategy.buildReleaseUniquesByOwner(params, timestamp)` and `CommonOperationStrategy.buildOwnerClaimKeys(params: OwnerClaimKeysParams)` (a `SELECT key` of the owner's live entries under one constraint, at every axis); the bundled backend sizes each call it makes to the release builder to its bind budget, and uses the read for a constraint whose kept claims alone do not fit. The contract:
  - **What it deletes:** every live (`deleted_at` unset) uniqueness entry with the given `graphId` whose owner is `(concreteKind, nodeId)` and whose constraint is one of `constraintNames`, at every axis (`node_kind`), except an entry whose `(constraintName, key)` pair is listed in `keep`. Match on owner and constraint only; compare no key other than those in `keep`, and never touch another owner's entry.
  - **How:** tombstone the entry (set `deleted_at`), as `deleteUnique` does. It must stop being returned by `checkUnique` and still be returned, with its key and owner, under `includeDeleted`, because `getOrCreateByConstraint()` finds a soft-deleted node through it.
  - **Where:** on the target the store calls it on. Inside a write that is the frame's `TransactionBackend`, so the statement commits or rolls back with the row write it follows.
  - **Size:** split a release your engine cannot bind in one statement by constraint, keeping each constraint's `keep` entries in the statement that names it. Never split one constraint's `keep` entries across statements; when they alone do not fit, read the owner's live keys under that constraint on the same target and tombstone, by key, those not in the complete list.
  - **Returns:** nothing; the store ignores the value. A release that matches no entry succeeds.
  - **Idempotent:** a second call with the same params changes nothing. An empty `constraintNames` releases nothing and needs no statement.

  A reference implementation over one SQL table with the bundled column names, where `execute` runs on the connection the member is called on (`$n` placeholders; adapt them to your driver):

  ```typescript
  import type { GraphBackend } from "@nicia-ai/typegraph/backend";

  type Execute = (sql: string, parameters: readonly unknown[]) => Promise<void>;

  function releaseUniquesByOwnerOn(
    execute: Execute,
  ): GraphBackend["releaseUniquesByOwner"] {
    return async (params) => {
      if (params.constraintNames.length === 0) return;
      const parameters: unknown[] = [
        new Date().toISOString(),
        params.graphId,
        params.concreteKind,
        params.nodeId,
      ];
      const bind = (value: unknown): string => {
        parameters.push(value);
        return `$${parameters.length}`;
      };
      const constraints = params.constraintNames.map((name) => bind(name));
      const kept = params.keep.map(
        (claim) => `(${bind(claim.constraintName)}, ${bind(claim.key)})`,
      );
      const keepTerm =
        kept.length === 0 ? "" : (
          ` AND (constraint_name, key) NOT IN (VALUES ${kept.join(", ")})`
        );
      await execute(
        `UPDATE typegraph_node_uniques SET deleted_at = $1
          WHERE graph_id = $2 AND concrete_kind = $3 AND node_id = $4
            AND deleted_at IS NULL
            AND constraint_name IN (${constraints.join(", ")})${keepTerm}`,
        parameters,
      );
    };
  }
  ```

  Index `(graph_id, concrete_kind, node_id)` so the statement does not scan; the bundled schema already has that index. The store now calls `deleteUnique` only to undo a claim a failed write just took, always with `nodeKind`. See "Releasing claims by owner" in the backend-authoring guide.
- **Statement cost of a node write on a kind with a unique constraint.** An update (`update()`, `upsertById()`, an import under `onConflict: "update"`) issues no claim statement for a constraint whose key it does not move, as before. For each constraint whose key moves, it probes the new key once and claims it, and then issues one release statement covering all of those constraints, where before it issued one release per key. A resurrection issues one more release statement. A soft delete issues one release statement instead of one per claim, and no longer re-reads the row after its tombstone. A probe that finds the node's own key held by another node (a duplicate an earlier release let in) refuses the update with `UniquenessError`.
- Not repaired: a claim an earlier release left keyed in another form does not collide with a new claim of the same value. A database written by an import under `onUnknownProperty: "allow"`, or by a provenance revival, before this release can hold a date claim under its unquoted ISO text, and a create of the same date is then admitted beside it. An update that leaves the key where it was leaves such a claim as it is, even when it restates the field. To re-key it, move the holder's value off and back (two updates); the update back claims the value as a create does and refuses with `UniquenessError` when a duplicate was already admitted, in which case resolve the duplicate, for example by hard-deleting one of the two nodes, and update the holder again. Until a holder is re-keyed, `getOrCreateByConstraint()` does not resurrect a soft-deleted holder whose released claim has the other form; it creates a new node.
- **Keys that move: an object-valued unique property produced in another key order than its schema.** A `z.object()` value whose parse output does not follow the shape's key order, which is a `.default()` or `.catch()` value whose literal states its keys in another order, was claimed by `create()` in that order and is now claimed in the shape's. Every other value keys exactly as before. An existing claim of such a value is a claim in another form: it does not fence a create of the same value, which is admitted beside it, and an update that leaves the key where it was leaves it alone. The holder's next write that moves the constraint's key or releases its claims (an update to another value, a soft delete, a retraction) gives it back by owner, and moving the value back claims it in the shape's order, refusing with `UniquenessError` when a duplicate was admitted meanwhile. Where the object can hold another value, heal such a claim at once by moving the holder's value off and back with two updates, as for the legacy date claims below. Where it cannot, because the object holds only fixed literals and the default is the only value the field can take, no update moves the key: an update restating the field compares equal keys and leaves the legacy claim alone. Re-key it instead by soft-deleting the holder and reviving it with the same id in one transaction, `store.transaction(async (tx) => { await tx.nodes.Kind.delete(id); await tx.nodes.Kind.upsertById(id, props); })`: the delete gives back every claim the holder holds, by owner, and the revival claims the shape-ordered key as a create does. When a node created since the upgrade already holds that key, the revival refuses with `UniquenessError` and the transaction rolls the delete back; resolve the duplicate (for example by hard-deleting one of the two nodes) and run it again. The revival is a resurrection, so it resets the row's validity window as any `upsertById` of a tombstone does. A holder with live edges cannot be repaired this way with its edges as they are: its kind's `onDelete` refuses the delete (`"restrict"`, the default), deletes the edges (`"cascade"`) or soft-deletes them (`"disconnect"`), and the revival does not restore them. For a holder whose edges must stay as they are, the one stale claim stays until the row is deleted, which releases it.
- Not repaired: an import under `onConflict: "update"` whose update moves a node onto a key it already holds at an axis other than the constraint's current one (a claim written before the axis move) keeps that claim, but the import's preflight reads the key there as free. A later row of the same import whose kind declares a constraint of the same name with `scope: "kind"` at that axis then passes the preflight and fails the flush with `UniquenessError`, which rolls the whole import back, where it should be refused for that row alone. This is unchanged from earlier releases.
- Not repaired: a date under a union whose branches disagree (`z.union([z.date(), z.string()])`) keys a stored row from its ISO text, while a create keys the `Date`. Such a value imported under `"allow"`, or revived by a provenance reopen, holds a text-keyed claim that a create of the same date does not collide with. Releases are unaffected.
- Not repaired: `getOrCreateByConstraint()` and `bulkGetOrCreateByConstraint()` with `ifExists: "update"`, or resurrecting a match, hand the matched row the props the lookup validated, which the update parses again as input. A schema whose parse does not accept its own output refuses (`z.string().pipe(z.coerce.date())`), and one that does not reproduce it stores the value parsed twice. This is unchanged from earlier releases. Because a soft-deleted holder of a piped date is now found by its key, `getOrCreateByConstraint()` for that date refuses with `ValidationError` where it previously created a second node.
- Not repaired: an import under `"allow"` keys a node's claims and an edge's match identity from the document's text (in the key owner's canonical rendering for a node), so a value whose parse otherwise differs from its text keys as the text: an edge identity field given `"REF"` under `z.string().toLowerCase()` admits a create of `"REF"` (identity `"ref"`) as a second edge. A later `update()` of such an edge re-validates the row and is refused with `ValidationError` as a change of an identity field. This is unchanged from earlier releases.
- Not repaired: a unique value whose validated key order follows its input (a `z.record()`, or the extra keys of a `z.looseObject()`) keys differently when two writers state its keys in different orders. On PostgreSQL an export and import of such a value is one such pair, because `jsonb` returns the keys in its own order: the imported claim does not collide with a create of the value in its original order. Declare unique constraints over `z.object()` values, whose validated keys follow the schema, or over scalars.
