`provenance.assertHolds(tx, …)` and `provenance.holding(tx)` in a transaction that can write now refuse, on PostgreSQL, a transaction whose reads could miss a retraction committed before they took the graph write lock. Both judge support from what they read under that lock, but a `REPEATABLE READ` or `SERIALIZABLE` transaction keeps the snapshot of its first statement, which can predate another session's retraction that the lock then waited for, so `assertHolds` could certify a fact that no longer held. The isolation is the one the lock statement observed on the transaction's session, the same evidence `tx.assertUnchangedSince()` requires, and any answer but read committed is refused with `UnsupportedBackendCapabilityError` (capability `observedReadCommittedIsolation`) before the first support read, leaving the transaction usable. Stores with TypeGraph-owned history capture already required read committed for every write transaction, so the refusal is new only for a backend with engine-native recorded time. `holding(tx)` in a read-only transaction is unchanged: it answers as of that transaction's one snapshot. A retraction called without a transaction now opens its own at read committed explicitly, so a server or role default of a snapshot isolation no longer applies to it. SQLite is unaffected.
