The composition part lifecycle is complete: a part names the edge that realizes its attachment, moves between wholes as one atomic operation, and reports what a whole's deletion took with it.

**The attachment names its realizing edge.** `partOf` — on `create`, `bulkCreate`'s per-item options, and both get-or-create entries — becomes `{ kind, id, via?, props? }`. `via` names the realizing edge kind and is required only when the part kind declares more than one composition pair toward that whole kind: omitting it there refuses with `ConfigurationError` (`COMPOSITION_VIA_AMBIGUOUS`) instead of resolving the ambiguity by sort order, and naming an edge kind that realizes no declared pair between the two refuses with `COMPOSITION_VIA_NOT_DECLARED`. `props` are the realizing edge's own properties, validated against that edge kind's schema exactly as `store.edges.<via>.create(...)` would — so a realizing edge with required schema fields is now attachable from a node create at all. `resolveCompositionAttachment` is the one owner of both refusals; `KindRegistry.getCompositionEdge`'s silent first-match resolution is gone.

**`nodes.<Kind>.reparent(id, attachment)` moves a part to a new whole.** Neither half of a move is legal on its own — the new attachment refuses while the old edge holds the part's one-whole claim, and `existence: "required"` refuses the detach while the part is live — so a caller had no legal order to write. `reparent` performs both under one per-graph fence, in one transaction, and validates the FINAL state: one whole, acyclicity over the oriented composition union, and a required part never left detached. The part keeps its id, its properties, and every descendant beneath it. How the old attachment retires follows its declared population: a `population: "one"` edge is deleted (a `one` binding persists for the row's whole life, so an ended row would still read as an attachment), while a `population: "oneActive"` edge has its window ended at the move instant, leaving the previous membership readable as valid-time history. The population comes from the INCUMBENT row's own pair, resolved through the realizing edge that holds the attachment. The move instant is read ONCE and is both the old window's `validTo` and the new edge's `validFrom`, so the two halves abut: no `store.asOf(t)` coordinate shows the part with zero wholes, and none shows it with two. Reparenting to the whole the part already holds is accepted as a no-op — no write, no history.

**`partOf` on `getOrCreateByConstraint` is now a POSTCONDITION, not a create-only option.** When the call returns, the resolved node holds exactly the stated attachment. The attachment is resolved before the match is read, so an undeclared whole kind, an unknown `via` and an ambiguous omitted `via` refuse with the same `ConfigurationError` whether the call created the node or found it. A node that already holds this whole through the resolved pair's realizing edge satisfies it and the call is idempotent; a node with no live whole has the attachment written now, whatever its pair's declared `existence`; only a node with a DIFFERENT live whole, or the same whole through another realizing edge, is refused, with `CompositionExistenceError` (`situation: "existing"`) naming both sides. `bulkGetOrCreateByConstraint` behaves identically per item. This reverses the previous unconditional refusal, which made a re-run of the same get-or-create fail purely because it was a re-run.

**A whole's delete says which parts it took.** The delete's `onOperationEnd` hook context and `store.transactionWithReceipt`'s receipt both carry `cascadedParts` — leaf-first `{ kind, id }` refs, taken from the plan the cascade executed, so they never name a part the cascade did not delete. The receipt covers `bulkDelete` too, accumulating every item's cascade in batch order; the batch path still emits no per-item operation hooks. `onOperationStart` never carries them (the cascade has not been planned yet), and the refs are not folded into the receipt's write counters: one caller-issued delete stays one write intent. There is no cascade preview API in this release; read the closure ahead of time with `store.subgraph(id, { edges: [], composition: true })`.

**`subgraph({ composition: true })` returns the COMPLETE owned unit.** The composition closure is bounded by its visited set, never by `maxDepth`: a part tree deeper than the default depth now comes back whole, because a whole plus a truncated prefix of its parts is not an export unit. `maxDepth` and `cyclePolicy` continue to bound the explicit `edges` traversal alone. The engine's own runaway ceiling on any recursive traversal (1000 hops) still applies to the composition closure, and truncates rather than refusing past it.

The ontology, errors, and limitations pages are rewritten to state what composition enforces today — one whole per part across every relation and both orientations, leaf-first cascade, acyclicity over the oriented composition union at write time, and `existence: "required"` — replacing the "planned for tier 1" and "forthcoming claim provisioning" language those pages still carried.

### Breaking

- `KindRegistry.getCompositionEdge(partKind, wholeKind)` is removed. Use `compositionPairsBetween(partKind, wholeKind)` (every declared pair, code-point ordered by realizing edge kind) or `compositionPairVia(partKind, wholeKind, viaEdgeKind)` (the pair a known realizing edge holds). The removed reader answered with the code-point-first pair alone, which silently chose a realizing edge for its caller.
- `partOf` on `create` / `bulkCreate` / `getOrCreateByConstraint` / `bulkGetOrCreateByConstraint` is typed `CompositionAttachment` (`{ kind, id, via?, props? }`) rather than `CompositionWholeRef`. Existing `{ kind, id }` call sites are unchanged, but a part kind with more than one declared pair toward the named whole kind now refuses until the call states `via`.
- `getOrCreateByConstraint` / `bulkGetOrCreateByConstraint` no longer refuse every `partOf` stated against a `"found"` / `"updated"` result. Code that relied on the refusal as a "this node already existed" signal must check the returned `action` instead.
- `TransactionReceipt` gains a required `cascadedParts` field (always present, empty when the transaction deleted no composition whole); anything constructing a receipt literal must add it.
- `OperationHookContext` gains an optional `cascadedParts`, and `StoreHooks`' runner signature gains a fourth, optional operation-facts argument; a hand-written hook runner implementing that internal shape needs the extra parameter.
- `CompositionExistenceErrorDetails` gains `currentVia`, `requestedWhole`, and `requestedVia` (all optional, `situation: "existing"` only), and the `"existing"` message now names both the held and the requested attachment. `requestedVia` carries the RESOLVED realizing edge rather than an echo of a stated `via`, so it is present even when the call omitted one.
- `NodeCollection` gains `reparent`; a hand-written implementation of that interface (rather than one built by `createStore`) must add it.
