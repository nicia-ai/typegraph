The composition part lifecycle is complete: a part names the edge that realizes its attachment, moves between wholes as one atomic operation, and reports what a whole's deletion took with it.

**The attachment names its realizing edge.** `partOf` — on `create`, `bulkCreate`'s per-item options, and both get-or-create entries — becomes `{ kind, id, via?, props? }`. `via` names the realizing edge kind and is required only when the part kind declares more than one composition pair toward that whole kind: omitting it there refuses with `ConfigurationError` (`COMPOSITION_VIA_AMBIGUOUS`) instead of resolving the ambiguity by sort order, and naming an edge kind that realizes no declared pair between the two refuses with `COMPOSITION_VIA_NOT_DECLARED`. `props` are the realizing edge's own properties, validated against that edge kind's schema exactly as `store.edges.<via>.create(...)` would — so a realizing edge with required schema fields is now attachable from a node create at all. That validation runs on every call that states `props`, including a `getOrCreateByConstraint`/`reparent` call that resolves to an attachment already holding: those write no edge, but still refuse a schema-invalid value, and still refuse (`CompositionExistenceError`, `situation: "props"`) a valid value that differs from the edge's live stored props rather than silently keeping the old one. `resolveCompositionAttachment` is the one owner of both refusals; `KindRegistry.getCompositionEdge`'s silent first-match resolution is gone.

**`nodes.<Kind>.reparent(id, attachment)` moves a part to a new whole.** Neither half of a move is legal on its own — the new attachment refuses while the old edge holds the part's one-whole claim, and `existence: "required"` refuses the detach while the part is live — so a caller had no legal order to write. `reparent` performs both under one per-graph fence, in one transaction, and validates the FINAL state: one whole, acyclicity over the oriented composition union, and a required part never left detached. The part keeps its id, its properties, and every descendant beneath it. How the old attachment retires follows its declared population: a `population: "one"` edge is deleted, removing the attachment from every `store.asOf(t)` read at every coordinate before the move (a `one` binding persists for the row's whole life, so an ended row would still read as an attachment); a `population: "oneActive"` edge instead has its window ended at the move instant, leaving the previous membership readable as valid-time history. The population comes from the INCUMBENT row's own pair, resolved through the realizing edge that holds the attachment. The move instant is read ONCE and is both the old window's `validTo` and the new edge's `validFrom`, so for a `oneActive` pair the two halves abut: no `store.asOf(t)` coordinate shows the part with zero wholes, and none shows it with two. Reparenting to the whole the part already holds is accepted as a no-op — no write, no history — though a stated `props` is still checked: valid and value-identical to the edge's live stored props, the no-op stands, and a valid but different value refuses (`situation: "props"`) rather than being silently dropped.

**`partOf` on `getOrCreateByConstraint` is now a POSTCONDITION, not a create-only option.** When the call returns, the resolved node holds exactly the stated attachment. The attachment is resolved before the match is read, so an undeclared whole kind, an unknown `via` and an ambiguous omitted `via` refuse with the same `ConfigurationError` whether the call created the node or found it. A node that already holds this whole through the resolved pair's realizing edge satisfies it — idempotently when stated `props` are omitted, or valid and value-identical to the edge's live stored props; a valid but DIFFERENT `props` is refused (`situation: "props"`) rather than silently kept, since a satisfied match writes no edge. A node with no live whole has the attachment written now, whatever its pair's declared `existence`; a node with a DIFFERENT live whole, or the same whole through another realizing edge, is refused with `CompositionExistenceError` (`situation: "existing"`) naming both sides. `bulkGetOrCreateByConstraint` behaves identically per item. This reverses the previous unconditional refusal, which made a re-run of the same get-or-create fail purely because it was a re-run.

Which of those three dispositions applies is decided under the per-graph write fence, from the incumbent re-read there — never from a lock-free read. `reparent` and the get-or-create postcondition are one write plan that takes an explicit incumbent disposition: `reparent` states "replace" (moving a part is what it is for), every get-or-create path states "refuse". So two concurrent get-or-create calls naming DIFFERENT wholes for one part end with exactly one attachment and one `CompositionExistenceError` — never a silent move, whatever order their lookups observed. A get-or-create whose `ifExists: "update"` also runs ONE write plan: the attachment and the property update commit together, so an update the row refuses (a unique conflict, a validation error) leaves ownership and history untouched instead of committing a move whose reason never applied. That fenced decision is reached before the update's first statement, so the refusals it owns leave the properties untouched as well — including when the caller catches the refusal inside an enclosing `store.transaction(...)`, where there is no nested frame to roll back. An already-satisfied call with no update to make stays read-only, restating the realizing edge's `props` included: agreeing props are part of what "already satisfied" means, so an idempotent ingest does not take the per-graph write fence to be told it has nothing to write.

**A whole's delete says which parts it took.** The delete's `onOperationEnd` hook context and `store.transactionWithReceipt`'s receipt both carry `cascadedParts` — leaf-first `{ kind, id }` refs, taken from the plan the cascade executed, so they never name a part the cascade did not delete. The receipt covers `bulkDelete` too, accumulating every item's cascade in batch order; the batch path still emits no per-item operation hooks. A `tx.measure(...)` scope's sub-receipt carries the refs for the deletes issued THROUGH that scope, alongside the transaction's own receipt, attributed the same way its write counters are — by the context the write ran through, not by timing, so a delete issued through the outer transaction during an open scope stays out of it. `onOperationStart` never carries them (the cascade has not been planned yet), and the refs are not folded into the receipt's write counters: one caller-issued delete stays one write intent. There is no cascade preview API in this release; read the closure ahead of time with `store.subgraph(id, { edges: [], composition: true })`.

**`subgraph({ composition: true })` returns the COMPLETE owned unit.** The composition closure is bounded by its visited set, never by `maxDepth`: a part tree deeper than the default depth comes back whole, because a whole plus a truncated prefix of its parts is not an export unit. It is a set-semantics (`UNION`) recursion over an `(id, kind)` frontier — the same device that makes the composition-union acyclicity probe exhaustive — so it reaches a fixpoint with no hop ceiling at all: the engine's 1000-hop cap on an explicit traversal does not apply to it, and a part chain longer than that is no longer silently truncated. Delivered or refused, never partial, against the engine as well: a closure statement the database cut short (a `statement_timeout`, a cancelled query) refuses with `ConfigurationError` (`COMPOSITION_UNIT_INDETERMINATE`) naming the root, through the same cut-short classification the acyclicity probe uses, rather than returning the rows it reached. `maxDepth` and `cyclePolicy` continue to bound the explicit `edges` traversal alone.

The ontology, errors, and limitations pages are rewritten to state what composition enforces today — one whole per part across every relation and both orientations, leaf-first cascade, acyclicity over the oriented composition union at write time, and `existence: "required"` — replacing the "planned for tier 1" and "forthcoming claim provisioning" language those pages still carried.

### Breaking

- `KindRegistry.getCompositionEdge(partKind, wholeKind)` is removed. Use `compositionPairsBetween(partKind, wholeKind)` (every declared pair, code-point ordered by realizing edge kind) or `compositionPairVia(partKind, wholeKind, viaEdgeKind)` (the pair a known realizing edge holds). The removed reader answered with the code-point-first pair alone, which silently chose a realizing edge for its caller.
- `partOf` on `create` / `bulkCreate` / `getOrCreateByConstraint` / `bulkGetOrCreateByConstraint` is typed `CompositionAttachment` (`{ kind, id, via?, props? }`) rather than `CompositionWholeRef`. Existing `{ kind, id }` call sites are unchanged, but a part kind with more than one declared pair toward the named whole kind now refuses until the call states `via`.
- `getOrCreateByConstraint` / `bulkGetOrCreateByConstraint` no longer refuse every `partOf` stated against a `"found"` / `"updated"` result. Code that relied on the refusal as a "this node already existed" signal must check the returned `action` instead.
- `TransactionReceipt` gains a required `cascadedParts` field (always present, empty when the transaction deleted no composition whole); anything constructing a receipt literal must add it.
- `OperationHookContext` gains an optional `cascadedParts`, and `StoreHooks`' runner signature gains a fourth, optional operation-facts argument; a hand-written hook runner implementing that internal shape needs the extra parameter.
- `CompositionExistenceErrorDetails` gains `currentVia`, `requestedWhole`, and `requestedVia` (all optional, `situation: "existing"` only), and the `"existing"` message now names both the held and the requested attachment. `requestedVia` carries the RESOLVED realizing edge rather than an echo of a stated `via`, so it is present even when the call omitted one. `situation` also gains `"props"`, with `currentProps`/`requestedProps` (optional, `situation: "props"` only) — a `getOrCreateByConstraint`/`reparent` call resolving to an attachment that already holds is now refused, rather than silently ignored, when its stated `props` are schema-valid but differ from the edge's live stored props.
- `NodeCollection` gains `reparent`; a hand-written implementation of that interface (rather than one built by `createStore`) must add it.
