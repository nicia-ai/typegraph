With statement logging turned on and prepared statements off, a single
managed node or edge write looked like this on the wire:

```
begin
SELECT ... schema-version fence probe
SELECT ... duplicate/endpoint check
INSERT ... (the write)
commit
```

Five statements, five round trips. On a pooled connection with sub-millisecond
latency to the database, that's invisible. On an edge-compute-to-managed-
PostgreSQL link — the shape serverless deployments actually run — round-trip
time is closer to 45ms, and every one of those statements pays it in full:
roughly 250–300ms for one write. Every latency figure in this post is that
arithmetic — a submission count multiplied by an assumed round trip — not a
measured wall-clock benchmark. What is measured here is the number of
submissions crossing the transport boundary. A captured first-provisioning flow for one
graph ran 97 statements total; roughly 40 of them, across just seven writes,
were fence probes, duplicate checks, and transaction framing — not the
writes themselves.

That gap is the subject of [issue #533](https://github.com/nicia-ai/typegraph/issues/533),
and closing it is most of what 0.52.0 was — and all of what 0.53.0
finishes. The fix isn't a cache or a timeout tweak. It's a different execution contract: an eligible write's
decision (does the schema fence pass, does the duplicate check pass, do the
endpoints exist, does the cardinality claim hold) and its mutation now share
one command boundary, compiled into one statement, instead of being a
sequence of application-level reads that individually decide whether to let
the write proceed.

## The command port

`GraphBackend.commands` replaces the old optional managed-create hook as a
required semantic execution port. A command carries an explicit root or
transaction session and, after the graph's advisory lock is actually
acquired, a coordination token bound to that graph and session — a wrapper
for a different connection can't reuse it. On PostgreSQL, the same
lock statement observes the effective transaction isolation and folds it
into the token, so match-key convergence knows whether it's running under
read-committed or serializable without a separate probe round trip. It's
correctness evidence that used to require asking, now carried by a
statement that already had to run.

A backend either executes every dimension a command requests or refuses
before issuing SQL — [`node.create`, `edge.create`, and
`edge.converge-create`](/backend-setup#authoritative-command-sessions) are
required cases, and an unsupported dimension gets a typed `unsupported`
result rather than being silently dropped. That's what lets the Store fall
back to the complete portable path cleanly instead of mixing partial
backend work with a second decision path.

For eligible first-party PostgreSQL writes — schema-managed, generated ID,
no claims outside what the command can carry, no history/revision/Operational
Identity sidecars — this folds the schema fence, endpoint predicate,
uniqueness verdict, and the insert itself into one statement. **Five to six
sequential requests become one: an 80–83% reduction**, which at that assumed
45ms round trip works out to roughly 180–225ms of removed network wait. On Neon's WebSocket driver, a
typical get-or-create miss against a schema-declared match identity drops
from the dispatcher read plus `begin`/lock/`commit` framing — five requests —
to one.

Writes that need more than a command can carry — dynamic call-level
`matchOn`, constrained single-edge cardinality claims, history or revision
capture, caller-owned transactions, custom backends — keep the interactive
transaction those guarantees actually require. This is fusion for the common
shape, not a rewrite of the transactional path underneath it. See
[Remote edge convergence](/performance/overview#remote-edge-convergence) for
the exact eligibility rules.

## Bulk writes on transactionless roots

The sharper version of this problem is on Neon HTTP, Cloudflare D1, and
libSQL — roots that don't offer an interactive multi-statement transaction
at all, only one-shot atomic dispatch (`transaction([...])`, `batch()`).
Before 0.52.0, a bulk call on one of these had to fall back to sequential,
non-atomic execution: no framing overhead to fuse away, just no atomicity
guarantee either.

0.52.0 adds a closed, precompiled write-program layer that these three
transports execute as one native atomic exchange:

- **`nodes.bulkInsert()`** for generated-ID, schema-managed batches with no
  claims, Operational Identity, history, revision, or projections compiles
  to one schema-fenced exchange. It also drops the existence-priming read
  that used to run first to confirm the batch was guaranteed-empty — that
  guarantee now comes from the generated-ID shape itself, not a read.
- **`edges.bulkInsert()` / `edges.bulkCreate()`**, unconstrained, fold
  endpoint validation into the write boundary instead of reading candidate
  endpoints first. A one-chunk batch goes from 2 exchanges to 1 when both
  endpoints share a kind, 3 to 1 across two kinds.
- **The same two methods with a declared durable `matchIdentity` or a
  cardinality claim (`one`, `unique`, `oneActive`)** carry that arbitration
  inside the same native transaction: claims are prepared without a database
  read, sorted by the existing canonical comparator, and acquired before the
  edge rows in the same lock order the interactive fallback already used.

Measured at the libSQL transport boundary — counting actual `execute()` /
`batch()` submissions, not SQL statements inside the resulting transaction:

| Managed bulk shape                 | Before | After | Reduction |
| ---------------------------------- | -----: | ----: | --------: |
| Unconstrained edge batch           |      1 |     1 | unchanged |
| Durable-match edge batch           |      6 |     1 |       83% |
| Cardinality-constrained edge batch |      8 |     1 |     87.5% |

Every chunk in a native program carries the same schema fence, so a stale
fence is a side-effect-free no-op rather than a partial write, and a later
endpoint, duplicate, or identity conflict rolls every earlier claim mutation
back in the same exchange. A dropped conflict arbiter fails closed with
`EDGE_MATCH_IDENTITY_STORAGE_UNAVAILABLE` instead of silently accepting
duplicates — the regression test for that path was written by deleting the
conflict-target clause and watching duplicates land, then restoring it and
watching the same input refuse.

When 0.52 shipped, caller-supplied-ID node insertion was still the slowest
common bulk shape on these transports at 5 transport submissions, named here
as the next candidate rather than something that release claimed. 0.53 closes
it: eligible plain node `bulkInsert()` and `bulkCreate()` calls now submit one
exchange for generated, caller-supplied, and mixed ID batches alike.

History/revision-enabled stores, caller-owned transactions, and derived or
custom backends all keep their existing transaction or typed-refusal path on
purpose; none of this is a public Store batch API, it's an internal execution
optimization underneath the same `bulkInsert`/`bulkCreate` calls you already
write.

## What 0.53 finished

0.52 fused the write that creates something. The shapes left over were the
ones that have to know what is already there — an update, an upsert, a
delete that must release the claims its row owned. 0.53 puts those on the
same programs.

- **Singleton `update()` and `delete()`** now run as one authoritative read
  or live-row gate plus one guarded atomic mutation, instead of an explicit
  managed transaction spanning both. That is roughly 60–67% fewer exchanges
  for the eligible shapes, and the per-operation hook contract is unchanged.
- **`bulkUpsertById()`** costs 2 exchanges — one batched preimage read, then
  one atomic mutation submission. A mixed create-and-update set used to need
  separate create and update submissions after that read, so it falls from 3
  to 2.
- **`nodes.<Kind>.bulkReplaceById()`** is new: every item supplies a complete
  document, so there is nothing to read first. Missing-row creation, live
  replacement, tombstone resurrection, claim release and acquisition, and
  fulltext/vector transitions all submit as one read-free atomic exchange.
- **Claims and search projections moved inside the program.** Uniqueness and
  disjointness claims, fulltext and per-vector-slot transitions, endpoint and
  schema fences, and postimage assertions now travel in the same submission
  as the rows they belong to, rather than as sidecar work after it.
- **Large D1 batches stay atomic.** The program chunks statements by the
  100-parameter bind budget inside one atomic batch, raising the previous
  17-node and 6-edge ceilings to 512 nodes and 187 edges per call. A terminal
  postimage assertion per chunk rolls the whole submission back if any guarded
  member moved; anything larger fails closed to the portable path rather than
  building an unbounded request.
- **PostgreSQL sessions run the same programs** on their pinned transaction,
  through a savepoint — so a deliberate refusal can be diagnosed and rolled
  back without poisoning the caller's surrounding transaction.

One behavioural change is worth reading twice. The guarded update converges
**optimistically** rather than holding a transaction lock across its read and
write: a one-row update gets four attempts against a moved preimage before
throwing `DatabaseOperationError`. Under sustained same-row contention that
can refuse a write which a transaction-capable backend previously serialized
for you. It is a real trade, not a free win.

## What made the arbitrated case fusible

Folding a cardinality claim or a match-on-endpoints convergence into one
statement needs something the database can arbitrate without an
application-level lock or cache: a real unique constraint. That's the other
piece of this release — **durable edge match identities**. An edge
registration can now declare one named, canonical property-field set:

```typescript
const worksAt = defineEdge("worksAt", {
  schema: z.object({ role: z.string() }),
});

edges: {
  worksAt: {
    type: worksAt,
    from: [Person],
    to: [Company],
    cardinality: "many",
    matchIdentity: { name: "employment", fields: ["role"] },
  },
},
```

TypeGraph persists the directed endpoint/property key on every row and
enforces it with a database unique arbiter — SQLite and PostgreSQL both
provision and idempotently upgrade the edge relation for it. Once that
arbiter exists, `getOrCreateByEndpoints` isn't "read, decide, then write and
hope nothing raced" — it's a single conditional-insert statement the
database resolves atomically, which is what makes the one-request path in
the previous section safe on a stateless edge worker with no in-process
cache to lean on. Dynamic, call-level `matchOn` remains available for
convergence you don't want to declare in the schema, through the same
transaction-fenced path it always used.

This is a breaking schema change: adding, removing, or changing a match
identity is refused while the affected edge kind holds rows. Export, hard
delete, migrate the schema, then reimport — see
[Upgrading an existing edge table for durable match identity](/backend-setup#upgrading-an-existing-edge-table-for-durable-match-identity)
if your DDL is managed outside `createStoreWithSchema()`.

## If you maintain a custom backend

Two contract changes apply regardless of which optimizations your backend
can actually implement:

- **`GraphBackend.commands` is now required.** Move managed-create and
  specialized edge-insert logic into `{ session, execute }` handling
  `node.create`, `edge.create`, and `edge.converge-create`; return the typed
  `unsupported` result for any dimension you don't lower to SQL. See the
  migration shape in [Authoritative command sessions](/backend-setup#authoritative-command-sessions).
- **`OptionalTransactionExecution` is now a discriminated union**,
  `{ mode: "interactive-transaction" | "sequential" }`, replacing the
  ambiguous `execution.atomic` boolean.
- **The top-level `capabilities.transactions` override is gone.** 0.52
  narrowed it to mean interactive callback/session support specifically,
  rather than generic atomicity; 0.53 removes it and **refuses it at
  construction** instead of silently retaining it as inert data. Declare
  `capabilities.execution.interactiveTransactions`. The distinction it was
  narrowed to still holds: a transactionless root is not non-atomic, it is
  atomic only for the shapes it natively batches.
- **`store.transaction()` and `store.transactionWithReceipt()` now refuse a
  backend without interactive transaction support** rather than degrading.
  Call ordinary Store write methods directly when your application means to
  own partial-failure recovery itself.

Both bundled backends already implement the full surface, so if you're only
using `createLocalSqliteBackend`, `createPostgresBackend`, or one of the
serverless root factories, none of this requires a code change on your
side.

## Also in these releases

- **Durable schema-only graph templates**, with idempotent v1 instantiation
  — provision the same starting schema shape repeatedly without hand-rolling
  the idempotency yourself. 0.53 makes registration and instantiation safe
  across serverless isolates, so a template registered in one isolate can be
  reopened through a verified store from a later one.
- **Conformance runners for custom atomic backends**, covering both transport
  mechanics (ordered result slots, exact statement and parameter forwarding,
  rollback without sidecar leakage) and semantic eligibility. Passing the
  transport runner certifies mechanics only; it does not by itself authorize
  the bundled mutation programs, which stay a separate fail-closed contract.
- **Fix:** reciprocal-rank-fusion scores in hybrid search now compute with
  floating-point division. Integer division was silently truncating fused
  scores toward zero.

## Upgrading

0.53 stamps deployment-wide base storage independently of your per-graph
schemas. An existing or externally provisioned database must be opened once
through privileged `createStoreWithSchema()` / `createAdapterStoreWithSchema()`,
or receive TypeGraph's generated base-schema migration, before the zero-DDL
verified-store and graph-template paths are used; until then those paths fail
early with `BaseSchemaMigrationError`. This also repairs externally
provisioned pre-0.52 databases whose graph schema never changed.

One more refusal to know about: a PostgreSQL-dialect backend declaring neither
usable pessimistic locks nor serialized writers can no longer open a
schema-managed store, and reports `WRITE_FENCE_UNAVAILABLE` rather than
accepting a declaration it cannot honor. Every first-party configuration —
PostgreSQL, Neon, PGlite, SQLite, D1, libSQL — keeps its existing posture.
