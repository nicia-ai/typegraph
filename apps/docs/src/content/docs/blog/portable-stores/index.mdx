Every `Store<G>` before 0.38 carried Drizzle's types whether the calling
code ever touched them or not. A strict TypeScript consumer that only
ever called `store.nodes.Person.create(...)` still had to resolve
`drizzle-orm`'s dialect declarations to typecheck at all: an unused
dependency showing up in another package's type-checking surface. 0.38
splits the Store contract in two: a portable `Store<G>` that's Drizzle-free
by default, and `AdapterStore<G, TNativeTransaction>` as the explicit
escape hatch for native SQL and transaction interop. 0.39 hardens the seam
between them.

## The portable path needs no Drizzle import at all

`createLocalSqliteStore` and `createLocalPgliteStore` (from
`@nicia-ai/typegraph/sqlite/local` and `@nicia-ai/typegraph/postgres/pglite`)
own the connection and return the complete portable `Store<G>`, with no
Drizzle handle anywhere in the application code:

```typescript
import { createLocalSqliteStore } from "@nicia-ai/typegraph/sqlite/local";

const store = await createLocalSqliteStore(graph, { path: "./graph.db" });
const alice = await store.nodes.Person.create({ name: "Alice" });
```

```text
created: LBPSjEoGPqI0P3C6kaJ5M Alice
capabilities.transactions: true
```

That store keeps the full graph API, `store.transaction(...)` included,
but its _type_ omits `withTransaction` and `withRecordedTransaction`,
which require a caller-owned adapter handle this store was never given.
`createStore` and `createStoreWithSchema` return this same portable
contract now too; reach for `createAdapterStore` /
`createAdapterStoreWithSchema` only when the application deliberately owns
a Drizzle connection.

## When you still need the adapter

An order-fulfillment write is a good example of needing more than the
portable surface: write an `Order` node, decrement the `InventoryItem` it
draws from, link them with a `fulfills` edge, and, in a real app, insert
a row into your own relational `order_audit` table on the same connection.
`createAdapterStore` keeps that native handle reachable:

```typescript
const store = createAdapterStore(graph, backend);

const order = await store.transaction(async (tx) => {
  const created = await tx.nodes.Order.create({ sku: "WIDGET", quantity: 3 });
  await tx.nodes.InventoryItem.update(itemId, { onHand: onHand - 3 });
  await tx.edges.fulfills.create(created, item, { quantity: 3 });
  return created;
});
```

```text
=== 1. Successful transaction ===
  committed: order yY0xWesod3Sk7V_E7baIo (quantity=3)
  committed: onHand=7, fulfills edges=1

=== 2. Failing transaction rolls back completely ===
  caught: insufficient stock: onHand would be -43
  rolled back: order count still 1 (the doomed order is gone)
  rolled back: onHand still 7 (decrement undone)
  rolled back: fulfills edges still 1
```

Real output from a real rollback: the callback throws mid-transaction, and
every write inside it (the order, the inventory decrement, the edge)
reverts together. The same example run _without_ a transaction leaves a
stranded order with no `fulfills` edge behind, which is exactly the
invariant a transaction exists to protect.

To write your own table on that same connection, narrow `tx.sqlAvailability`
before touching `tx.sql`. It has been a required discriminant since 0.36,
not an optional property to truthiness-test:

```typescript
await store.transaction(async (tx) => {
  await tx.nodes.Document.update(documentId, props);
  if (tx.sqlAvailability !== "available") {
    throw new Error(`Native transaction unavailable: ${tx.sqlAvailability}`);
  }
  await tx.sql.insert(documentVersions).values(versionRow);
});
```

`sqlAvailability` is `"available"` only on a plain adapter store. On a
history-enabled store it's `"history"` or `"revisionTracking"`; raw SQL
is disabled there on purpose, since writing through it would bypass
recorded-time capture. On a backend with no transactions at all it's
`"unavailable"`, and `tx.sql` is `undefined`. Branching on the
discriminant instead of `if (tx.sql)` matters because the disabled cases
used to read truthy and then throw on use.

## The migration, if you're on 0.37

The old `/sqlite` and `/postgres` entrypoints are gone, not aliased.
0.38 uses those names to distinguish the managed Store API from the
bring-your-own-connection adapters:

| 0.37 entrypoint                                   | 0.38 entrypoint                     |
| ------------------------------------------------- | ----------------------------------- |
| `/sqlite` for `createSqliteBackend`               | `/adapters/drizzle/sqlite`          |
| `/sqlite/local` for `createLocalSqliteBackend`    | `/adapters/drizzle/sqlite/local`    |
| `/sqlite/libsql`                                  | `/adapters/drizzle/sqlite/libsql`   |
| `/postgres` for `createPostgresBackend`           | `/adapters/drizzle/postgres`        |
| `/postgres/pglite` for `createLocalPgliteBackend` | `/adapters/drizzle/postgres/pglite` |

`Store<G, TNativeTransaction>` becomes `AdapterStore<G, TNativeTransaction>`;
`createStoreWithSchema(...)` followed by reading `tx.sql` becomes
`createAdapterStoreWithSchema(...)`. If you never read `tx.sql`, nothing
changes: the portable `Store<G>` your code already had is what
`createStore`/`createStoreWithSchema` still return.

## What's still Drizzle underneath

`@nicia-ai/typegraph/sqlite/local` and `/postgres/pglite` keep Drizzle out
of their _public declarations_, but their built-in database implementation
still uses Drizzle internally; `drizzle-orm` remains a required peer
dependency of the package either way. Declaration isolation isn't
installation isolation; the win is that a strict consumer's own
type-checking surface no longer has to resolve Drizzle's types to compile,
not that the dependency disappears from `node_modules`.

For adapter and strategy authors going the other direction (implementing
a custom `GraphBackend` or vector/fulltext strategy), the query compiler
now speaks `SqlFragment` instead of a raw Drizzle `SQL` value. Render one
with `toSQL()` for a dialect-agnostic `{ sql, params }` pair, or
`renderSqlite()` / `renderPostgres()` when you need the dialect-specific
form directly. The full contract vocabulary is importable from
`@nicia-ai/typegraph/backend`, itself Drizzle-free: every operation
parameter, row shape, and dialect port a custom backend needs.
