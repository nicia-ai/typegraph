Most applications that end up needing real structure (a knowledge base, an
org chart, an agent with shared memory) assemble the same three pieces: an
ORM for the actual data, a vector store bolted on for retrieval, and, once
the relationships get complicated enough, a graph database on top of both.
Three systems, three consistency models, three places for the schema to
drift out of sync with itself. Meanwhile TypeScript already has Zod, a
schema language good enough to define all of it, and none of those three
systems treats it as a source of truth.

TypeGraph is the other bet: keep the graph inside your application, as a
library, storing everything in the SQLite or Postgres you already run.

## Runs in your process

TypeGraph is a dependency. It runs in your process, writes through your
existing database connection, and commits in the same transaction as the
rest of your application's data. There is no separate deployment, no
network hop between your app and its own graph, and no second system to
keep online.

## One schema, not three

Zod schemas are the only place you describe your data:

```typescript
const Person = defineNode("Person", {
  schema: z.object({ name: z.string(), role: z.string() }),
});

const worksOn = defineEdge("worksOn", {
  schema: z.object({ since: z.string() }),
});

const graph = defineGraph({
  id: "org",
  nodes: { Person: { type: Person } },
  edges: { worksOn: { type: worksOn, from: [Person], to: [Person] } },
});
```

From that one definition TypeGraph derives runtime validation, inferred
TypeScript types, storage layout, and query-builder constraints. There's no
second schema language to keep in sync, and no hand-written types
duplicating what the schema already says.

## Graph semantics an ORM doesn't give you

A foreign key tells you two rows are related. It doesn't tell you a
`Podcast` is a kind of `Media`, that `marriedTo` implies `knows`, or that a
`Person` and an `Organization` can never be the same row. TypeGraph's edges
are first-class, typed, and carry their own properties, and the ontology
layer adds real semantic relationships (`subClassOf`, `implies`,
`disjointWith`, `equivalentTo`) that expand queries and enforce
constraints instead of living only in a comment or a code review. Traversals
compile to a query-builder AST and then to SQL, so a multi-hop traversal is
one compiled query, not an N+1 loop of manual joins.

## Vector search is a field type

Embeddings are a first-class field type. Declare one on a node schema and
TypeGraph stores and indexes it natively on whichever backend you're
already running:

```typescript
const Document = defineNode("Document", {
  schema: z.object({ title: z.string(), embedding: embedding(1536) }),
});

const similar = await store
  .query()
  .from("Document", "d")
  .whereNode("d", (d) => d.embedding.similarTo(queryVector, 10))
  .select((ctx) => ctx.d)
  .execute();
```

`.similarTo()` is a predicate like any other: it composes with metadata
filters and traversal in one query, instead of a separate round trip to a
vector database and a join back to your actual data.

## What TypeGraph deliberately isn't

It's not trying to replace Neo4j for billion-edge analytics. There's no
PageRank, no community detection, no distributed storage, and (this
early) no built-in traversal algorithms beyond what you write yourself as
a query. TypeGraph is tuned for thousands to millions of nodes living
inside one database, not a standalone analytical system at a different
scale. If your graph _is_ the standalone system, you want a real graph
database instead.

## Where things stand

This is early, a few releases past the first commit. The core DSL, the
ontology layer, native vector search, and both backends are solid. What
ships next depends on where real usage pushes it.
