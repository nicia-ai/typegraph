The [first version of this benchmark](#the-gap-in-the-first-run) measured
seven short-read queries against three competitors. TypeGraph/SQLite won
every one of them, which was true and also not much of a test: an
in-process engine with direct index seeks can't lose a point-read race
against anything that pays a network round trip. We've since expanded the
harness to **five engines** and the queries a purpose-built graph database
is actually supposed to win — shortest path, weighted shortest path, and
whole-graph algorithms — at both SF1 and SF10. The honest picture:
**TypeGraph/SQLite still wins every point read, often by 10-100x.
Native-CSR engines win the graph algorithms by three to four orders of
magnitude.** Neither number cancels the other out, and the second one is
new information, not a rerun of the first post with a bigger table.

## The gap in the first run

The original run's "What this isn't yet" section named its own limitation:
one EC2 run per scale, and — the bigger gap — a query set that couldn't
show a graph engine's actual value proposition. IS1-IS7 are point lookups
and one-hop walks; nothing in that set exercises multi-hop traversal,
shortest path, or a whole-graph algorithm, which is exactly where a
CSR-backed engine is supposed to separate from a general-purpose database.
Publishing only that set and calling TypeGraph "faster" would have been
true and misleading by omission. This run fixes that.

## The setup, expanded

Five engines now, all against the same shared harness
([`packages/benchmarks/src/real/`](https://github.com/nicia-ai/typegraph/tree/main/packages/benchmarks/src/real)):
TypeGraph on SQLite, TypeGraph on PostgreSQL, Neo4j (now with the Graph
Data Science plugin loaded), LadybugDB, and a new entrant, **Evokoa
pgGraph**. pgGraph isn't a separate database — it's a PostgreSQL extension
that stores the same normalized relational tables Postgres already has,
then builds a derived CSR (compressed sparse row) index over them and
exposes traversal and pathfinding as SQL functions
(`graph.shortest_path`, `graph.traverse`, `graph.build`). Its point reads
are just tuned Postgres; the CSR index sits idle for IS1-IS7 and only
earns its keep once a query actually traverses.

| Engine                         | Version                                                                      |
| ------------------------------ | ---------------------------------------------------------------------------- |
| SQLite                         | 3.53.2 (via `better-sqlite3` 12.11.1)                                        |
| PostgreSQL (TypeGraph backend) | 18.1 (`pgvector/pgvector:pg18` image)                                        |
| Neo4j                          | `neo4j:2026.05.0` server image, `neo4j-driver` 6.2.0, GDS plugin             |
| LadybugDB                      | `@ladybugdb/core` 0.18.0                                                     |
| pgGraph                        | Evokoa pgGraph 0.1.8 (`ghcr.io/evokoa/pggraph:0.1.8`, bundles PostgreSQL 17) |

The query set grew from 7 to 17: the original IS1-IS7 short reads; IC13
(shortest path) and the new **IC14** (weighted shortest path, exercising
TypeGraph's own `store.algorithms.weightedShortestPath`); BFS3 (a bounded
neighborhood walk); three complex reads (IC2, IC8, IC9); and four
graph-algorithm queries — GA_DEGREE (a seed person's `knows` degree),
GA_WCC (weakly connected components), GA_BFS and GA_SSSP (whole-component
reachability and shortest-path depth from a seed). Every engine that
can't run a given query in a comparable form now **declares a typed
gap** instead of being silently skipped, so a `gap` cell in the tables
below means "this engine has no equivalent primitive," not "we didn't
measure it." Correctness is still checked the way the original run
established — a full value-level canonical digest, per row, per query,
across every engine that runs it — and every run in this post is parity
green (`failures: []`).

Two scales, same as before: **SF1** (9,892 persons, 361K directed `knows`
edges) and **SF10** (65,645 persons, 3.88M `knows`, 21.9M comments — 10x
SF1), on a shared-vCPU EC2 host. Treat sub-millisecond and high-variance
(CV>25%) cells as order-of-magnitude, not precise.

## Fast to read, still

The original finding holds exactly: TypeGraph/SQLite wins every IS row,
often by one to two orders of magnitude, because it's the only engine
here paying no network round trip and no query-planning overhead per
call. GA_DEGREE and IC8 — both effectively point lookups dressed up as
"algorithm" or "complex read" queries — go the same way. None of that
changed with the expanded lane; it's exactly the result you'd expect from
an in-process engine, confirmed again on more queries.

## Where the graph engines actually win

This is the part the original run couldn't show. GA_WCC, GA_BFS,
GA_SSSP, and IC13 are the queries a graph database's specialized index
exists for, and here the native-CSR engines dominate:

- **pgGraph wins GA_WCC (9.53ms) and IC13 (2.18ms)** — its union-find and
  shortest-path primitives run directly over the CSR index it maintains
  alongside the same Postgres tables TypeGraph's own SQL backend would use.
- **Neo4j's GDS plugin wins GA_BFS (24.5ms) and GA_SSSP (23.6ms)** — loading
  GDS and projecting the Person + undirected-`knows` subgraph once turns
  these from Cypher path enumeration (which Neo4j does natively, but
  slowly) into the same set-based traversal pgGraph and TypeGraph's own
  algorithms use.
- **TypeGraph, on either backend, is three to four orders of magnitude
  slower on GA_WCC** (7269ms sqlite / 24237ms postgres vs. pgGraph's
  9.53ms). That gap is architectural, not a bug: TypeGraph's algorithms
  run as rounds of SQL — a window/aggregate query per round, however
  well-indexed — while pgGraph and Neo4j GDS hold the graph as an
  in-memory CSR structure built for exactly this access pattern. No
  amount of query tuning turns SQL iteration into a CSR traversal.

None of this is new information about TypeGraph getting worse — it's the
information the first run's query set structurally couldn't surface.

`gap` here also covers neo4j's GA lanes — this SF10 run predates loading

ladybugdb 373s, neo4j 409s, pggraph 1,119s, typegraph-sqlite 2,199s,
typegraph-postgres 3,278s (~55 min).

The interesting comparison isn't the SF10 numbers alone, it's how much
each engine's GA_WCC time grew from SF1 to SF10 — 10x the data:

| Engine             |     SF1 |   SF10 | Growth |
| ------------------ | ------: | -----: | -----: |
| pggraph            |  9.53ms | 69.0ms |    ~7x |
| typegraph-sqlite   |  7269ms | 119.9s |   ~16x |
| typegraph-postgres | 24237ms | 506.0s |   ~21x |

pgGraph's CSR index scales close to linearly with the data. TypeGraph's
SQL-iteration algorithm scales worse than linearly — more rounds over
more edges compounds — so the gap to the native-CSR engine doesn't just
persist at 10x scale, it **widens**. This is the honest
specialized-engine-vs-general-database story, and it gets sharper with
scale, not softer.

## In-process beats networked, even within TypeGraph itself

A narrower, TypeGraph-only comparison inside the SF10 table is worth
pulling out on its own, because the direction is counterintuitive and an
earlier draft of this investigation got the explanation wrong:

| Query            | typegraph-sqlite | typegraph-postgres | sqlite advantage |
| ---------------- | ---------------: | -----------------: | ---------------: |
| GA_WCC           |           119.9s |             506.0s |            ~4.2x |
| IC9              |            11.9s |              76.7s |            ~6.4x |
| GA_BFS / GA_SSSP |             2.8s |              22.3s |              ~8x |
| BFS3             |             1.7s |               7.2s |            ~4.3x |

Both backends run the identical logical algorithm, so this gap is a
PostgreSQL-specific execution constant factor — but it is **not** "network
round-trip overhead," despite how tempting that explanation is. Three
things rule it out: GA_BFS/GA_SSSP already issue exactly one
`INSERT ... RETURNING` per round, so there's nothing left to collapse;
Postgres is reached over loopback (~1ms for a point query), which can't
explain hundreds of seconds of gap; and the PG/SQLite ratio is stable —
about 8.1x at SF1 and 8.0x at SF10 for BFS/SSSP — which is the signature
of a per-row or per-edge executor cost plus temporary-relation overhead,
not a fixed tax that would shrink as a fraction of a larger run. Reducing
it is an open investigation, not a solved problem. (Postgres still wins
IC14, the one place its set-based frontier expansion parallelizes better
than SQLite's row-wise settle.)

## IC14: the query only TypeGraph can run

IC14 asks for the _weighted_ shortest path between two people — not just
fewest hops, lowest total cost. Every synthetic `knows` edge weight is a
deterministic hash, so both TypeGraph backends produce byte-identical
results. No competitor in this lineup can run it in a comparable form:
Neo4j's GDS has no stored `knows` weight to project for
`gds.shortestPath.dijkstra`, pgGraph's `graph.shortest_path` is hop-only,
and LadybugDB's weighted-shortest-path primitive isn't wired into this
harness. So the IC14 row isn't "TypeGraph is slower here" — it's the one
row where TypeGraph is the only engine that can answer the question at
all, on either backend, at real LDBC scale (5.6s / 4.9s at SF1, 75s / 57s
at SF10). Postgres beats SQLite on this specific query, the opposite of
the graph-algorithm rows above, because an unbounded cost-ordered Dijkstra
over a large frontier is exactly where Postgres's set-based iteration
plus a generous `work_mem` outperforms SQLite's row-at-a-time settle.

## Still slow to load, but the gap is closing

Bulk-load time hasn't caught up to the read-side story, but it's moved a
lot since the original post — because
[trustedImportGraph/trustedImportGraphStream](/blog/trusted-bulk-loads)
shipped in the meantime, and this benchmark's loader now uses it:

| Engine             | SF1 load | Was (original post) | SF10 load |
| ------------------ | -------: | ------------------: | --------: |
| ladybugdb          |      46s |               41.6s |      373s |
| neo4j              |      66s |               71.4s |      409s |
| pggraph            |     120s |                   — |    1,119s |
| typegraph-sqlite   |     164s |              587.1s |    2,199s |
| typegraph-postgres |     344s |              669.3s |    3,278s |

typegraph-sqlite's SF1 load dropped from 587.1s to 164s (~3.6x) and
typegraph-postgres from 669.3s to 344s (~1.9x) — directly attributable to
the trusted-import path, not incidental host variance, since the rest of
the harness and dataset are unchanged. typegraph-sqlite is now within
~1.4x of pgGraph's load time (164s vs. 120s); typegraph-postgres is still
roughly **3x slower than pgGraph** at both scales. The reason is
architectural, not a bug: pgGraph and TypeGraph's trusted-import path both
skip live index maintenance during the bulk write, but pgGraph loads over
batched `INSERT`s tuned for its own schema, while TypeGraph's write path
still goes through prepared statements rather than PostgreSQL's `COPY`
protocol. `COPY` is the next lever, and — per the load investigation behind
this run — it's the one genuinely broad, tractable win left in this whole
benchmark: everyone who bulk-loads through TypeGraph/Postgres would feel
it, not just this benchmark's dataset.

## A promising direction: pgGraph as a drop-in accelerator

pgGraph's architecture makes it a more interesting result than "one more
competitor in the table." It isn't a separate database to migrate to — it's
a PostgreSQL extension that indexes tables that already look like the ones
TypeGraph's own PostgreSQL backend writes: normalized nodes and edges, in
Postgres, queryable in the same connection. That's not a coincidence
pgGraph is closer to "tuned Postgres" than "different system," and it's
exactly why its point-read numbers above are unremarkable while its
traversal numbers aren't.

**This isn't built today.** The pgGraph driver in this benchmark loads its
own copy of the dataset into pgGraph's own schema and registers the CSR
index directly — it doesn't sit on top of a live, TypeGraph-managed
Postgres backend. But the shape of a future integration is visible in
this run's own numbers: keep using TypeGraph's query builder and portable
`Store<G>` contract for the point reads and everyday writes it already
wins — no reason to give that up — and when profiling shows a genuine
whole-graph workload (component analysis, centrality, unweighted
shortest path at scale), register a pgGraph CSR index over the same
underlying tables and route just that query through `graph.*` SQL, the
same way [`AdapterStore`'s native-SQL escape
hatch](/blog/portable-stores#when-you-still-need-the-adapter) already
exists for exactly this kind of interop. Use TypeGraph with your
PostgreSQL database normally; drop in pgGraph for the specific queries
where a CSR index is worth the operational cost of maintaining one. That
pairing isn't shipped. It's the most concrete, load-bearing direction
this round of numbers points at.

## What these numbers do and don't mean

It's tempting to read the graph-algorithm rows as a list of TypeGraph
bugs to fix. Mostly, they aren't:

- **IC9 is a schema-modeling artifact, not an engine limitation.** LDBC
  models `creator` as an edge, so a feed query has to fetch the sort key
  for every candidate message before it can rank them — 1.2M candidate
  fetches at SF1 to return the top 20. A real feed workload would
  denormalize the owner onto the item and index `(owner, created_at)`,
  already supported today via `defineNodeIndex`, and this would be fast.
  No index reshuffle inside the current schema fixes it; the fix is
  modeling the query pattern, not tuning the engine.
- **GA_WCC/GA_BFS/GA_SSSP are architectural**, full stop. Whole-graph
  analytics are genuinely better served by a specialized CSR engine.
  SQL-iteration tuning narrows the gap — an in-place delta-frontier
  rewrite to the connected-components algorithm nearly halved
  typegraph-postgres's GA_WCC time earlier in this investigation — but
  never closes it, and closing it isn't the goal; pairing with something
  like pgGraph for exactly these queries is.
- **IC14 is niche and benchmark-amplified.** It picks random person pairs
  near the graph's diameter, the worst case for a single-source Dijkstra.
  Real weighted shortest-path queries are usually between related,
  nearby entities, where the same algorithm already terminates fast. Not
  worth a correctness-critical rewrite for a rarely-hit path shape.

The one broad, tractable win this round surfaced is bulk-load throughput
on PostgreSQL — `COPY` over prepared inserts — covered above. Everything
else here is either already explained by the schema, or an honest
tradeoff between "general-purpose database" and "specialized graph
engine" that no amount of query tuning erases.

## What this isn't yet

Still one EC2 run per scale on a shared-vCPU host, not a distribution —
several cells above are flagged NOISY (CV>25%) in the underlying report
and should be read as order-of-magnitude, not precise. What's already
solid regardless of that caveat: every query in both tables passes full
value-level parity across every engine that runs it, the direction of
every finding (TypeGraph wins point reads, native-CSR engines win
whole-graph algorithms, the gap widens with scale) is large enough to
survive normal run-to-run noise, and the capability-gap mechanism means
the tables say exactly what wasn't measured instead of hiding it.
