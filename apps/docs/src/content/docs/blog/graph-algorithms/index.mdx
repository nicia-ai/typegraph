`store.algorithms.shortestPath` and `.reachable` answer questions about two
nodes at a time: how do I get from A to B, what's within N hops of A. A
different class of question needs the whole graph at once. Is this
dataset one connected body, or several islands? Which nodes matter most,
structurally, not just by raw count? Do communities fall out of the
topology on their own? Those need an algorithm that runs several rounds
over the entire visible graph in one repeatable snapshot, which is a much
bigger engineering lift than a single traversal: a pinned transactional
connection, a temporary working table, and a typed convergence contract
instead of "just keep expanding the frontier."

0.37 adds the first two, `weaklyConnectedComponents` and
`weightedShortestPath`, on the same set-based BFS engine that replaced
recursive-CTE path enumeration for the point-query traversals. 0.38 adds
global and personalized `pageRank` plus deterministic `labelPropagation`
(the LDBC Graphalytics CDLP benchmark's algorithm). All five run as SQL:
no export step, no separate analytics engine, no second copy of the graph
to keep in sync.

## The corpus

Same citation graph as [the research-copilot
example](/examples/research-copilot): 18 landmark ML papers, 55 authors,
14 topics, and 37 real citation edges, from Rumelhart, Hinton & Williams'
1986 backpropagation paper through LLaMA in 2023. That example runs point
queries: semantic search, `shortestPath`, `degree`. This post runs the
whole-graph algorithms over the same data instead.

```typescript
const backend = createExampleBackend();
const [store] = await createStoreWithSchema(graph, backend);
// Ingested 18 papers, 55 authors, 14 topics, 37 citation edges.
```

## Is this literature one body of work, or islands?

Treat `cites` as undirected and partition by connectivity. One call, one
answer:

```typescript
const components = await store.algorithms.weaklyConnectedComponents({
  edges: ["cites"],
  nodeKinds: ["Paper"],
});
```

```text
18 papers partition into 1 component(s):
  • component of 18 paper(s), rooted at "Adam: A Method for Stochastic Optimization"
```

Every paper in the corpus traces back to every other paper through some
citation chain; there's no isolated cluster citing only itself. On a
real, heterogeneous dataset this is the sanity check worth running first:
`nodeKinds: ["Paper"]` keeps authors and topics out of the partition, so a
result of more than one component would mean a genuinely disconnected
sub-literature, not an artifact of a lightly-cited author node.

## The cheapest lineage isn't the shortest one

Citations always point from a newer paper to an older one it cites, which
makes "cost" trickier to define than it looks. The obvious first weight,
`yearGap` (the number of years a citation reaches back), **telescopes**:
because every hop along a `cites` path steps strictly newer→older, the
sum of gaps along _any_ route from paper A to paper B collapses to exactly
`A.year - B.year`, independent of which route you took. Every path ties,
so weighting by `yearGap` degenerates into `shortestPath` with extra
arithmetic.

`yearGapCost = yearGap²` breaks the tie on purpose. Squaring is convex: one
27-year leap costs `27² = 729`, but the same span crossed by several
smaller citations sums to much less. That's a genuinely different
optimization, "prefer the smoothest incremental lineage," and it's where
`weightedShortestPath` stops agreeing with `shortestPath`:

```typescript
const hopPath = await store.algorithms.shortestPath(from.id, to.id, {
  edges: ["cites"],
  maxHops: 10,
});
const byConvexCost = await store.algorithms.weightedShortestPath(
  from.id,
  to.id,
  { edges: ["cites"], weightProperty: "yearGapCost" },
);
```

```text
transformer → backprop:
  shortestPath (fewest hop):   2 hops   transformer(2017) → adam(2014) → backprop(1986)
  weighted by yearGapCost:     4 hops   totalWeight=353   transformer(2017) → dropout(2014) → alexnet(2012) → lenet(1998) → backprop(1986)   ◀── more hops, lower convex cost

clip → backprop:
  shortestPath (fewest hop):   3 hops   clip(2021) → simclr(2020) → dropout(2014) → backprop(1986)
  weighted by yearGapCost:     7 hops   totalWeight=359   clip(2021) → gpt2(2019) → bert(2018) → transformer(2017) → dropout(2014) → alexnet(2012) → lenet(1998) → backprop(1986)   ◀── more hops, lower convex cost
```

The direct route from Transformer to backprop is a single 31-year leap
through Adam; the convex-cost route takes four smaller steps instead and
comes out at less than half the cost. Same two papers, same graph, two
legitimately different answers to "what's the best path" (the fewest-hop
one and the smoothest-lineage one), and `weightedShortestPath` finds the
second without enumerating every route by hand. Weights are audited before
any traversal round runs, so a negative or non-numeric `yearGapCost`
anywhere in the selected edges throws `InvalidEdgeWeightError` up front
rather than silently mis-answering.

## Propagated authority vs. raw citation count

Citation count answers "how many papers cite this one." PageRank answers
"how much does this paper matter, given what cites it": a citation from a
heavily-cited paper counts for more than one from an obscure one, and that
propagates transitively.

```typescript
const pageRankScores = await store.algorithms.pageRank({
  edges: ["cites"],
  nodeKinds: ["Paper"],
  direction: "out", // random surfer follows citations forward, toward the classics
});
```

```text

     7    0.05818      3       5   -2  Dropout: A Simple Way to Prevent Neural Networks ...
     8    0.05592      3       4   -4  Deep Residual Learning for Image Recognition
```

Backprop wins both ways; it's the corpus's true root, so that's not a
surprise. The interesting row is LeNet: one direct citation puts it at raw
rank 13, but PageRank moves it to rank 6, seven places higher, because the
one paper that cites it is AlexNet, itself heavily cited. A citation
count treats every citation as equal; PageRank doesn't, and that's the
whole point of propagated authority over a raw tally.

## What's important to CLIP, specifically

Personalized PageRank runs the identical power iteration but teleports
back to a chosen seed instead of spreading uniformly across the graph,
answering "important relative to this paper" instead of "important
globally":

```typescript
const personalized = await store.algorithms.personalizedPageRank({
  edges: ["cites"],
  nodeKinds: ["Paper"],
  direction: "out",
  seeds: [{ id: clip.id, kind: "Paper" }],
});
```


## Do research communities emerge?

Deterministic label propagation (CDLP) finds communities by having each
node adopt its most common neighbor label, round after round, over the
_undirected_ projection of `cites`. Run it the strict way first:

```typescript
const converged = await store.algorithms.labelPropagation({
  edges: ["cites"],
  nodeKinds: ["Paper"],
  onMaxIterations: "throw", // default
});
```

```text
onMaxIterations: "throw" raised GraphAlgorithmConvergenceError —
the undirected citation graph oscillates (tree / even-cycle structure
that mirrors labels back and forth).
```

The throw is documented, provable behavior. Synchronous label voting has
no self-vote, so a tree-shaped neighborhood (common once a directed
citation DAG is projected to undirected) can mirror two labelings back
and forth forever, and no amount of extra `maxIterations` fixes it.
`onMaxIterations: "return"` accepts the fixed-round labeling instead, the
same contract the LDBC Graphalytics CDLP benchmark uses:

```typescript
const fixedRound = await store.algorithms.labelPropagation({
  edges: ["cites"],
  nodeKinds: ["Paper"],
  onMaxIterations: "return",
});
```

are printed for the reader, not fed to the algorithm.

## What's still missing

Shortest path (weighted and unweighted), reachability, neighborhoods,
degree, weakly connected components, deterministic label propagation, and
global/personalized PageRank cover a lot of ground, but not everything:
strongly connected components, topological sort, betweenness/closeness/
eigenvector centrality, and modularity-optimizing community detection
(Louvain, Leiden) aren't in `store.algorithms`. For those, export the edge
list via `.query().traverse()` or `store.subgraph()` and hand it to a
specialized in-memory library like
[graphology](https://graphology.github.io/). TypeGraph's job here is
being the source of truth and the fast path for the algorithms that come
up often enough to earn a place on the store itself, not to replace a
dedicated analytics library for everything else.
