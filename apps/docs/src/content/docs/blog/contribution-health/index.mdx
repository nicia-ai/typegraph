[Hybrid Search](/blog/hybrid-search) gave TypeGraph native BM25 fulltext
and reciprocal-rank fusion, with no external search service. The tables
behind that are **contributions**: storage a strategy provisions on
first use and records with a durable marker row.

The marker is the problem. Every gate trusts it without probing the
catalog. A database whose strategy-owned tables were dropped out of band
— a restore from a partial dump, a migration that recreated a schema, an
edge runtime that lost a file — opens completely clean and fails at the
first dependent read or write.

That failure used to surface as a raw driver error about a missing
relation. It now surfaces as `ContributionUnavailableError`, with
`state: "physical-storage-missing"` and rebuild guidance, and only for
the specific case that earned it: a missing-relation failure whose driver
error names the declared fulltext table. Healthy operations keep the
cached marker fast path untouched — the translation lives on the error
path, not the hot one, and it never launders an unrelated database
failure into a friendly message.

## Where this actually bites

Cloudflare Durable Objects, mostly. [One SQLite file per
tenant](/blog/infinite-graph-databases) means thousands of small
databases whose lifecycle you do not individually supervise, and edge
SQLite is where storage goes missing in ways a single supervised
Postgres instance rarely does. The Durable Objects translation exists
because that is where the raw failure kept showing up.

## One ladder, three rungs

Each rung does strictly more, and costs strictly more, than the one below
it. Start at the top and stop as soon as the projection is `ready`.

| Rung       | Call                                    | Writes                                           | Use when                                              |
| ---------- | --------------------------------------- | ------------------------------------------------ | ----------------------------------------------------- |
| 1. Probe   | `store.probeContributions()`            | Nothing                                          | You want to know whether search is coherent right now |
| 2. Repair  | `store.repairContributions()`           | Marker rows, idempotent `CREATE … IF NOT EXISTS` | Storage is intact and only the bookkeeping is wrong   |
| 3. Rebuild | `store.rebuildContribution("fulltext")` | **Deletes and refills this graph's rows**        | The contribution is `stale` or `orphaned-marker`      |

### Rung 1 — the read-only probe

One entry per search projection the graph declares, so a caller can
decide whether to issue a query without running a write first:

```typescript
const health = await store.probeContributions();

for (const entry of health.entries) {
  if (entry.state !== "ready") {
    console.warn(
      `${entry.contribution} search is ${entry.state}`,
      entry.detail,
    );
  }
}
```

It writes nothing, so it is safe on a read path, on a replica, and under
a least-privilege role. It shares the detection logic of the other two
rungs rather than reimplementing it, which is the property that matters:
it cannot disagree with the gate the hot path actually consults.

Two readings to get right. `entries` is empty when there is nothing to
assess — a graph with no `searchable()` or `embedding()` fields, or a
backend with no contribution machinery. It is _never_ empty because a
check was skipped: a backend that provisions contributions but cannot
probe its catalog throws `ConfigurationError` and declares the gap as
`capabilities.contributions.probe === false`. And route on `state`;
`detail` is a human-readable summary, not a stable format. For structured
per-table findings, use `verifyContributions()`.

### Rung 2 — diagnose, then repair

`store.verifyContributions()` compares each contribution the active graph
and backend strategies currently expect against its marker and the
catalog. It is `SELECT`-only — no DDL — so the least-privilege role can
run it, and it is deliberately not part of any open path.

Its limits are worth stating, because an empty result is _not_
initialization proof: it does not audit retired marker rows, and a
never-attempted contribution with neither marker nor table is omitted
entirely.

```typescript
const result = await adminStore.repairContributions();
```

`repairContributions()` re-audits current declarations, preserves data
while repairing `missing-marker` and `failed-materialization`, and
reports `stale` or `orphaned-marker` as `requires-rebuild`. Run it
through the DDL-capable migration role, not the least-privilege runtime
role.

Follow the per-state table in the troubleshooting guide rather than
applying one repair to every entry — the states mean genuinely different
things about what is on disk.

### Rung 3 — the destructive one

A `stale` contribution has a table that exists at a shape the current
`createDdl` no longer produces. There is no non-destructive fix for that,
and `rebuildContribution()` is the only repair:

```typescript
await store.rebuildContribution("fulltext");
```

It deletes and refills only the calling graph's rows in the shared
fulltext table, escalating to drop-and-recreate when that table holds no
other graph's rows — under a database-scoped DDL advisory lock, since
that DDL is database-global. The whole sequence runs inside one
transaction under the schema-write fence.

It refuses in two cases rather than destroying something it cannot
reconstruct. Vector storage, whose embeddings exist _only_ in the table it
would drop, refuses with
`ContributionRebuildUnsupportedError` and
`reason: "vector-source-unavailable"`. A `stale` shape whose storage
still holds another graph's rows refuses with
`reason: "shared-storage-in-use"`, naming them in
`details.otherGraphIds`.

Plan a maintenance window. The transaction is held for the whole refill,
and on PostgreSQL a drop's `ACCESS EXCLUSIVE` lock blocks searches _and_
writes to any kind with `searchable()` fields until it commits. Reach it
from a `createStore()` Store — the managed factory's boot step refuses to
open while a contribution is `stale`.

## Each rung is a separate capability

`backend.capabilities.contributions` declares how far up the ladder a
backend goes, and each rung is separate because a backend can genuinely
stop at any of them:

| Backend                                                      | `supported` | `probe` | `rebuild`          |
| ------------------------------------------------------------ | ----------- | ------- | ------------------ |
| SQLite (better-sqlite3, bun:sqlite, libSQL, Durable Objects) | ✅          | ✅      | ✅                 |
| SQLite with `transactionMode: "none"`                        | ✅          | ✅      | ❌ no schema fence |
| PostgreSQL (`pg`, `postgres-js`, PGlite, `neon-serverless`)  | ✅          | ✅      | ✅                 |
| PostgreSQL over `neon-http`                                  | ✅          | ✅      | ❌ no schema fence |
| Custom fulltext strategy without `dropDdl`                   | ✅          | ✅      | ❌ no teardown DDL |

`rebuild` needs two things at once: a strategy that declares `dropDdl`,
and a transactional schema fence to run under. The HTTP-only PostgreSQL
drivers cannot hold a session across statements, so they have no fence —
the same reason they already declare no
`capabilities.execution.interactiveTransactions`.

A third-party strategy predating `dropDdl` keeps working for everything
else and is reported as not rebuildable, rather than being dropped
through a statement TypeGraph guessed at. Vector contributions are never
rebuildable on any backend; that is a property of what TypeGraph stores,
not of the engine.

A rung a backend cannot serve refuses with a typed error rather than
returning something that looks like success. That is the whole point of
the exercise — the failure mode this post opens with was a system
reporting health it had never actually checked.
