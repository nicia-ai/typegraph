Three fixes shipped in 0.35 that don't share a subsystem, a PR, or even a
theme, except that each one moves a mistake that used to surface at
runtime (or not at all) into a compile error or a thrown exception at the
point it's made. None is big enough for its own post. Together, they're
worth one.

## A projected id keeps its brand

`NodeId<N>` is a branded string: `store.nodes.Person.getById()` only
accepts a `NodeId<Person>`, not any old string, so passing the wrong
kind's id is a type error, not a runtime "not found." Before 0.35, a
`.select()` projection widened `id` back to a bare `string`, so a
perfectly well-typed id you'd just read out of a query needed a manual
`asNodeId<typeof Person>(...)` re-brand before you could pass it back in.
Not anymore:

```typescript
const rows = await store
  .query()
  .from("Person", "p")
  .select((ctx) => ({ id: ctx.p.id, name: ctx.p.name }))
  .execute();

// rows[0].id is already NodeId<typeof Person>: no cast, no asNodeId() call.
const person = await store.nodes.Person.getById(rows[0].id);
```

```text
re-fetched by projected id, no cast: Alice
```

`asNodeId`/`asEdgeId` still exist, and you still need them at a genuine
untyped boundary: an id round-tripping through your own database column,
a JSON payload, a URL param. What changed is that TypeGraph's own query
results no longer manufacture one of those boundaries by accident.

## `implies()` now checks its own endpoints

An ontology `implies(edgeA, edgeB)` relation only makes sense if every
node kind `edgeA` can connect could also, in principle, satisfy `edgeB`'s
domain. Otherwise `expand: "implying"` traversal would fold rows whose
kinds don't match what the traversal actually asked for. Before 0.35, that
was a silent hole. Now:

```typescript
const graph = defineGraph({
  id: "papers",
  nodes: {
    Author: { type: Author },
    Paper: { type: Paper },
    Topic: { type: Topic },
  },
  edges: {
    authored: { type: authored, from: [Author], to: [Paper] },
    covers: { type: covers, from: [Paper], to: [Topic] },
  },
  ontology: [implies(authored, covers)],
});

createStore(graph, backend);
```

```text
ConfigurationError: implies("authored", "covers") is endpoint-incompatible:
from kind(s) [Author] declared on "authored" cannot be assigned to any of
"covers"'s from kind(s) [Paper].
```

`Author -> Paper` implying `Paper -> Topic` was always nonsensical: an
`authored` edge starts at an `Author`, never a `Paper`, so folding it into
a `covers` traversal could never produce a `covers`-shaped row. It's the
kind of mistake that's easy to make copying an `implies()` chain and easy
to miss, because nothing about it looks wrong until a traversal quietly
returns rows that don't belong.

Two things worth knowing before upgrading, since this validation runs
wherever the graph is built or loaded (`createStore`, `createStoreWithSchema`,
`store.evolve({ ontology })`, and `deserializeSchema(...).buildRegistry()`):

- **It checks a persisted schema, not just source code.** A schema
  already saved under 0.34 with a now-rejected `implies()` relation throws
  at the first load after upgrading; audit persisted schemas, not only
  the graph definitions in your repo.
- **It rejects superset domains too, not only disjoint ones.** `implies(a, b)`
  where `a` is `from: [Person]` and `b` is `from: [Employee]` (with
  `Employee subClassOf Person`) is rejected, even though every `a` row on
  disk might happen to start at an `Employee`. The _declaration_ is what
  the traversal folds on, not what the data happens to contain, and a
  `Person`-rooted row folded into an `Employee`-scoped traversal would be
  unsound.

## Every error subclass has its own typed `details`

`TypeGraphError.details` is `Record<string, unknown>` at the base, and
every subclass used to inherit that same untyped grab-bag, so narrowing to a
specific error still left you guessing (or checking source) at what keys
`details` actually carried. Each fixed-shape subclass now `declare`s its
own exported details type:

```typescript
export type NodeNotFoundErrorDetails = Readonly<{ kind: string; id: string }>;

export class NodeNotFoundError extends TypeGraphError {
  declare readonly details: NodeNotFoundErrorDetails;
  // ...
}
```

```typescript
try {
  await store.nodes.Person.update(badId, { name: "New Name" });
} catch (error) {
  if (error instanceof NodeNotFoundError) {
    error.details.kind; // string: typed, not unknown
    error.details.id; // string: typed, not unknown
  }
}
```

Once `instanceof` narrows to `NodeNotFoundError`, `error.details.kind` and
`error.details.id` are typed properties, not `unknown` values you'd have
to assert or guess the shape of from the docs. Every error with a
predictable, fixed shape (not the handful whose details vary per call
site) got the same treatment.
