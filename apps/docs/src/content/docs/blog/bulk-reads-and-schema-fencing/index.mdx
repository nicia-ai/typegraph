[Type Safety, Tightened](/blog/type-safety-sweep) collected three small
fixes that shared a thread. This is the same shape, over a longer stretch:
a run of changes that individually didn't warrant a post, and together say
something specific. Two things, really — reads and writes stopped scaling
with the size of the _result set_ instead of the size of the _question_,
and the schema-commit path stopped assuming it was the only writer in the
database.

## The N+1 read, retired

Reading a page of nodes and then each node's edges is the oldest shape in
the book, and it cost one statement per node:

```typescript
const people = await store.nodes.Person.find({ limit: 50 });
const jobsPerPerson = await store.edges.worksAt.bulkFindFrom(people);
// jobsPerPerson[i] holds the worksAt edges of people[i]
```

`bulkFindFrom` / `bulkFindTo` are `findFrom` / `findTo` with the endpoint
predicate widened from `from_id = ?` to `from_id IN (...)` — the same
index prefix seek, the same temporal model, the same per-endpoint
ordering. A page of N nodes costs one statement per endpoint kind and
bind-budget chunk, rather than N singleton statements.

The result shape is the part that makes it a drop-in: index `i` holds the
edges of `froms[i]`, an endpoint with no edges gets an empty array, and
repeated inputs each get their own copy. `limitPerInput` bounds each
endpoint's fan-out while keeping the leading edges of that endpoint's
`findFrom` order. Large inputs split transparently across statements to
respect the backend's bind budget.

Store-level heterogeneous bulk edge reads do the same for a mixed set,
keeping round trips independent of schema breadth — the count of
statements tracks how many endpoint kinds you actually touched, not how
many kinds the graph declares.

## The whole-set update, in one statement

Deactivating every stale employee used to mean reading them and writing
them back one at a time. `updateWhere()` is a typed, transactional
set-based update that returns the number of rows changed:

```typescript
const result = await store.nodes.Person.updateWhere({
  patch: { active: false },
  where: (person) => person.lastSeen.lt(cutoff),
  exists: [
    {
      edgeKind: "worksAt",
      direction: "out",
      relatedKind: "Company",
      whereRelated: (company) => company.field("status").string().eq("closed"),
    },
  ],
});
// { affectedCount: number }
```

A selector is **mandatory** — `where`, one or more `exists` relationship
predicates, or the explicit `all: true` acknowledgement. There is no way
to accidentally update a whole kind by omitting a filter, which is the
failure mode this API shape exists to prevent.

Each `exists` entry is evaluated independently and ANDed with the others.
The patch is shallow: values replace top-level properties, explicit
`null` is preserved, and `undefined` removes an optional property. It is
current-state only and intentionally unavailable on a `StoreView`.

Two smaller read-path items in the same vein. `in()` / `notIn()` now
accept list-valued parameters, so a predicate can be parameterized by a
runtime-sized list instead of being rebuilt per call. And smart-select
planning stopped re-running selective-projection fallback queries it had
already resolved — a repeated cost that scaled with how often you asked,
for no additional information.

`store.batch()` got no new behavior, only an honest cost statement where
callers actually see it: it runs its operations sequentially. The
documentation used to leave that inferable rather than stated, which is
how it ended up in hot paths expecting concurrency.

## The schema-commit path had a concurrency model. It just wasn't written down.

The second half is less about throughput and more about two writers
meeting somewhere neither expected.

**`migrateSchema()` was silently dropping runtime-committed kinds.** A
graph extended at runtime through [graph
extensions](/blog/runtime-schema-evolution), then migrated, lost the kinds
that had been committed at runtime rather than declared in source — they
weren't in the declaration the migration compared against, so they read as
removals. Silently, which is the worst available option for a schema
operation.

Around it, three fences that all address the same class of race:

- **Schema-version commits are fenced against concurrent schema-managed
  Store writes**, so a commit can't land while another writer is mid-write
  against the version it is replacing.
- **Deferred kind cleanup is fenced against concurrent schema re-adds.**
  Removal now can't race a kind coming back — previously the cleanup for a
  removed kind could run after that kind had been re-added, deleting rows
  belonging to the new declaration.
- **The kind-removal status table is ensured before `evolve()` checks
  it**, so a database that had never performed a removal doesn't fail the
  check on a table that was never created.

And one clarification that is really a correction of a mental model:
**schema-managed Stores are immutable schema snapshots.** A Store holds
the schema it was opened with. It does not track subsequent commits, so
after a migration you reopen rather than continue — and now the docs say
so rather than leaving it to be discovered.

## Reading the committed schema

Adjacent, and useful whenever you need to know what a database already
has: the committed-schema reads are exported from the package root.

```typescript
import {
  getActiveSchema,
  isSchemaInitialized,
  type SerializedSchema,
} from "@nicia-ai/typegraph";
```

`getActiveSchema` returns the committed schema document — the same JSON
stored in `typegraph_schema_versions.schema_doc`, parsed. Read it instead
of querying that table by hand. Integrations building schema metadata can
use the returned `committedRow` without issuing a second read.

The schema-commit surface also exposes its **decisions as data** rather
than prose, so a caller can branch on what a commit would do instead of
parsing a message. Related: restating a kind in a different declaration
order is no longer reported as a schema change. It never was one.
