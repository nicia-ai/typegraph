Say you have a PostgreSQL-compatible engine. Same wire protocol, but no advisory
locks, and when two transactions write the same row it lets both proceed and
fails the loser's `COMMIT` instead of blocking it. You want TypeGraph on it.

Through 0.56 that was a source change, not a configuration one. TypeGraph
answered "which lock do I take", "how do I introspect the physical schema" and
"what exclusion primitive does this engine have" by asking what dialect it was
running on. Running the repository's own lint selectors — `x === "sqlite" | "postgres"` and
`case "sqlite" | "postgres"` — over the library's `src/` at the 0.56.0 tag
finds **38 such branches in 14 files**. Each is a fork with two arms. Your
engine has no arm.

0.57 replaces the questions with declarations. The same selectors at the 0.57.0
tag find 16 branches in 7 files, and each of those is a named, permanent
exception. This post is about what took their place, what it costs, and what
it doesn't do yet.

[Bring Your Own Backend](/blog/backend-capabilities) covered a different half of
the boundary: making Drizzle optional and declaring what an engine can't do
(no recursive CTEs, for example). That post also describes
`capabilities.pessimisticLocks`. `capabilities.writeFence`, below, is what
replaced it — 0.57 removed the old name.

## A profile is data; a backend is what it becomes

`createPostgresBackend` and `createSqliteBackend` are now the same function,
`createSqlBackend`, applied to a `SqlEngineProfile`: the dialect tokens,
execution adapter, provisioning, and capability declarations one engine
contributes. A new entrypoint, `@nicia-ai/typegraph/adapters/drizzle/engine`,
exports the two bundled profile builders, `createSqlBackend`, and
`deriveEngineProfile`. The changelog is explicit that the bundled backends emit
the same SQL, advertise the same capabilities, and behave as they did in 0.56.

What changed is where decisions come from. Three that used to be dialect
comparisons are now facts a profile states:

- **`catalog`** — physical-schema introspection: does this table exist, what
  state is this index in.
- **`fenceSql`** — how this engine spells the lock a fence takes.
- **`writeFence`** — which exclusion primitive the engine actually provides.

Here is the last one, derived. It's a SQLite database, so read it as a
demonstration of what the declaration produces rather than a recommendation:

```ts
import {
  buildSqliteEngineProfile,
  createSqlBackend,
  deriveEngineProfile,
} from "@nicia-ai/typegraph/adapters/drizzle/engine";
import { createLocalSqliteBackend } from "@nicia-ai/typegraph/adapters/drizzle/sqlite/local";

const { db } = createLocalSqliteBackend();
const base = buildSqliteEngineProfile(db);

const derived = deriveEngineProfile(base, {
  declaredCapabilities: {
    ...base.declaredCapabilities,
    writeFence: {
      mechanism: "row",
      drain: "quiescent",
      conflict: "commit-time",
    },
  },
});
const backend = createSqlBackend(derived);

console.log(backend.capabilities.writeFence);
// { mechanism: "row", drain: "quiescent", conflict: "commit-time" }
console.log(backend.capabilities.execution?.unitOfWork);
// "optimistic-retry"
```

`unitOfWork` isn't something you set. It's derived from the declaration, which is
the point: TypeGraph reads what the engine said and decides what follows,
instead of deciding from the engine's name.

The ban that enforces this now covers all of `src/**`, not just the query
compiler. The 16 remaining branches are listed file by file in
`DIALECT_LITERAL_EXEMPTIONS` with a reason each: one-shot migrations and repair
tools that write dialect-specific DDL or decode a legacy column, the fence
planner's default declaration for the two bundled dialects, a driver fact in the
serialized-resource audit, PostgreSQL-only error classification, and one flag
that SQLite's `BEGIN IMMEDIATE` transactions already hold the write lock. A test
checks that list against the tree in both directions, so a stale entry fails as
loudly as a new, unlisted one.

## Derivation is bounded on purpose

`deriveEngineProfile(base, overrides)` builds a variant of a bundled profile.
Eleven fields can be overridden: `declaredCapabilities`, `fenceSql`,
`resourceAudit`, `autocommit`, six runtime dependency bags, and `close`. Everything
else — `dialect`, `tableNames`, `execution`, `strategy`, `fulltext`, `vector`,
`provisioning` — is refused:

```ts
import {
  buildSqliteEngineProfile,
  deriveEngineProfile,
} from "@nicia-ai/typegraph/adapters/drizzle/engine";
import { createLocalSqliteBackend } from "@nicia-ai/typegraph/adapters/drizzle/sqlite/local";

const { db } = createLocalSqliteBackend();
const base = buildSqliteEngineProfile(db);

try {
  // The types already forbid this key; the cast shows the runtime does too.
  deriveEngineProfile(base, { execution: base.execution } as never);
} catch (error) {
  console.log((error as { details: unknown }).details);
  // { code: "ENGINE_PROFILE_OVERRIDE_UNSUPPORTED", key: "execution" }
}
```

The refusal exists because the bundled builders close over those fields in more
than one place. Overriding only the profile's head would leave some members
applying your value and others reading the one the builder captured, and a
backend that's half one engine and half another is worse than an error at
construction. Three sub-fields inside otherwise-derivable objects
(`maxBindParameters`, `execution.interactiveTransactions`, `resourceAudit.kind`)
are refused too: the PostgreSQL builder bakes a copy of each into `execution`
before the profile object exists.

A derived profile is also a new object, so it never carries first-party
standing. In practice that means it takes its own schema fence on every managed
write instead of leasing one across a transaction. That's a real cost, and it's
the price of the bounded surface. See
[Authoring an engine profile](/backend-authoring) for the field table and the
refusals a profile can hit.

## Three ways to exclude a writer, and a fourth for engines with none

`capabilities.writeFence` is a union on `mechanism`. The bundled backends
declare the first two. `caller-serialized` and `row` are new in 0.57:

| `mechanism`         | What excludes a second writer                                         |
| ------------------- | --------------------------------------------------------------------- |
| `advisory`          | A keyed lock the caller takes (`pg_advisory_xact_lock` on PostgreSQL) |
| `engine-serialized` | The engine itself — SQLite's single writer slot                       |
| `caller-serialized` | A deployment-level promise that nothing else writes                   |
| `row`               | A row TypeGraph upserts in its own `typegraph_fences` relation        |

The `row` mechanism is for the engine in the opening paragraph. Every keyed lock
site acquires it with one statement TypeGraph spells itself, so the profile
never has to. The fence key reuses each site's existing advisory namespace
verbatim, which means the lock-order contract carries over unchanged. Two facts
qualify it: `drain` says whether a caller that already holds the fence can also
take a relation-wide lock, and `conflict` says what happens when two writers
reach the same fence row — `"wait"` for a lock-based engine, `"commit-time"` for
an optimistic one.

`conflict: "commit-time"` is what produced `"optimistic-retry"` above. Under that
tier every TypeGraph-owned transaction that takes a fence row replays a real
commit-time conflict as one whole unit, up to three attempts, invisible to hooks
and to the caller. On a backend like the one above, committing a store's schema
takes a fence row, `typegraph:schema-commit:<graphId>`, in `typegraph_fences`.

`caller-serialized` deserves a warning. TypeGraph enforces the in-process half
of that promise with a per-backend queue. The other half, that no other client
writes to the database, is yours, and TypeGraph can't verify it.

Existing databases need the regenerated migration SQL
(`generateSqliteMigrationSQL` / `generatePostgresMigrationSQL`) before you
declare `row`, because `typegraph_fences` is new. The two bundled mechanisms need
no migration. See
[Write fence declaration](/backend-setup#write-fence-declaration-writefence).

## Conflicts get one type

Before 0.57, a PostgreSQL serialization failure or deadlock surfaced as whatever
the driver threw, and the store recognized conflicts in more than one place.
Now one predicate classifies them everywhere, and one typed error,
`TransactionConflictError`, reports them. `store.transaction()` also accepts
`retry: { attempts }` so your own callbacks can get the same replay.

SQLite never raises SQLSTATE `40001`, so the example below throws it by hand.
That's the shape the classifier recognizes; it isn't a claim about SQLite:

```ts
import { z } from "zod";

import {
  createStoreWithSchema,
  defineGraph,
  defineNode,
  TransactionConflictError,
} from "@nicia-ai/typegraph";
import { createLocalSqliteBackend } from "@nicia-ai/typegraph/adapters/drizzle/sqlite/local";

const Account = defineNode("Account", {
  schema: z.object({ owner: z.string(), balance: z.number() }),
});
const graph = defineGraph({
  id: "ledger",
  nodes: { Account: { type: Account } },
  edges: {},
});

const { backend } = createLocalSqliteBackend();
const [store] = await createStoreWithSchema(graph, backend);

// SQLite never raises 40001; this stands in for what PostgreSQL would.
function serializationFailure(): Error {
  return Object.assign(new Error("could not serialize access"), {
    code: "40001",
  });
}

try {
  await store.transaction(async (tx) => {
    await tx.nodes.Account.create({ owner: "ada", balance: 100 });
    throw serializationFailure();
  });
} catch (error) {
  if (error instanceof TransactionConflictError) {
    console.log(error.code, error.details);
    // TRANSACTION_CONFLICT { operation: "store.transaction()", attempts: 1 }
    console.log((error.cause as { code: string }).code); // "40001"
  }
}

let attempts = 0;
await store.transaction(
  async (tx) => {
    attempts += 1;
    await tx.nodes.Account.create({ owner: "ada", balance: 100 });
    if (attempts < 3) throw serializationFailure();
  },
  { retry: { attempts: 3 } },
);
console.log(attempts, (await store.nodes.Account.find()).length);
// 3 1 — two rolled-back attempts left nothing behind
```

Retry re-runs the whole callback, so the callback has to be safe to run more
than once. The
[replay contract](/schemas-stores#retrying-on-conflict) has four parts: await all
of your own work, read and write only values created fresh on each call, cause
no effect outside the transaction, and tolerate being invoked up to `attempts`
times. Hooks get a 1-based `attempt` field so a listener can tell a replay from
a new operation. Graph-merge's commit paths go through the same retry owner with
their existing budget of three, so a `MergeError` that exhausts it now carries
the `TransactionConflictError` one level deeper: `mergeError.cause.cause` is the
driver error.

## Engines that already do the work themselves

Some databases already implement, natively, what TypeGraph otherwise builds in
software. 0.57 gives them three places to say so.

**`lineage`** is an opaque whole-database revision plus "which rows of this
graph changed since revision R". Graph-merge prunes its diff to that set instead
of scanning. Neither bundled backend declares one. When a store has
`history: true`, it derives an equivalent from its own recorded relations (see
[Lineage and pruned diffs](/graph-merge#lineage-and-pruned-diffs)).

**`recordedTime`** lets an engine answer temporal reads from its own
system-versioned tables. TypeGraph then builds no capture relations and runs no
clock. Every recorded read in the library resolves through one
`RecordedReadSource` seam, so TypeGraph's capture, an externally bound relation
and an engine's native history are three interchangeable bindings. Anchors from
such a store use an `e1:` form instead of `r1:` (see
[Engine-native recorded time](/queries/temporal#engine-native-recorded-time)).

**`forkedWorkingCopyStrategy`** is the second bundled way to `branch()`. The
existing `cloneWorkingCopyStrategy` streams the base through interchange into a
fresh backend. The forked strategy hands off to whatever your host can do: a
file copy, `CREATE DATABASE ... TEMPLATE`, a provider's branch API. Because a fork
is the same physical database, it carries what interchange can't:

```ts
import { copyFileSync, rmSync } from "node:fs";

import { z } from "zod";

import {
  createStoreWithSchema,
  defineGraph,
  defineNode,
} from "@nicia-ai/typegraph";
import { createLocalSqliteBackend } from "@nicia-ai/typegraph/adapters/drizzle/sqlite/local";
import {
  branch,
  cloneWorkingCopyStrategy,
  forkedWorkingCopyStrategy,
  unwrap,
} from "@nicia-ai/typegraph/graph-merge";

const Widget = defineNode("Widget", { schema: z.object({ name: z.string() }) });
const graph = defineGraph({
  id: "widgets",
  nodes: { Widget: { type: Widget } },
  edges: {},
});

// Rollback-journal mode, so a committed database is exactly one file.
const open = (path: string) =>
  createLocalSqliteBackend({ path, pragmas: false }).backend;
const unused = () => Promise.reject(new Error("a strategy is supplied"));

const [store] = await createStoreWithSchema(graph, open("base.db"), {
  history: true,
});
const widget = await store.nodes.Widget.create({ name: "v1" });
const beforeUpdate = await store.recordedNow();
if (beforeUpdate === undefined) throw new Error("history is on");
await store.nodes.Widget.update(widget.id, { name: "v2" });

const forked = unwrap(
  await branch(
    store,
    unused,
    undefined,
    forkedWorkingCopyStrategy({
      fork: async () => {
        copyFileSync("base.db", "fork.db");
        return { dispose: async () => rmSync("fork.db") };
      },
      connect: async () => open("fork.db"),
    }),
  ),
);
const atFork = forked.store.asOfRecorded(beforeUpdate);
console.log((await atFork.nodes.Widget.getById(widget.id))?.name);
// "v1" — history from before the fork came along

const cloned = unwrap(
  await branch(
    store,
    unused,
    undefined,
    cloneWorkingCopyStrategy(async () => open("clone.db")),
  ),
);
try {
  cloned.store.asOfRecorded(beforeUpdate);
} catch (error) {
  console.log((error as Error).constructor.name); // ConfigurationError
}

await forked.close();
await cloned.close();
```

The fork answers an `asOfRecorded` instant from before it was taken. The clone
never enables history, so it refuses the same call. A fork also keeps
soft-delete tombstones, `created_at`/`updated_at`, and the `version` column,
none of which travel through interchange.

A file copy is only a valid fork when nothing is mid-transaction. That's why the
example opens the database with `pragmas: false`: in WAL mode, committed data can
still sit in a `-wal` sidecar that a copy of the main file would miss, while in
rollback-journal mode a committed database is the one file.

## Two fixes that land on every backend

**`Store.clear()` now rotates the graph's revision-origin nonce.** A `base@V`
token names its origin as well as a counter and an instant, and `merge()` refuses
a branch whose base token no longer matches. Before 0.57, `clear()` left the
origin alone. Running the snippet below against the 0.56.0 source prints `true`;
on 0.57.0 and later it prints `false`:

```ts
import { z } from "zod";

import { createStore, defineGraph, defineNode } from "@nicia-ai/typegraph";
import { createLocalSqliteBackend } from "@nicia-ai/typegraph/adapters/drizzle/sqlite/local";
import { computeBaseVersion } from "@nicia-ai/typegraph/graph-merge";

const Person = defineNode("Person", { schema: z.object({ name: z.string() }) });
const graph = defineGraph({
  id: "people",
  nodes: { Person: { type: Person } },
  edges: {},
});

// A base@V token reads "<schema>#s1 revision:<origin>:r1:<counter>:<instant>".
const originOf = (token: string) => /revision:([^:]+):/.exec(token)?.[1];

const { backend } = createLocalSqliteBackend();
const store = createStore(graph, backend, { revisionTracking: true });
await store.nodes.Person.create({ name: "Alice" }, { id: "alice" });
const before = originOf(await computeBaseVersion(store));

await store.clear();
await store.nodes.Person.create({ name: "Alice" }, { id: "alice" });
const after = originOf(await computeBaseVersion(store));

console.log(before === after); // 0.56: true · 0.57 and later: false
```

The changelog describes the failure this closes: a graph repopulated to look the
same could mint a token byte-identical to one from before the clear, and a
branch forked in the older epoch would pass the merge precondition against
different content. A full token collision wasn't reproduced here: in runs against 0.56.0 the
counter and instant still differed across the clear, so the tokens didn't match.
What the snippet shows is the safeguard that was missing: the origin used to be
the same across a clear, and now it isn't. A branch forked before a `clear()` now fails
`merge()` with `BaseVersionMismatchError`, including when the graph was
repopulated identically. Re-branch from the cleared store.

**Constrained edge writes no longer scale badly on PostgreSQL.** A `bulkCreate`
or `bulkInsert` on an edge kind declaring `cardinality: "one"`, `"oneActive"` or
`"unique"` built its atomic claim statements with one predicate arm per proposed
row, each with its own subqueries. The planner had to initialize thousands of
subplans, and the cost per arm wasn't constant. The changelog reports that a
chunk of a few thousand rows could run for minutes, grow past two gigabytes of
server memory, and ignore cancellation. Each statement now drives from a single
relation of the chunk's rows, planned once.

These are the measurements in [the PR](https://github.com/nicia-ai/typegraph/pull/662)
(PostgreSQL, a graph with 40k background edges, two runs per point). They were
not re-run for this post:

| Rows in `bulkInsert` | Before (ms)   | After (ms) |
| -------------------: | ------------- | ---------- |
|                  200 | 171 / 137     | 40 / 38    |
|                 1000 | 1072 / 998    | 309 / 343  |
|                 2000 | 12355 / 11588 | 459 / 553  |

The shape matters more than any single row. Before, per-row cost climbed from
0.60 to 6.18 ms across the range, which is what makes a large chunk unbounded
instead of merely slow. After, it held between 0.18 and 0.34 ms per row. The PR is also
candid about one claim it can't time: it argues the stale-statistics plan
degradation is structurally unreachable now, but a 30k-row reproduction of the
original single-create case showed no difference (5.6 ms vs 5.8 ms).

## What this does not do

**It doesn't let you build an engine from scratch.** `deriveEngineProfile`
adapts a bundled profile. A from-scratch profile needs an execution adapter, an
operation strategy and an assembly, and the constructor for that assembly isn't
exported from any entrypoint. The docs say so directly. What you can reach today
is a variant of PostgreSQL or SQLite: a different lock spelling, a different
declared fence, a different resource-audit verdict.

**`lineage` and `recordedTime` aren't reachable through derivation.** Both live on
a profile's `provisioning`, which `deriveEngineProfile` refuses to override. The
library's own tests attach them by mutating that object in place. They're
exercised against simulated engines built on the bundled SQLite and PostgreSQL
backends, plus a shared conformance suite for `lineage`. That's real coverage of
the seam, with no real system-versioned database behind it.

**No third engine has run through this yet.** The optimistic-retry tier is
proven with a fault injector that injects conflict errors into real transactions
on SQLite and PGlite. `row` + `commit-time` hasn't been run against an engine
that resolves conflicts at commit on its own, so retry under genuine commit-time
conflicts is tested by injection, not by observation.

**Derived profiles pay for being derived**, as above: no first-party standing,
so no lazy schema-fence lease.

**And nothing in the boundary work is faster,** with one exception: the
PostgreSQL edge-claim fix above. The claim is about who decides, not how quickly.

## Upgrading

- **Applications.** Match `TransactionConflictError` instead of SQLSTATE, driver
  message or a driver error class, and read the original off `cause`. Check a
  callback against the replay contract before you pass `retry`.
- **Operators.** Run the regenerated migration SQL before declaring
  `writeFence.mechanism: "row"`. The base schema gains `typegraph_fences` on both
  dialects.
- **Graph-merge.** `WorkingCopyStrategy.create(baseStore)` becomes
  `create(baseStore, base)`. `branch()` passes it; a direct caller passes
  `await computeBaseVersion(baseStore)`. `GraphBranch` gains a required
  `close()`, and `Store` a required `workingCopyOptions` getter.
- **Custom backends.** Replace `capabilities.pessimisticLocks` with
  `capabilities.writeFence`, and `recordedTimeOwnership` with
  `EngineProvisioning.recordedTime`. A profile that declares `recordedTime` must
  also declare `lineage`. Build profiles through a bundled builder or
  `deriveEngineProfile`; a profile literal is no longer constructible.

The full list is in the
[0.57.0 changelog](https://github.com/nicia-ai/typegraph/blob/main/packages/typegraph/CHANGELOG.md).
